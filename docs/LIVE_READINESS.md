**▶ 지금 실행: 운영자 (읽기 전용, 리뷰 승인 범위).** 비밀 값은 출력하지 않는다. 조회가 실패하면 실패 메시지를 그대로 남긴다. 실패를 "백업 없음"으로 읽지 않는다.

```bash

DC="docker compose -f docker-compose.prod.yml"
# ⓐ 초기화 비밀번호가 설정돼 있는가 — '설정됨'/'미설정' 만 출력
$DC exec -T backend sh -c '[ -n "$DB_RESET_PASSWORD" ] && echo 설정됨 || echo 미설정' || echo "조회 실패: backend exec"
```

**읽는 법**
- `pg_dump … | gzip` 은 덤프가 실패해도 gzip 이 성공하면 **빈 압축 파일과 "백업 완료" 로그를 남긴다**(`docker-compose.prod.yml:98-99`). 그래서 로그 문구를 근거로 삼지 않는다.

- 🔴 이번 확인 결과는 **"파일 존재·크기 확인, 복구 가능성 미검증"**으로 기록한다. 복구 훈련은 이번 범위가 아니다(리뷰 3차).
- 보존 기간은 7일이다. 사라지는 것은 **오래된 날짜의 백업본**이다. 현재 DB 에 남아 있는 과거 기록은 최신 전체 덤프에도 들어 있다(리뷰 22차 정정).

### 3-7. #5 실자금 동시 쓰기 경로 대조 (리뷰 28차, 2026-10-29) — 🟢 완료(리뷰 33차) · 기술 검토 완료(리뷰 30차) · 배포 진행 동의(리뷰 32차) · 운영 적용(개입 #13)

범위(리뷰 28차): LIVE·DYNAMIC 에서 **평가 틱 · WS 손절·익절 · 수동·비상 정지 · 체결 정산·청산 정리**가 같은 세션·포지션을 고치는 경로. 기존 시험이 있는 조합은 다시 만들지 않았고, 빠진 조합만 실제 동시 실행으로 시험했다. 확인 기준은 셋: **매도 제출 중복 없음 · 잔액·수량 정확히 한 번 · 정지 후 신규 진입 차단과 기존 주문 추적 유지.**

**공통 장치(코드 확인)**: 모든 청산 트리거(틱·WS·정지·정리 작업)는 `executeSessionSell`(LIVE)·`executeSell`(DYNAMIC)·정지 청산·정리 작업 안에서 **`markClosingIfOpen` 조건부 UPDATE(OPEN→CLOSING, 한쪽만 1)** 를 거친 뒤에만 매도를 낸다. 매도 제출 입구는 다시 **반영되지 않은 매도가 있는 포지션의 새 매도를 거절**한다. 정지의 세션 행 쓰기는 상태 전환만 재조회·재시도(`balanceUpdater`)하고 청산은 다시 실행하지 않는다. 거래소 주문이 포함된 평가 전체를 재시도하는 경로는 없다.

| 경합 (같은 세션·포지션) | 지키는 장치 | 근거 시험 (LIVE·DYNAMIC) | 이번 |
|---|---|---|---|
| 평가 틱 ∥ WS 손절·익절 — 같은 포지션 매도 | `markClosingIfOpen` + 제출 입구의 미반영 매도 차단·의도 직렬화 | `LiveSellIdempotencyTest`(원자 전환), `DoubleSellGuardTest`(동시 청산 8 → 거래소 1) | 새 시험 (나)에서 전환을 실제 동시 경합으로 확인(정지와). 틱 자체(캔들·전략 판정)는 돌리지 않았다 |
| 정지(일반·비상·전체·서킷 브레이커) ∥ 평가 루프·체결 반영의 세션 행 쓰기 | 상태 전환만 재조회·재시도 | `LiveStopUnderConcurrentWriteTest`, `LiveEmergencyStopUnderConcurrentWriteTest`(3경로), `DynamicStopOptimisticLockTest`, `PaperStopUnderConcurrentWriteTest` | — |

**재현한 결함 — 정지가 진행 중 청산과 겹치면 그 포지션이 정리 대기에서 빠졌다 (LIVE·DYNAMIC 모두)**

**국소 수정**
- 정지 청산 끝에서 **닫히지 않은 포지션(CLOSING·OPEN)을 모두 다시 읽어 정리 대기로 등록**한다(등록은 중복되지 않는다 — `registerIfAbsent`). 매도는 내지 않는다. 누가 먼저 CLOSING 으로 바꿨든, 정지 처리 중 예외로 건너뛴 포지션이든 정리 작업이 맡는다.
- DYNAMIC 은 정리 대기를 **포지션 자신의 종류**로 등록한다(종전 늘 `DYNAMIC`). 정리 작업은 `DYNAMIC` 행만 보고 실거래소로 매도를 낸다 — 페이퍼 포지션이 그 작업에 오를 수 있던 구조를 없앴다(코드 확인, 재현 아님). 이 덕분에 페이퍼·실전에 같은 등록 규칙을 쓴다. 📌 처음에 페이퍼만 CLOSING 으로 한정하는 분기를 넣었다가 **엔진 동등성 시험(`DynamicPaperLiveRuleParityTest`)이 허용되지 않은 페이퍼 분기로 잡아** 이 방식으로 바꿨다.
