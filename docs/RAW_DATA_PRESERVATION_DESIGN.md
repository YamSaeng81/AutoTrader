## 3. 보존 방식 — 세 층

| 층 | 무엇 | 언제 | 어떻게 |
|---|---|---|---|
| **L1 범위 스냅샷** | D1~D6 | **월 1회** + **사건 전후**(정비·배포·개입 직전과 직후) + **T_end 직후 1회** | 집계기 `extract.sql` 과 같은 방식 — 한 트랜잭션 `REPEATABLE READ READ ONLY` 안에서 `\copy` 로 CSV 를 쓰고 `ROLLBACK`. 열 전부, 시각은 UTC 문자열. 파일마다 `gzip` + `sha256` + 목록 파일(§4) |
| **L2 전체 백업 보존** | F6 | 주 1회 | 기존 매일 백업 중 **주 1개를 회전 밖 폴더로 복사**한다(백업 컨테이너 설정은 그대로 — 설정을 바꾸는 방식은 **P5**) |
| **L3 파일 묶음** | F1~F5 | 월 1회 + F3 은 **만료 전에 회전 파일 전부** | 회전이 끝난 파일만 `tar` 로 묶고 `sha256`. 쓰는 중인 `system.log` 같은 현재 파일은 다음 회차에 회전된 이름으로 담긴다 |

**사본 규칙**: 같은 자료가 **두 곳 이상**, 그중 **하나는 서버 밖**(운영자 PC 또는 외장 저장소 — **P3**). 서버 안 사본만으로는 §1 ③ 을 막지 못한다.

**서버 부담**: L1 은 66세션 범위의 읽기 전용 조회라 짧다. 크기는 D5 가 좌우한다 — H1 평가가 세션당 하루 약 24행이면 6개월에 약 29만 행이고, `indicators_json` 이 행마다 들어 있어 원본으로는 수백 MB 가 될 수 있다. 🔴 **측정한 값이 아니다** — 첫 실행 전에 읽기 전용 크기 조회로 확인한다(§9 P1).

## 4. 무결성

| 장치 | 내용 |
|---|---|
| 파일 해시 | 모든 파일의 `sha256` 을 목록 파일 `MANIFEST.json` 에 적는다 |
| 목록 파일 | 스냅샷 시각(`transaction_timestamp()`), 스키마 버전(`flyway_schema_history` 최대값), 테이블별 **전체 행 수**, 내보내기 스크립트의 git SHA, 파일 크기·해시. 🔴 **금액·손익·팔별 건수는 넣지 않는다** |
| 외부 기록 | `MANIFEST.json` 의 해시(와 목록 파일 자체 — 행 수와 해시만 담는다)를 저장소에 커밋한다 → git 원격의 시각이 붙은 기록이 되어, 보존본이 나중에 바뀌면 드러난다 |
| 사본 검증 | 복사한 곳마다 `sha256sum -c` — 복사 직후와 월 1회 |
| **추가 전용 대조** | 이번 스냅샷과 직전 스냅샷을 비교해, **바뀌면 안 되는 행이 바뀌거나 사라졌는지** 본다: 매도까지 끝난 포지션과 그 주문, 2일보다 오래된 캔들. 바뀌어도 되는 것은 세션 잔액·상태, 열린 포지션이 닫히는 것, 새 행. 🔴 **같은지 다른지만 보고 값으로 계산하지 않는다** — 다르면 행 번호만 보고한다 |

📌 행 수는 성과가 아니다(집계기의 건수 전용 모드와 같은 원칙). 다만 테이블 **전체** 행 수만 적고 팔별로 나누지 않는다.

## 5. 복구 방법

### 5-1. 어디서 되찾는가 — 순서

| 순서 | 출처 | 담는 범위 | 한계 |
|---|---|---|---|
| 1 | 운영 DB (T_end 직후 추출) | 전부 | 사고가 있으면 이미 잃었을 수 있다 |
| 2 | 최근 L2 전체 백업(주 1개) 또는 기존 매일 백업(7일) | 그 백업 시각까지 전부 | 그 뒤는 없다 |
| 3 | 최근 L1 범위 스냅샷 | D1~D6, 그 스냅샷 시각까지 | 범위 밖 자료 없음 |

- 🔴 **되찾은 자료로 빈 구간을 메우지 않는다.** 어느 출처로도 메울 수 없는 세션·일자는 집계기 R6 그대로 **측정 결측 → 판정 불가**다. 복구 출처와 시각은 개입 기록 형식으로 남긴다.
- 운영 DB 에 되돌려 넣는 것은 **운영 개입**이다 — 그 자체로 별도 승인과 개입 기록이 필요하다. 이 설계는 운영 DB 에 쓰는 절차를 정하지 않는다. 집계는 되찾은 자료를 **서버 밖 격리 DB** 에 올려서 한다.

### 5-2. 되돌려 보는 절차 (복구 훈련)

```
① 해시 확인        sha256sum -c MANIFEST 의 해시 — 하나라도 다르면 그 사본을 쓰지 않는다
② 격리 DB 준비     로컬 PostgreSQL 에 새 DB 를 만들고 Flyway 로 목록 파일의 스키마 버전까지 적용
                   (집계기 저장 경로 시험의 fa_storage_check 와 같은 방식)
③ 적재             L1 CSV 를 \copy 로 넣는다 / L2 백업은 격리 컨테이너에 그대로 복원
④ 대조             테이블별 행 수 = 목록 파일 · 스키마 버전 = 목록 파일 · 주요 키 중복 없음
⑤ 정리             격리 DB 를 지운다
```

- **첫 L1 스냅샷 직후 한 번, 그 뒤 월 1회.** "복원해 본 적 없는 백업은 백업이 아니다"(`20260415_analy.md`) — 그 문서가 요구한 월 1회 복원 드릴이 실제로 돌았다는 기록은 찾지 못했다(확인 범위: 저장소 문서).
- 🔴 훈련은 해시·행 수·스키마만 본다. **집계기의 `verify`·`final` 을 보존본에 돌리지 않는다**(§7).
- 기존 `scripts/db-restore-drill.sh` 는 그대로 쓰지 않는다 — 포트 `15432` 가 로컬 시험 DB(`cat-rt-pg`)와 겹치고, 확인 대상 테이블 목록(`order_details` 등)이 현재 스키마와 맞는지 확인되지 않았다. 쓰려면 먼저 검토한다.

## 7. 🔴 보존 자료로 중간 성과를 계산하지 않는다

L1 스냅샷에는 잔액·체결가가 들어 있다. 보존은 계산이 아니므로 다음을 지킨다.

- 보존본에 집계기 `verify`·`final` 을 돌리지 않는다. 손익·수익률·자산을 계산하지 않는다.
- 무결성 장치(§4)와 복구 훈련(§5-2)은 **해시·행 수·스키마·행 단위 같음 여부**만 본다. 다름이 나오면 행 번호만 보고한다.
- 건수 전용 모드(R11)를 보존본에 돌리는 것도 그 모드의 승인과 함께 따로 정한다.
- 종료 뒤 `final` 의 입력은 원칙적으로 **T_end 직후의 운영 추출 한 번**이다. 보존본은 그 추출이 불가능하거나 손상됐을 때만 §5-1 순서로 쓴다.

## 8. 비밀값

- 앱은 텔레그램 Bot API 주소에 토큰을 넣어 부른다(`TelegramNotificationService.java:56`). 전송 실패 예외가 그 주소를 로그에 남길 수 있다 — 🔴 **실제로 남았는지는 확인하지 않았다.** 그래서 TIME_STOP 로그 조회 도구도 출력에서 토큰을 가렸다(`time_stop_logs_20261027.sh`).
- 로그 원본을 서버 밖으로 옮기면 토큰도 함께 나갈 수 있다. 원본을 고치면(가리기) 증거의 해시가 달라진다 → **P4** 에서 정한다.
- `.env`·자격 증명 파일은 어떤 층에도 넣지 않는다. 목록 파일·커밋에도 들어가지 않는다.

|---|---|---|---|
| **P0** | 만료가 임박한 회전 로그(`system.2026-10-*.log` 부터)의 사본 | **10-30 이전**에 회전이 끝난 `logs/backend/*.2026-*.log` 를 서버 안 별도 폴더로 복사하고 `sha256` 을 남긴다. 복사만 하며 서비스·설정은 건드리지 않는다 | 운영 서버 작업(읽기·복사) — 승인 필요 |
| **P1** | D5 신호 기록의 범위 | 전체 행 보존. 첫 실행 전에 읽기 전용 크기 조회로 크기를 확인하고, 지나치게 크면 `indicators_json` 제외 + 일별 건수만 보존하는 안을 다시 올린다 | 설계 판단 |
| **P2** | L1 주기 | 월 1회 + 사건 전후 + T_end 직후 | 설계 판단 |
| **P3** | 서버 밖 사본 위치 | 운영자 PC + 외장 저장소(또는 운영자가 고르는 다른 곳) 중 최소 하나. 전송은 운영자가 `scp` 로 | 운영자 결정 |
| **P4** | 로그의 토큰 | ① 원본은 서버 안 보존 폴더에만 두고 서버 밖에는 가린 사본 + 원본 해시를 둔다 ② 원본을 암호화해 서버 밖에 둔다 — **제안 ①** | 운영자 결정 |
| **P5** | 백업 보존 연장 | 백업 컨테이너 설정(`-mtime +7`)은 그대로 두고, 주 1개를 별도 폴더로 복사 | 서버 설치 — 별도 승인 |
| **P6** | 무결성 외부 기록 | 목록 파일(행 수·해시만)을 저장소에 커밋 | 설계 판단 |
| **P7** | 자동화 | 수동 실행으로 시작하고, 두 번 이상 깨끗하게 돈 뒤 cron 설치를 따로 올린다 | 서버 설치 — 별도 승인 |

### 구현 순서 (각각 승인 뒤)

1. P0 로그 사본(시간 제한)
2. L1 내보내기 스크립트 작성 + 가짜 데이터·로컬 PostgreSQL 시험(집계기 시험과 같은 방식) → 리뷰
3. 첫 L1 실행(운영 추출) → 서버 밖 전송 → 복구 훈련 → 목록 파일 커밋
4. L2·L3 수동 운영 → cron 설치(별도 승인)

## 10. 이 설계가 하지 않는 것

- 서버에 접속하거나, 무엇을 설치·복사·추출하지 않았다.
- 운영 DB 에 쓰는 복구 절차를 정하지 않는다(운영 개입 — 별도).
- 보존 자료로 성과를 계산하지 않는다.
- 집계기의 판정 기준·종료 조건·T0 를 건드리지 않는다.
