## 2. 두 정책 판단

### 과거 종결 주문 — 시각만으로 일괄 면제하지 않는다

현행 W2와 읽기 게이트v3/R3의 **등록 밖 종결 행도 검토하는 계약을 유지**한다. 과거 세션 번호·STOPPED·FILLED/CANCELLED·기준 이전이라는 이유만으로 위험을 지우거나 현재 등록표에 과거 세션을 가짜 등록하지 않는다. 현재 SQL에는 주문별 정산 확정/미해결 차이의 완전한 증거가 없고, 과거 운영 행의 존재도 이번에 읽어 확인한 것이 아니다.

실제 읽기 승인 뒤 종류+세션ID+주문/포지션ID의 금액 없는 목록으로 과거 행을 식별하고, 소유·종결·반영 대기·미해결 정산·열린 연결과 재변경 여부를 확인할 별도 인수안을 제출한다. **이번에는 예외 목록/시간 필터를 구현하지 않는다.** 추후 행별 인수를 결정해도 원천·기존 경보는 보존하며 P7의 현금흐름 원천에서 행을 삭제하지 않는다. 경보가 남는다는 이유로 성급히 실제 병행 시작을 허용하지 않는다.

### P0 — 기존 DB 연결 획득 시간 초과 기준을 유지한다

고정 D81D4R의 [U변수/holdobs](../d81d4r-20261120/d4/blocks-d81/U변수.sh)가 쓰는 **`Connection is not available, request timed out`**를 따른다. 이 기준을 새 임계값으로 넓히지 않는다. holdobs 종료1은 P0로 멈추고,0은 그 제공 로그에서 해당 패턴 없음,3은 장기 대여 경고를 별도로 남기는 상태다. 정상 로그에서 연결 획득 실패가 없다는 것과 운영 전체 안전은 다르다.

- 앱 정지·재시작·기동 구간, 공유 풀 이상 등 기존 🔴는 기존 대응/보고를 유지하되 모두 P0로 재분류하지 않는다. 뉴스 Connection reset·캔들 HTTP오류·외부 API timeout도 이 DB P0 패턴과 구분한다.
- 로그 조회 실패·빈 로그·판정 실패·요구한 관측 범위 미확인은 **P0 검사 미완료**로 멈춘다. P0=0이나 정상으로 바꾸지 않는다. 현재 N03 보고에 P0 키가 없다는 사실은 P0가 없다는 증거가 아니다.
- 따라서 기존 N03 결과만으로 P0 빈 목록을 합성하지 않는다. P0 검사 원천은 해당 구간 backend 로그와 수집 종료값/범위이고, 뉴스/66 상태의 원천은 기존 N03다. 서로 다른 원천을 같은 파일에서 관측한 것처럼 표시하지 않는다.
