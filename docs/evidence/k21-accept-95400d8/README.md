## 직접 확인

- 새 근거 34/34, 이전 총괄 근거 20/20이 작업 파일·고정 커밋 블롭·SHA256SUMS에서 일치한다.
- 기존 계획 bash84개는 순서·내용이 같고 새 L8개는 문서 및 제출 추출본/해시와 같다. `bash -n` 8/8. 나머지 7개는 판 표지 확인 줄만 바뀌었고 L 변수는 `httpobs`와 표지만 바뀌었다. F15개·OPS7개는 그대로다.
- 제출의 같은 입력 21개를 문서에서 꺼낸 Python 원문으로 직접 실행했다. **21/21** 기대와 같고, stdout에 본문·sourceId 값·스레드 이름·가짜 비밀 문자열이 없으며 stderr도 비었다. 이전 입력15개와 총괄 입력4개는 바이트가 같다.
- 다른 스레드 결과는 짝이 아니므로 종료3. 경고2개/결과1개는 짝1·미확인1로 종료3. 같은 스레드 정상 대조군은 종료0, 미검증 sourceId 입력도 그 값을 출력하지 않고 종료0. CoinGecko/다른 출처 결과 혼합은 종료3이다.
- 6995c52의 `NewsAggregatorService.collectFromSource`는 같은 호출 스레드에서 `source.fetch(config)`와 상위 결과 기록을 이어서 실행한다. 확인용 발췌를 `source-call-path.txt`에 보존했다.

## 한계와 실행 기준

- 첫 같은 스레드 기록과 5개 로그 머리 줄 제한은 보수적 관측 규칙이다. DEBUG/다른 기록/교차 로그 때문에 짝을 못 찾으면 ⚪로 남기며 정상 완료로 해석하지 않는다. 요청 ID 기반 추적을 검증한 것은 아니다.
- CoinGecko HTTP 줄에는 sourceId가 없다. 다른 출처의 sourceId가 로그에 나타나면 거부하지만, 로그에 없는 ID의 설정상 소속까지 증명하지는 않는다. 이 한계를 수용하며 앱/설정/실행 ID 추가는 요구하지 않는다.
- 고정 한 줄만 있고 짝이 없으면 ⚪/종료3, 본문 형식·연속 줄이면 🔴/종료1이다. 실행 단계의 기존 처리와 명시된 되돌림 기준을 따른다.
- 자연 발생한 비200이 없으면 **미관측**이다. 실패를 유도하거나 수집 API를 강제로 부르지 않는다. CryptoPanic 403 원인과 Connection reset 회복은 미해결이며 기존 catch ERROR/미분류 분류를 유지한다.
- 총괄은 Python 관측 함수 및 bash 문법만 로컬 실행했다. L 단계 source/실행, 서버·DB·외부 HTTP 접속, 앱 시험, jar 재빌드/변형 시험, 전체 리허설은 하지 않았다. 기존 실제 jar 대조는 앞선 `k21-review-ea15998`에서 수용한 근거를 유지한다.
- 실행 순서: 같은 고정 출처의 F → G → §63 L 변수, L0 → L1 → 기존 절차의 **L2 직전 운영자 확인1회** → L2 → 기동5~10분 뒤 L3 → 기동30분 뒤 L4 → L 뒤 뉴스 관측. L0 시작 시각/직전 정기 보고 조건을 지키고, §61의 이전 L 블록과 섞지 않는다.
- 결과가 올 때까지 F1 핀/최종 S/점검d491fd1·장부·cron·203 CREATED·12-01 08:50은 유지한다. 22:00 N03 읽기는 §58의 범위대로 병행한다.
