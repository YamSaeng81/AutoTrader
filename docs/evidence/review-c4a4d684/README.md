## 2. S1~S4 수용과 추가 성과 경합 S5

- 정지 커밋 시점의 `SessionValuation`을 반환하고 선택 모드의 보고 예외를 격리한 점, 일괄 정지가 DB에 확정된 결과를 잃지 않는 점을 국소 수용한다. 알림 실패는 메서드 예외 주입이며 실제 큐 포화 관측이 아니다.
- 보유는 `status IN ('OPEN','CLOSING')` 한 SQL이다. 잔고/목록은 REPEATABLE READ에서 대기 수와 함께 읽고, 대기 중 현재 평가값을 비우는 방식도 수용한다.
- **S5 — 성과 조회에는 같은 스냅샷 보장이 아직 없다.** `getOverallPerformance()`는 기본 READ COMMITTED로 세션을 먼저 읽은 뒤 포지션을 읽는다. 그 사이 별도 시세 처리 스레드가 실제 정산을 커밋하도록 국소 시험에서 순서를 고정했다.
  - 응답: `평가 완료`, 대기0, 완료 거래1, 현재 자산 **20,200.00**, 실현손익 **0.00**.
  - 실제 DB: 포지션 CLOSED, 자산 **20,369.71**, 실현손익 **169.71**.
  - 포지션은 정산 뒤, 세션 금액은 정산 전 값이다. 실제 Spring/H2·별도 스레드의 제품 정산 경로를 사용한 경합 재현이며 운영 발생·PG 부하 실측은 아니다(`Review19Test.java`, `witness-tests.txt`).
- **다음 보완을 승인한다.** 성과의 세션 금액·보유/완료 상태·건수·전체 합계도 한 일관된 읽기 스냅샷에서 만든다. 잔고/목록과 같은 읽기 전용 REPEATABLE READ 등 최소 변경으로 하고, 실제 PG에서 정산 전/후 어느 한쪽의 일관된 결과인지를 확인한다. 정산 전 값을 허용하되 그 값에 정산 뒤 완료 표시를 섞지 않는다. 읽기 위해 매매 쓰기 잠금을 새로 걸지 않는다.
- 총괄 관측 1차는 같은 스레드에서 정산을 호출해 읽는 쪽 영속성 컨텍스트에 CLOSING이 먼저 붙었으므로, 의도한 별도 시세 경합을 만들지 못했다(후보8건은 이 실행에서도 전부 통과). 다른 스레드에서 정산 완료를 기다리도록 관측만 고친 뒤 S5가 재현됐다. 두 원문을 모두 보존했다. 1차 실패를 제품 결함이나 S1~S4 실패로 세지 않는다.

## 3. 완성기 보완 결정, 지문, arms.csv

### 생성 세션 대조를 보완한다

사용자가 보고한 공백을 수용하며 **도구 수정·실패 시험·실제 로컬 PG 연결 재검증을 바로 진행한다.** v3 원문/기존 기록은 보존하고 새 판으로 만든다.

총괄도 `run3-wrongdb`의 초안과 실제 psql 출력 원문을 v3 완성기에 그대로 넣었다. API 생성 시각07:21과 DB 시작 시각07:07이 다른 **8개 모두** `db_verified=true`가 된다. 같은 ID·설정·T0 이전이라는 것만으로 이번에 생성한 세션임을 확인할 수 없다. 잘못된 DB를 읽었다는 재현은 맞지만, 시각 대조를 추가한다고 DB 서버의 신원을 인증하는 것은 아니다. 실제 실행에서는 승인된 서버/DB 연결 출처와 원문 해시도 함께 기록한다. 새 인증·서명 시스템은 요구하지 않는다.

**제안한 단순 시각 등식은 그대로 넣지 않는다.** 정상 `run-final-19dbad3a`조차 초안4개와 DB4개의 시각이 1마이크로초씩 다르다. 예: 초안 `07:36:29.080737Z` / DB `07:36:29.080738Z`. 생성기는 POST의 `startedAt`을 Python `datetime`으로 바꾸며 마이크로초 아래를 잃고, DB 저장은 별도의 정밀도 변환을 거친다. 문자열만 같게 비교하거나 초/분 단위 허용 오차를 새로 두지 않는다. 총괄의 첫 도구 점검도 정상8개가 정확히 같다고 가정해 실패했으며, 이 차이를 확인한 뒤 대조 결과를 보존했다(`tools-review.json`).

**기본 구현 경로는 다음으로 정한다.**

1. 생성 응답의 원문 `startedAt` 정밀도를 보존한다. 초안의 `created_at`은 현재 API가 준 **startedAt**에서 온 값임을 명시한다.
2. 이미 수행하는 사후 API 목록 대조에서 같은 ID의 **DB 재조회 startedAt**도 보존한다. POST 원문과 저장 후 시각의 차이는 로컬 PG에서 확인한 저장 정밀도 계약으로 검사한다. 임의의 초/분 허용 오차나 로컬 현재 시각 대체는 넣지 않는다. 필요하면 원문 나노초를 보존해 PG/JDBC의 마이크로초 변환까지 확인한다.
3. 완성기는 사후 API 목록의 저장 후 시작 시각과 psql의 시작 시각을 UTC의 같은 시각으로 정확히 대조한다. ID/설정/팔/시각 집합 8개를 모두 확인하고, 누락·시간대 없음·상이한 생성 회차·한 세션만 다른 경우도 완성본을 쓰기 전에 거절한다. 새 판의 필수 근거가 없는 옛 초안에 DB 값만 복사해 채우지 않는다. 과거 근거는 과거 판으로 보존한다.
4. 기존 정상과 같은 시간대 표기 차이, 실제 PG 정밀도 경계, 다른 DB/세대의 같은 ID, 한 행만 바뀜, 필드 누락을 검사한다. 거절 시 완료 파일0·추가 생성 POST0이어야 한다. 다른 DB 혼용은 실제 로컬 연결에서도 다시 잡는다. 이 오류를 이유로 이미 생성한 세션을 자동으로 재생성하지 않는다.

### 팔마다 같은 규칙 지문은 현재 설계와 맞는다

`RulesetRegistry.hashFor(VirtualBalanceEntity)`는 엔진·공통 청산/관문/복합전략 규칙·세션 주기/보유시간/하한/비율·strategy_params·모의 슬리피지를 담고, 전략 이름과 코인은 담지 않는다. 코인은 대상이어서 제외한다는 원문 주석도 있다. 따라서 설정이 같은 A끼리 같은 지문, B끼리 같은 지문인 결과는 해시 충돌이나 이번 결함의 증거가 아니다.

**기존 지문 체계는 이번에 바꾸지 않는다.** 이를 전략/세션/코드의 완전한 식별자로 쓰지 않는다. A/B의 구분은 `code SHA + protocol SHA + pair/arm + 전략/코인/주기/저장 파라미터 + session ID/저장 시작 시각 + ruleset hash + T0`로 유지한다. 같은 지문이라는 이유로 다른 전략·코인 쌍을 합산하거나 독립 표본으로 더하지 않는다. 지문 원문과 저장값을 보존한다.

### arms.csv 변환은 도구로 고정한다

완성본→arms.csv 전용 도구를 만들도록 승인한다. 시험 헬퍼를 운영자가 손으로 호출하거나 CSV를 손으로 고치지 않는다. 완성기 출력/프로토콜을 검증하고 정확히8팔·ID/설정/코드/T0·42일 끝을 보존하며, `params_json` 객체→문자열을 일관되게 변환한다. 완성본/프로토콜 입력 해시와 CSV 해시를 기록하고 출력 덮어쓰기를 거절한다. 완성되지 않은 초안/필수값 누락/팔·ID 뒤바뀜을 거절하는 국소 시험과 실제 psql→완성→변환→집계 연결을 확인한다. 평가 기준·비용·A/B 설정을 바꾸는 도구는 아니다.
