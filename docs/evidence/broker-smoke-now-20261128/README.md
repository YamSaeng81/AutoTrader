# v1.261 즉시 실체결 왕복 시험 — 앱 장부 검증과 구분

2026-11-28 사용자는 “실주문 바로 하면 안되는 이유?”에 이어 “시간을 아껴. 진행 가능하면 바로바로 진행”이라고 지시했다. 운영 대리인 위임과 매수대금+매수수수료 누적1만원 승인을 적용한다. 사용자가 제공한 비밀번호는 사용하지 않고 기존 SSH 키와 서버 메모리의 기존 거래소 키만 쓴다.

## 확인과 선택

고정 운영1b719645의 TradingController에는 수동 실주문 API가 없다. SettingsController의 `/upbit/test-order`는 실거래 없는 `/v1/orders/test`다. 즉시 앱 내부 장부 왕복 시험을 할 수 있다고 단정한 설명은 부정확했다. 이를 실제 주문으로 오인하거나 새 테스트용 엔드포인트를 급히 배포하지 않는다.

현재 실행 범위는 **거래소 REST API의 실제 주문·체결·수수료·잔량 확인**이다. 앱의 신호/예약/정산 장부 전체 경로 검증, 자연 전략 매도, 수익성 검증은 별도로 남는다. 실제 외부 시험 주문을 앱 DB에 가짜로 삽입하거나 SID203 거래로 귀속하지 않는다.

## 실행 원문

- `broker_trial.py`: 새 전용 비공개 서버 폴더에서1회 실행. 날짜·제품/이미지/같은 인스턴스·공식 점검/최신 입력·계좌 여유·기존 BTC0·KRW잠금0·활성/보유/정리0·배정20,200을 검사한다. 기존#204/#205 매수0 종료도 다시 확인한다.
- `launch.py`: 내일09:03 서버 예약에 CANCEL을 기록하고 scheduler-final이 CANCELLED/trial_started=false임을 실제 확인한 뒤에만 시작한다. 재전송·재실행·새 예약은 없다.
- 정확한 BTC 마켓 수수료와 최소 주문액을 새로 읽고 `9950×(1+bid_fee)≤10000`이어야 매수한다. 매수와 매도에 서로 다른 고정 identifier를 사용한다. POST 전 단1회 의도를 fsync하고, 불명 응답은 같은 identifier GET으로 조회하며 POST 재시도는 하지 않는다.
- terminal 주문의 체결 목록/건수·수량·대금·수수료를 대조한다. 시장가 매수가 일부 잔액 환급으로 cancel이어도 체결량을0으로 취급하지 않는다.
- 매수 체결 수량과 거래소 BTC 가용량이 정확히 같고 잠금0일 때만 그 수량을 매도한다. 매수 후 예외이면 동일 체결을 조회해 아직 보내지 않은 매도1회만 정리 시도한다. 이미 매도 의도가 있으면 재전송하지 않는다. 잔량/불명/출처 오류는 완료로 쓰지 않는다.
- 최종 완료는 BTC가용/잠금0·KRW잠금0·매수/매도 수량 일치·매수원가≤1만원·계좌 KRW증감=주문원천 순손익 일치다. 조회/완료 기다림은 유한하며 무한 재시도는 없다.
- 원문 주문/계좌 응답은 서버0700 폴더 안에만 두고 로컬에는 자기 시험의 대금/수수료/손익·판정·원문 해시만 반출한다. API키/JWT/전체 계좌 원문을 반출하지 않는다. 제품·운영 Git·DB·cron·기존 보유APENFT·SID203은 바꾸지 않는다.

순수 경계14/14(서명 파라미터·terminal/부분체결·원천 건수·수량·수수료 NULL/NaN/음수·금액상한) 통과, 외부 호출0. 기존 PG/전체 회귀/jar는 반복하지 않았다.

Upbit 공식 [주문 생성](https://docs.upbit.com/kr/reference/new-order), [개별 주문 조회](https://docs.upbit.com/kr/reference/get-order), [인증](https://docs.upbit.com/kr/reference/auth)의 시장가 매수/매도·identifier 조회·HS512/query_hash 계약을 실행 전에 확인했다. 문서 예시 잔고나 수수료를 실제값으로 쓰지 않는다.
