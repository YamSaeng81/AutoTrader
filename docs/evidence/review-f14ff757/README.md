## 2. 실현손익 정의 — 표시 문제로 종결하지 않는다

REAL 저장 손익이 매수 수수료를 제외한다는 실제 PG 관측을 수용한다. 그러나 “차이는 손익 표시 열에만 있다”는 서술은 철회하고 정정 메모를 추가한다. 운영 0e1d2a02의 `OrderRepository.sumLiveSessionRealizedLossSince`·`sumDynamicRealSessionRealizedLossSince`는 매도 반영 대금−매도 수수료−수량×`avg_price`를 읽는다. `RiskManagementService`의 연속 손실 검사도 `position.realized_pnl`을 읽는다. 일·주·월 한도, 연속 손실, 전략의 수익률 경계에 영향이 있는지 구분해야 한다.

- **다음 우선 작업:** 같은 입력을 실제 호출 경로로 넣는 로컬 시험과 소비 경로 표를 만든다. 매수 대금7,500·수수료3.75, 순매도7,501이면 REAL 관례 +1과 비용 뒤 −2.75로 부호가 갈린다. 이는 이번 총괄의 산술·소스 반례이며 제품 실행 결과로 쓰지 않는다. LIVE·DYNAMIC REAL·DYN_PAPER와 LIVE_ALIGNED를 구분하고 손익 표시/전략 판단/연속 손실/일·주·월 보호식/정정 후 정산 행을 연결한다.
- 성적표의 공통 경제 손익은 **양쪽 수수료를 포함한 주문 원천과 잔액**으로 정의한다. 기존 REAL 판단 평균가를 곧바로 수수료 포함으로 바꾸면 SL/TP·시작 계약도 바뀌므로 일괄 수정하지 않는다. 종전 v1.147 R5·v1.158 보호식 계약과 차이를 표로 내고, 가격 기준과 비용 기준을 분리하는 최소 수정안을 제출한다.
- 이번 단계는 시험·영향 조사·수정안까지다. 운영·과거 행·평균가·전역 손실 SQL·F 핀·위험 한도를 바꾸지 않는다. 제품 수정이 필요한 부분은 별도 후보 판정 뒤에 한다. 이 조사 때문에 금액/BTC PG·성적표 보완·운용안 작업을 멈추지 않는다.
