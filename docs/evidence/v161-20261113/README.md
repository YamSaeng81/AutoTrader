## 3. 실행 안내 (§4-3) — 실제 실행 승인 뒤에만

순서: **F → G → V161D4 U변수 → U0 → U1 → ⏸ 운영자 확인 1회 → U2(backend) → U3 → UF2(frontend) → U4 → U뒤관측**. 블록 원문과 해시는 `d4/blocks-d4/`·`blocks-d4.sha256`을 고정 출처로 쓴다. 이 요약에서 명령을 재구성하지 않는다.

1. **U0**: 손실 조회 v2 판정이 `진행 가능(손실 세 보호식 모두 허용)` 한 줄이 아니면(거절·**판정 불가**·필수값 누락·조회 실패) 배포 전에 중단한다. frontend 실행 이미지가 FEIMGOLD와 다르면 멈춘다. 통과 뒤 30분 안에 U1을 실행하고, 매시 :14~:24는 피한다.
2. **U1**: 빌드와 보존 태그만 만들고 재기동은 하지 않는다. 운영자에게 U1 출력을 보여 주고 **U2 직전에 한 번 확인을 받는다.** 확인할 범위는 ① backend 재기동, ② 새 backend 기동 때 Flyway V96 적용(DDL, 되돌려도 지우지 않음), ③ U3 통과 뒤 이어지는 frontend 교체(UF2)다. U2를 하지 않기로 하면 U1-되돌림을 쓴다(재기동 없음).
3. **U2 → U3**: U3의 목표 시점은 U2 기동 뒤 **5~10분**이다. U3는 5분 전이면 거절한다. BTC 입력이 미충족이면 바로 되돌리지 않고, 재기동 없이 5분 뒤 U3만 한 번 다시 실행한다.
4. **UF2**: U3(deploy) 통과 뒤 frontend만 교체한다. U2~UF2 사이에는 구 frontend가 새 모드 CLOSING을 **0원·보유 0**으로 보인다. 그래서 **양쪽 설치·관측이 끝나기 전에는 새 모의 세션을 만들지 않는다.** 새 frontend 이미지 ID는 U1의 실제 빌드 뒤 `image-fe-new.txt`에 기록되며, 지금 미리 적지 않는다.
5. **U4**: 기동 30분 뒤에 실행한다(30분 전이면 거절). 이어서 U뒤관측을 실행한다.
6. **출력·종료값 보존**: 블록별 기록 파일은 `~/maint-v161` 아래 이름이 겹치지 않는다(`image-fe-before.txt`·`svc-deploy.txt`·`gate-out.txt` 등). 화면 출력은 블록마다 따로 보존한다. 각 블록 `( … )` 직후 `echo "<블록> 종료 $?" >> ~/maint-v161/exit-codes.txt`로 종료값을 남긴다. 멈춘 블록 출력을 다른 블록 출력으로 덮어쓰지 않는다.

## 4. 복구 안내의 판단 입력 (§4-4)

- **V96은 구판 복구 때 지우지 않는다.** U되돌림 뒤에도 V96 이력이 남는다(V160D4 대역 v15). 구판 b5cd1d0이 V96 DB에서 기동하는 것은 v159 실제 기동 18/18로 확인했다.
- **관문이 거절하면** U되돌림은 HEAD·backend를 구판으로 되돌리지 않고 멈춘다. 이때는 현재(새) 바이너리로 정지·유효 가격 대기·정산/정리를 계속하고 `gate-out.txt`를 보고한다. 0원 정산·행 삭제·마이그레이션 삭제는 하지 않는다(블록 문구 그대로).
- **거래소 대조 파일(`EXCH_RECON`)**: 실계좌 보유나 RUNNING이 있으면 승인된 읽기 블록의 대조 출력을 관문에 넘긴다. 관문은 파일이 있는지와 해시만 본다. **수량·잔액이 맞는지는 운영자가 파일 내용을 보고 판단해야 한다.** 파일 존재·해시를 그 판정으로 대신하지 않는다.
- DYNAMIC REAL 잔액식은 관문 범위 밖이다. 블록에 자동 되돌림을 추가하지 않았다(모든 되돌림은 운영자가 블록을 직접 실행한다).
