# v1.262 운영 활성 조건을 먼저 확인하는 전략 시험 사본

사용자가 확정한 **누적 매수대금+매수수수료 총5만원**과 앞 비용9,954.18210375원 포함·한 번에 한 LIVE·단일매수·BTC잔량0 종료 조건은 [첫 고정 시험안](../strategy-live-suite-20261128/README.md) 그대로다. 운영 제품/이미지·전역 설정·기존66세션/SID203을 바꾸지 않는다.

## 첫 시도와 실제 활성 상태

첫 배치는 COMPOSITE_BREAKOUT 생성 요청에서 HTTP 오류로 멈췄고 신규 세션0·시작0·주문0이었다. 조회된7개 중6개가 strategy_type_enabled의 false였다. 실제 source의 StrategyEnablementGate는 이 검사를 생성의 맨 앞에서 수행한다. 최초 진단 SQL은 열명을 strategy_type으로 잘못 써 실패했고, 고정 엔티티의 strategy_name으로 고쳐 읽었다. 실패 stderr 원문은 미보존·길이/해시만 보존했고 정상 진단 원문/당시 상태는 첫 폴더에 남겼다.

비활성화6개를 true로 바꾸거나 거래가 나오도록 임의 설정을 하지 않는다. 새 사본은 **생성 전에** 전략·H1 활성 플래그를 읽어 false면 SKIPPED_DISABLED/생성0·매수0으로 기록한다. 행 부재는 현재 제품과 같은 허용, 존재하는 행의 NULL/형식 불명은 거절이다.

## 고정 후보 순서와 한도

처음7개 순서는 유지하고, 가격/신호/성과를 보지 않은 상태에서 코드상 ENABLED인 다음4개를 뒤에 붙였다: COMPOSITE_MOMENTUM, COMPOSITE_MOMENTUM_ICHIMOKU, COMPOSITE_MTF_BTC, COMPOSITE_MTF_MOMENTUM. 순서/판정은 plan.py에 고정한다. 조회 기준 실행 가능한 것은 MOMENTUM_ICHIMOKU_V2, MOMENTUM_ICHIMOKU, MTF_BTC, MTF_MOMENTUM의4개다. 조회 뒤 바뀔 수 있으므로 각 생성 전에 다시 검사한다.

후보11개 중 실제 생성은 최대7개다. 한 사례 원가 예약5,600원, 기존 비용+7×5,600=49,154.18210375원 이하, 실제 원가만 누적·매도 대금으로 한도를 복원하지 않음·남은 예약액이 부족하면 새 생성 없음을 유지한다. 더 많은 후보가 있어도5만원이나7개 상한을 넘어 반복하지 않는다. 이전 배치는 종료돼 신규 세션/주문0인 사실과 새 사전 읽기의 활성/보유0을 확인한 후 새 서버 폴더에서1회 시작한다.

추가 직접 경계는 실제 활성 행/부재/거절/NULL 및4개 요청 계약이다. 파일 시험39/39 통과. 새 제품 빌드·회귀·PG는 반복하지 않았다. 게이트 SQL/판정기·관측기·실제 입력/이미지 사전 검사 원문은 첫 배치와 같다. 차이는 사전 활성 검사·고정 후보 확장·최대 생성7개 및 HTTP 상태 코드 기록뿐이다.
