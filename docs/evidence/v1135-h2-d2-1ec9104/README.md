# H2 jar 비교기 v2 · O1·O3 배포 초안 D2 · 전체 단계 대역 (총괄 v1.135 §2 H2·§5-3, 2026-11-09, 로컬)

**개발 결과다. 총괄 판정 전이다. D2는 미승인·서버 실행 금지 초안이다.** 서버·DB·운영 Docker·원격 셸에는 닿지 않았다. D1(`o1o3-candidate-1899b49/w6/blocks-d1`)·옛 비교기(`k23-prep-51dcee5/jars/jarcmp.py`)·승인 블록·과거 근거는 고치지 않았다. 운영 이미지 ID는 만들거나 추정하지 않았다. 대역은 D2 U변수 원문의 IMGOLD 값을 대역 이미지 이름으로만 썼다.

## 1. 비교기 v2 (`comparator/`)

`jarcmp_v2.py`는 v1과 항목 비교·출력 형식이 같다(변경/추가/삭제 줄, `(끝) a b`). 다만 아래를 **옛 쪽과 새 쪽 모두** 검사한다.

- 바깥 jar 이름 중복. 디렉터리 항목 중복과 같은 바이트의 중복도 포함한다.
- 자체 모듈(core-engine·strategy-lib·exchange-adapter) jar **내부** 이름 중복.
- 판 번호만 다른 자체 모듈 jar 두 개가 같은 이름으로 겹치는 경우. v1은 뒤의 jar가 앞의 jar를 덮어썼다. 총괄이 지적하지 않은 같은 계열의 공백이라 함께 막았다.
- 바깥 jar나 자체 모듈 jar가 zip 형식이 아닌 경우.

하나라도 있으면 차이를 내지 않고 `🔴 jar 비교 거절` 줄을 낸 뒤 **종료 3**으로 끝난다. 양쪽에 같은 중복이 있어도 상쇄하지 않는다.

**합성 대조** `bench-r2.txt`: **26/26**. 각 사례는 v1 출력도 함께 적었다.

- 대조군과 정상 판정:
  - 같은 내용
  - 시각·압축 방식만 다른 재포장(차이 0)
  - 자체 모듈 판 번호만 바뀜(차이 0)
- 중복 거절:
  - 내부 중복: 다른 바이트·같은 바이트, 새 쪽·옛 쪽·양쪽
  - 바깥 중복: 다른 바이트·같은 바이트, 새 쪽·옛 쪽·양쪽
  - 디렉터리 항목 중복
  - 자체 모듈 이름 겹침
  - jar 형식 아님
- 차이 줄로 보이는 변화: 클래스 변경, 리소스 누락·추가, 설정 변경, 마이그레이션 추가, 외부 라이브러리 판 변경, 로더·META-INF 변경.
- 총괄 fixture 세 개: base는 차이 0, inner-duplicate·outer-duplicate는 거절. v1은 inner-duplicate를 차이 0으로 판정했다.
- 실제 보존 jar 1899b49(`a4fd4e34…`) → 0d142aa(`dc26fe4b…`): **v1 출력과 v2 출력이 바이트까지 같고**, 3항목·`(끝) 881 881`이다.
- 대역 결함 1건(보존): `bench-r1.txt` 25/26. 외부 라이브러리 사례에서 **기대 목록의 줄 순서**를 정렬 순서와 반대로 적었다. 비교기 출력은 두 줄 모두 맞았다. `test_jarcmp_v2.r1.py` 대비 그 한 줄만 정렬 순서로 고쳐 r2로 돌렸다.

**실제 jar 기반 재현** `realjar-dup-preview.txt`: 실제 0d142aa jar에 중복 항목 하나만 더한 대역 jar로 비교했다(`mkdupjar.py`).

| 대역 jar | v1(D1 U1과 같은 함수) | v2 |
|---|---|---|
| core-engine 내부 다른 바이트 중복 | 3줄·`(끝) 881 881`, **D1 U1이 통과했을 입력** | 종료 3 거절 |
| core-engine 내부 같은 바이트 중복 | 3줄·`(끝) 881 881`, 통과했을 입력 | 종료 3 거절 |
| 바깥 같은 바이트 중복 | 3줄·`(끝) 881 882`, D1은 항목 수 검사로만 멈춤 | 종료 3 거절 |

**실제 보존 jar에는 중복이 없다.** 총괄 검토와 같으며, 과거 3항목 차이와 #26 결과는 취소하지 않는다. 이미 배포된 jar에서 중복을 발견했다고 기록하지 않는다.

**최종 SHA jar** (`final-jar-build.txt`, `final-jar-compare.txt`, `build-1ec9104.log`):

- 깨끗한 분리 작업 사본(HEAD `1ec9104`, 변경 0)에서 bootJar를 한 번 만들었다(시험 제외). 결과 `76a8e403…`.
- 보존 후보 jar 0d142aa와 v2로 비교하면 **항목 차이 0**(`(끝) 881 881`)이다. 1ec9104는 시험 파일만 바뀌었다.
- 1899b49 대비 차이는 같은 3항목·881→881이다. 그래서 D2의 RARX는 D1과 같다.

## 2. D2 블록 (`d2/`)

`mkdraft2.py`가 D1 여덟 블록에서 D2를 만든다. 각 치환은 지정한 횟수만큼 정확히 맞아야 하며, 남은 D1 표기가 있으면 멈춘다. 차이 전체는 `D1-to-D2.diff`에 있다.

- 판 표지 `UB=O13D2`. 여덟 블록이 모두 확인한다. 멈춤 문구는 "초안 D2 판이 아님"이다.
- `NEW=1ec91046bf2bf0b7af0e6f05c04267a6c78efc21`. 후보 브랜치 원격 HEAD와 같다.
- `DIFFN`은 실제 `git diff --name-only 1899b49 1ec9104` 6경로다(`diffn-1ec9104.txt`). 제품 2·시험 4이며, D1에 ExecutionDriftTrackerTest가 더해졌다. U0 문구는 "6개 파일"이다.
- U1은 jar 비교기를 v2로 바꿨다. 내장 본문은 `jarcmp_v2.py`와 바이트가 같다(`embed-check.txt`).
  - D1의 `| tee` 파이프 대신 출력을 파일로 받아 종료값 `JC`를 확인한다.
  - **비0이면 `stop "jar 비교기 v2 거절(종료 $JC) … (재기동 전). U1-되돌림"`으로 끝난다.** `ok-U1` 표지 앞이다.
  - RARX 3줄과 `(끝) 881 881` 확인은 그대로다.
- 그 밖의 로직은 D1과 같다. 시각 창, IMGOLD, 복구 태그, 설치본, cron, SID 203, BTC, 뉴스·HTTP·HOLD·N15~N20 관측, U3·U4 P0 위치, 되돌림이 모두 해당한다.
- 여덟 블록 모두 `bash -n`을 통과했다(`d2-syntax.txt`). 해시는 `blocks-d2.sha256`에 있다.

## 3. 전체 단계 대역 (`standin/`)

장치(`harness/`)는 N20 D1·D2 대역(`n20-d1-standin-1899b49`)의 가짜 명령을 옮겼다. 바뀐 값은 `conf.sh`·`conf.local.sh`에 모았다: 기점 1899b49, 최종 1ec9104, #26 이미지, 보존 jar와 최종 jar, 실제 diff 6경로.

- 블록에는 현재 main 계획서의 F(`NEW=1899b49`, v1.132)와 G를 앞에 붙였다(`fg/`). U1-되돌림 한 줄(`extra/`)은 계획서 §98 원문이다.
- 가짜 명령:
  - `docker cp`는 **실제 jar**를 꺼내 준다. U1의 v2 대조는 실제 jar로 계산된다.
  - ssh·scp·curl·psql·sudo·systemctl·gradle·java 등은 금지 기록을 남기고 종료 99로 끝난다.
  - 실행 전 확인(`preflight.txt`): 대역 PATH의 해당 명령이 모두 가짜 명령으로 풀렸고, 블록·F·G의 절대 경로 명령은 0줄이었다.
- **대역 35개(`d2-*`) 금지 명령 기록 0줄.** 요약은 `scenarios-d2-summary.txt`, 대역별 원문·호출 기록은 `runs/`에 있다.
- jar 사본은 보존하지 않았다. 해시는 `jars-not-preserved.sha256`에 있다.
- `x0-shake`는 최종 SHA 고정 전에 장치를 시운전한 것이다. 가짜 NEW와 0d142aa jar를 썼으며 결과로 세지 않는다.

대역 응답·로그·설치 해시는 고정값이다. **이 대역은 다음을 주장하지 않는다.**

- 운영에서 D2가 통과한다는 것
- 운영 이미지 ID
- 실제 서버의 응답

## 하지 않은 것

- 서버 빌드·배포·재기동·설치·cron·DB 설정·주문·세션 조작.
- D1 덮어쓰기, 옛 비교기 수정.
- 운영 이미지 추정.
- 이미 v2로 검증한 입력의 반복.
- 이 발견만으로 새 앱 jar를 운영용으로 빌드하지 않았다. 최종 SHA jar는 로컬 대조용으로 한 번만 만들었다.
