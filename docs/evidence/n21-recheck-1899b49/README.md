## 영향

- 후보를 적용하면 재조회가 일시 실패한 회차는 🟢 대신 ⚪(net)나 🔴(404)가 된다. 그래서 72시간 연속 구간이 지금보다 더 자주 끊길 수 있다. 이것은 기존 계약("보지 못한 것을 통과로 세지 않는다")으로 돌아가는 것이고, 새 기준이 아니다.
- 다음은 바꾸지 않았다: 재시도 횟수·시간제한·간격, 70초 재확인, 90분·72시간, 경보 등급, 앱·주문·N03 설치판.
- **이 결함은 11-09 218분 관측 공백의 원인이 아니다.** 제출된 실제 9행에는 `net`·`404`이면서 이전 `exTo`가 남은 항목이 0개다(총괄 `review.json`). 04:58~06:19 KST의 🟢21도 이 결함으로 생긴 것이 아니다.
- N21의 등급은 감시 판정 P1이다. 로컬 재현으로 확인했고 운영은 고치지 않았다. 주문·정산 경로 결함이나 DB 연결 획득 P0는 아니다. 서버를 되돌리거나 감시 도구를 손으로 다시 돌릴 이유로 삼지 않는다.
- 운영 서버의 감시 도구는 배포 체크아웃(1899b49)에서 돈다. 이 후보는 배포 승인 전까지 운영에 반영되지 않는다.

## 정정 메모 (§105-2, 옛 근거·체크섬·과거 판단 행은 그대로 둔다)

1. **`at`의 뜻은 회차에 따라 다르다.** 배포판 `cmd_freshness`는 `now`를 두 곳에서만 정한다.
   - 최초 DB 조회 뒤, 거래소 1차 조회 반복 전
   - 재확인 대상이 있으면 재확인 반복 뒤

   따라서 재확인 회차에서 `at`은 재확인 뒤 시각이고, 재확인이 없는 회차에서는 1차 조회 전 시각이다. `v1136-gap-1109`와 PROGRESS 346차는 `at`을 "완료 시각"이라고 썼는데, 이것은 재확인 회차에만 맞는다. 19:56·19:57·19:58·20:50Z 행은 모두 재확인 회차라 그 대조는 유효하다. 21:19Z 행은 재확인이 0이므로 같은 해석을 적용하지 않는다. `at`을 파일 mtime이나 실제 종료 시각과 같다고 보지도 않는다. 기존 `test_freshness_spacing.py` 다섯째 줄의 "JSON at 은 … 재조회 뒤 관측 시각" 확인도 재조회 회차에만 해당한다.
2. **시작과 완료의 짝은 확정하지 않는다.** cron 시작 기록(syslog·journal)에는 PID와 종료 기록이 없다. 04:56~04:58 KST의 세 행과 05:50 KST 행이 어느 회차(02:19·03:19·04:19·05:19 KST 시작)에서 나왔는지, 각 회차가 얼마나 걸렸는지, 어떤 순서로 끝났는지는 확정하지 않는다. "05:19 시작 → 05:50 행"도 유력한 짝일 뿐이다.
3. **N21은 관측 사건의 원인이 아니다.** 위 '영향' 항목대로다.
