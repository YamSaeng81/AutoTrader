## 1. 고정1(SID203) 시작 조건 초안

새 LIVE를 만들지 않는다. 기존 SID203(CREATED 유지)을 그대로 연결한다.

| 항목 | 값 | 출처·상태 |
|---|---|---|
| 세션 | SID203, LIVE, KRW-BTC, DAILY_SMA20, H1 | [현재 계획 §4](../../LIMITED_LIVE_TEST_PLAN.md) — 확정 계약 |
| 자본·주문 | 초기 20,200원, 1회 최대 20,000원, stopLossPct 5, maxHoldHours 0 | 같은 곳 — 확정 계약 |
| 기간 | 실제 started_at부터 56일 또는 중단 중 먼저 오는 시점. 추가 입금·증액·연장·재개 없음 | 같은 곳. 12월 말 평가로 바꾸지 않음 |
| 기존 중단선 | 누적 −15,000원, 24시간 −3,000원, CAPITAL_LOSS −15%, MAX_DRAWDOWN −20%, CB_REPEAT ≥3, 왕복 비용 >0.40% | 같은 곳 — 유지 |
| 사용자 예산 | 합산 100,000원(SID203 20,200원 포함), 12월 합산 허용손실 40,000원 | [budget.json](../dec-launch-order-20261123/budget.json) |
| 예산상 미배정 | 79,800원 | **계산값일 뿐 실제 계좌 현금·cash_base가 아님** |
| 실제 계좌 현금·배정 | 미확정 | 승인된 계좌 읽기 원천 없음 |
| 규칙 지문(ruleset) | 미확정 | 승인된 원천 없음 |
| 시작 시각·T0 | 미정 | 12-01 08:50~08:55 창은 목표이며 승인 아님 |

**고정1 단독일 때 두 한도의 관계(출처 계산):** SID203 자본이 20,200원이므로 고정1만으로는 손실이 40,000원에 도달할 수 없다. 이보다 먼저 기존 누적 −15,000원선이 발동한다. 따라서 고정1 단독 단계에서 묶이는 기준은 기존 중단선이다. 40,000원 상한은 DYNAMIC 배정이 더해질 때 실제 의미가 생긴다.

**달력월 40,000원의 자동 제어 여부:** d81c3f2f의 `RiskManagementService`는 1·7·30일 이동 창의 **손실률(%)**만 계산한다. 근거는 `calculateLossPct(now.minus(30, DAYS))` 등(182~184행)이다. **달력 12월의 합산 절대금액을 측정·차단하는 코드는 이 파일에서 찾지 못했다.** 그래서 이 한도는 운영자 관측과 조치로 지키는 정책으로 두고, 측정 방법과 담당은 아래 관문 표에서 빈칸으로 남긴다. 새 월 한도 엔진은 착수하지 않는다. stopLossPct나 risk_config에 40%를 넣지 않는다.

**ENTRY_REJECTED로 복구가 막히는 경우:** d81이 운영에서 ENTRY_REJECTED 행을 하나라도 남기면, 4판 관문은 STOP_INCOMPATIBLE(3)을 낸다. 이 상태는 기다려도 풀리지 않는다(대역 S01~S04). 그때의 대응은 아래와 같다.

- 현재 바이너리(d81)를 유지한다. 행 삭제, NULL 치환, DB 과거 복원은 하지 않는다.
- 신규 진입은 기존 정지 경로로 막는다(세션 정지·비상정지). 실행 절차 §6-2를 따르며 새 명령을 만들지 않는다.
- 거래소 미결 주문과 보유 확인은 운영자가 직접 한다. 확인 방법·대응 가능 시간·담당은 **운영자 기입 빈칸**이다.
- 호환 바이너리를 쓸지는 미결정으로 남긴다.

## 3. 고정1 단독 대조(F3/P7)의 d81 유효성 — 출처 차분

비교 대상은 P7 v8([reconcile.py](../dec-registry-p7v8-20261120/p7v8/reconcile.py))과 F3 v9([f3.py](../dec-f3-v9-20261120/f3v9/f3.py))의 입력 계약, 그리고 0e1d2a02..d81c3f2f 제품 차분(14파일, migration 0)이다.

| d81 변경 | 대조기 입력 영향 | 판단 |
|---|---|---|
| `ExitReason.ENTRY_REJECTED` 추가 | P7/F3는 `exit_reason`을 읽지 않는다(grep 0). 포지션 입력은 id·kind·session·coin·size·status뿐이다. ENTRY_REJECTED 행은 CLOSED·size 0이라 OPEN 수량 합산에 들어가지 않는다 | 영향 없음(출처 기준) |
| `OrderSettlementService` | 반환형과 알림 요약 적재만 바뀌었다. 체결 반영 계산 경로의 값 변경은 없다 | 영향 없음(출처 기준) |
| `OrderRepository`·`PositionRepository` 조회 추가 | 제품 내부 조회이며 대조기 추출 SQL이 아니다 | 영향 없음. 추출 SQL v3는 96/96 대조로 연결됨 |
| DDL | 없음(V96 유지) | 입력 열 변화 없음 |

**한계:** 출처 차분만으로 본 결론이다. 실제 d81 운영 행으로 P7/F3를 돌린 근거는 없다. 실제 계좌 대조는 registry-3과 승인된 계좌·DB 읽기가 있어야 하며 아직 없다. 옛 registry-v2 초안이나 합성 입력은 실제 근거로 쓰지 않는다.

**고정1 단독에 필요한 다음 읽기(제안만, 실행 안 함):**
- 거래소 계좌 KRW·BTC 잔액 1회.
- SID203의 available_krw·status.
- LIVE/DYNAMIC 실자금 미체결 주문과 OPEN·CLOSING 포지션의 식별 목록(금액 제외).

목적은 registry-3 cash_base와 holdings_base의 초기값을 정하는 것이다. 구체 열과 출처는 오늘 상태 읽기 결과를 본 뒤 좁혀서 제출한다.

**DYNAMIC 병행에 추가로 필요한 것:** 실제 registry-3, P7 전체 관측, W1 집합과 고정 조건, 새 병행 감시가 필요하다. 모두 아직 없다.
