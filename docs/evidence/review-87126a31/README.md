## 2. P7 시계 보완을 로컬에서 진행한다

**보완을 승인한다. v4는 보존하고 새 v5 사본에서 시간 비교의 근거를 분리한다.** [저장 입력·출력](observations.json)의 L/D 01b는 정상 생성에도 `REGISTRY_CONTRACT_MISMATCH`가 나는 반례다. 수집기 축의09 보류와 구분한다. 시계 관계를 모를 때 시간 차이만으로 이상을 확정하지 말고 해당 비교를 보류한다. 실제 전략/모드/코드/자본 불일치와 확정된 현금·보유 부족은 계속 이상으로 남긴다.

1. **축을 명시한다:** 수집 단계·DB `observed_at`·앱의 세션/주문 `created_at`·등록 `effective_from/to`·거래소 주문 생성/조회 기간의 축과 근거를 기록한다. 모두 UTC 표기라는 이유로 같은 시계로 보지 않는다. 과거 시각을 옮기거나 단일 평균 오프셋/임의 초 단위 유예로 통과시키지 않는다.
2. **차이를 측정하는 안을 바로잡는다:** “가장 최근 행의 앱 생성 시각과 현재 DB now()”는 행의 나이까지 포함하므로 시계 차이 측정으로 쓰지 않는다. 거의 동시에 실제로 읽은 시계 값과 수집기 요청 시작/끝·단조 시계의 왕복 시간을 쌍으로 남겨 오차 범위를 만든다. 현재 `at_db`는 각 단계 직전의 조회 표본이지 거래소 응답/추출 전체의 완료 시각은 아니다. 이벤트 시작·끝과 표본의 관계를 구별한다. 운영 앱 시각을 읽을 방법이 승인돼 있지 않으면 추정값을 만들지 않고 보류한다. 새 운영 엔드포인트나 제품 시계 변경은 이번 범위에 넣지 않는다.
3. **범위로 판정한다:** 근거가 있는 같은 축/변환 범위에서만 순서를 확정한다. 경계가 겹치거나 보정 근거가 없거나 시계 이동/오래된 표본으로 비교를 확정할 수 없으면 `CLOCK_AXIS_UNCONFIRMED` 등으로 해당 계산을 보류한다. 표본75개의 관측 차이가 +1,366~1,498ms로 변한 것도 고정 상수가 아님을 보여 준다. 보류 하나로 이미 확인한 −1.50원·담보 부족 같은 별개 이상을 숨기지 않는다.
4. **입력 계약을 구분한다:** 축 정보 없는 실제 입력을 암묵적으로 같은 시계로 승격하지 않는다. 기존 합성 시험은 별도 v5 입력에서 가정한 축/근거를 명시하고 원본94/109 입력은 보존한다. 거래소 조회 기간과 DB 의도 생성 시각도 동등하다고 가정하지 않는다. 수집 메타데이터안은 먼저 격리 환경에서 확인한다.
5. **시험 범위:** 01b의 실패 재현을 먼저 고정하고 0·양/음 차이, 경계 겹침, 누락/오래된 표본·시계 이동, 확정된 선후 관계, 별개 이상과의 동시 발생을 확인한다. 바뀐 시간 검사·관련 파일 입력만 검증한 뒤 v5 계약에 맞춘 회귀를 한 번 돌린다. 무관한 Java 전체 회귀·jar·기존 변형은 반복하지 않는다.
