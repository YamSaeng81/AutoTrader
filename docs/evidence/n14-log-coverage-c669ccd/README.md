## 2. 바뀐 것

1. **2-1 ERROR 로그 범위(새 절)** — 앱 컨테이너 절(2) 바로 뒤에 넣었다.
   - **생성 시각 읽기**:
     - 실제 실행에서는 `docker inspect --format '{{.Created}}' <backend 컨테이너>` 를 읽는다. 상태 조회와 같은 컨테이너 ID 다.
     - 시험에서는 `APP_STATE` 와 함께 `APP_CREATED` 를 준다.
   - **판정**:
     - 값이 `YYYY-MM-DDTHH:MM:SS[.소수 1~9자리](Z|±HH:MM)` 이고 GNU `date` 가 읽으면, 나노초까지 비교한다.
       - **생성 시각 > 구간 시작** 이면 ⚪ `ERROR 로그 범위 미확보 — 구간 안에 backend 컨테이너가 새로 만들어졌다(생성 MM-DD HH:MM:SS). 구간 시작 MM-DD HH:MM ~ 생성 전 로그는 ERROR 집계 밖`.
       - 생성 시각 ≤ 구간 시작 이면 공백 없음.
     - 값이 없거나 형식이 다르거나 날짜로 읽히지 않으면 ⚪ `ERROR 로그 범위 확인 불가 — backend 컨테이너 생성 시각을 읽지 못했다(받은 값)`.
       - 받은 값은 ASCII 인쇄 문자만, 첫 줄의 앞 40자만 보인다.
       - 컨테이너가 없을 때도 여기에 해당한다.
   - **상세 줄**은 늘 하나 낸다: `로그 범위: 요청 MM-DD HH:MM ~ 실행 시각 · 현재 컨테이너 생성 …(구간 시작 전·같음 — 재생성 공백 없음 | 구간 안 — 생성 전 로그 미포함 | 확인 불가)`.
2. **ERROR 상세 줄의 머리**:
   - 공백이 없으면 종전과 같은 `ERROR(구간): …` 이다.
   - 공백이면 `ERROR(현재 컨테이너 생성 MM-DD HH:MM:SS 뒤만 — 구간 앞부분 미포함): …` 이다.
   - 확인 불가면 `ERROR(로그 범위 확인 불가): …` 이다.
   - 분류·건수·🔴/🟡 는 그대로다.
3. **`CHECK_SINCE_ISO`(시험용)** — 비면 종전처럼 `date -u -d "-${WINDOW_HOURS} hours"` 이다. 경계 시험에서 구간 시작을 고정하는 데만 쓴다. cron 줄에는 넣지 않는다.

**바꾸지 않은 것**:
- 머리글 규칙: ⚪ 가 하나라도 있으면 `⚪ 판정 불가`, 다음 🔴, 다음 🟢.
- ⚪ 가 있어도 🔴·🟡 줄은 모두 그대로 나온다.
- 구간 안 기동 🔴(StartedAt)·재시작 횟수 🔴.
- DB·BTC·66세션·텔레그램 검사, 오류 분류 패턴, `daily_checks.sql`, 잠금, 전송, cron.
- 이전 컨테이너 로그는 합산하지 않는다. 로그 회전·보존 한도까지 검증했다고 하지 않는다.

**StartedAt 과 Created 를 나누는 이유**:
- 같은 컨테이너의 재시작은 StartedAt 만 바뀌고 json-file 로그가 남는다. 그래서 `compose logs --since` 가 구간 앞부분도 준다.
- `compose up` 의 재생성(새 이미지 배포)은 새 컨테이너다. 그 전 로그는 이전 컨테이너에 있다.
- 11-04 22:00 보고에서는 16:39 KST 재생성으로 10:00~16:39 의 로그가 집계 밖이었다.
- 이번 후보는 그 경우를 ⚪ 로 드러낸다. 다음 N03 보고(11-05 10:00, 구간 11-04 22:00~)는 생성 시각 16:39 가 구간 전이므로 공백이 없다.

## 5. 한계

- 재생성으로 **확실한** 공백만 표시한다. 같은 컨테이너 안의 로그 회전(json-file `max-size`)으로 앞 로그가 잘린 경우는 이 후보가 잡지 않는다.
- 운영 `docker inspect` 의 실제 `Created` 값 형식은 서버에서 다시 보지 않았다. 대역에는 Docker 의 RFC3339 나노초 형식(`…T07:39:13.123456789Z`)과 소수 없는 형식을 썼다.
- 이 근거를 담은 main 커밋의 SHA 는 여기에 적지 않는다(N06).
