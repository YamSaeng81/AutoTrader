## 3. 조회 개선 효과의 관측과 중단 기준

`holdobs <앱 로그>` 는 앱 로그를 읽기만 한다.
- 출력은 시각·스레드 종류·앱 프레임·건수뿐이다. 연결 식별자·정확한 스레드 이름·질의문·본문은 내지 않는다.
- HOLD 경고는 Hikari 누수 경고(대여 60초 초과) 가운데 첫 앱 프레임이 `SignalQualityService.evaluateHoldBaselineLoop` 인 것이다(11-04 초기 자료의 모든 장기 대여가 이 프레임 227/228행이었다. 후보는 서비스를 바꾸지 않아 줄 번호가 같다).
- 반환(`unleaked`) 짝, 그 밖의 장기 대여 경고, `Connection is not available, request timed out` 줄, 시작 catchup 시작·완료 시각도 센다.

| 종료 | 뜻 | 블록의 처리 |
|---|---|---|
| 0 | 장기 대여 경고 0·획득 시간 초과 0 | 통과 |
| 3 | 장기 대여 경고 있음(HOLD 또는 그 밖) | ⚪ 개선 미확인 — `hold-check-*.txt` 를 남긴다. **되돌리지 않는다**(구판으로 돌아가도 같은 경고가 난다). 출력을 보고 |
| 1 | 연결 획득 시간 초과 줄 있음 | 🔴 **P0 — 멈추고 즉시 보고**. 되돌림 여부는 총괄 판단(P 되돌림 블록 준비됨). P0 기준선에서 나오면 배포하지 않는다 |

- **관측 시점**:
  - 기동 직후 `ApplicationReadyEvent` 의 시작 catchup 이 HOLD 질의를 바로 돈다.
  - 정기 회차는 기동 5분 뒤 처음 돌고, 그 뒤 30분마다 돈다.
  - P4(기동 30분 뒤)의 로그는 catchup 과 첫 정기 회차를 포함한다.
  - 개선을 확인했다고 쓰려면 다음이 모두 필요하다: P4 에서 `시작 Catchup 완료` 줄, HOLD 경고 0, 획득 시간 초과 0. 그리고 P 뒤 관측(다음 정기 보고 무렵)에서도 같아야 한다.
- **배포 전 기준선**: P0 가 지금 컨테이너 로그(11-04 16:39 KST 이후 전체)에 `holdobs` 를 돌려 `hold-before.txt` 로 남긴다. 22:00 보고 로그에서는 경고 35·반환 34 였다. 기준선의 종료 3 은 멈추지 않는다.
