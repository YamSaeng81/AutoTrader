# 문서 전체 점검 — 현재 안내·명령·고정 계약·이력 분리

2026-11-12 사용자가 진행 지시와 프로젝트 관리에 쓰는 문서 전체의 가독성·중복·토큰 낭비를 점검해 달라고 요청했다. Markdown 파일의 분량·분류·판정 배너를 조사하고, 자주 읽는 관리 문서와 실제 추출 도구의 참조를 집중 검토했다. 모든 문서의 기술 주장이나 제품 코드를 새로 검증한 것은 아니다.

## 발견과 조치

| 문제 | 조치 |
|---|---|
| PROGRESS 첫머리에 많은 판정 전문, 뒤에는 수개월 전 배포/전략 권고 | 최근 제출·수용을 구분한 짧은 색인으로 변경, 전체 원문 보존 |
| 준비 목록·11월 표·점검 문서에 같은 판정 요약을 반복 | 현재 조건·담당·실행 원문의 역할을 나누고 현재 상태는 계획 한 곳으로 연결 |
| 날짜가 붙은 아침 인계가 장기간 현재 상태표처럼 사용됨 | 날짜 인계는 당시 기록으로 닫고 CURRENT_HANDOFF를 현재 접점으로 사용 |
| 문서 색인이 9월 NEXT를 현재 작업으로 안내 | START_HERE와 현재 계획으로 진입점을 변경, NEXT는 과거 원문으로 연결 |
| 줄 수는 작아도 한 줄이 매우 긴 과거 요약이 많음 | 줄 수와 함께 바이트 수·중복 배너 수를 기록. 정확한 모델 토큰 수를 측정했다고 쓰지 않음 |
| 긴 사전 등록·기술 설계까지 전부 읽게 되는 흐름 | 해당 계약/§번호로만 찾도록 분류. PREREG·코드가 인용하는 경로/번호·실행 원문 유지 |

## 정리한 파일

| 파일 | 정리 전 줄 | 정리 후 줄 |
|---|---:|---:|

| OPS_DAILY_CHECK | 337 | 209 |

숫자는 `changes.json`의 이번 분리 시점 기준이다. 자주 읽는 위 관리 문서5개(PROGRESS·준비 목록·관리표·OPS·날짜 인계)는 합계 **5,373→357줄**, **1,056,378→38,677바이트(96.34% 감소)**다. 정확한 모델 토큰 수를 측정한 값은 아니다. 앞선 별도 요청에서 정리한 LIMITED_LIVE_TEST_PLAN 11,932→110줄은 이번 감소량에 다시 넣지 않았다. OPS는 명령/조건을 유지하므로 150줄로 억지로 줄이지 않았다.

`START_HERE.md`와 `CURRENT_HANDOFF.md`를 추가하고 루트 README에서 연결했다. AGENTS.md·CLAUDE.md에도 짧은 탐색 안내를 두었다. 권한 설정을 바꾸거나 운영 실행을 자동 승인하는 내용은 없다. 현재 문서의 150줄 안팎·PROGRESS 최근5건 기준은 편집 기준이며 필요한 계약을 잘라내는 실행 제한이 아니다.

## 원문과 기술 계약의 보존

- 바꾼 관리/색인 문서7개의 **분리 직전 전체 바이트**를 같은 docs 폴더의 `*_ARCHIVE_20261112.md`로 보존했다. 같은 폴더라 원래 상대 링크가 폴더 이동으로 깨지지 않는다. archive SHA256은 changes.json의 before_sha256과 같다.
- PROGRESS 보존본에는 개발의 **397차/v1.158 제출**도 들어 있다. 처음 점검을 시작한 뒤 추가된 결과를 지우지 않았다. 이 개발 결과는 총괄 검토 전으로 명시하며 새 수용 판정을 내리지 않았다.
- PREREG 문서7개와 LIVE_RISK_IMPLEMENTATION_REVIEW·UNKNOWN_ORDER_STATE_DESIGN·DESIGN의 **10개 문서 본문은 변경하지 않았다**. 보호 목록은 protected-documents.json이다. 특히 긴 LIVE_RISK 2,471줄·Supertrend 사전 등록 2,408줄·UNKNOWN_ORDER 1,389줄은 자동 전체 읽기 대상에서 제외하고 필요한 절로 안내했다.
- 날짜가 붙은 다른 인계, 과거 evidence 원문·체크섬·고정 출처와 제품 코드는 바꾸지 않았다. 이번 새 기록 외에 앞선 검토 근거를 수정하지 않았다.
- .gitattributes에 새 보존본의 `-text`를 지정했다. 줄바꿈 정규화 때문에 원문 SHA가 달라지는 문제를 피한다.

루트 README의 수정 전 사본도 별도로 남겼다. 처음에는 Git의 LF 블롭을 작업 사본의 해시와 직접 비교해 중단됐다. 작업 사본은 CRLF였고, Git 원문에 CRLF를 복원한 바이트가 inventory-before의 해시와 정확히 같음을 확인해 root-readme-before.txt로 보존했다. 관리 문서7개의 원문은 재구성하지 않고 읽은 바이트를 직접 보존했다.

## 실행 문서 검증 범위

OPS의 **bash7개와 §1~§5 본문은 동일**하고, 코드가 추출하는 §3-1~§4 경계도 같다. F 실행 문서와 지난 계획서 전체 보존본은 이번 작업에서 변경하지 않았다. 기존 cron 연결 시험은 로컬 대역으로 **44/44 통과**했고, 결과는 cron-switch.txt에 보존한다. 정적 확인189개는 모두 통과했다(로컬 링크100개, 보존본7개, 고정 계약/참조10개와 이전 근거 등의 대조 포함). 정적 링크·원문/명령 해시·고정 계약 보존 결과는 verification.json에 기록한다.

이번에는 서버 접속·운영 DB·네트워크 조회·Docker·앱/PG·전체 회귀·jar 빌드·배포·세션 생성·권한 변경을 하지 않았다. 커밋·push도 하지 않았다. 검증 목적은 문서 참조와 원문 보존이며 전략 수익성/제품 동작의 재검증이 아니다.

## 이후 문서 작성 규칙

1. 현재 상태는 LIMITED_LIVE_TEST_PLAN, 최근 결과는 PROGRESS, 담당은 NOVEMBER_LIVE_UPGRADE, 시작 조건은 LIVE_READINESS, 현재 인계는 CURRENT_HANDOFF로 관리한다.
2. 상세 판정·실패 원문·시험 표는 해당 evidence 폴더 한 곳에 둔다. 관리 문서에 전문을 반복하지 않는다.
3. 보존본·코드가 인용하는 설계·사전 등록은 날짜/§번호/키워드로 검색하고 필요한 부분만 읽는다. 요약으로 고정 명령을 재구성하지 않는다.
4. 이력의 새 결과는 다음 정리 시점을 이름으로 가진 보존본에 옮긴다. 이번 보존본을 덮어쓰지 않는다.
5. 제출과 수용, 로컬 검증과 운영 반영, 관측0과 해결을 계속 구분한다.

`prepare.py.txt`는 이번 정리의 일회성 기록 스크립트다. 다시 실행하지 않는다. `inventory-before.json`은 구조 점검 당시 메타데이터이며 그 뒤 새로 생긴 파일까지 포함하는 실시간 목록은 아니다. 이전 문서 정리 근거의 파일 해시는 그 작업 직후를 기록한 값이고, 이번 관리 문서의 후속 변경은 changes.json으로 따로 연결한다.
