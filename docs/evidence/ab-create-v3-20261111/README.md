# 총괄 v1.149 §4 — A/B 생성 호출기·완성기·집계기 v3 (2026-11-11)

v1.149가 재현한 네 공백(C1·C2·A1·A2)과 §4-1·§4-2의 보완 항목입니다. 판정은 총괄 몫입니다. 실제 생성·집계는 하지 않았습니다. 서버·운영 DB·토큰·실제 HTTP는 쓰지 않았습니다.

- 과거 폴더 `ab-create-v2-20261111`은 고치지 않았습니다.
- 이 폴더는 v2 파일을 복사해 고친 새 판입니다.
- `protocol.json`은 그대로이며, sha256은 `8d787fe9…d3db`로 같습니다.

## 2. 바꾼 것

### 생성 호출기 `create/ab_create.py`

**API 대조 성공 조건**
- 사후 목록이 성공일 때만 성공으로 처리합니다.
- 조건은 정확한 팔 집합 8개, 팔별 ID 1개(= OK 응답 ID), 예상 밖 ID 0개, 잠정 후보 0개입니다.
- 조회 실패·형식 이상·불완전 집합은 성공으로 채우지 않습니다. 초안에 `api_reconcile_problems`로 적고 종료 3으로 끝냅니다.

**보내기 전 기록부 검사(종료 4)** — 다음 중 하나라도 있으면 아무것도 보내지 않습니다.
- 결과 없는 의도
- 파손된 줄, 끝나지 않은 마지막 줄, `kind` 없음
- 다른 프로토콜·대상 코드·본문 계획
- 본문 sha가 다른 의도
- OK가 아닌 결과, 또는 이미 있는 결과

사전 RUNNING 목록이 비었다는 사실로 과거 전송 미접수를 확정하지 않습니다.

**잠금과 기록 쓰기**
- 기록 폴더에 `.ab_create.lock`을 O_EXCL로 만듭니다.
- 잠금이 이미 있으면 동시 실행이거나 비정상 종료 흔적이므로 거절합니다.
- 정상·예외 종료에서는 잠금을 풉니다. 프로세스가 죽으면 잠금이 남고, 사람이 판단합니다.
- 기록 쓰기는 flush와 fsync를 거칩니다. 의도 기록이 실패하면 그 본문을 보내지 않습니다. 결과 기록이 실패하면 더 보내지 않습니다(종료 4).

**형식 검사**
- 응답 봉투, `success` 값, `data` 객체, ID(정수, bool 아님), `startedAt`(시간대 있는 ISO)을 확인합니다.
- 목록은 `data` 목록, 행의 ID·상태·시각을 확인합니다.
- 틀리면 고정 UNKNOWN 또는 "목록 형식 이상"으로 기록합니다.
- 서버 오류 원문은 기록부·출력에 남기지 않고 `error_present`만 남깁니다.

**창 재확인**
- C+6분~C+12분 창을 요청마다 직전에 다시 확인합니다.
- 창을 지났으면 `window_closed`를 기록하고, 더 보내지 않으며, 부분 결과로 종료 3입니다.

**응답 불명 뒤 목록의 새 ID**
- `provisional`(잠정 후보)로만 적고 팔에 귀속하지 않습니다.
- 규칙 지문에 팔 표지나 통계 오버라이드를 넣지 않았습니다.
- 자동 이어 보내기와 서버 API 우회는 없습니다.

### 완성기 `create/ab_complete.py` (신규)
- 입력은 API 초안과 `post_creation_check.sql`의 psql `--csv` 출력(@@ 구획)입니다. 출력은 완성 기록부입니다.
- 팔은 DB 저장값(A = 빈 하한, B = 5)으로 확정하며, 초안과 다르면 거절합니다.
- 다음 경우 완성본을 쓰지 않습니다(종료 3):
  - 구획 누락·순서 이상(확인 SQL이 끝까지 돌지 않음)
  - ID 집합 불일치
  - 저장값 불일치: 전략·코인·주기·상태·자본·비율·상한·보유·파라미터·started_at<T0
  - 지문 없음·복수·형식 이상(16진 12자)
  - T0 이전 주문·포지션
  - 초안의 API 대조 실패
- 완성본에는 `db_check`(상태 "확인됨", DB 출력 sha256, DB 시각)를 넣습니다. 이미 있는 파일은 덮어쓰지 않습니다.

### 확인 SQL `create/post_creation_check.sql` v3 (실행 금지 초안)
- 모든 결과 앞에 @@ 표지를 두었습니다.
- `max_investment`를 뽑습니다.
- **v2의 `:t0`는 따옴표가 없어 psql에서 오류가 나는 형식이었습니다.** v3는 `:'t0'::timestamptz`로 고쳤습니다. 이 오류는 v2를 실행하지 않아 발견되지 않았습니다.

### 집계기 `tool/ab_aggregate.py` v3

**완성본 검사**
- `db_verified`가 정확히 `true`여야 합니다.
- `db_check`(상태·sha256·DB 시각)가 있어야 합니다.
- `code_sha`는 40자 16진입니다.
- 세션 필수 필드와 저장값 키가 모두 있어야 합니다.

**지문**
- 행과 기록부 모두 16진 12자로 있어야 합니다.
- 서로 빈 값이 같다는 것은 유효로 보지 않습니다.
- 팔마다 다른 지문은 허용합니다.

**포지션 상태**
- OPEN·CLOSING·CLOSED만 받습니다.
- CLOSING은 미정산 보유입니다. 청산 시각·매도 현금이 비어 있어야 하며, 열린 보유로 평가합니다.
- T1 평가가가 없으면 판정 불가입니다.

**유지한 규칙**
- 42일, 4쌍 동일 가중, 고정 비용, 전체 시도는 그대로입니다.

**정직한 한계**
- 집계기의 완성본 검사는 형식 검사입니다. DB를 읽지 않고 플래그와 근거 필드를 손으로 꾸민 파일을 막지 못합니다.
- 그래서 운용 계약은 "완성본은 `ab_complete.py`가 DB 확인 출력에서 만든 것만"입니다.

### 추출 SQL `create/extract_positions.sql` (신규, 실행 금지 초안)
- 상태를 거르지 않습니다.
- CLOSING은 `closed_at`·`sell_cash_in`을 빈 칸으로 둡니다.
- `buy_cash_out`은 `invested_krw`(수수료 포함, 후보 `executeBuy`의 investAmount)입니다.
- CLOSED의 `sell_cash_in`은 `invested_krw + realized_pnl`(= 매도 순수익)입니다.
