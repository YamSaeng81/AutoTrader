## 4. 새 시험을 고르지 않은 이유

- 지시는 "구체적으로 비어 있는 연결만" 실제 서비스로 검증하라고 했다. K12·K13은 이미 실제 Spring 문맥, 처리기, 주문 대역(보호 매도 수)까지 이어 단언한다.
- K14는 HMR → MPB 상태(N20)와 MPB → 소비처(K10·PoolLossLimitTest)로 나뉘어 있다. 하지만 이음매가 같은 객체의 공개 상태(`freshPrice`)이고, 이음매 양쪽을 단언한다.
- 이미 통과한 114건·173건을 다시 돌리지 않았다.

## 5. 관찰 — 총괄 판단 항목 (보호 공백 아님, 수정하지 않음)

**O1. 강제 갱신 로그의 원문 출력.** N19 보완(총괄 v1.123)과 N20(v1.126)은 새로 넣은 WARN에 REST 응답의 market 원문·가격·예외 문구를 싣지 않게 했다. N17(7a94472, 그 이전에 수용)의 강제 갱신 WARN은 아직 원문을 싣는다.

- `LTS:2762`·`DTS:3647`: `market={}, trade_price={}`로 REST 응답 원문을 출력한다.
- 강제 갱신의 catch(`LTS`·`DTS` `forceRefreshPrice` 끝)도 `e.getMessage()`를 싣는다. 이것은 N17 이전부터 있던 문구다. N19도 폴백의 기존 배치 ERROR(`e.getMessage()`)는 "기존 ERROR 한 줄 그대로"로 남겼다.
- 보호 동작에는 영향이 없다.
- 고정 문구 규칙을 강제 갱신에도 넓힐지는 정책 범위의 판단이라 후보를 만들지 않았다. 바꾸면 운영 로그 문구가 바뀐다.
  - 계획서 §5-9의 관측 블록이 이 문구의 앞부분을 센다(6298f5b의 `LIMITED_LIVE_TEST_PLAN.md` 8925·9630·10363·11126줄, `PAT = … 발행하지 않음 \(`).
  - 괄호 앞까지만 맞추므로, 괄호 안만 바꾸면 그 정규식은 계속 맞는다. 그래도 승인 블록과의 관계는 총괄이 확인해야 한다.
- 필요하면 N19 ⑤와 같은 방식의 단위 시험 1건과 최소 후보를 낼 수 있다.
