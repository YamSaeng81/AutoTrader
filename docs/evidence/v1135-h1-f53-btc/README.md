# H1 F5-3 BTC 대조 줄 숫자 판정 (총괄 v1.135 §2 H1, 2026-11-08, 로컬)

앱·DB·외부 명령 없이 순수 함수와 가짜 입력으로만 검증했다. **하네스 보완만으로 긴 리허설은 다시 돌리지 않았다.** 운영 F3/F5 블록, 계좌 허용오차, 정기 점검 분류는 바꾸지 않았다.

## 공백

`judge.f53_ok`는 `'거래소 BTC 증감 0'`을 부분 문자열로만 찾았다. 그래서 `거래소 BTC 증감 0.0016 · …`도 맞는 것으로 판정했다.

총괄 가짜 입력 `f53-nonzero-btc.input.txt`는 W3 run5 `F5-3-w4exec.out`과 **48번째 줄 한 곳만** 다르다(`0` → `0.0016`).

## 실패 먼저 (수정 전 판정 `judge.before.py` = HEAD a762b8cb 판)

- `before-fix-output.txt`: 가짜 입력 → **True(허위 통과)**, run5 실제 원문 → True.
- `test_judge-on-old-judge.txt`: 새 시험 47개를 옛 판정에 걸면 **41/47, 종료 1**. 실패한 6개는 다음과 같다.
  - 가짜 입력
  - 주문 순체결량 0.0016
  - 열린 포지션 수량 0.0016
  - 형식 이상
  - 값 뒤에 덧붙은 문자
  - 서로 다른 BTC 줄 2개
- 나머지 새 시험은 옛 판정에서도 결과가 같았다: `-0.0016`, NaN, 누락은 부분 문자열이 맞지 않아 거절됐고, 동등한 0과 중복은 통과했다.

## 보완 (`harness.diff`)

새 함수 `f53_btc_zero(out)`가 BTC 대조 줄을 다음 순서로 판정한다.

1. `거래소 BTC 증감`이 들어간 줄을 **모두** 모은다. 임의의 한 줄만 고르지 않는다.
2. 줄이 1개 이상이어야 하고, 서로 다른 줄이 섞이면 안 된다. 같은 줄의 반복이나 CRLF 차이만 있는 줄은 하나로 본다.
3. 줄 전체가 `^거래소 BTC 증감 X · 주문 순체결량 Y · 열린 포지션 수량 Z$` 형식이어야 한다.
4. X·Y·Z를 `Decimal`로 읽어 셋 다 유한한 0이어야 한다. `0`, `0E-8`, `-0`, `0.00000000`은 통과한다. `0.0016`, `-0.0016`, NaN, 숫자가 아닌 값은 거절한다.

`f53_ok`는 원래 검사를 그대로 둔다: 종료 0, F3 해시, `⛔ 판정: 세션 상태 STOPPED`, `DB 정리 조건 충족`. 여기에 `f53_btc_zero`를 더했다. 부분 문자열 `'거래소 BTC 증감 0'`은 `F53_MARKS`에서 뺐다. 호출부는 `rehearse_w3.py`의 F5-3 한 곳이고 바뀌지 않았다.

## 결과

`test_judge-output.txt`: **47/47, 종료 0**.

- **종전 35개 기대값은 그대로다.** F5-3 대조군 입력의 BTC 줄은 run5 실제 행 형식(`거래소 BTC 증감 0 · 주문 순체결량 0E-8 · 열린 포지션 수량 0`)으로 바꿨다. 짧은 `거래소 BTC 증감 0` 한 줄은 새 형식 검사를 통과하지 못한다. 기대값(통과)은 바꾸지 않았다.
- 새 12개:
  - run5 실제 원문은 통과한다(대조군).
  - 총괄 가짜 입력은 거절한다(허위 통과 4).
  - 다음은 거절한다: `-0.0016`, 순체결량 0.0016, 열린 수량 0.0016, 줄 누락, 형식 이상, NaN, 덧붙은 문자, 서로 다른 두 줄.
  - 다음은 통과한다: 동등한 0, 같은 줄 중복과 CRLF.

**run5 원문은 실제 BTC 증감 0·장부 차이 0이므로 앞선 F5-3 통과는 유지한다.** 이 공백은 판정 도구의 공백이다. 제품의 주문·정산 결함이나 운영 계좌 차이를 발견한 것이 아니다.
