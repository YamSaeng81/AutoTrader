## 2. 계약과 구현

| 항목 | 내용 |
|---|---|
| 저장 | 기존 DYNAMIC `strategy_params`(JSONB). DDL 없음. 세션 생성 때만 받는다. 기존 세션에 값을 넣거나 바꾸는 경로는 없다(엔티티 setter를 쓰는 서비스 경로 0) |
| 생성 검사(저장 전) | 두 키를 **함께** 명시해야 한다. `maxOrderKrw`는 숫자형·원 단위 정수이고 5,000 이상이어야 한다. 상한 기준은 실자금이면 공유 풀 포지션당 상한, 모의면 초기 자본이다. 문자열·불리언·null·NaN·소수·범위 밖은 거절한다. `excludeCoins`는 `KRW-[A-Z0-9]+` 문자열 목록만 받고 중복·소문자·숫자·문자열 단독·null은 거절한다. 빈 목록은 "제외 없음"으로 명시한 것으로 본다 |
| 정규화 | 제외 목록은 정렬하고 상한은 정수로 저장한다. 순서나 숫자 표기가 달라도 값이 같으면 같은 규칙 지문이 된다. 지문은 기존 `strategy.params` 정규화 그대로 쓰며 지문 코드는 바꾸지 않았다. **두 키가 없으면 입력 맵을 그대로 저장**하므로 기존 세션 지문은 변하지 않는다 |
| 매수 | `executeBuy`에서 요청액 = min(둘째 자리 버림(가용×비율×배수), `maxOrderKrw`)이다. 그 뒤 기존 최소 주문 보정(5,000원 올림)을 거치고, 보정 뒤에도 상한을 넘으면 막는다. 예약 서비스의 포지션당/총 상한 검사(최종 보호선)는 그대로다. REAL·PAPER가 같은 식을 쓴다. 상한이 적용되면 원래 요청액과 상한을 로그에 남긴다 |
| 제외 적용점 | ① `resolveWatchlist`의 세 경로(캐시·새 목록·공용 유니버스) 결과. 기록용 `watchlistJson`은 원래 목록으로 둔다 ② 코인 선택 직전(빠진 후보의 신호 기록은 차단으로 남김) ③ 회차 승인 `approveQueuedEntry` ④ 최종 `executeBuy` |
| 제외하지 않음 | BTC 급락 관문(`btcMarketGate`는 감시 목록과 무관하게 KRW-BTC 봉을 따로 읽음), 기존 보유 매도·보호 매도·정지 청산(매도 경로는 이 설정을 읽지 않음) |
| 저장값 손상 | 저장값이 계약 밖이면(직접 DB 수정 등) 신규 매수를 막는다(`진입 설정 손상`). 매도는 막지 않는다 |
| 전략 입력 | 두 키는 엔진 설정이므로 전략 `evaluate` 파라미터에서는 뺀다 |

주요 확인값(가상 금액): 가용 25,001×0.8 → 20,000.80. 키 없는 세션은 종전대로 `PER_POSITION_CAP` 거절이고, `maxOrderKrw` 10,000이면 10,000으로 예약·주문되어 가용이 15,001이 된다(PAPER도 10,000 체결). 상한 5,000·감액 4,000이면 기존 보정으로 5,000이 된다. 가용 6,000·감액이면 종전대로 `가용 KRW 부족`. 생성 뒤 포지션당 상한을 15,000으로 내리면 상한 20,000 요청도 예약 서비스가 거절하고 차감은 0이다. `KRW-BTC` 제외 세션은 감시 목록·최종 진입·회차 승인 모두 0건이고 KRW-ETH는 산다. 평가 회차에서 BTC 봉이 없으면 제외 설정과 무관하게 관문 판정 불가로 매수 0이고, 봉이 최신이면 KRW-IOTA를 산다. 제외 세션의 기존 KRW-BTC 보유는 청산된다.

전체 회귀·jar·이미지 빌드는 하지 않았다. 환경: Windows, JDK 17.0.12, Gradle `--offline`, H2 시험 프로필.

## 4. 한계·남은 것

- 숫자(실제 `maxOrderKrw`·총원금·월 손실 상한)는 미정이다. 운영 세션 생성·배포는 별도 승인이다.
- 상한 적용 진입의 원래 요청액·적용 상한은 로그로만 남는다. 성적표가 읽을 신호 기록 필드는 새 열이나 기존 텍스트 열 사용 판단이 필요해 보류했다.
- 방어를 여러 겹으로 두었으므로 회차 승인 재확인 하나만 빠져도 최종 진입이 같은 사유로 막는다. 그래서 시험은 각 층을 따로 떼어 검출하지 않는다(변형 시험 없음).
- 실제 PG에서는 이 변경을 돌리지 않았다(H2 통합 시험만). PG 매도 보충과는 별개다.
