## 3. 1회 제한 — 스키마 없는 B안으로 별도 후보 구현 승인

**B안을 선택한다.** Flyway96을 유지하고 V97/카운터 열은 만들지 않는다. d81c3f2f에서 별도 작업 사본·후보 가지로 구현하며 main 제품이나 D81 배포 후보에 아직 합치지 않는다. 예: `candidate/live-one-entry-d81c3f2f`.

구현 계약:

- 새 LIVE의 `strategy_params.maxEntries`는 **미지정이면 기존 동작·지문 그대로**, 지정하면 정확히 1만 받는다. null/빈 문자열/불리언/소수/음수/다른 정수 등 잘못된 값은 생성의 자본 배정·계좌 동기화·저장보다 먼저 명시적으로 거절한다. 이 계약은 새 옵션에 한정하고 다른 전략 파라미터의 의미를 바꾸지 않는다. 옵션 있는 새 세션은 기존 canonicalParams를 통해 지문이 달라져야 한다.
- 계좌 잠금을 획득한 **뒤**, 차감·새 주문 의도 확정 전, 정확한 `session_kind=LIVE, session_id, side=BUY`의 **수명 전체 커밋 이력**을 확인한다. 상태·기간 필터를 두지 않는다. UNKNOWN·FAILED·CANCELLED·커밋 뒤 철회도 1회 소진이다. 소유 종류가 다른 같은 ID를 섞지 않는다.
- 예약·주문 의도는 같은 트랜잭션이며 롤백 시 의도도 사라지는 기존 계약을 유지한다. 동시 예약은 먼저 커밋된 이력을 본 뒤 둘째를 거절해야 한다. 실행 환경의 실제 격리 수준·잠금 보유 구간을 코드/PG로 확인하고 READ COMMITTED라는 주석만으로 단정하지 않는다.
- 매도/청산/정지·DYNAMIC·기존 PAPER 경로를 바꾸지 않는다. 제한은 “새 매수 의도 최대 1회”이며 정지와 동시 승인 경합을 해결했다고 쓰지 않는다. 사용자 시험 총액·수수료·실제 계좌 여유는 별도 조건이다.
- 제한 없는 구판으로 복구하면 옵션이 무시된다. 시험 세션이 있으면 **그 세션 정지와 미해결 제출/주문/잔량 확인 전 구판에서 RUNNING 재개 금지**를 복구 제한으로 남긴다. STOPPED 하나만으로 완료 처리하지 않는다. 코드상 실현 가능한 확인 경로가 없다면 그 제한을 보고하고 실행을 보류한다.

검증 범위는 새 옵션의 순수/직접 단위 시험과 **격리 PG 1묶음**이다. 후보와 기점에서 같은 새 시험으로 먼저 차이를 기록하고 최소 구현 뒤 확인한다. 사례는 옵션 미지정 불변/지문, 입력 거절, 매수→매도 정산 뒤 재진입 거절, 동시 예약 2개에서 의도 1개, 예약·만료 롤백, UNKNOWN/철회 뒤 거절, 다른 종류의 같은 세션 ID 제외, 새 트랜잭션 재조회다. 새 트랜잭션 재조회를 앱 재기동 증거로 쓰지 않는다. 조회 실패는 허용으로 처리하지 않는다.

전체 회귀·jar·다른 PG 묶음은 아직 돌리지 않는다. 직접 영향이 실제로 넓어지면 그 이유를 보고하고 필요한 검사만 정한다. 실패를 시험 데이터로 덮지 말고 원문과 이유를 보존한다. 후보를 원격에 보존하는 일반 push는 허용한다. 본운영 포함·서버 배포·실제 생성/start·주문은 아직 승인하지 않는다. **이 후보 때문에 D81 비용 보호 배포를 지연시키거나 두 변경을 몰래 묶지 않는다.**
