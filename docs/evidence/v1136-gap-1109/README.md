여기서 확인한 것:

- **cron이 실행되지 않은 것이 아니다.** 17:19·18:19·19:19Z 시작 줄이 있고, 기록은 19:56~19:58Z 3분 안에 3줄이 몰려 있다. 시작된 회차가 오래 걸려 끝난 뒤에야 기록됐고, 여러 프로세스가 겹쳐 돌다가 거의 같은 때 끝났다는 것과 맞는다. 20:19Z 회차도 31분 걸려 20:50Z에 기록됐다.
- 시작과 기록을 1:1로 짝지은 원문은 **없다**(기록에 시작 시각·PID가 없다). 아래 재현의 짝은 모형에서 나온 것이다.
- 판정기(`_alerts_report`)는 **기록 시각(`at`) 사이 간격**만 본다. 그래서 16:19:01.85 → 19:56:42.59 = 218분이 "실행 누락"으로 나왔다.
- **새로 보인 사실**: 거래소 응답의 최신 H1 봉이 19:58·20:50·21:19Z 회차 모두 **16:00Z**였다(21종). 그 시각에 업비트가 돌려준 H1 봉 중 17:00~21:00Z 봉이 없었다는 뜻이다. DB 최신 봉도 16:00Z로 같았으므로 도구는 🟢 "일치"로 셌다. 이 기록만으로 업비트 쪽 거래 중단인지, 다른 원인인지는 **확정하지 않는다**. 그 봉들이 지금 거래소·DB에 있는지는 조회하지 않았다(읽기 범위 밖). 나중의 최신 봉 정상만으로 장애 구간 과거 봉을 모두 보충했다고 쓰지 않는다.

## 3. 로컬 국소 재현 (`repro/`)

`repro.py`는 배포판 `start_66.py`(`start_66.1899b49.py`, `git show 1899b49:` 원문, 블롭 `460031d3…` = 서버 블롭)를 **고치지 않고** 불러, `cmd_freshness`와 `_alerts_report`를 그대로 돌린다. 가짜로 바꾼 것은 다음 경계뿐이다.

- 시계: `datetime.now`, `time.sleep`
- DNS: `api.upbit.com`을 문서용 주소 `192.0.2.x` N개로 돌려준다
- 소켓: `connect`가 설정된 시간 초과만큼 시계를 넘기고 TimeoutError를 낸다. 실제 연결은 없다(문서용 주소가 아니면 단언으로 멈춘다)
- 접속 가능 시각의 업비트 응답
- 앱 API(`need_env`·`_db_latest`)
- 기록 파일(임시 폴더)

장애 구간은 앱 로그의 관측 구간(17:02:09~19:56:43Z, 19:58:53~20:48:53Z)을 그대로 썼다. 같은 구간에 감시 도구도 실패했다는 것은 **가정이다**. 시작은 운영 cron 시각이다.

- N=1: 같은 장애 구간에서도 매 회차가 27분 안에 끝나 ⚪22로 기록된다. 판정기는 "판정 불가 4회"만 내고 **실행 누락은 없다**.
- N=8: 판정기가 **"🔴 실행 누락 11-08 16:19 → 11-08 19:57 218분"**을 낸다. cron은 매시 시작했는데도 그렇다. 재확인 수와 ⚪ 수는 운영 기록과 같고, 기록 시각은 운영보다 16~33초 늦다.
- 재현의 🔴 수(6·1·1·1)는 운영(1·1·1·1)과 다르다. 재현의 가짜 거래소는 매시 새 봉을 돌려주지만, 운영 거래소는 그 시각에 16:00Z 봉만 돌려줬기 때문이다(2절). 시각 모형의 차이가 아니라 가짜 응답의 차이다.
- 가짜 connect 시도는 N=1에서 528회, N=8에서 1888회였다. 모두 가짜이고 앱 API 호출도 0이다(호출하면 단언으로 멈춘다).

**이 재현은 운영 218분의 원인을 확정하지 않는다.** 보인 것은 다음 세 가지다.

1. `at`이 끝난 시각이라서, 시작은 제때 했어도 실패 시도가 길어지면 "실행 누락"으로 표시될 수 있다.
2. 실패 시도 한 번이 약 80초(주소 8개 × 10초)라고 두면 운영 기록의 시각·재확인 수·⚪ 수가 거의 그대로 나온다.
3. 겹친 회차들이 접속이 돌아온 직후 몰아서 끝난다.

운영 서버에서 `api.upbit.com`이 실제로 몇 개 주소로 풀렸는지, 시도 한 번이 실제로 몇 초 걸렸는지는 기록이 없다. DNS 조회는 금지 범위라 하지 않았다. 따라서 **원인 후보로만 둔다.**

## 4. 결함 여부와 하지 않은 것

- 관측된 동작은 코드에 쓰인 대로다. 시도 3회, 시도마다 `urlopen(timeout=10)`, 70초 뒤 재확인이 그 내용이다. 표시 문구 "실행 누락"은 실제로는 "기록 공백"을 센다. 그 기록 공백을 `MAX_GAP_MIN` 90분으로 판정하는 것도 문서화된 계약("직전 관측과 90분 넘게 벌어지면 관측 누락")과 맞다. **계약 위반 결함은 찾지 못했다.**
- 다음은 이번 지시 범위에서 새 숫자나 정책이 필요하므로 정하지 않았고, 고치지도 않았다.

  - 겹침 방지(잠금)
  - 시작 시각 기록
  - 문구 변경
- 하지 않은 것:
  - 감시 도구·수집·앱 API 실행
