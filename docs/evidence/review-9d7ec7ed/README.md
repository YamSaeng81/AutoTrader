## 1. 수용과 원인 판정

- 실제 세션 출력은 STOPPED, 활성 주문·회계 반영 대기·미반영 매도·정리 대기·미입증 종결·미해결 불일치 0이고, v3의 `open_or_residual_positions`만 1이다. CLOSED의 저장 수량을 실보유 잔량으로 해석한 **게이트와 합성 정상 자료의 가정 결함**이다.

## 2. 게이트 v4 수정 범위 — 지금 진행

기존 v3·r1·r2 원문과 체크섬을 보존하고 새 폴더에 v4를 만든다. 재착수 확인을 묻지 않는다.

1. 포지션 보유 차단은 **`status IN ('OPEN','CLOSING')`**으로 정한다. 수량이 0이어도 이 상태는 차단한다. CLOSED의 양수 size만으로 보유라고 세지 않는다. 알 수 없는 상태·NULL 상태의 별도 FAIL은 유지한다.
2. 기존 열 이름 `open_or_residual_positions`를 호환 목적으로 유지해도 되지만, 뜻이 '제품이 보유/청산 중으로 관리하는 포지션 수'임을 문서에 명시한다. 수량을 실제 거래소 잔량으로 확정하는 필드라고 설명하지 않는다.
3. CLOSED라는 이유로 다른 차단·보류를 없애지 않는다. 활성 주문, `fill_accounting_pending`, 미반영 FILLED 매도, 미완료 정리, 미입증 종결, 미해결 정산 불일치, 대상·REAL·등록값·정수 maxEntries=1·BUY 횟수 검사는 유지한다. STOPPED만 자동 PASS, EMERGENCY_STOPPED는 HOLD다.
4. CLOSED 상태만으로 거래소 보유 0을 입증하지 않는다. 장부 밖 체결·잘못 닫힌 포지션의 거래소 잔량은 A3·계좌 대조의 별도 범위다. 이 로컬 게이트 수정으로 계좌 읽기나 운영 복구를 승인하지 않는다.
5. 관련 SQL·판정기·초안의 참조를 새 v4 경로와 해시로 연결한다. 과거 v3 파일을 수정하거나, r2의 FAIL을 PASS로 고쳐 적지 않는다. 다른 제품 변경·범위 확대는 하지 않는다.

## 3. 격리 PG 게이트 검증 r3 1묶음 승인

**실제 LIVE 매수→매도 Java 경로와 합성 29건 전체를 반복하지 않는다.** r2의 기존 검증은 연결하고, 바뀐 게이트만 다음 범위로 확인한다.

- 보존된 `oe2_r2`의 실제 세션을 **읽기 전용으로만** v3와 v4에 각각 넣는다. v3는 기존 사유로 FAIL, v4는 PASS가 되어야 한다. 대상 ID·제품/시험 SHA·포지션/주문 연결·잔액이 r2와 같은지 기록한다. r2 DB를 고치거나 size를 0으로 만들지 않는다. DB가 없거나 동일성을 확인할 수 없으면 원문만 보고 통과 처리하거나 실제 경로를 다시 돌리지 말고 보고한다.
- 새 합성 DB에서 아래 경계만 추가 검증한다. 기대를 실행 전에 고정한다.

| 사례 | 기대 |
