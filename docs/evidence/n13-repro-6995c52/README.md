2026-11-04 KST. 총괄 지시(`n13-next-scope/README.md` 1절)에 따른 원인 구분 시험이다.
- **앱 코드는 바꾸지 않았다.**
- 고정 `6995c52` 를 스크래치의 분리 작업 사본(`git worktree --detach`)에 두고, 시험 클래스 하나만 더해 돌렸다. 저장소 main 에는 시험 클래스를 넣지 않았다. 이 폴더의 `.java` 는 근거 사본이다.
- 서버·운영 DB·외부 HTTP 에는 접속하지 않았다(`./gradlew --offline`).

## 1. 시험 기반

- 실제 Spring 컨텍스트를 썼다(`@SpringBootTest`, 기존 `test` 프로필, H2 PostgreSQL 모드). Hikari 와 `SignalQualityService` 프록시도 실제 것이다.
  - 0번 시험에서 빈이 AOP 프록시이고 대상 클래스가 `SignalQualityService` 임을 확인했다.
- **정기 경로**: 앱의 `taskScheduler` 빈(scheduler 스레드)에서 프록시의 `evaluateSignalQuality()` 를 불렀다. `@Scheduled` 실행기도 같은 빈(프록시)의 메서드를 부른다.
  - `test` 프로필은 `@Scheduled` 를 끄므로 30분 예약 자체는 쓰지 않았다.
- **시작 catchup 경로**: 프록시의 `catchupOnStartup()` 을 불렀다. `@Async` 가 적용돼 task 스레드에서 돌았다.
  - 기동 때 `ApplicationReadyEvent` 로 자동 실행되는 catchup 도 같은 프록시를 거친다. 시험은 그 자동 실행이 끝나 풀이 2초 연속 빌 때까지 기다린 뒤 시작했다.
- **질의 지연 대역**: 데이터소스를 감쌌다. HOLD 기준선 native 질의(`DISTINCT ON`)의 `executeQuery` 바로 앞에서 400ms 를 기다린다. 이때 연결은 실제로 빌린 상태다.
- **외부 가격 조회 대역**: `UpbitRestClient` 를 목으로 바꿨다. `getCandles` 안에서 400ms 를 기다린 뒤 가격을 주거나 `Exception("Upbit API 호출 실패: 500")` 을 던진다.
- **기록**: 연결 대여·반환, 질의 대기 시작·끝, 가격 조회 대기 시작·끝마다 다음을 적었다(`events.txt`).
  - 스레드 종류
  - `TransactionSynchronizationManager.isActualTransactionActive()`
  - 그 스레드가 쥔 연결 수
  - Hikari 사용 중 연결 수
- 운영의 141~545초를 기다리는 시험은 만들지 않았다. 행 2개(HOLD, 30시간 전, 코인 2개)만 넣었다.

## 2. 결과 — 6/6 통과(`junit-summary.txt`)

| 시험 | 질의 대기 중 | 가격 조회 대기 중 | 끝 |
|---|---|---|---|

- 정기·catchup 경로(1~4)에서는 질의 줄마다 연결을 따로 빌리고, 질의가 끝나면 바로 돌려준다.
  - 가격 조회 대기 중에는 그 스레드가 연결을 쥐지 않는다.
  - 저장(`saveAll`)도 따로 빌려 32ms 안에 돌려준다.
  - 이는 운영 로그의 "질의 줄마다 따로 대여, 반환 뒤 수 초 안에 다음 질의 대여" 형태와 같다.
- 메서드의 `@Transactional` 은 1~4에서 적용되지 않았다(같은 클래스 안 호출). 다른 빈처럼 프록시를 거친 5에서만 적용됐다.
  - 5의 모습은 "트랜잭션 안 REST 호출이 연결을 잡는다"는 앞선 가설과 같다. 그러나 운영 호출 경로는 5가 아니라 1~3이다.
- 가격 조회 실패와 질의 오류 뒤 연결은 모두 반환됐고, 다음 회차는 정상 진행됐다. 이 시험 범위에서 영구 미반환은 재현되지 않았다.
- 3번 시험 한 줄에서 풀 사용 중이 2로 찍혔다. 같은 순간 다른 스레드가 빌린 것으로 보인다. 그 줄에서도 catchup 스레드가 쥔 연결은 1이다.

## 3. 해석 범위

- 오래 잡힌 시간은 질의 단계 쪽으로 좁혀진다. 이 재현은 그 사실을 **경로 구조**로 확인했다.
- 운영 141~545초가 DB 실행 시간인지는 확정하지 않는다. 결과 매핑 시간, DB 대기, 실행 계획 중 무엇이 차지하는지는 이 시험으로 알 수 없다.
- 같은 날 실행 계획 조회(`n13-plan-6995c52`)에서 안쪽 Seq Scan 과 Merge Anti Join(시간대 조건이 Join Filter)이 나왔다. 둘을 함께 보면 질의 자체가 후보다. 그러나 추정치이며 실측은 하지 않았다.
- 수정 후보는 만들지 않았다. 범위는 총괄이 정한다. 트랜잭션을 실제로 적용하면(5) 연결이 REST 대기까지 잡히므로 더 나빠질 수 있다.

## 4. 시험 기반 한계와 실행 경위

- H2 는 native 질의의 PostgreSQL 간격 표기 `interval '1 hour'` 를 읽지 못한다. 첫 실행에서 `Cannot parse "INTERVAL" constant` 로 질의가 준비 단계에서 실패했다.
  - 그래서 데이터소스 대역 안에서만 그 표기를 같은 뜻의 `INTERVAL '1' HOUR` 로 바꿨다. 앱 소스의 질의는 그대로다.
  - 질의의 실행 시간·계획은 H2 와 운영이 다르다. 이 시험은 연결·트랜잭션 경계만 본다.
- 첫 실행에서 `ThreadPoolTaskScheduler` 의 오류 처리기가 예외를 삼켜 `Future` 가 정상 완료로 보였다. 그래서 호출 스레드 안에서 정상 반환·예외를 기록하도록 바꿨다.
- 두 번째 실행에서 두 가지가 겹쳤다.
  - 기동 자동 catchup 이 1번 시험과 겹쳐 스레드별 보유 수가 −1로 찍혔다.
  - 3번 시험의 대기 확인이 기록을 잠시 꺼 이벤트 1줄이 빠졌다.
  - 그래서 시작 전 풀 비움 대기를 넣고, 대기 확인만 시험 스레드에서 기록하지 않게 바꿨다.
  - 앞의 두 실행 출력은 보존하지 않았다. 판정은 세 번째 실행(`events.txt`)만으로 했다.
- `lock_timeout`·`statement_timeout` 같은 PostgreSQL 서버 동작은 이 기반에서 검증되지 않는다(기존 `application-test.yml` 주석과 같음).
- 기존 167건·뉴스 시험·전체 리허설은 반복하지 않았다.
