## 3. 이어서 고칠 범위 — 추가 착수 승인 불필요

### 3-2a. 만료·모든 매매 쓰기 경계

1. R1을 실패 시험으로 고정한 뒤 승인 직전뿐 아니라 지문/설정 조회·매수 쓰기 경계까지 같은 E·시계로 검증한다. 만료 시 신호 사유를 남기되 주문·포지션·자금 부분 반영은 0이어야 한다. 이미 확정된 체결을 나중에 취소하는 정책은 추가하지 않는다.
2. 현재 원자화한 것은 승인 매수와 `closeAligned` 경로다. **전략 SELL은 여전히 `closePosition`을 직접 부르고, 회차 비활성 선택 모드 BUY도 `executeBuy`를 직접 부른다.** 두 경로도 선택 모드 안에서 원자성이 필요한지 저장 단계 실패 주입으로 확인하고, 필요한 최소 트랜잭션을 적용한다. 종전 PAPER/66 분기는 바꾸지 않는다. 이 항목은 이번 총괄의 소스 확인이며 부분 반영 실행 재현은 아직 하지 않았다.
3. 신규 재시도 트랜잭션 안의 알림 버퍼·인메모리 상태 삭제는 DB 롤백과 함께 복원되지 않는다. 성공 커밋 뒤 한 번만 반영되도록 검사한다. `pendingTimeExitNote`가 체결 성공 전에 map에서 지우는 경계도 포함한다. 재시도 후 중복 알림·소실된 판단 시각·미확정 매수 성공 로그를 정상으로 세지 않는다.

### 3-2b. 가격 없는 정지/시간 청산

1. **LIVE_ALIGNED에 0원·음수 체결을 허용하지 않는다.** 시간/정지 청산 판단과 실제 모의 체결을 구분한다. 정지 요청은 즉시 새 진입을 막고, 가격이 없으면 포지션/청산 대기를 보존하며 첫 유효 시세에서 한 번만 정산한다. 청산 대기를 처리하는 상태·API 반환·다음 회차/재기동 복원까지 후보로 구체화한다. 포지션을 남긴 STOPPED를 완료된 정산으로 표시하면 안 된다.
2. 오래된 봉 종가를 출처만 적고 현재 시장가 체결로 사용하는 것은 이 문제의 완료 조건이 아니다. 유효 가격이 없으면 대기한다. 기준은 기존 유효기간/가격 계약을 재사용하고 새 허용 수치를 임의로 만들지 않는다.
3. R3/R4를 포함해 보류 사유/판단 시각을 보존한다. 주기·실시간·재시도·재기동을 거쳐도 TIME_STOP이 TAKE_PROFIT/STOP_LOSS로 다시 선택되지 않아야 한다.
4. 기존 키 없는 PAPER의 0원 정지는 **별도 미해결 제품 결함**으로 목록에 남긴다. 이번에 66의 규칙·성과를 몰래 바꾸거나 열람하지 않는다. 별도 국소 재현/영향 표는 가능하며 운영 정지·정산 인계의 확인 항목에 포함한다. 실제 운영에서 0원 청산이 있었다고 추정하지 않는다.

### 3-2c. 위험 판단과 재기동

1. R6의 REAL/DYNAMIC 조기 반환·조회 순서를 복원한다. 비활성/MDD 초과 대조에서 CLOSED 조회 0회, 정상 연속 손실 경로는 종전 결과 유지로 확인한다. PAPER 값 입력형은 별도로 유지할 수 있다.
2. PAPER 성적표의 비용 후 손익을 바꾸지 말고, **LIVE와 비교할 위험 입력 정의**를 따로 맞춘다. 같은 체결/수수료의 실제 매수→매도에서 작은 이익·손익0 부근·손실을 만들고, 연속 손실·일/주/월 관문이 어떻게 같거나 다른지 검증한다. B03 일일 손실 사례의 LIVE `checkRisk`는 승인 목이므로 양쪽 동일성 검증으로 쓰지 않는다. 공유 REAL 풀/예약과 모의 단일 계좌의 차이는 계속 명시한다.
3. MDD 피크를 메모리에만 두고 재기동 시 초기 자본으로 되돌리는 것은 새 모드의 지속적 위험 판단과 다르다. 피크/청산 대기 복원 최소안을 먼저 만들고 로컬에서 검증한다. 기존 저장 구조를 사용한다면 규칙 지문/strategy_params와 런타임 상태를 섞어 표본이 바뀌지 않게 한다. 새 DDL이 필요하면 구체 변경안으로 별도 제출하고 그동안 독립 작업을 계속한다. 운영 DB 변경 승인은 아니다.

### 3-2d. 시험 범위와 통합

- B01의 마지막 평가 봉 표시 삭제는 국소 SELL/정산 비교까지만 인정한다. 다음 봉을 실제로 공급하는 경로를 공통 시계/고정 봉으로 검사한다. 단언을 없애거나 같은 봉 중복 방지 규칙을 끄지 않는다.
- 이번 비교 실행기/최종 회귀가 쓰는 완료 대기는 우선 확정적인 완료 신호로 보완한다. 같은 옛 대기 조건 21개를 맹목적으로 일괄 치환하지 말고 제출 경로별로 확인한다. 기존 시험 기대값은 보존한다.
- 새 실패 재현 → 최소 후보 → 관련 시험 순서로 한다. 전체 회귀/PG/실제 jar는 후보 통합이 안정된 뒤 필요한 범위로 실행한다. 별도 시험 가지 A12/F/D복원/정지 대기를 최종 SHA에 연결한다.

## 5. 총괄 실행의 실패·한계와 보존물

- 첫 Gradle `--offline`은 로컬 BOM 캐시 해석 문제로 exchange-adapter 컴파일 전에 실패했다. 제품 실패나 0건 통과로 세지 않는다. 네트워크로 의존성을 새로 받지 않았다.
- 대체 javac 첫 실행은 클래스패스 argfile의 wildcard가 확장되지 않아 실패했다(검토 장치 결함). 명시적 로컬 jar 목록으로 고친 뒤, 동일 제품 소스와 Spring/H2 관측 시험을 컴파일·실행했다. 제품 코드는 바꾸지 않았다. 정상 실행 4/4, 위험 입력·구판/후보 조기 반환 대조도 기대대로다.
- Gradle 표준 전체 회귀, 실제 PostgreSQL, 다음 봉 전체 흐름, 부하/운영 성공을 주장하지 않는다. 테스트용 자바 코드가 관측한 반례와 소스 검토 사항을 위에서 구분했다.
- `audit.json`: 제출 체크섬·보존 XML. `review.json`: 실제 대상/재현 요약·제품 바이트 대조. `libraries.json`: 사용 로컬 의존 jar 해시. `AlignedReview949Test.java`, `RiskReview949.java`, 실행기 스크립트와 원문 출력/실패 로그를 보존했다. `doc-check.json`: 문서 수정 전후 실행 블록 불변 대조.
- 총괄은 서버·운영 DB·실제 외부 API·jar 빌드·배포·커밋·푸시를 하지 않았다. 별도 사본의 컴파일/국소 시험과 로컬 문서만 수행했다.
