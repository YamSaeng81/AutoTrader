## 총괄이 추가 실행한 경계 — 기대와 다른 3건, 정상 대조군3건

외부 HTTP/서버/DB 접속 없이 HttpClient 대역을 주입했다. 고정 후보의 `NewsFetchResult`·`NewsSource`·`RssNewsSource`·`UpbitNoticeSource` 원문4개를 ignored scratch로 꺼내 JDK17 javac로 직접 컴파일했다. 변경하지 않은 NewsItem/설정 엔티티와 로깅/Jackson 등 의존 클래스는 기존 후보 빌드/로컬 캐시를 읽었다. 전체 앱/Gradle/기존 회귀는 실행하지 않았다.

| 입력 | 기대 | 후보 관측 |
|---|---|---|
| 업비트 `success:false`, `data.notices:[]` | FAILED·항목0 | **SUCCESS·항목0** |
| 업비트 `success:false`, `data.notices`에 항목1 | FAILED·항목0 | **SUCCESS·항목1** |
| 업비트 `success:true`, 빈 배열 | SUCCESS·항목0 | 같음 |

재실행의 종료코드는1(기대와 다른3건)이다. 각각 HTTP 대역 호출1회이며 실제 HTTP 송신은 없다. 이번 실행은 출처 반환값을 확인했다. 상위 수집기가 해당 SUCCESS를 완료로 기록하고 항목을 저장하는 연결은 후보 코드에서 확인했으며, 이 경계 입력으로 상위 수집/DB 저장까지 실행한 것은 아니다. 해당 응답이 실제 운영에서 발생했다는 증거도 아니다.

### 1. 업비트의 명시적 실패 무시

`UpbitNoticeSource`는 본문의 `success` 값을 검사하지 않고 배열만 찾는다. 실패를 명시한 응답도 SUCCESS가 되고, 항목이 있으면 그대로 반환된다. HTTP200/배열 존재만으로 정상 수집으로 정하지 않는다.

**보완 지시**: `success`가 명시적으로 false면 FAILED로 반환하고 항목을 캐시에 넘기지 않는다. 필드가 있을 때 boolean이 아닌 값도 정상으로 해석하지 않는다. 기존에 허용하던 필드 부재/대체 배열 응답의 호환성은 별도로 유지·시험하고, 정상 true의 빈 배열과 구분한다. 실패 종류는 비밀값 없는 고정 분류값으로 기록하며 기존 ERROR 문구/점검 분류를 바꾸지 않는다.

### 2. RSS의 channel 이름만 검사

새 검사는 문서 전체에서 `channel` 태그 하나라도 찾으면 통과시킨다. 따라서 RSS가 아닌 XML도 정상0건이 된다. 단순 이름 존재를 피드 구조 확인으로 쓰지 않는다.

**보완 지시**: 지원하는 피드 구조와 루트를 명시하고 일관되게 검사한다. RSS가 아닌 루트 아래 channel은 INVALID_RESPONSE로 거부한다. 기존 코드가 읽던 피드 형식을 무심코 탈락시키지 않도록 정상 빈 피드/1건·기존 지원 형식을 대조한다. 이번에 Atom 등 새 포맷 지원을 추가하지 않는다. 현재 실제 RSS4개 응답을 읽지 않았다는 한계는 유지하며, 가짜 입력 통과를 실제 출처 검증으로 적지 않는다.
