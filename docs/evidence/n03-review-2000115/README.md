# N03 11-04 10:00 결과 검토·N11 착수 근거

총괄 로컬 검토일: 2026-11-04 KST. 제출 커밋은 `20001155d07e5ecde2c34623c5cdaf4c6e5435c4`, 코드 검토 기준은 실제 운영 `ea4490099f0fa6b614fe71102534b0ba84c0eb7f`다. 서버·DB·HTTP 접근, 보고 재실행/재전송, 앱 시험·빌드는 하지 않았다.

## 대조한 것과 한계

- 제출 `n03-1104-1000/SHA256SUMS`의 9개 파일은 작업 사본과 해당 커밋 Git 블롭 모두 바이트 해시가 같다. 보고에서 전송 결과 마지막 줄을 뺀 내용은 `.msg`와 같고(끝 줄바꿈 제외), 마지막 줄은 `last_send`와 같다.
- DB 키 32개가 두 칸·비어 있지 않은 단일 값이다. BTC 관측 `11-04 10:00:02`에 2분 유예식을 적용하면 필요 봉은 `08:00`, 최신 완료 봉 `09:00`은 이를 충족한다. B1 true, B3 20/20. 장부 CREATED·20200.00·balance_diff/raw_diff 0.00·주문/보유/불명 0과 끝 표시를 확인했다.
- 설치 상태 기록의 셸/SQL 전체 해시는 고정 설치 SHA d491fd1의 파일과 같다. 기록된 현재/보존 cron 해시도 같다. 이 기록은 개발의 10:09 서버 읽기 결과이며 총괄이 서버를 다시 조회한 것은 아니다.
- **서버 원본 5개 해시 일치(5/5)는 개발 보고로 구분한다.** 보존 근거에는 그 원격 해시 다섯 값의 별도 목록이 없다. 총괄이 독립 대조한 것은 로컬/Git 9개이며, `install_state.txt`에는 ERROR 추출본의 원격 해시만 있어 이것은 직접 맞춰 볼 수 있다. 이를 새 결함이나 보고 수신 실패로 판정하지 않으며, 이미 받은 원본을 다시 요청하지 않는다. 다음 새 원본 수집 때는 원격 해시 목록도 함께 남긴다.
- 서버 전송은 10:00:04 성공 기록으로 수용한다. 휴대폰 실제 수신은 미확인이다.

## N03 판정

정기 점검의 자동 생성/서버 전송, BTC 입력, 장부, 설치·cron 보존은 수용한다. 전체 보고를 정상으로 바꾸지는 않는다. ERROR 17줄 중 뉴스 Connection reset 3줄은 전날과 같은 세 출처에서 다시 나왔다. 기존 미분류 🔴를 유지하고 복구 미확인으로 둔다. 원인은 로그 문구만으로 DNS/TLS/연결 재사용/제공처/서버 네트워크 중 하나로 확정할 수 없다.

통신 실패 10건은 **ERROR 줄 수**다. 00:00 KST PUNDIX·ELF·JUP의 요청 3건이 각각 수집 실패/동기화 실패 두 줄씩, 총 6줄을 냈다. 전날 ADA 요청 1건의 2줄을 대체해 분류 건수가 6→10(+4)이 됐다. 서로 다른 구간의 합계이므로 “추가 요청 6건”으로 적지 않는다. 이 세 코인의 이후 수집 회복은 이번 ERROR-only 근거로 확인되지 않는다. BTC 입력 정상만으로 다른 코인의 회복을 확정하지 않는다.

## 운영 코드에서 찾은 관측 공백 — 정적 검토

`NewsSource.fetch`의 반환형은 뉴스 목록 하나이며 실패 시 빈 목록 반환 계약이다. 세 오류 출처는 예외를 기록한 뒤 목록(초기 빈 목록 또는 중간 결과)을 반환한다. `NewsAggregatorService`는 반환 뒤 실패 여부를 검사할 정보가 없고, `lastFetchedAt`을 갱신하고 `수집 완료`를 기록한다. 정상 응답이 0건인 경우와 출처가 잡아 처리한 수집 실패를 구분할 수 없다.

- `lastFetchedAt`은 실제로 다음 수집 시점을 결정한다. **성공 시에만 갱신하도록 단순 변경하면 재시도 주기가 달라진다.** 다음 수정에서도 기존 시도 간격을 보존해야 한다.
- `수집 완료 ... 0건`이나 `last_fetched_at` 갱신만으로 복구를 확인하지 않는다. 특정 실패 뒤 운영에서 실제로 그 완료 줄이 찍혔다는 동적 재현을 이번에 한 것은 아니다.
- 운영 소스의 뉴스 캐시 직접 참조는 조회 컨트롤러·브리핑/Discord에 있다. 서비스/전략 코드에서 위 수집기/저장소 세 타입의 직접 참조는 검색되지 않았다. 공유 스케줄러/DB/네트워크의 간접 영향까지 없다고 증명한 것은 아니다.
- 해당 뉴스 인터페이스·수집기·세 출처 파일은 제출 main과 운영 SHA에서 바이트가 같다. 원문 발췌/전체 파일 해시는 `source-excerpts.txt`와 `review.json`에 있다.

## 개발 지시 — N11, 비긴급 P2, 로컬 후보 목표 11-06

1. **실패를 먼저 재현한다.** 실제 외부 접속 없는 HTTP/뉴스 출처 대역으로 Connection reset과 정상 빈 응답을 실제 출처→상위 수집 경로에 넣어, 현 코드에서 둘을 완료로 구분하지 못하는 결과를 보존한다. 코드 검토 근거와 실행 근거를 구분한다.
2. **최소 결과 계약을 보완한다.** 성공(0건 포함)/실패/부분 수집을 구분하고 실패 뒤 성공 완료로 기록하지 않는다. 성공은 응답·파싱이 끝난 경우여야 한다. sourceId·판정 시각·실패 종류를 남기되 토큰·전체 URL/본문은 남기지 않는다. 기존 출처 ERROR 원문·점검 분류는 보존한다. 인터페이스를 바꾸면 나머지 CoinGecko 출처와 수동 조회 호출부의 호환성도 확인하며, 구형 경로를 근거 없이 성공으로 간주하는 기본값은 넣지 않는다.
3. **주기/데이터 계약을 보존한다.** `last_fetched_at`의 현재 시도 기준과 fixedDelay/소스별 간격을 유지한다. 실패 정보를 전하려고 DB 마이그레이션·즉시 재시도·타임아웃 확대·TLS 설정 변경을 하지 않는다. 실패 때문에 다음 출처 수집이 건너뛰어지지 않아야 한다. 부분 결과 저장 정책은 명시하고 기존 캐시를 삭제하지 않는다.
4. **국소 시험만 한다.** 세 출처의 실패, 정상 0건/1건, 중복 뉴스로 신규 0건, HTTP 비200/잘못된 응답, 다음 출처 진행, 시도 간격 유지, 나머지 호출부 호환성을 확인한다. 정상 빈 배열과 필요한 필드가 없는 응답을 혼동하지 않는다. 관련 시험과 후보 diff/전체 SHA를 제출한다. 기존 167건·전체 리허설·운영 설치는 반복하지 않는다. 본 코드 후보는 운영 ea44900 기점에 격리한다(main의 미배포 V95 제외).
5. **원인/회복 조사는 기존 로그 읽기만 한다.** 다음 N03 확인 때 이미 보존된 같은 두 구간 로그에서 해당 sourceId의 실패 앞뒤 수집 기록과 PUNDIX·ELF·JUP H1의 뒤이은 수집/최신성 기록을 범위 지정해 읽는다. 완료 0건만 있으면 회복 미확인으로 둔다. 성공을 확정할 자료가 없으면 그 한계를 적고, 확인을 위해 수집 API/수동 재시도/재전송을 실행하지 않는다. 같은 시각대라는 상관관계와 원인을 분리한다.

로컬 착수에 추가 승인은 필요 없다. 배포 후보와 운영 적용은 이 결과를 검토한 뒤 별도 판단한다. 40시간 한도 안에서 사용 시간을 기록하고 남은 시간을 추정해 적지 않는다. N09/N10 완료와 운영 ea44900·점검 d491fd1·SID 203 CREATED·F0/위험 한도·12-01 08:50 일정·11-30 최종 S는 유지한다. 이 근거와 문서 5개는 다음 실제 보완/관측 결과와 함께 커밋하며, 확인용 회신이나 단독 커밋은 만들지 않는다.
