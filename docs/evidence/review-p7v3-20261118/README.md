## 3. 실제 현금흐름·수집 계약·후보 작업을 이어 간다

1. **격리 PG 실제 현금흐름 대조:** v1.187 §3-2는 미완료다. 실제 엔진의 매수→정산, 부분 체결 뒤 취소/잔액 환급, 후속 수수료 정정·반복 반영을 좁게 확인한다. 거래소 응답은 대역이고 PG·엔진 반영은 실제 경로로 한다. 직접 만든 잔액/주문 행만으로 엔진 현금흐름이 확인됐다고 쓰지 않는다. 해당 경로의 원시·설명·조정 잔차와 주문/세션/계좌의 상태를 연결하고, 기존의 거래0·기존 보유·신규 배정 경계도 구별한다. PG가 켜져 있으면 기존 승인된 로컬 격리 자원만 사용한다.
2. **시계:** 수집 PC와 DB의 시계가 같다는 가정은 운영 검증으로 승격하지 않는다. 로컬에서 차이/경계 사례를 만들고, 수집 시각의 기준과 DB 시각의 관계를 증명할 수 있는 메타데이터 안을 제출한다. 차이가 미확인인 경우 보류하며 임의 유예 시간을 새 정책으로 만들지 않는다. 이를 이유로 운영 DB 비밀번호나 추가 접속을 요구하지 않는다.
3. **공개 API 계약:** 종료 주문 API는 **주문 생성 시각 기준·요청당 최대7일·최대1,000건**, 종료 상태는 done와 cancel을 포함한다. [Upbit 공식 문서](https://docs.upbit.com/kr/reference/list-closed-orders)를 11-18 확인했다. 이를 가정 미확정으로 남길 필요는 없다. 다만 DB 의도 생성 시각과 거래소 주문 생성 시각은 다른 값이므로 경계에서 같다고 가정하지 않는다. 수집안에 필터·기간 분할·잘림/연속 조회·중복 제거·부분 취소 체결·미확정 범위를 기록한다. 합성된 10-01~11-18·pages=1을 실제 한 번 조회의 증거로 쓰지 않는다. 실제 API 호출과 수집기 운영 설치는 승인하지 않았다.
4. **독립 로컬 작업:** v1.187 §3-3~6은 그대로 허용돼 있다. 모드18f3a795+쿨다운89336440의 별도 로컬 통합, 기존 strategy_params를 쓰는 금액/BTC 독립 후보, 파일 월 성적표·최소 알림 보완안을 이어 간다. PG 작업이 막혀도 독립 항목을 진행한다. 원본 가지·기존66·실자금 위험 한도·main 제품·운영 핀·설치 N03/RUNBOOK/F는 변경하지 않는다. 결과가 같은 시험을 시간 채우기용으로 반복하지 않는다.
