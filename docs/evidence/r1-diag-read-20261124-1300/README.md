## 2. 종료값 255의 위치 — 확정하지 않음

- 255는 (2) `ssh … cat-prod "<서버 가드>; docker compose … exec -T db psql …"` 파이프 첫 단계의 실제 종료값이다.
- 다음 경우는 이 숫자가 아니다.
  - v1.235 서버 시각 가드가 창 밖에서 막으면 6이다.
  - psql ON_ERROR_STOP(R1D_GUARD 포함)에 걸리면 3, 접속 실패면 2, 일반 오류면 1이다.
  - 따라서 OpenSSH 클라이언트 자체의 실패(연결·인증·세션 수립 등. ssh는 이때 255로 끝남)일 가능성이 높다.
  - 다만 원격 명령이 255를 돌려준 경우도 배제하지 못한다.
- 첫 호출은 같은 별칭·같은 키로 1초 전에 rc0로 끝났다. 두 번째 연결만 실패한 이유는 모른다.
- **표준오류 원문은 열람·인용·해석하지 않았다.** v1.235 §3-3에 따라 OTHER 원문은 검토 전 반출 근거로 커밋하지 않는다. 로컬 파일 `r1.stderr`로만 보존했다(`.gitignore`로 제외, 해시는 위와 `read-SHA256SUMS`에 있음). 원문 확인 여부는 총괄 판단 대기다.
- 서버에서 psql이 시작됐는지, SQL이 DB에 도달했는지는 이 기록만으로 알 수 없다. 설계상 SQL은 READ ONLY·ROLLBACK이라 쓰기는 없다.

## 3. 사전 확인(실행 전, 로컬)

- 이번 커밋 기준 해시가 일치했다.
  - SQL `4134c631…e269`
  - 검사기 `7f56f640…b469`
  - 실행기 v1.235 사본 `1366a607…1bee`
  - 실행기는 수정 없이 인자 1개(이 폴더 절대 경로)로 실행했다.
- 결과 폴더와 다른 `r1-diag-read-*` 폴더는 실행 전 0개였다.
- `command -v ssh` = `/usr/bin/ssh`다.
  - `~/bin`은 비어 있고 PATH 대역은 없다.
  - `ssh -G cat-prod`는 실제 운영 호스트·포트 1822·BatchMode yes로 해석됐다. 연결 없이 설정만 확인했다.
- 이 세션의 예약 작업은 0건이다. N03 22:00 단일 예약 6fe39570과 겹치지 않으며, 진단 예약은 추가하지 않았다.
- 사용률은 관측하지 못했다(미확인, 0으로 두지 않음).

## 5. 다음 최소 조치(총괄 판단)

1. `r1.stderr`(46바이트, 해시 위) 원문을 누가 어떤 범위로 볼지 정한다. SSH 계층 메시지면 금액·비밀값과 무관한 연결 오류일 가능성이 크지만, 이는 확인 전 추정이다.
2. 원인이 SSH 연결 수립이면 두 번째 연결의 실패 조건(연결 간격, 서버 측 제한 등)을 확인한다. 그런 다음 **새 승인 창·새 결과 폴더 이름**으로 1회 재승인할지 정한다. 이 폴더가 남아 있으므로 현재 실행기는 같은 승인으로 다시 돌지 않는다(종료 2).
