## 2. 최소 설계 — 세션별 진입 횟수 상한 (기본 비활성)

### 2-1. 저장

| 항목 | 내용 |
|---|---|
| 새 열 | `live_trading_session.max_entries INTEGER NULL` — NULL이면 제한 없음(지금과 같다) · `live_trading_session.entry_count INTEGER NOT NULL DEFAULT 0` |
| DB 제약 | `CHECK (max_entries IS NULL OR max_entries >= 1)` · `CHECK (max_entries IS NULL OR entry_count <= max_entries)` — 코드가 잘못돼도 DB가 초과 커밋을 거절한다 |
| 기존 세션 | 새 열은 NULL/0으로 채워진다. SID203·기존 LIVE·DYNAMIC·PAPER의 행·동작은 바뀌지 않는다 |
| 지문 | `RulesetRegistry.hashFor`(121)는 손대지 않는다. 새 열은 지문 입력에 넣지 않는다. 그래서 기존 세션의 ruleset 해시는 그대로다 |
| 생성 API | `POST /sessions` 요청에 선택 칸 `maxEntries`를 추가한다. 없으면 NULL이다. 이번 시험은 1만 허용한다(1 밖의 값은 400) |

**strategy_params에 넣지 않는 이유:** strategy_params는 지문 입력이다(123행). 전략·청산 설정 해석(ExitRuleOverrides)도 이 값을 읽는다. 시험용 제한이 전략 설정과 섞인다.

### 2-2. 차단 위치 — 주문 의도와 같은 잠금·트랜잭션

`CapitalReservationService.reserveForBuy`의 LIVE 분기에 넣는다. 위치는 세션 행을 읽은 직후(240), 자금 확인(245) 앞이다.

```
if (session.getMaxEntries() != null && session.getEntryCount() >= session.getMaxEntries())
    return logged(sessionId, Decision.reject(ENTRY_LIMIT_REACHED, "세션 진입 횟수 상한 도달"));
...
session.setAvailableKrw(after);
if (session.getMaxEntries() != null) session.setEntryCount(session.getEntryCount() + 1);
sessionRepository.save(session);      // 기존 254~255와 같은 저장
```

- 계좌 잠금(193)을 쥔 뒤다. 그래서 같은 계좌의 다른 예약과 직렬화된다.
- 증가는 자금 차감·슬롯(포지션)·주문 의도와 **같은 트랜잭션**에서 커밋된다(reservationTx, 1651). 거절·의도 실패·만료가 나면 `ReservationRejected`로 함께 롤백된다. 따라서 롤백분은 세지 않는다.
- 거절은 기존 예약 거절과 같은 경로를 탄다(1656: 롤백, 신호 품질 기록, 알림·서킷 브레이커 없음).

### 2-3. 요구 동작별 결과

| 경우 | 동작 |
|---|---|
| 재기동 | `entry_count`는 DB 열이라 재기동 뒤에도 남는다 |
| 동시 신호 | 계좌 잠금이 직렬화한다. 둘째는 증가된 값(1)을 읽고 거절된다. DB CHECK가 마지막 방어다 |
| UNKNOWN 이후 | 기존 코드에는 재제출 경로가 없다(조회만 한다). 만약 생겨도 의도 생성 때 이미 1이 됐으므로 새 예약은 거절된다 |
| 디스패치 실패로 철회(1670) | 의도는 커밋 뒤 철회된다. 카운트는 1로 남는다. 즉 그 세션은 다시 사지 않는다. 시험 목적에서는 보수 쪽이다(실제 매수 0회, 재시도 없음) |
| 매도 후 재진입 | 카운트가 1이라 거절된다. 이것이 이번 설계의 목적이다 |
| 기존 보유 매도·정지 | 매도·청산·정지·정리 대기 경로는 reserveForBuy를 거치지 않는다. 그래서 영향이 없다 |
| DYNAMIC | 이번 범위가 아니다. DYNAMIC 분기는 바꾸지 않는다 |

### 2-4. 이번 설계에 넣지 않은 것 (선택 사항)

- **정지 경합(§1 표 "정지 직전의 승인"):** 제한 세션에 한해 잠금 안에서 `status = RUNNING`을 다시 보는 검사를 추가할 수 있다. 1회 상한만으로도 누적 1회·1만원은 지켜진다. 그래서 필수에서는 뺐다. "정지 뒤 매수 0"까지 요구하면 이 검사를 넣는다.
- 계좌 KRW 여유: 반올림된 계좌 요약으로 정확한 여유 현금을 확정하지 않는다. A3의 계약 범위를 따른다.

## 3. 비용과 영향

- **스키마가 바뀐다(V97).** 지금의 배포 출처는 전부 Flyway 96을 전제로 한다(U 블록 v96h, 검사기의 Flyway 96, rollback 관문). 그래서 이 설계는 d81c3f2f 유지보수 배포에 실을 수 없다. **d81 다음의 별도 후보가 필요하다.**
- 스키마 없이 하는 대안도 있다. 주문 행에서 그 세션의 BUY 의도 수를 잠금 안에서 세는 방식이다. 그러나 상한 값을 둘 곳이 없다. 열을 추가하지 않으면 strategy_params(지문 변경)나 전역 설정(전 세션 영향)에 둬야 한다. 그래서 권하지 않는다.
- 시험안의 금액 산술(9,950원 요청 → 매수대금+수수료 ≤ 9,954.98원)은 그대로 둔다. 실제 수수료와 예약 계약은 실행 환경에서 다시 확인한다.
