### 지금 고칠 범위

1. **정지 성공은 DB 커밋 결과로 반환한다.** 선택 모드 정지의 대기/완료 알림도 예외를 고정 경고·별도 관측으로 격리한다. 알림 실패 때문에 정지를 다시 실행하거나, 성공한 세션을 일괄 결과에서 빼지 않는다. 단건 응답·일괄 정지의 수/대기 상태와 다음 세션 처리까지 확인한다. 정상1회·롤백0회·알림 실패 시 확정 상태 유지 계약을 유지하고 종전 66의 거래 정책은 바꾸지 않는다.
2. **미정산 보유 조회를 한 SQL `status IN (OPEN,CLOSING)`로 읽는다.** 기존 OPEN 의미는 유지한다. 같은 ID를 나중에 중복 제거하는 방식만으로 끝내지 말고 조회 스냅샷을 하나로 만든다. 전환 중 중복 노출과 정상 OPEN/CLOSING/CLOSED 대조를 확인한다.
3. **잔고·세션 목록·성과의 `currentAsset`까지 평가 상태를 연결한다.** CLOSING이 있고 유효 평가가가 없으면 현재 총자산/평가액/손익·수익률을 확정 수치처럼 주지 않는다. 마지막 기록값은 명확한 이름과 시각 미상/현재 평가 아님 표시로 분리하고, 현금 잔액·확정 실현손익은 구분한다. 대기 수/상태·완료 거래 아님을 API마다 유지한다. 정산 직후 대기 수와 잔액을 서로 다른 시점으로 섞어 옛 반환 엔티티를 최종 자산으로 출력하지 않는지도 확인한다.
4. **화면의 최소 연결도 로컬에서 준비해도 된다.** 현재 PAPER 상세 화면은 `Number(pos.unrealizedPnl)`/`Number(pos.unrealizedPnlPct)`라 null을 0/0.00%로 표시하고, 상태·판단 사유도 표시하지 않는다. 해당 타입을 nullable로 맞추고 청산 대기/평가 불가를 명시한다. PAPER 목록·상세/정지 결과의 같은 표시를 대조한다. 성과 화면의 `fmt(null)`은 이미 `-`를 반환하므로 전 화면이 0으로 보인다고 쓰지 않는다. REAL 화면이나 디자인 전면 변경은 이 작업에 섞지 않고, 프런트엔드 후보/산출물은 backend jar와 별도로 식별한다. 아직 화면 렌더링은 검증하지 않았다.

## 4. PostgreSQL과 마이그레이션 방향 — 결정 완료, 로컬에서 계속

- **Docker를 켜도 되는지 다시 묻지 말고 로컬 시험을 진행한다.** 로컬 Docker Desktop/WSL과 이 작업의 격리 PostgreSQL 15 환경 기동·생성 자료 입력·검증·종료까지 허용한다. 운영 접속·서버 DB 복제·기존 다른 DB 데이터 삭제는 포함하지 않는다. 캐시 이미지로 가능한 검증부터 진행한다. 환경이 실행되지 않으면 정확한 오류/영향만 기록하고 공통 시계·현금흐름·도구 등 독립 작업은 계속한다.
- **이번 후보는 V94 기점 + 런타임 두 열의 V96만 유지한다.** main의 미배포 V95 슬리피지 기능을 이 검증을 위해 함께 배포하는 선택은 하지 않는다. V95의 기능/SQL 내용을 이 후보에 가져오거나 기존 적용 SQL을 고치지 않는다. V96 번호는 그대로 두고, 후속 main 통합에서 아직 어디에도 적용하지 않은 기존 V95를 V97 이상으로 옮길 계획/차분을 별도로 제출한다. **V96을 V97로 옮기는 것만으로 나중 V95 적용 순서 문제가 해소되지는 않는다.** 운영 변경 전 최종 실행 출처에서 Flyway 적용 순서를 확정해야 한다.
- 실제 PG에서 V94→V96 migrate/validate, 두 열의 타입·NULL/default·기존 행 불변, 조건부 피크 갱신/동시 갱신·시각 정밀도·호출자 롤백을 확인한다. H2에서 한 순차 호출을 동시성 검증으로 확대하지 않는다. 같은 PG DB로 새 컨텍스트에서 사유/시각·미실현 피크를 복원하고 첫 유효 시세 정산1회·두 번째0회를 확인한다. 예외나 저장 실패를 숨겨 상태 보존 완료로 보고하지 않는다.
- **생성 확인 SQL·포지션 추출 SQL도 실제 psql로 끝까지 실행한다.** 합성 CSV 연결 시험은 SQL 구문/열 이름/출력 형식을 검증하지 않는다. 정상 생성8개를 로컬 DB에서 만들어 실제 출력→완성기→집계기로 연결하고, T0 전 거래·CLOSING·지문 누락/복수 등 음성 입력을 대조한다. 실제 서버 생성 호출 승인이 아니다.
- JPA 매핑 때문에 새 열은 키 없는 PAPER의 SELECT에도 포함된다. “키가 없으면 열을 SQL로 읽지도 않는다”는 설명은 정확하지 않다. **키 없는 모드에서 그 값을 판단에 사용하거나 갱신하지 않는다는 범위**로 정정한다. 새 바이너리를 운영에 올리려면 첫 새 세션 생성보다 먼저 스키마가 준비돼야 한다. nullable 두 열이 남은 DB에서 옛 바이너리로 복구 가능한지도 로컬로 확인한다. 운영 DDL 실행 승인은 아직 아니다.

### 생성·완성·집계

- C1(사후 목록 실패), C2(미결 전송), A1(DB 미확인), A2(빈 지문) 보완은 **메모리 목/합성 연결 범위에서 수용**한다. 잠금·의도 fsync·결과 실패 후 중단·요청별 시각 창·잠정 후보를 팔로 확정하지 않는 방향도 수용한다. 응답 불명 뒤 자동 이어 보내기나 수동 플래그로 확정하는 절차를 추가하지 않는다.

## 6. 이어갈 순서와 기록

1. 위 정지 결과/미정산 노출/조회 보완과 실제 PG·SQL 확인을 진행한다. 독립 작업은 서로 기다리지 않는다.

## 7. 재현 파일

`prepare.py`는 고정 Git 출처의 근거/제품 사본을, `run_java.py`는 JDK17 수동 컴파일과 Spring 실행을 준비한다. `run_python.py`는 고정 도구38건과 보존 jar 확장/중복 음성 대조를 실행한다. `audit.json`, `review.json`, `libraries.json`, `jar-review.json`, `python-tests.txt`, `spring-tests.txt`, `doc-check.json`을 함께 보존했다. 재현 시 스크립트와 관측 Java 파일을 **Git에 넣지 않는 `core-engine/build/<새 검토 폴더>/`로 복사**한 뒤 prepare→run_java/run_python 순으로 사용한다. 이전 캐시 라이브러리와 D:/tmp의 보존 jar 경로는 해당 환경에 있어야 한다. 증거 폴더 안에서 빌드하지 않는다.

Git archive는 `core.autocrlf`의 줄바꿈 변환을 적용할 수 있어 컴파일 소스와 고정 커밋의 원본 바이트 해시/줄바꿈을 제외한 내용 대조를 `review.json`에 나눠 기록한다. 원래 제품 소스·제출 근거·과거 체크섬은 바꾸지 않았다.
