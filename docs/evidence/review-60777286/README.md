## 결정 1 — 시험 외부 알림 차단을 먼저 한다

**추가 승인 없이 시험 설정을 보완한다.** 일반 H2/PG/Spring·스케줄러 시험의 기본값은 기존 `telegram.enabled=false`를 사용한다. test/scheduler 프로필 조합과 실행기의 유효 설정을 확인하고, 시험 프로세스에 운영 토큰/대상 값을 상속하지 않는다. 실제 기본 chat-id를 시험 대상으로 사용하지 않는다. 운영 설정·기본 운영 동작·알림 사유/재시도/큐 계약은 바꾸지 않는다.

전송 계약을 검증하는 시험은 실서비스를 계속 사용하되 **enabled=true를 명시하고 목적지를 127.0.0.1의 HTTP 대역으로 고정**한다. Mockito/CountingService 대역은 그 자체의 호출 단언을 유지한다. 기존 TelegramMarkdownFallbackTest·TelegramRiskLimitRetryHttpTest가 이 구조를 이미 사용한다. 알림 비활성화에서 반환되는 성공을 실제 전송 성공의 증거로 쓰지 않는다. 생산자 호출·커밋 뒤 알림·롤백/큐 거절·재시도·서식 폴백 시험을 없애거나 기대를 완화하지 않는다.

보완 후 대표 H2/PG·스케줄러 시험과 알림 계약 시험에서 유효 enabled/대역 목적지·시도 수를 기록한다. 일반 시험은 외부 Telegram 시도0, 명시적 전송 시험은 로컬 HTTP 요청 수로 확인한다. 빈 토큰/404는 차단 장치가 아니다. 다른 외부 클라이언트를 사용하는 진단도 실행 전에 대역/로컬 경계를 확인한다. 기존 전체 회귀를 이 설정 변경 하나로 즉시 반복하지 말고, 관련 검증 후 최종 통합 회귀에 연결한다.

과거 외부 요청 사실·원문은 지우지 않는다. 이번 제출 README 첫 문장의 “알림은 대역”은 §7 실제 시도와 충돌하므로 정정 메모를 더한다. 이번 총괄 탐침은 알림·웹소켓·거래소를 모두 대역으로 고정했고 외부 자격증명 환경 항목도 제거했다.

## 결정 2 — 전역 REAL 손실은 기존 보호식을 유지하고 추가 보호식을 병행한다

**LIVE+DYNAMIC 자본 합계 하나로 기존 분모를 대체하는 안은 채택하지 않는다.** LIVE 손실 2.00% 거절이 DYNAMIC 자본을 더했다는 이유로 1.00% 승인으로 바뀌면 안 된다. 새 숫자나 별도 완화 설정을 만들지 않고, 각 일/주/월 창마다 아래 세 식을 같은 기존 한도로 판정하는 독립 후보를 만든다. **어느 한 식이 기존 비교 규칙상 한도를 넘으면 신규 실자금 매수를 거절한다.**

| 보호식 | 손실 원천 | 자본 기준 |
|---|---|---|
| 기존 보호식 | 종전 비세션 FILL + 확정 LIVE 세션 매도 손실 | 종전 LIVE RUNNING 초기자본, 기존 설정/최종 폴백 그대로 |
| DYNAMIC REAL 보호식 | 확정 DYNAMIC REAL 세션 매도 손실 | DYNAMIC REAL RUNNING 초기자본 |
| 전체 REAL 보호식 | 위 두 손실 원천의 합, 각 한 번 | LIVE+DYNAMIC REAL RUNNING 초기자본 합, 비세션만이면 종전 설정/폴백 |

이익으로 손실을 상쇄하지 않고 PAPER/DYN_PAPER·추정 청산을 분자·분모에서 뺀다. 기존 LIVE/비세션 보호식은 제거하지 않는다. LIVE/DYNAMIC REAL 즉시 진입·회차 승인·비세션 BUY에 같은 관문을 연결한다. PAPER 모의 한도는 기존 선택 모드의 계약을 보존하고 REAL 자료로 오염시키지 않는다.

새 DYNAMIC 보호식에서 손실이 있는데 유효한 자체 자본이 없거나 자료를 읽지 못하면 손실0/무한 자본으로 간주하지 않고 **판정 불가로 신규 진입을 막는다**. 자체 손실이0인 경우에는 자본 없는 비활성 엔진 때문에 자동 차단하지 않는다. REAL 없음/비세션만은 기존 보호식으로 판단한다. 중지/재시작·자본 추가/삭제와 기간 내 과거 손실이 남은 경우의 판정 변화를 표로 제출한다. DYNAMIC 중지 후 자체 분모가 없어지는 경우 차단이 더 엄격해짐도 명시한다. 이는 보수적인 로컬 후보 계약이며 운영 정책 적용은 실제 후보 검토 뒤다.

제출의 −4,002 사례는 DYNAMIC/전체 식으로 차단되고, LIVE −2,001 사례는 DYNAMIC 자본을 더해도 기존 LIVE 식이 계속 차단해야 한다. 각 창의 경계/기존 한도 동률 비교·반복 정산·늦은 정정·롤백·혼합 엔진·PAPER 제외를 실제 PG와 실제 승인 경로로 확인한다. 실패 먼저→최소 수정→관련 시험 순서로 진행한다.

## 결정 3 — 확인한 정리 경합을 별도 제품 후보로 보완한다

단순한 시험 대기 문제로 닫지 않는다. CLOSING 커밋 뒤 비동기 SELL 의도가 만들어지기 전에 `reconcileClosingPositions`가 주문 부재만 보고 OPEN으로 되돌리는 경합은 제품 문제로 취급한다. **제출 진행/불명 상태의 증거를 확인하기 전에 주문 행 부재만으로 OPEN으로 되돌리지 않는 계약**으로 독립 최소 후보를 준비한다.

총괄도 84fb03d6 실제 Spring/H2에서 주문 작업자를 래치로 붙잡아 같은 순서를 실행했다. 대역 체결 응답은 실제 `checkOrderStatus` 폴러를 거쳤다.

| 단계 | 관측 |
|---|---|
| 정리 요청/의도 실행 대기 | CLOSING, 주문0 |
| 일반 청산 확인이 먼저 실행 | OPEN으로 복귀 |
| 실행기 해제 | OPEN, SELL SUBMITTED1, 거래소 호출1 |
| 실제 폴러가 FILLED 반영 후 일반 청산 확인 | 여전히 OPEN, sell_applied_at null, 가용7,000.00 |
| 정리 작업 재실행 | CLOSING 복원, 아직 가용7,000.00 |
| 다음 일반 청산 확인 | CLOSED, 반영 표시 있음, 가용9,742.63 |
| 다시 두 작업 실행 | 매도1·입금 추가0 |

이 **관측 흐름 1/1**은 지연된 제출과 상태 복귀·정산 우회/회복을 확인한 것이다. 과거 실패 회차의 60초 지연 전체 원인을 입증한 것이 아니며, H2 결과로 PG 잠금 동작을 일반화하지 않는다. 첫 총괄 탐침은 정리 작업이 곧바로 정산한다고 잘못 기대해 실패했다. 실제로는 CLOSING 복원→다음 청산 확인의 두 단계다. 원문을 보존하고 그 기대만 정정해 재실행했다.

보완에서는 정리·실시간 손절의 같은 창을 각각 재현하고, 가능하면 CLOSING과 식별 가능한 SELL 의도/제출 소유권이 함께 확정되도록 기존 저장 구조/트랜잭션 순서를 검토한다. 구현 선택은 맡긴다. 근거 없이 일정 시간만 기다렸다 OPEN으로 바꾸거나 다시 매도하는 방식은 쓰지 않는다. 반대로 영구 CLOSING만 남기는 것으로 회복 계약을 없애지도 않는다. 실행기 거절·예외·트랜잭션 롤백·의도 확정 뒤 응답 불명·지연 체결·재기동·정지/비상정지·기존 매도와의 중복 방어를 포함한다. 기존 불명 주문/자금 복원/잠금 순서는 보존한다. 상태 일관성·정상 정산 경로·입금1회·중복 매도0을 실제 PG로 확인한다. 60초 시험은 별도 원인 확인 전 기대/시간 제한을 바꾸지 않는다.

## 결정 4 — 수용 범위와 통합 순서

- **49d485f0**: 실제 판정과 같은 식을 사용한 백분율/다중 보호선 보완을 로컬 통합으로 수용한다. F 디스패처 위의 실행 확인은 아직 필요하다. 보호선 캐시에 없는 신규 포지션/변경된 보호선이 다음 전체 점검부터 반영되는 한계와 DYNAMIC 매도 호출 실패 뒤 OPEN 잔존 시 다음 정기 점검을 기다리는 한계는 유지한다. 해결로 표시하지 않는다.
- **76ea3050**: 확정분 보존과 phantom 입금을 같은 트랜잭션으로 묶은 보완을 로컬 통합으로 수용한다. 실제 확정 손실과 추정 손익을 합계 포지션 열과 주문 원천으로 구분한 설명은 수용하되, 포지션 합계를 전부 확정 손실로 사용하지 않는다. 격리/반복/롤백뿐 아니라 동일 세션 여러 포지션·낙관적 충돌·관련 정산의 원자성도 최종 통합에서 확인한다. 추정가 정책은 변경하지 않는다.
- **ee5beb18·0a807cbb**: 결정적 진단에 근거한 시험 준비 래치 수정으로 수용한다. 다른 옛 대기20개 분류는 이어 간다. SchedulerProfileCleanupTest의 과거 지연은 미해결로 남긴다.
- **5f195542/도구v4**: 실제 연결과 사전 확인의 로컬 결과를 수용한다. 구판 AbChain은 구판 도구의 재현으로 남기고, 최종 사용할 v4 연결을 필수로 삼는다. 이것은 전략 성적이나 운영 생성 성공의 증거가 아니다.

84fb03d6 위에 새 통합 가지를 만든다. throttle 가지는 b5 기점이므로 파일 전체를 덮어쓰지 않고 필요한 커밋/변경만 옮긴다. F 디스패처의 단일 이벤트 진입·처리기의 @Transactional과 비동기 경계, B01/판단 시계, 부분 손익, 선택 모드/기존 PAPER 분리를 보존한다. 옛 @EventListener/@Async를 처리기에 되살리거나 F·V96·PAPER 보완을 없애지 않는다.

권장 실행 순서는 **시험 알림 격리/바이트 보존 → 정리 경합·손실 후보 → 미착수 DYNAMIC 판단 시계 및 대기20 분류 → 포함표/통합**이다. 독립 후보 준비는 추가 확인 없이 계속한다. DYNAMIC 시계 범위는 §125-5 그대로이며 C/D/E를 바꾸지 않는다. 서로 영향을 받는 파일은 최종 포함 SHA의 관련 시험을 먼저 돌리고 F+throttle 조합·phantom/정리·정산·위험 PG를 확인한다. 최종 SHA를 고정한 뒤 필요한 전체 회귀1회·실제 jar·프런트 연계·의미상 복구·구체 D4로 이어 간다. 제품 변경 뒤 84fb03d6 전체 통과를 새 후보 결과로 쓰지 않는다. 새로운 실패는 원문을 보존해 원인을 좁히고 통과할 때까지 무작정 반복하지 않는다.

D4/포함표 초안은 최종 SHA를 기다리지 말고 지금 작성한다. 후보/이미지/jar 기대값은 미정으로 명시하고 실행 금지로 둔다. 각 미완료 항목·중단/복구 조건·관측 방법을 채우며 실제 최종 빌드 뒤 값을 고정한다. V94→V96/V95 제외, 생성 전후 구판 복구 제한·장부 기록 실패 시 거절을 유지한다. 새 전역 정책/정리 경합 후보·DYNAMIC 시계·81b쿨다운의 포함 여부를 분명히 한다. 운영 실행은 아직 승인하지 않는다.
