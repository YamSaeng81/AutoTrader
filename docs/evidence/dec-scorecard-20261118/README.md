## 1. 월 성적표 시제품

[scorecard/scorecard.py](scorecard/scorecard.py)는 `scorecard-input-1` JSON 파일을 받아 `scorecard.json`과 `scorecard.md`를 만든다. 네트워크·DB 접속은 하지 않는다. 입력 계약을 어기면(실수형·세션 중복·모르는 포지션 상태) 산출 없이 rc2로 끝난다.

| 규칙 | 구현 |
|---|---|
| 월손익 | 기말 평가 − 기초 평가 − 순입금(배정·회수). 셋 중 하나라도 모르면 0으로 채우지 않고 `미확정`과 이유를 낸다 |
| CLOSING·가격 없음 | 0원이 아니라 미확정으로 둔다(S02·S05) |
| 수수료 | 손익에 이미 반영된 값이므로 따로 **표시만** 한다. 실현손익은 주문 원천(매수 대금+수수료로 만든 평균가, 매도 대금−수수료)으로 다시 계산하고, 저장 `realized_pnl`과 0.01원을 넘게 다르면 어느 쪽도 고르지 않고 불일치로 표시한다(S01·S08·S13) |
| 포함 범위 | 손실·거래0·중단 세션을 모두 넣는다. 합계는 모든 세션이 확정일 때만 내고, 아니면 "확정 부분 합"과 미확정 세션 목록을 따로 낸다(S03, 예시) |
| 낙폭 | 일별 평가 표본이 있을 때만 계산하고 "일별 표본 낙폭(장중 최대 낙폭 아님)"으로 이름 붙인다. 없으면 `미확인`이며 다른 자료로 복원하지 않는다(S07) |
| 출처 | 코드 SHA·규칙 지문·전략/주기/모드·시장 상황은 입력 출처를 그대로 싣고, 없으면 `미확인`으로 둔다. 구간 중 지문이 바뀌면 분리 필요로 표시한다(S06) |
| 비교 | 현금 0과, 같은 기초 자본으로 BTC를 보유했을 때의 손익을 낸다. BTC 가격이 없으면 미확인(S09) |
| 계좌 대조 | 계좌 기말 − 기초 − 순입금을 세션 합과 나란히 두고 차이를 그대로 표시한다(S10) |
| 기간 경계 | 기간 밖 매도는 그 달 실현·수수료에 넣지 않는다(S12). 기간 안 새 세션은 기초 0 + 배정 순입금으로 계산한다(S11) |

[합성 사례](scorecard/cases_scorecard.py) **21/21 통과**([run1/cases.out.txt](scorecard/run1/cases.out.txt)). 기대값은 손으로 계산해 적었다. 예: 매수 50,000+25, 매도 52,000−26이면 실현 1,949이고, 수수료 51을 다시 빼면 나오는 1,898이 아니다. 여러 사례를 묶은 [예시 성적표](scorecard/run1/demo/scorecard.md)는 CLOSING 세션 하나 때문에 전체가 `미확정`이고 확정 부분 합 398을 따로 보여 준다.

### 입력을 만들 기존 자료 (읽기안, 실행·예약 없음)

| 입력 칸 | 기존 출처(0e1d2a02) | 비고 |
|---|---|---|
| 매수/매도 대금·수수료·수량 | `order.applied_executed_funds`·`applied_paid_fee`·`filled_quantity`·`side`·`created_at` | 반영값 = 정산이 실제로 쓴 값 |
| 저장 실현손익 | `position.realized_pnl`, DYNAMIC은 `dynamic_sell_settlement.realized_pnl` | 대조용으로만 쓰고 원천은 주문 |
| 기초/기말 세션 평가 | 세션 `available_krw` + OPEN/CLOSING 포지션 `size`×그 시각 가격 | 가격은 월 경계 시각의 시세 기록. 없으면 미확정 |
| 순입금 | 세션 생성 배정(`initial_capital`)·회수 | 계좌 순입금은 거래소 입출금 기록(외부) |
| 코드 SHA | 외부 등록표·배포 기록 | DB에는 세션별 코드 SHA가 없다(P7과 같은 전제) |
| 규칙 지문·시장 상황 | `position`/`strategy_log`의 `ruleset_hash`·`market_regime` | 분류 기준은 제품 정의 그대로 |
| 일별 평가(최소안) | 매일 같은 시각에 위 세션 평가 읽기 1회를 파일로 보존 | 운영 예약·DB 열은 만들지 않는다. 실행은 승인된 읽기 범위가 정해진 뒤다 |

### 제품 관찰(판정 아님): REAL과 PAPER의 저장 실현손익 정의 차이

코드를 읽은 결과다. DYNAMIC **PAPER** 매수는 평균가 = 수수료 포함 투입액/수량이다(`DynamicTradingService` S:1854 `avgPriceWithFee`). 반면 **REAL** 체결 정산은 평균가 = 체결대금/수량으로 수수료를 넣지 않고, 투입액에만 수수료를 더한다(`OrderSettlementService` S:406·466, 정정 S:511~512). 매도 실현손익은 두 모드 모두 `순매도대금 − 수량×평균가`다(DYNAMIC S:3108, LIVE S:3090·3314). 따라서 REAL의 저장 `realized_pnl`에는 매수 수수료가 빠져 있을 수 있다. 세 엔진은 체결 오차 말고는 같은 규칙이어야 하므로 확인이 필요한 차이다. 성적표는 주문 원천으로 다시 계산하므로 이 차이를 불일치로 드러낸다(S13: 저장 1,974 vs 원천 1,949, 차 +25). 이 차이는 [매도 PG 보충](../dec-pg-sell-20261118/README.md#4-실현손익-정의--실제-pg-확인-판정-아님-제품-관찰)에서 실제 PG로 확인했다(평균가 300.00000000, 저장 246.125 vs 주문 원천 242.375, 차 = 매수 수수료 3.75). 제품은 고치지 않았다.

## 2. 최소 알림안 (제출, 구현 안 함)

| 빈틈(0e1d2a02) | 근거 | 최소안 |
|---|---|---|
| 같은 세션 왕복이 다른 묶음에 나뉨 | DYNAMIC 매수는 `OrderExecutionEngine` S:2289의 `"세션#"+id`, 매도는 `DynamicTradingService` S:3188의 `"동적#"+id`다. LIVE 매도는 `LiveTradingService` S:3364 `"세션#"`, 모의는 `PaperTradingService` S:1946·2014 `"[모의투자] 세션#"`이다. 같은 번호의 LIVE와 DYNAMIC 매수가 한 묶음에 섞인다 | 표시를 `종류#ID`(LIVE/DYNAMIC/DYN_PAPER/PAPER)로 통일한다. 주문에는 이미 `session_kind`가 있으므로(`order.getSessionKind()`) 호출 4곳의 문자열만 바꾸면 되고, 새 열·큐·DDL은 필요 없다 |
| 재기동하면 반나절 요약이 빠짐 | 버퍼는 메모리 `CopyOnWriteArrayList`(S:93)이고 12:00·00:00 KST 요약(S:489·495)이 비운다 | 기동 시각을 기억해 두고, 그 요약 구간 안에 재기동이 있었으면 요약 머리에 "HH:MM 재기동 — 그 앞 거래는 이 요약에 없음, DB 주문/정산이 원본"을 한 줄 넣는다. 버퍼를 영속화하지 않는다 |
| 알림 꺼짐일 때 버퍼가 계속 쌓임 | `sendDailySummary`가 `if (!enabled) return;`(S:501)으로 버퍼를 비우지 않는다 | 꺼짐이면 적재하지 않거나 요약 시각에 버리고 개수만 로그로 남긴다 |
| 요약이 성적표 원천이 됨 | — | 성적표는 위 1장처럼 DB 주문/정산에서 만든다. 알림 버퍼는 원천으로 쓰지 않는다 |

즉시 체결 알림은 12월 새 필수 배포 조건에 넣지 않는다. 정지·위험 알림의 **휴대폰 실제 수신 확인**은 기존 시작 조건 그대로 남는다(전송 기록 `success`는 텔레그램 API 응답까지만 뜻한다).

## 3. 파일·재현

```
python -I scorecard/cases_scorecard.py --out scorecard/run1
python -I scorecard/scorecard.py --input <입력.json> --out <폴더>
```

Windows Python 3.13.14. 산출물은 LF·UTF-8이고 `.gitattributes`(`* -text`)와 [SHA256SUMS](SHA256SUMS)를 둔다.
