# v4.2.2 기록 실패 보완 — 중간 범위 수용

2026-11-17, v1.178 보충 지시의 후속 점검이다. 아직 미커밋 제출이므로 **실행 틀 해시 `660e2332433c50aadcf68b4e92b03d1ae2509e76a34f610ba0217e000c5653c7`의 기록 실패 보완만 범위 수용**한다. 전체 생성 묶음과 실제 운영 세션 생성·T0 승인은 별도다. [원래 보충 지시와 v4.2.1 재현](../README.md)은 변경하지 않았다.

## 대조 결과와 한계

- 마지막 로그를 먼저 쓰고 rc 표지를 임시 파일에서 이름 바꾸기로 확정한다. 앞 단계의 임시 파일이나 비정상 rc는 다음 단계를 막는다. 마지막 로그 실패 뒤 성공 rc가 남던 이전 공백은 검사한 입력에서 막혔다.
- 개발 보존 출력은 29개 통과 줄·종료0이며, T20~T25의 첫 호출/다음 호출 종료값을 사례 파일과 대조했다. 시험 원문은 같은 OUT에서 다음 단계를 직접 호출하고 도구 호출 증가가0인지 단언한다. 총괄은 이 전체 실행 틀 시험을 다시 돌리지 않았다.
- 총괄은 보존 함수만 로컬 Bash에서 별도로 호출했다. 정상 대조, 마지막 로그 실패, **rc 내용 쓰기 실패**, 이름 바꾸기 실패, 도구3+로그 실패, 도구3+rc 내용 쓰기 실패, 확정 직전 강제 종료의 7개 시나리오를 검사했다. 실패 6개는 성공 rc가 남지 않고 다음 선행 조건이 거절했으며 도구3은3을 유지했다. 정상은 다음 선행 조건을 통과했다. [재현기](audit_record.py)와 [결과](result.json)의 56개 검사 성공은 함수 동작·보존 출력 대조를 합친 수치이며 제품 시험 수가 아니다.
- 총괄의 다음 단계 호출 표지는 무해한 로컬 표지다. 실제 생성기·전체 단계·docker·서버·DB·네트워크는 실행하지 않았다. 쓰기 실패는 함수 대역 주입이며 서버 디스크 고갈·전원 장애·기록의 영구 저장까지 검증한 것은 아니다.
- 개발 T21은 `mv` 실패를 주입한 **rc 확정 실패**다. 파일 내용 쓰기 실패와 구분한다. 내용 쓰기 실패는 이번 총괄 함수 검사에서 별도로 확인했으므로 같은 검사를 추가 반복할 필요는 없다.
- 1회차26/29는 보존된 화면 출력 범위에서만 기록한다. 사례 파일이2회차에 덮인 사실과 첫8/19의 POST0이 제출자 설명이라는 한계는 유지한다. 이번 검사로 유실된 원문을 복원했다고 쓰지 않는다.

## 이어갈 작업

1. 예약된 SMA20 로컬 HTTP·격리 PG 연결, N03·09:30 장부 읽기, 제한된 통신 로그 조사는 기존 승인대로 진행한다. 예정 시각과 실제 시작·끝·종료값을 구분하고 미실행이면 그대로 남긴다. 추가 착수 확인은 필요 없다.
2. 최종 제출에서 T21을 이름 바꾸기 실패로 명확히 적고, 총괄의 내용 쓰기 실패 결과를 연결한다. 향후 회차는 실행 전에 고유 보존 경로를 확정하고, 덮어쓰기나 보존 실패가 있으면 해당 회차의 성공 근거로 합치지 않는다.
3. 세 작업 결과, 도구·본문·실행 틀 해시, 기존 총괄 근거·관리 문서와 이번 하위 폴더를 다음 실질 결과 커밋에 함께 넣는다. 커밋 블롭 누락·해시를 확인한다. 원래 보충 폴더의5개 체크섬은 그대로 둔다.
4. 고정 생성 묶음 검토 전에는 실제 운영 생성·T0를 실행하지 않는다. 이번 검사는 새 승인 단계나 전체 회귀·빌드 반복을 추가하는 지시가 아니다.
