# 개입 #20 절차 보완 — K1 바깥 항목·뉴스 도래 후 미관측 (계획 §5-9 55)

2026-11-04 KST. 총괄 v1.86(§5-9 54, [`k20-review-350efd1`](../k20-review-350efd1/README.md))의 두 보완 지시에 따른 로컬 작업이다. 서버·운영 DB·외부 HTTP 에는 접속하지 않았다. 운영 설치도 하지 않았다. jar 도 다시 빌드하지 않았다. 비교에는 §53 근거의 로컬 jar 두 개를 그대로 썼다(`ea44900` `f07b455e…`, `b1d7664` `a0cb2885…`, [`jar-sha.txt`](../k20-prep-b1d7664/jar-sha.txt)). 기존 167건·뉴스 시험·전체 리허설은 다시 돌리지 않았다.

바뀐 블록은 다섯 개다. K 변수·K1·K3·K4·K 뒤 뉴스 관측이다. K0·K2·K 되돌림은 §53 원문 그대로다. 블록 해시는 §53 근거와 같다. 계획 문서의 bash 블록은 71개에서 76개가 됐다. 앞의 71개는 바이트 그대로다.

## 1. K1 — 바깥의 모든 비디렉터리 항목

§53 K1 은 `BOOT-INF/classes/` 와 `BOOT-INF/lib/` 만 돌았다. 그래서 바깥 항목 98개를 보지 않았다. 내역은 Spring Boot 로더 94개, `META-INF/MANIFEST.MF`, `META-INF/services/…FileSystemProvider`, `BOOT-INF/classpath.idx`, `BOOT-INF/layers.idx` 다.

새 K1 은 다음과 같이 비교한다.

- 바깥 jar 의 디렉터리가 아닌 항목을 모두 비교한다.
- 자체 모듈 jar 3개는 기존처럼 풀어서 안쪽 항목을 비교한다.
- 외부 라이브러리 jar 는 통째로 비교한다.
- 같은 이름의 항목이 두 번 있으면 차이로 낸다.
- 비교 대상은 항목 내용의 sha256 뿐이다.

## 2. `newsobs` — 관측 시각

`newsobs` 에 다섯째 인자로 관측 시각을 넣었다. K3·K4·K 뒤 뉴스 관측에서 관측 시각은 뉴스 설정을 읽은 시각이다. 로그는 그 뒤에 읽는다.

판정 대상은 사용 중이고, 완료·미완료 줄이 없고, 기동 뒤 시도 기록도 없는 출처다.

- **계산상 회차**: 도래 시각 뒤의 첫 명목 회차다. 명목 회차는 기동 3분 뒤부터 15분 간격으로 센다.
- **관측 시각 < 계산상 회차**: "미관측 — 계산상 차례 전", 종료 0.
- **계산상 회차 ≤ 관측 시각**: "⚪ 확인 필요", 종료 3. 정상 관측으로 세지 않는다.
- 종료 1·2 가 함께 있으면 그쪽이 우선한다.

인자가 5개가 아니면(§53 식 4개 호출) 종료 2 로 멈춘다.

`newsobs-cases.txt` 의 11사례는 모두 기대와 같다. 총괄 4입력은 총괄 근거의 입력 파일 그대로, 고정 맥락은 기동 12:00 KST·관측 12:35 KST 다.

| 입력 | §53 함수(총괄 관측) | 새 함수 |
|---|---|---|
| 총괄: last_fetched_at NULL·30분·로그 없음 | 차례 전·종료 0 | **⚪ 확인 필요(회차 12:03 ≤ 관측 12:35)·종료 3** |
| 총괄: 10:00 정체·30분·로그 없음 | 차례 전·종료 0 | **⚪ 확인 필요·종료 3** |
| 총괄 대조: 11:59 시도·120분 | 미관측·종료 0 | 미관측(13:59 도래, 첫 회차 14:03 무렵)·종료 0 |
| 총괄 대조: 12:03 시도·로그 없음 | ⚪·종료 2 | ⚪·종료 2 |
| 경계: NULL·관측 12:02:59 / 12:03:00 | — | 종료 0 / 종료 3 |
| 경계: 12:10 도래·관측 12:12 / 12:19 | — | 종료 0(회차 12:18 전) / 종료 3 |
| 혼합: 로그 있는 출처·사용 안 함·도래 후 미관측 1 | — | 출처별 줄과 `🔴 새 판정` 줄, ⚪ 1개·종료 3 |
| 혼합: 간격 변경 + 도래 후 미관측 | — | 종료 1(설정 변경 우선) |
| 인자 4개 | — | 종료 2 |

**⚪ 의 한계**: 회차 시각은 명목값이다. fixedDelay 라 실제 회차는 앞 회차 소요만큼 늦다. 그래서 ⚪ 는 수집 실패·원인·회복을 확정하지 않는다. 특히 K3(기동 5~10분)에서는 첫 회차(기동 3분)가 아직 도는 중이어도 ⚪ 가 나올 수 있다. 이것은 보고 대상이며 멈춤·되돌림 조건이 아니다.

## 3. K3·K4 가짜 입력 — 20사례, 기대와 모두 같음(`k-cases-summary.txt`, 원문 `cases/*.out`)

§53 근거와 같은 실행기를 썼다. 블록은 계획 문서에서 꺼낸 그대로 실행했다. 대역은 서버 명령뿐이다. 앞의 17사례는 §53 근거와 결과(종료값·표지·마지막 줄)가 같다. 새 사례는 3개다.

## 4. 안내 정정

§5-9 55 에 반영했고, §53 의 해당 머리·문구에는 취소선과 대체 안내를 달았다.

- **K1-되돌림**: `git checkout` 뒤의 멈춤에만 한다. 이 멈춤 문구에는 "K1-되돌림" 이 붙어 있다. 그 전의 멈춤(K0 30분 경과·보존 태그 등)은 문구에 "K1-되돌림 하지 않는다" 를 넣었다.
- **K0 의 30분**: K1 을 시작하는 시점의 신선도다. 빌드 완료 제한이 아니고, K4 가 다음 정기 점검 전에 끝난다는 보장도 아니다.
- **K4 의 뉴스 회차**: 3·18분 무렵 명목 회차까지이며, 33분 회차는 아직이다.

## 5. 하지 않은 것과 한계

- 서버·DB·외부 HTTP, docker 빌드, 앱 기동, jar 재빌드, 기존 시험 반복은 하지 않았다.
- K1 은 Python 비교 부분과 기대 검사 두 줄만 실제 jar 로 돌렸다. 블록 전체(docker 부분)는 `bash -n` 만 했다. K2·K 되돌림은 §53 과 같이 문법만 확인했다.
- 서버 docker 빌드 jar 가 로컬과 다르면 K1 이 재기동 전에 멈춘다. #19 에서는 같았다.
- 뉴스 줄 형식은 여전히 후보 코드 기준이다. 운영 로그로는 확인하지 않았다.
