## 2. 축과 근거

| 축 | 값 | 근거 |
|---|---|---|
| collector | `meta.steps`·표본의 c0/c1 | 수집기 벽시계 |
| db | `db.observed_at`, 표본 d | extract.sql의 `now()`(추출 트랜잭션 시작), 표본은 `clock_timestamp()` |
| app | 세션·주문 `created_at` | 0e1d2a02 `OrderEntity`·`LiveTradingSessionEntity`·`DynamicSessionEntity`의 `@PrePersist Instant.now()` |

| 등록 | `effective_from/to` | 등록표 `effective_axis`(전체) 또는 항목별 `effective_axis`로 선언. 없으면 축 미선언 |

## 3. 판정 규칙

- **관계는 관측 `meta.clock`에서만 온다.** `samples`: 같은 연결에서 수집기 c0~c1 사이에 읽은 X 시계 d → (X−수집기) ∈ [d−c1, d−c0]. `same_source`: 같은 물리 시계라는 선언과 basis. 기준·현재 모두에 같은 선언이 있을 때만 쓴다(K03). 평균·고정 오프셋 키가 있으면 관측 무효(K27·F12).
- **한 관측 안에서도 차이가 움직인다.** 저장 PG 표본에서 00-start 안 4개 표본이 +1,494.8→+1,490.3ms, L1 안에서 +1,480.6→+1,477.2ms로 수십 ms 사이에 몇 ms씩 변했다. 그래서 관측 전체에 한 범위를 쓰지 않고, 옮길 시각을 **앞뒤로 감싸는 표본들의 범위 외포**만 쓴다(그 사이 단조 변화 가정). 한쪽 표본만 있으면 외삽하지 않고 보류(K29).
- **시계 이동·오래된 표본:** 벽시계 c1<c0, 단조 시계 왕복과 벽시계 왕복 차이 >0.5ms인 표본은 버린다(K11). 0.5ms 이하 차이는 그만큼 범위를 넓힌다(K31) — 통과 쪽으로 느슨해지지 않는다. 표본 순서에서 X 시계가 거꾸로 가면 그 관계를 쓰지 않는다(K12). 관측 수집 구간 밖 표본은 버린다(K09·K30).
- **단계는 구간이다.** `{step, start, end}` = 사건이 그 안에 있음. 저장 PG 스냅샷은 표본 k 직후~표본 k+1 직전으로 바꿨고, 마지막 단계 끝은 기록되지 않아 관측 사이 순서는 `COLLECTION_ORDER_UNCONFIRMED`(막는 통화 없음)로 남는다. 끝을 기록하면 사라진다(K26). v4 점 형식 `{step, at}`은 같은 축 순서 검사에만 쓴다.
- **범위 판정:** 확정 참/거짓이면 v4 판정 그대로, 경계 겹침(K07)·관계 없음(K02)·축 미선언(K28)이면 `CLOCK_AXIS_UNCONFIRMED`로 **그 비교만** 보류한다. 막는 통화가 없어 −1.50원(K17)·담보 부족(K18)·전략 불일치(K19)·확정된 생성 선후(K06)·확정된 구간 밖 주문(K21)·확정된 규칙 위반(K25)은 이상으로 남는다.
- **바뀐 비교 7곳:** DB 추출 ∈ 거래소 앞/뒤 읽기(K14·K16) · 새 세션 생성 ≥ 적용 시작 · 기존 세션 적용 시작 ≥ 생성 · 주문 생성 ∈ 등록 적용 구간(미확정이면 등록 여부만 보류하고 계산에는 넣음, K20) · 규칙 대상 구간 주문(미확정 주문만으로 생긴 위반은 보류, K24) · 주문의 조회 기간 포함 · 비교 구간 전체 덮음.
- **거래소 조회 기간 ≠ DB 의도 생성:** 거래소 주문 생성은 [DB 의도 생성(앱 축), 현재 DB 추출(db 축)] 안에 있다고만 본다. 조회 끝이 현재 DB 추출보다 앞이면 덮지 못한 것으로 확정한다(K23). 창 끝은 현재 거래소 뒤 읽기 **시작**이다(조회 요청이 그 단계 안에서 나가므로).

## 4. 수집 메타데이터안 — 격리 환경 확인 범위

저장 PG 스냅샷의 표본(`at`·`at_db`·`rtt_ms`, 같은 JVM 벽시계)으로 위 규칙이 실제 값에서 동작함을 확인했다(P 30쌍, 계좌 계산은 v4와 같음). 단조 시계 왕복과 단계 끝 시각은 이 스냅샷에 없어서 합성 변형(K11·K13·K26·K31)으로만 확인했다. 실제 수집기에 넣을 형식은 단계마다 `start/end`(벽시계)와 앞·뒤 표본 `{c0, d, c1, mono_rtt_ms}`다. 매도 PG 보충 시험에서 이 형식으로 처음 기록할 예정이다.

운영 앱 시각을 읽는 승인된 방법은 없으므로 운영 입력에는 앱=수집기 관계가 없다. 그러면 앱 축 비교는 추정 없이 보류된다(K02·K20). 거래소 시계 관계도 현재 근거가 없어 실제 거래소 조회 기간 비교는 보류된다(K22). 새 운영 엔드포인트·제품 시계 변경은 넣지 않았다.

## 6. 한계

- 모든 입력은 로컬 가정값·격리 PG 값이다. 운영 사용·운영 시계 차이 측정은 주장하지 않는다(P7 운영 사용은 총괄이 아직 수용하지 않음).
- 표본 사이 단조 변화는 가정이다. 표본 사이에 튀었다가 돌아온 시계는 잡지 못한다.
- 저장 PG 스냅샷은 마지막 단계 끝이 없어 관측 사이 순서가 모두 보류로 남는다. 새 수집기 기록으로 확인해야 한다.
- 거래소 미체결 주문 전체 보류, 매도 정산 검증은 v4 한계 그대로다.
