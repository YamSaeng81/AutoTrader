## 2. 새로 확인한 공백과 결정

[새 입력 관측](contract-probes.json)은8건이며 P0는 정상 대조군이다. [검토 코드](review_checks.py)는 고정 블롭의 순수 함수를 메모리에서 호출했다. 운영·DB·거래소·애플리케이션 실행은 없다.

1. **미확정 매수 원가가 확정 실현손익에 섞인다(S1).** 변환기는 `[T,M]`의 유효 매수 포착이 없어도 마지막 포착의20,000원·수수료10원을 넘기고 시각만null로 바꾼다. 성적표 v3는 이 숫자로 매도10,000원·수수료5원의 **확정 실현−10,015원**을 낸다. 시각 미상과 원가 미상을 별도로 전달해야 한다. 영향을 받는 실현·승패·왕복은 미확정으로 두고, 원가가 확인된 다른 거래의 부분 합은 보존한다. 최신 수치를 확정 비용으로 쓰거나 해당 거래를 조용히 누락해0으로 만들지 않는다.
2. **`reported_observed_at < T`는 주문 값의 불변 근거가 아니다(S2).** 경계 포착의 매수 수수료4원(정산 미확정)이1월에6원으로 확정돼도 관측 시각은12월 값으로 남을 수 있다. 변환기는 차이2원을1월 정정으로 표시하면서도6원을12월 비용에 넣어 확정 수수료11원을 낸다. d81의 `OrderRepository.applySettlementIfVersionMatches`는 대금·수수료를 정정하면서 `reportedObservedAt`을 갱신하지 않는다. C4의 현재 확정 조건은 철회한다. 경계 당시의 값·확정 상태 또는 값별 변경/반영 근거가 없으면 미확정이다. SELL에도 이 BUY 관측 열을 보편적인 최종 변경 시각으로 쓰지 않는다.
3. **축 이름만 있고 시계 관계는 검사하지 않는다(S3).** 같은 새 세션 입력에서 배정 이벤트 축만app→db로 바꿔도 관계 자료 없이 순입금이 확정된다. 기간 경계·생성·포착·이벤트·정정 구간의 기준 축을 명시하고, 서로 다른 축은 기존 P7 v5의 범위 판정 방식 또는 검증된 동일 시계 근거로만 비교한다. 관계가 없거나 경계에 걸치면 그 계산만 보류하고 독립된 이상은 유지한다. 새 시계 측정이나 운영 읽기는 이번에 실행하지 않는다.
4. **미래 기준값도 합산을 통과한다(P3).** 현재 관측은2026년인데 cash_base·holdings_base를2030년으로 바꾸고 배정 두 건을 포함 선언해도 overall OK·합산 일치다. 두 기준 모두 현재 관측 이전인지 해당 축으로 확인해야 한다. 확실히 미래면 모순 이상, 선후 불명이면 해당 통화 합산 보류다. 포함 이벤트도 현재 관측 뒤의 것을 기준값 안에 숨길 수 없게 한다. 음수 미배정 잔액 등 불가능한 잔액은 별도 이상으로 확인한다.
5. **계좌 숫자 일치와 F3 통과를 구분한다(P1·P2·P4).** 지문 미확인은 overall HOLD, 지문 불일치는 ANOMALY, 거래소 완료 조회 미완료는 HOLD지만 세 경우 모두 account_sum은일치다. P7의 기존 전체 판정은 이를 잡고 있으므로 합산 숫자 자체가 잘못됐다고 고치지 않는다. 초안의 F3 `account_sum.status == 일치` 단독 조건을 철회하고 **전체 판정OK·등록표 유효·필수 출처/조회/지문 확인 완료·합산 일치**를 함께 요구한다. 보류를 경고로 낮춰 통과시키지 않는다.
