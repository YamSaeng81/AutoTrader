# N05 연결 검토 수용과 22시 전 후속 지시 (총괄 v1.118, 2026-11-05)

## 판정

- 제출 `0bf874f`의 N05 연결표(K1~K11)는 **코드·기존 시험의 연결 검토로 수용**한다. 전체 리허설 완료, 모든 보호 동작의 운영 관측, 결함 없음 확정으로 확대하지 않는다. N05 최종 정합성 확인(11-23~27)은 남는다.
- N15/N16은 #23 결과 수용에 따른 **운영 반영 완료**를 유지한다. K9를 이유로 운영 미반영 P0로 되돌리지 않는다.
- K9는 단순히 시험 이름만 없는 곳이 아니다. 신선한 REST 0·음수 가격을 `PUBLISHED`로 내보내고, DYNAMIC은 이후 실제 점검 기록이 없을 때 원인을 이벤트 경로 문제로 안내할 수 있다. **N17(P1): REST 가격 유효성과 SL 감시 결과·문구 연결**로 보완한다. REST에서 이런 값이 실제로 왔다는 운영 증거는 없다.
- 보호 매도 차단·이력 보존은 N16 코드와 기존 시험에 근거한다. 이번 총괄 국소 실행은 강제 갱신 메서드와 원인 문구만 실행했으며, Spring 비동기 처리기·실제 매도까지 새로 검증한 것은 아니다.

## 총괄이 실제로 확인한 것

- 제출 연결표 체크섬 **1/1**, 앞선 총괄 근거 **7/7**을 작업 사본·커밋 블롭·SHA256SUMS와 대조했다.
- 운영 `1103f48505a1457029f6555547a87aa986535738`에서 관련 원문을 읽었다. 만료 콜백 앞 검사, 의도 승인 뒤 만료 검사, 같은 트랜잭션 복원, 가격 거절과 점검 기록의 순서, 체결·호가 시각 보정, 두 강제 갱신 메서드를 대조했다.
- 보존된 XML 25개 **173/173**, 실패·오류·건너뜀 0과 연결표의 기존 시험 클래스 이름을 읽어 대조했다. 앱 시험은 재실행하지 않았다.
- LIVE·DYNAMIC의 `forceRefreshPrice` 원문, 공통 `ForceRefreshResult`·`RealtimePriceEvent` 원문, `isStale` 원문을 로컬 Java 17에서 컴파일했다. REST 클라이언트·이벤트 발행기·로거만 대역이다. 새 Spring 컨텍스트, Gradle, HTTP, DB, 서버는 쓰지 않았다.
  - 각 엔진의 신선한 0·음수: **PUBLISHED, 이벤트 1개**. 이것이 N17의 실패 먼저 근거다.
  - 정상 양수: PUBLISHED 1개, 낡은 양수: STALE 1개, 누락·숫자가 아닌 값: FAILED 0개. **12입력**의 현재 동작을 기록했다. STALE 발행은 기존 동작이지 이번 수정 권고가 아니다.
  - DYNAMIC의 원문 원인 분기를 `PUBLISHED`, 구독 있음, 연속 미점검 5회로 평가하면 “실시간 이벤트 경로가 죽었을 수 있습니다”가 나온다. 실제 스케줄러를 5회 돌린 결과가 아니라 해당 분기의 국소 실행이다.
  - 같은 낡음 식의 고정 시각 대조: **120.999초는 유효, 121초부터 낡음**이다. 코드의 `Duration.getSeconds() > 120`을 따른다.
- `review.py`는 원문을 고정 SHA에서 추출하며, `reproduce.txt`, 원문 메서드 사본과 `review.json`을 남겼다. 최초 확인기에서 메서드 호출 인자/단계 문자열을 잘못 가정해 ValueError가 났다. 실제 원문과 맞춘 뒤 통과했으며 운영 코드나 시험 기대값을 고친 것은 아니다.

## 연결표 표현 보완

- K10의 “120초 뒤 낡음”은 위 **121초 경계**로 읽는다. 기존 제출을 덮어쓰지 않고 다음 실제 결과 기록에서 정정한다.
- “신규 진입만 막음”은 **공유 풀 진입 가드의 효과**를 말한다. 같은 낡은 가격을 손절·익절의 유효한 현재가로 쓰겠다는 뜻이 아니다. 신선한 가격이 없으면 가격 기반 판정은 할 수 없고, 가격 없이 가능한 시간 청산·정지/비상정지 시장가 청산 경로가 유지된다는 뜻으로 구분한다. 미점검 경보가 곧 손절 정상 작동의 증거는 아니다.
- K9의 “다음 주기 재경보”도 경보 채널과 기존 연속 미점검 기준을 구분한다. LIVE 경보와 DYNAMIC의 연속 횟수/알림 초기화를 같은 매분 텔레그램 동작으로 단정하지 않는다.

## 지금부터 승인 대기 없이 진행할 로컬 작업

### 1. N17 국소 재현 → 최소 수정 → 관련 검증

1. **운영 1103f48 기점 격리 브랜치**에서 작업한다. main의 미배포 V95·설정·다른 개선은 섞지 않는다. 위 12입력을 참고하되 앱 연결 재현을 먼저 보존한다.
2. LIVE와 DYNAMIC 모두에서 신선한 0·음수가 현재 `PUBLISHED`가 되는 것을 실패 먼저 시험으로 잡는다. 실제 소비 경로까지 연결해 매도 0·OPEN 유지·점검 시각/가격 이력 오염 없음·다음 감시 주기 유지도 확인한다. 정상 가격을 뒤이어 받으면 기존 점검/보호 매도가 가능해야 한다.
3. **가격 검사 뒤에만 발행**한다. 두 엔진 모두 `MarkPriceBook.isPrice` 기준을 쓴다. 파싱된 0·음수는 별도 **`INVALID_PRICE` 조회 결과**로 구분하고 이벤트를 내보내지 않는다. 누락/null/형식 이상도 PUBLISHED나 정상 점검으로 만들지 않는다. 기존 FAILED로 남겨도 되며, 통신 실패와 가격 이상을 한 원인으로 단정하지 않는다.
4. LIVE·DYNAMIC 알림과 로그에서 가격 이상을 정확히 안내한다. 이 경우 “발행”, “점검 재개”, “이벤트 경로 고장”, “손절이 정상 동작한다”로 쓰지 않는다. DYNAMIC은 INVALID_PRICE를 유효한 조회·발행으로 세지 말고, 기존 복구 실패 경보 규칙을 적용한다. **60초 주기, 3분 미점검 기준, 연속 횟수·초기화 등 기존 숫자와 정책은 바꾸지 않는다.** 새 결과에 대한 분기와 그 영향은 결과에 명시한다.
5. 양수·신선함/낡음, 조회 실패, 빈 응답·누락/null/형식 이상, 비정상 가격 뒤 정상 값 회복을 대조한다. 새 결과값의 사용처 전체와 switch/조건식을 검색해 빠진 분기를 점검한다. 기존 STALE/FAILED의 의미와 120초 정의, 장부 시각 보정은 유지한다. 가격 이상을 새 ERROR로 쌓거나 정기 보고 분류를 바꾸지 않는다.
6. 새 시험과 바뀐 경로의 기존 SL 감시기/가격 방어 시험만 실행한다. **관련성이 없는 173건 전체·167건 점검·기존 성능 실험은 반복하지 않는다.** 기대값 변경은 계약 변경에 필요한 것만 이전 기대와 이유를 남긴다. 실행별 소스·XML·로그·종료값을 별도 보존해 뒤 실행이 원문을 덮어쓰지 않게 한다. 외부 주문·알림·시세 요청은 대역이다.
7. 통과하면 40자리 후보 SHA와 변경 경로, 원문 근거를 고정해 푸시한다. 이것은 로컬 후보 제출이며 운영 완료가 아니다. 이 단계 뒤 총괄 회신을 기다리며 멈출 필요 없이 아래 준비를 계속한다.
