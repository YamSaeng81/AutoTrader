# 불명 주문 상태·예약·복구 설계안 (2026-10-07)

> **이 문서는 설계안이고 구현이 아니다.** 아직 코드로 옮기지 않았다. 검증 66세션은 그대로
> 유지하며, 운영 재배포는 보류 상태다. 선행 조건 5번은 미완료다.
>
> 근거가 되는 재현·측정은 [`LIVE_RISK_IMPLEMENTATION_REVIEW.md`](LIVE_RISK_IMPLEMENTATION_REVIEW.md)
> §4.6 에 있다. 여기서는 그 결과를 전제로 **무엇을 어떻게 바꿀지**만 적는다.

## 0. 해결하려는 문제 하나

**지금 코드는 "확정 실패" 와 "응답 불명" 을 같은 상태로 다룬다.** 거래소 접수 후 응답이 오지 않으면
주문은 `FAILED` 로 기록되고 `exchangeOrderId` 는 `null` 이다. 그러면

- `pollActiveOrders()` 는 활성 주문만 보므로 **그 주문을 더 쫓지 않는다**,
- 정지는 `FAILED` 매수를 보고 **KRW 를 복원하고 슬롯을 해제한다** — 실제로는 쓰인 자금일 수 있다.

🔴 **이 문서가 바꾸려는 것은 그 한 가지다.** 중복 복원·버전 충돌은 이미 따로 고쳤고(§4.6), 그것들이
이 문제를 해결하지 않는다.

### 전제 — 업비트 식별자 규칙 (확인됨)

`POST /v1/orders` 의 `identifier`(≤64자, 계정 전체 고유, **재사용 불가**)로 제출하고,
`GET`/`DELETE /v1/order?identifier=...` 로 **응답 UUID 없이도** 조회·취소할 수 있다.

🔴 **멱등 API 가 아니다.** 같은 키로 재요청하면 기존 응답을 준다는 보장이 없다. 🔴 **조회 가능 보존
기간**과 **"조회 실패 = 미접수"** 보장도 문서에 없다. 그래서 **조회 실패는 "없다" 가 아니라 "모른다"**
로 다룬다.

## 1. 상태 전이표

현재 `order.state` 는 `PENDING · SUBMITTED · PARTIAL_FILLED · FILLED · CANCELLED · FAILED` 다.
여기에 **두 상태를 추가**한다 — 기존 값의 의미는 바꾸지 않는다(기존 데이터 해석을 보존한다).

| 상태 | 뜻 | 활성? | 자금·슬롯 |
|---|---|---|---|
| `INTENT_READY` | **신규** — 의도가 커밋됐고 **제출 작업자가 아직 가져가지 않았다.** 외부로 나간 적이 없음이 확정된다 | 예 | **예약** |
| `SUBMITTING` | **신규** — 제출 작업자가 **가져갔다**(claim). 외부 호출이 시작됐거나 시작될 수 있으므로 **접수 가능성이 있다** | 예 | 예약 유지 |
| `SUBMITTED` | 거래소가 접수했음을 **응답으로 확인**했다 | 예 | 예약 유지 |
| `UNKNOWN` | **신규** — 보냈으나 **결과를 모른다**(시간 초과·연결 끊김·응답 파싱 실패) | 예 | **예약 유지** |
| `PARTIAL_FILLED` | 일부 체결을 확인했다 | 예 | 체결분 확정 + 잔량 예약 유지 |
| `FILLED` | 전량 체결을 확인했다 | 아니오 | 확정 |
| `CANCELLED` | **거래소 응답으로** 취소를 확인했다 | 아니오 | 해제 |
| `FAILED` | **나간 돈이 없음이 확정**됐다. 🔴 근거는 `failure_code` 로 구분한다(V86) — 거래소의 명시적 거절(`EXCHANGE_REJECTED`)과 우리의 미제출 철회(`WITHDRAWN_*`)는 근거가 다르다 | 아니오 | 해제 |

🔴 **`FAILED` 의 의미를 좁힌다**: "보냈는데 결과를 모른다" 는 더 이상 `FAILED` 가 아니라 `UNKNOWN` 이다.
해제가 일어나는 두 상태(`CANCELLED`·`FAILED`)는 **나간 돈이 없다는 근거가 있을 때만** 쓴다.

🔴 **2026-10-12 정정 (V86) — `FAILED` 에는 근거가 두 종류다.** 초판은 `FAILED` = "거래소가 거절했음을 응답으로
확인" 이라고 적었지만, 구현은 **claim 전 철회**에도 `FAILED` 를 썼다. 둘 다 "나간 돈이 없다" 는 점은 같아
복원 경로를 공유하지만 **근거가 다르다** — 거절은 **거래소의 진술**이고, 철회는 **우리의 불변식**(claim 이
없었으므로 외부 호출이 없었다)이다. 상태를 쪼개면 `FAILED` 를 "체결 없이 종결" 로 읽는 복원 경로 12곳 이상을
모두 바꿔야 하므로 **사유 코드**(`order.failure_code`)로 구분한다:

| `failure_code` | 근거 | 주체 |
|---|---|---|
| `EXCHANGE_REJECTED` | 거래소의 명시적 거절 응답 | 거래소 — 🔴 **현재 기록되지 않는다.** 제출 중 예외는 HTTP 4xx 를 포함해 전부 `UNKNOWN` 이다(구분하지 않고 더 위험한 쪽으로 가정). 그래서 지금의 `FAILED` 가 거래소 거절을 주장하는 일은 없다 |
| `WITHDRAWN_STOPPED` | claim 직전 세션 잠금 안에서 정지를 확인 | 작업 자신 |
| `WITHDRAWN_OWNER_LOST` | 의도를 만든 프로세스가 지금 프로세스가 아니다 | 복구 |
| `WITHDRAWN_DISPATCH_LOST` | 같은 프로세스지만 그 의도를 맡은 작업이 없다(실행기 거절·claim 전 예외) | 작업 자신 또는 복구 |
| `RISK_REJECTED` · `CLIENT_UNAVAILABLE` | 의도 단계 거절(외부 호출 전) | 작업 자신 |
| `NULL` | V86 이전 행 — 의미를 재해석하지 않는다 | — |

### 전이와 그 근거

| 전이 | 근거 |
|---|---|
| (없음) → `INTENT` | 제출 결정. `identifier` 를 만들어 **외부 호출 전에** 함께 커밋한다 |
| `INTENT` → `SUBMITTED` | 주문 생성 API 가 **성공 응답**을 돌려줬다(uuid 확보) |
| `INTENT` → `UNKNOWN` | 호출이 **시간 초과·연결 오류·응답 해석 실패**로 끝났다 |
| `INTENT` → `FAILED` | 거래소가 **명시적 거절**을 응답했다(검증 오류 등). 🔴 네트워크 오류는 여기 오지 않는다 |
| `UNKNOWN` → `SUBMITTED`/`PARTIAL_FILLED`/`FILLED`/`CANCELLED` | `GET /v1/order?identifier=` **조회 결과** |
| `UNKNOWN` → `UNKNOWN` | **조회 실패 또는 미발견.** 🔴 머문다. 미접수로 단정하지 않는다 |
| `SUBMITTED` → `PARTIAL_FILLED`/`FILLED`/`CANCELLED` | 폴링·조회 결과 (현행과 동일) |
| `INTENT_READY` → `SUBMITTING` | 제출 작업자가 **claim 을 커밋**했다. 🔴 이 커밋이 "외부로 나갔을 수 있다" 의 경계다 |
| `INTENT_READY` → (철회) | 아직 나간 적이 없으므로 철회가 **안전**하다. 🔴 그러나 안전과 **정당**은 다르다 — §1.2 의 근거가 있을 때만 철회한다 |
| `SUBMITTING` → `UNKNOWN` | 호출이 시간 초과·연결 오류로 끝났다. **또는 재기동 후 `SUBMITTING` 으로 남아 있었다** — 호출 직전에 죽었더라도 **보수적으로 불명 처리한다** |
| 🔴 `UNKNOWN` → `FAILED` | **자동 전이도, 사람에 의한 전이도 두지 않는다.** §1.1 을 본다 |

🔴 **`INTENT` 를 둘로 쪼갠 이유**: 초판에는 `INTENT` 하나만 두고 "재기동 후 조회해서 없으면 같은
`identifier` 로 재제출" 이라고 적었다. **그것은 "미발견은 미접수의 증거가 아니다" 와 정면으로
충돌한다** — 삭제했다. 대신 **아직 가져가지 않은 의도**(`INTENT_READY`)와 **제출 시도가 시작돼 접수
가능성이 있는 의도**(`SUBMITTING`)를 영속 상태로 구분한다. 전자만 안전하게 제출·철회할 수 있고,
후자는 **호출 직전에 죽었더라도 보수적으로 불명 처리한다.**

### 1.1 🔴 사람의 판단도 "거래소 거절" 의 증거가 아니다

장기 `UNKNOWN` 을 수동 처리할 때 **`FAILED` 로 바꾸지 않는다.** `FAILED` 는 이 설계에서 "거래소가
거절했음을 응답으로 확인" 이라는 뜻이고, 사람의 판단은 그 증거가 아니다. 대신 **수동 조정을 별도로
보존한다**: 조정의 **근거 · 금액 · 책임자 · 조정 시각**, 그리고 **그 주문이 여전히 미해결이라는
위험**을 함께 남긴다. 주문 상태는 `UNKNOWN` 으로 두고, 회계만 수동 조정으로 맞춘다.

🔴 **기존 `FAILED` 데이터를 새 의미로 일괄 해석하지 않는다.** 과거의 `FAILED` 에는 **응답 불명이 섞여
있다**(지금까지 시간 초과를 `FAILED` 로 기록해 왔다). 마이그레이션에서 과거 행을 "확정 실패" 로 읽으면
그 자체가 오판이 된다 — 새 의미는 **전이 시점 이후**에만 적용하고, 과거 행은 **의미 불명으로 표시**하거나
적어도 구분 가능하게 남긴다.

### 1.2 🔴 철회의 정당성 — 경합의 해결과 별개다 (V86, 2026-10-12)

V84 보완은 철회를 claim 과 **같은 조건부 전환**으로 바꿔 **승자를 하나로** 만들었다. 그것은 경합을 해결할 뿐
**철회가 옳은지는 정하지 않는다.** 당시 규칙은 "60초가 지난 `INTENT_READY` 는 철회" 였으므로, 실행기 큐가
밀려 정상 작업이 60초 넘게 claim 하지 못하면 **철회가 먼저 성립해 정상 주문이 취소됐다** — 시간 기반 철회다.

**규칙: claim 할 작업이 존재하지 않음이 확정될 때만 철회한다.** 의도를 claim 할 수 있는 것은 그 의도를
만든 프로세스의 작업뿐이므로, 생존은 두 단계로 판정한다.

| 판정 | 근거 | 결과 |
|---|---|---|
| 소유자(`intent_owner`)가 지금 프로세스가 아니다 | 기동마다 새 식별자를 쓴다. 작업 큐는 프로세스와 함께 사라졌다 | 철회 — `WITHDRAWN_OWNER_LOST` |
| 소유자는 지금 프로세스, 그 의도가 **소유권 등록부**에 없다 | 등록부는 의도 커밋 **전에** 넣고 claim 시도가 끝나면 뺀다 | 철회 — `WITHDRAWN_DISPATCH_LOST` |
| 소유자는 지금 프로세스, 등록부에 있다 | 작업이 살아 있다(큐 대기 포함) | 🔴 **철회하지 않는다 — 나이와 무관하다.** 60초를 넘기면 경보만 남긴다 |
| 실행기가 작업을 거절했다 | 호출자가 거절을 받았다 | 호출자가 즉시 철회 — `WITHDRAWN_DISPATCH_LOST` |
| claim 이 예외로 끝났다 | 작업 자신이 안다 | 작업 자신이 철회 시도. 실패하면 등록부에서 빠졌으므로 복구가 이어받는다 |
| claim 직전 정지를 봤다 | 세션 잠금 안에서 읽은 상태 | 작업 자신이 철회 — `WITHDRAWN_STOPPED` |

모든 철회는 여전히 **조건부 전환**이다 — 정당성은 위 판정이, 경합은 조건부 전환이 맡는다.

🔴 **전제: 애플리케이션 인스턴스는 하나다.** 소유자가 지금 프로세스가 아니면 죽은 것으로 본다. 여러 인스턴스를
띄우면 이 판정이 틀린다(살아 있는 다른 인스턴스의 의도를 철회한다) — 그때는 소유자 생존 신호가 필요하다.
폴러·스케줄러 전체가 이미 단일 인스턴스를 전제한다.

🔴 **배포 선행 조건 (2026-10-12 추가)** — "`intent_owner` 가 다르다 = 소유자가 종료됐다" 는 **재배포 중에도**
단일 인스턴스가 유지될 때만 참이다. 새 인스턴스가 옛 인스턴스보다 먼저 뜨는 겹침 배포(블루-그린·롤링·`--scale`)
에서는 새 쪽 폴러가 옛 쪽의 살아 있는 의도를 `WITHDRAWN_OWNER_LOST` 로 철회한다. 조건부 전환이므로 **같은 의도가
두 번 나가지는 않지만**, 정상 주문이 취소되고 그 순간 두 폴러·스케줄러가 함께 돈다. 그러므로:

| 조건 | 내용 |
|---|---|
| 정지 후 기동 | 옛 인스턴스가 **완전히 종료된 뒤** 새 인스턴스를 띄운다(실행기 종료 대기 30초 포함) |
| 겹침 배포 금지 | 블루-그린·롤링·복제본 2 이상을 쓰지 않는다. 쓰려면 먼저 소유자 생존 신호를 구현한다 |
| 확인 방법 | 배포 절차서에 "옛 컨테이너 종료 확인 → 새 컨테이너 기동" 순서를 명시하고, 기동 로그의 `inst-…` 가 하나뿐인지 본다 |

이 조건이 문서로만 남아 있고 코드로 강제되지 않으므로 **배포 차단 항목**이다.

🔴 **철회가 이기면**: claim 은 0행을 받아 외부 호출로 가지 않고(호출자는 밀린 사유를 구분해 기록한다),
`FAILED`+size=0 포지션을 고아 매수 정리가 닫으며 **`reserved_krw` 만큼만** 복원한다. 시험이 복원액(7,000 → 10,000)과
재실행 시 이중 복원 없음을 확인한다.

## 2. 영속화·복구

```
① INTENT 커밋 (identifier + 주문 의도 + 자금·슬롯 예약)   ← 외부 호출 전
② 외부 호출 (POST /v1/orders, identifier 포함)
③ 결과 기록 (SUBMITTED | UNKNOWN | FAILED)
```

**어느 지점에서 프로세스가 죽어도 복구된다**:

| 죽은 지점 | 재기동 후 상태 | 복구 방법 |
|---|---|---|
| ① 전 | 아무것도 없다 | 복구 불필요 |
| ① 후, claim 전 | `INTENT_READY` | **외부로 나간 적이 없음이 확정된다.** 그대로 제출하거나, 정지 등으로 필요 없어졌으면 **철회하고 예약을 해제**한다. 🔴 조회에 의존하지 않는다 |
| claim 후 ② 전 (호출 직전) | `SUBMITTING` | 🔴 **보수적으로 `UNKNOWN` 으로 넘긴다.** 실제로 나가지 않았을 수 있지만 **구분할 근거가 없으므로 접수 가능성이 있다고 다룬다** — 자금·슬롯을 유지하고 `identifier` 로 조회를 시작한다. **자동 재제출하지 않는다** |
| ② 중 (호출 도중) | `SUBMITTING` | 위와 같다 |
| ③ 전 | `SUBMITTING` | 위와 같다 |
| ③ 후 | `SUBMITTED`/`UNKNOWN`/`FAILED` | 활성 상태면 추적 경로가 잇는다 |

🔴 **`INTENT_READY`·`SUBMITTING`·`UNKNOWN` 은 모두 활성으로 취급한다**(`ACTIVE_STATES` 포함). 🔴 단
**활성 상태를 추가하는 것만으로 복구가 완성되지 않는다** — 아래 제출 승인(§4)과 정산(§5) 규칙이
먼저다. 상태만 늘리고 그 규칙이 없으면 추적 대상만 늘어난다.

🔴 **현재 구조와의 차이**: 지금은 자금 차감이 **주문 제출 뒤**에 오고, 슬롯은 `size > 0` 만 세므로

### 3.1 🔴 예약을 추가하는 것만으로 선행 조건 3번이 닫히지 않는다

**한도 확인 · 자금·슬롯 예약 · 의도 저장이 하나의 원자적 작업이어야 한다.** 셋이 갈라지면 지금과 같은
TOCTOU 가 이름만 바꿔 돌아온다 — 각자는 한도 안인데 **합계가 상한을 넘는다**.

#### 3.2 🔴 두 한도는 별개다 (2026-10-12)

V85 의 상한은 **계좌 잔고** 하나였다. 그러나 계좌 잔고와 **사전 등록한 공유 풀 한도**는 다른 것을 묻는다.
계좌에 다른 자금이 있어도 단계별 자본·포지션당 금액·동시 보유를 넘으면 안 되고, 등록 한도 안이어도 계좌에
없는 돈을 승인하면 안 된다. **같은 계좌 잠금 아래에서 둘을 모두 보고, 더 좁은 쪽이 승인을 정한다.**

| | 등록 풀 한도 (`CapitalPoolLimits`) | 계좌 여력 |
|---|---|---|
| 묻는 것 | 이 단계에서 쓰기로 **등록한** 돈을 넘는가 | 거래소에 **실제로 있는** 돈 중 아직 묶이지 않은 몫을 넘는가 |
| 항목 | 총 자본 상한 · 포지션당 · 동시 보유 | 총잔고 스냅숏 |
| 노출의 기준 | 열린 실자금 포지션(LIVE·DYNAMIC)의 **배정액**(`investedKrw`) 합. 평가액이 아니다 — 가격이 움직여도 한도가 움직이지 않는다 | — |
| 슬롯의 기준 | 열린 실자금 포지션 수. 🔴 **체결 전 포지션(size=0)도 센다** — 그것이 예약된 슬롯이다 | — |
| 미설정 시 | 🔴 **거절**. 기본값을 두지 않는다 — "등록하지 않았는데 한도가 걸린 줄 아는" 상태를 막는다 | 🔴 **거절**(스냅숏 없음·15분 초과) — 종전에는 0 이면 검사를 **건너뛰었다** |

**계좌 여력의 정의** — 이것을 명시하지 않으면 이중 차감이나 과대 승인이 난다:

```
스냅숏 = 총잔고 = 가용(balance) + 주문 잠금(locked)          ← 주문 가능 잔고가 아니다
묶인 돈 = 열린 매수 주문의 약정액 합                          ← 스냅숏 안에 있다
        + 스냅숏 이후 로컬에서 종결된 매수의 약정액 합         ← 스냅숏이 체결 전 값이므로 아직 안에 있다
여력   = 스냅숏 − 묶인 돈
```

- **총잔고를 쓰는 이유**: 열린 주문의 돈은 제출 전이면 가용에, 접수 후 미체결이면 잠금에 있다. 총잔고는 그 돈을
  단계와 무관하게 **정확히 한 번** 담고 있으므로 열린 주문을 한 번 빼면 맞다. 주문 가능 잔고를 쓰면 접수된 주문의
  돈이 이미 잠금으로 빠져 있어 **이중 차감**이 된다.
- **스냅숏은 기존 예약이 차감되지 않은 값이다** — 거래소는 우리 예약을 모른다. 반대로 **세션 가용 KRW 는 예약이
  이미 차감된 값**이다. 둘을 섞지 않는다: 매수는 "스냅숏 − 묶인 돈" 을, 배정(생성·재시작)은 "스냅숏 − 묶인 돈 −
  다른 활성 세션의 가용 KRW" 를 본다.
- **남는 오차는 한 방향이다**: 거래소에서 체결됐는데 로컬에 아직 반영되지 않은 주문은 스냅숏에서 빠졌는데 묶인
  돈에도 들어간다 → **과소 승인**. 과대 승인을 만드는 경우(스냅숏 이후 로컬 종결)는 별도 항으로 막았다.
- `reserved_krw` 가 없는 열린 매수(V85 이전, 예약 경계를 지나지 않는 DYNAMIC)도 약정액으로 센다.

🔴 **실자금 동적 세션의 생성·재시작에는 종전에 자본 검사가 전혀 없었다**(LIVE 에만 있었다). 이제 LIVE·DYNAMIC
의 생성·재시작이 모두 이 잠금과 규칙을 지난다.

🟢 **DYNAMIC 매수도 같은 예약 경계를 지난다 (2026-10-12 2차).** 종전에는 생성·재시작만 검사하고 실제 매수가
경계를 우회했다 — 전체 한도가 강제되지 않았다. 이제 틱 트랜잭션 안에서 계좌 잠금 → 등록 풀 → 계좌 여력 → 세션
자금 → 슬롯 → 의도를 함께 쓰고, 제출은 커밋 후다. 틱이 롤백되면 전부 사라지고 제출은 0회다(종전 계약 유지).
- 차감이 같은 트랜잭션이 되면서 **REQUIRES_NEW 차감과 롤백 보상이 매수 경로에서 빠졌다**
  (`registerBuyDeductionCompensation` 은 남아 있으나 매수 경로가 부르지 않는다).
- 틱이 들고 있는 세션 엔티티는 같은 틱의 워치리스트 기록(별도 트랜잭션) 때문에 낡았을 수 있다 — 낡은 채 쓰면
  낙관적 잠금 충돌로 틱이 실패했다(측정). 예약과 상태 전환은 **행을 잠근 채 최신으로 다시 읽고** 쓴다.
- 종전 불변식 "바깥 연결은 세션 행을 쓰지 않는다" 를 **"바깥이 행을 잠근 뒤 같은 스레드의 별도 연결이 그 행을
  쓰지 않는다"** 로 바꿔 고정했다(자기 대기의 실제 조건).
- 시험: DYNAMIC 슬롯 한도·포지션당 상한 거절 시 슬롯·차감·의도가 남지 않음, **LIVE 와 DYNAMIC 이 마지막 슬롯
  하나를 동시에 다투면 하나만 승인**(실측 `LIVE:승인, DYNAMIC:SLOT_LIMIT`).
- ~~🔴 남는 것: DYNAMIC 에는 LIVE 의 정지 가드·회계 미반영 가드·원자적 체결 회계가 없다.~~ → **§5.10 에서 통합했다
  (2026-10-13).**

#### 3.4 스냅숏과 로컬 약정의 시간 경계 — 시험 결과 (2026-10-12, `SnapshotBoundaryRaceTest`)

식만으로는 이중 차감·과대 승인이 모두 막혔다고 확정할 수 없어 경계마다 돌렸다. 🔴 **둘이 실제로 깨져 있었다.**

| 경합 | 측정(수정 전) | 조치 | 결과 |
|---|---|---|---|
| ① 거래소엔 체결 반영, 로컬은 열림 | 실제 여유 7,000 / 승인 가능 4,000 | — | **과소 승인만**(같은 3,000 을 두 번 뺀다). 다음 스냅숏·로컬 종결로 풀린다 |
| ② 스냅숏 조회 중 체결·취소 + 로컬 종결 | 🔴 **실제 여유 7,000 에 7,001 승인 — 과대 승인** | 스냅숏 기준 시각을 **응답 시각 → 조회 시작 시각**으로 | 7,001 거절·7,000 승인. 응답이 체결 후 잔고면 과소 승인만(②-b) |
| ③ 부분 체결 후 취소 | 🔴 **잔액 7,118.53 — 60원 과복원**(종전 경로의 원금 차이 60 + 정산의 미사용 58.53) | `cancel`+체결 응답도 원자적 회계 경로로. 생성 응답이 이미 종결이어도 거기서 반영하지 않는다(③-c) | 7,058.53, 세 번 조회해도 동일. 체결 없는 취소는 예약 전액 1회 복원 |
| ④ 스냅숏 교체 순간 | 잔고·시각을 따로 읽었다(현재 읽기 순서로는 과소 쪽이었으나 우연에 기댔다) | **잔고·시각을 불변 객체 하나로**, 늦게 도착한 옛 응답은 새 스냅숏을 덮지 않는다 | 20만 회 교체 중 섞인 짝 0, 옛 응답 거부 |

🔴 ②의 원인: 거래소가 잔고를 계산한 시점은 조회 시작과 응답 사이 어딘가이고 우리는 모른다. 응답 시각을 기준으로
쓰면 그 사이 로컬에서 종결된 체결이 "스냅숏 이전" 으로 분류돼 약정에서 빠지는데, 잔고는 체결 전 값일 수 있다.
시작 시각을 쓰면 그 체결은 한 번 더 빠질 뿐이다. **이 수정은 위 표에서 시험한 경합에서 과대 승인을 막았다는
범위로만 기록한다** — 정확해진 것은 아니다.

🔴 **전역 보장이 아니다 (2026-10-13 정정).** 5차 보고의 "오차를 과소 승인 한 방향으로 묶는다" 는 **시험한 네 경합(①
~④)과 정밀도 경계**에 대한 말이다. 시험하지 않은 경로 — 예: 로컬 약정 합계 질의의 범위 밖에 있는 주문(세션 없는
수동 주문, 매도 대금이 잔고에 반영되는 시점), 조회 중 시계 역행, 다른 프로세스의 동시 주문 — 에서 과대 승인이
나지 않는다는 근거는 아직 없다.

🔴 **같은 경계의 두 번째 결함 — 시각 정밀도** (반복 전체 실행에서 발견): DB 시각은 **마이크로초**, 메모리의 기준
시각은 **나노초**였다. 기준 시각 직후 같은 마이크로초 안에 종결된 체결이 저장 후 `.733551` 로, 기준 `.7335514` 보다
**앞으로** 보여 엄격 비교(`>`)에서 빠졌다 — 1µs 미만의 과대 승인 창이다. 기준 시각을 마이크로초로 **내림**하고
비교를 **포함(≥)**으로 바꿨다. 기준 뒤의 어떤 사건도 저장 시각이 내림한 기준 이상이므로 빠지지 않는다(같은
마이크로초의 앞선 사건이 들어오는 것은 과소 승인 쪽이다).

#### 3.5 🔴 요청 한도 제한기 정정 (2026-10-12)

3차 보고에서 `RateLimiterEmergencyStopTest` 의 실패를 "부하로 리필이 끼어든 정상 동작" 으로 보고 상한을 경과 시간만큼
넓혔다. **틀렸다.** 제한기는 문서에 "슬라이딩 윈도우" 라고 적혀 있었지만 실제로는 **생성 시점 기준 1초 고정 주기
리필**이라, 버스트가 리필 시각을 걸치면 **1초 안에 최대 14건**이 나간다(내부 한도 7/초의 두 배). 전체 실행에서 999ms 에
8건으로 다시 드러났다. 시험이 아니라 구현이 한도를 어긴 것이다 — 최근 발급 시각 7개를 기억하는 **슬라이딩 윈도우로
교체**하고, 시험은 "첫 1초 창에 돌아온 발급 ≤ 7"(반환 시각 ≥ 발급 시각이므로 거짓 실패가 없다)과 "8번째 발급은 첫
발급으로부터 1초 뒤" 로 고정했다. 🔴 한도 초과의 결과가 가볍지 않다 — 주문 POST 가 429 로 거절돼도 현재 제출 경로는
4xx 를 구분하지 않으므로 `UNKNOWN` 이 되고, 그 세션의 신규 매수가 사람이 종결할 때까지 막힌다.

🔴 **한도 수치 정정 (2026-10-13)** — 5차 보고와 코드 주석은 "업비트 주문 한도 초당 8건" 이라고 적었는데 **현재 공식
문서와 맞지 않는다.** 공식 그룹별 한도(초당, 계정 단위): `order`(주문 생성·취소 후 재주문) **12**, `order-test`(주문
테스트) **8**, `default`(주문 조회·취소·잔고 등) **30**, `order-cancel-all` 2초당 1. 같은 그룹의 API 는 한도를 함께
차감하고, 응답 헤더 `Remaining-Req: group=…; min=…; sec=…` 의 `sec` 가 **그 그룹의** 남은 요청 수다(`min` 은
폐기 예정). 문서는 공지나 장애 시 한도가 낮아질 수 있다고 적는다.

| 구분 | 값 | 비고 |
|---|---|---|
| 거래소 `order` 그룹 한도 | 12/초 | 주문 생성 |
| 거래소 `default` 그룹 한도 | 30/초 | 주문 조회·취소·식별자 조회 |

| `Remaining-Req` | **읽지 않는다** | 거래소가 한도를 낮춰도 제한기는 모른다 |

미착수다.

🔴 **운영 적용 조건**: 운영 설정에 `trading.capital-pool.*` 이 없으면 실자금 진입·배정이 **모두 거절된다**.
배포 전에 단계 값을 등록해야 한다(운영 설정은 이번 작업에서 바꾸지 않았다).

| 요구 | 내용 |
|---|---|
| 원자성 | `공유 풀 한도 확인 → 예약 → 의도 저장` 을 **한 트랜잭션**에서, **직렬화가 보장되는 방식**으로 수행한다(공유 풀 행 잠금 또는 예약 합계에 대한 제약) |
| 시험 | 🔴 **서로 다른 세션의 동시 요청에서도 합계가 상한을 넘지 않아야 한다.** 세션 N개가 동시에 진입을 시도할 때 예약 합계 ≤ 상한, 초과 승인 0건 |
| 판정 | **이 시험을 통과하기 전까지 선행 조건 3번은 미완료다.** 예약 코드를 넣은 것만으로는 닫히지 않는다 |

## 4. 정지와의 관계

**신규 진입 차단과 기존 주문 추적은 분리한다.**

🔴 **먼저 짚을 문제 — 외부 호출을 트랜잭션 밖으로 옮기면 기존 정지 가드가 그대로 성립하지 않는다.**
지금 구현된 가드는 `submitOrder` 의 트랜잭션 안에서 세션 행을 잠근 채 거래소를 호출하므로 "정지 커밋
후 제출 0회" 가 성립한다(§4.6 ③-1). 그런데 §5 는 **외부 호출을 트랜잭션 밖으로** 빼라고 한다(커넥션·
잠금 점유를 피하려고). 그러면 **의도 커밋 → 잠금 해제 → 정지 완료 → 외부 제출** 이 가능해진다.
**둘을 동시에 만족시키는 순서를 다시 설계해야 한다.**

🟢 **2026-10-12 구현됨 (V84).** 아래 순서를 그대로 구현했고, 그 대가로 **정지 보장의 범위가 좁아졌다**:

```
종전: 정지 커밋 후 **제출** 0회
이후: 정지 커밋 후 **신규 claim** 0회 + 이미 claim 된 주문의 추적·정리 지속
```

🔴 **바꾼 이유는 추적 불가가 더 큰 위험이기 때문이다.** 제출을 막지 못한 주문은 식별자로 추적되지만,
추적 단서가 없는 주문은 영구히 확인할 수 없다. 🔴 **이것은 개선이 아니라 교환이다** — 좁아진 쪽을
그대로 적고, 정지는 미해결 주문이 남은 세션을 **정리 완료로 표시하지 않는다**(텔레그램 통보).

🔴 **구현 중 시험이 잡은 결함 둘**:
1. `UNKNOWN` 을 활성 상태에 넣자 정지가 그 주문을 **취소하려 들었다** — 현행 취소 경로(`cancelOrder`)는
   **거래소 주문번호(UUID)로만** 취소하므로 UUID 가 없는 주문에 "취소 불가 상태" 예외를 던지고, 그 예외가
   `@Transactional` 안에서 났으므로 **정지 트랜잭션 전체가 rollback-only** 가 되어
   `UnexpectedRollbackException` 으로 **정지가 깨졌다.**
   → 🔴 **현재 처리: `cancelSessionActiveOrders` 가 `INTENT_READY`·`SUBMITTING`·`UNKNOWN` 에 대해 현행 취소
   경로를 건너뛰고, 식별자 추적·후속 정리로 넘긴다.** (2026-10-12 정정 — 초판은 "거래소 주문번호가 없어 취소
   자체가 불가능한 상태" 라고 적었다. **틀렸다**: 업비트는 `DELETE /v1/order?identifier=` 로 UUID 없이 취소할 수
   있다(§0 전제). 불가능한 것은 **현행 코드의 UUID 취소 경로**이고, 식별자 취소 경로는 **미구현**이다.)
   🔴 정지 시험(`STOPPED` + 미해결 1건 + 잔액 미복원)은 **정지가 깨지지 않고 예약이 유지된다**는 근거다.
   **늦은 체결이 들어왔을 때 그 포지션을 누가 관리·청산해 정리 완료에 이르는지는 입증하지 않았다**(아래 표의
   "늦은 체결"·"잔여 포지션" 행, 미결정).
2. 5초 폴러가 **방금 만든 `INTENT_READY` 를 철회**해 진행 중인 제출을 가로챘다(claim 이 0행을 받아
   주문이 조용히 사라진다). → V84 는 철회에 **유예 60초**를 뒀다. 🔴 V86 에서 **시간 기준을 버렸다** — 유예는
   경합을 줄일 뿐 철회의 근거가 아니다. 이제 **소유 작업이 존재하지 않음이 확정될 때만** 철회한다(§1.2).

**제안하는 순서** (🟢 V84 로 구현됨):

| 단계 | 경계 | 내용 |
|---|---|---|
| A | 트랜잭션 + 세션 행 잠금 | 한도 확인 → 예약 → `INTENT_READY` 커밋. **세션이 `RUNNING` 이 아니면 여기서 거절**한다 |
| B | 트랜잭션 + 세션 행 잠금 | `INTENT_READY` → `SUBMITTING` **claim 커밋**(조건부 UPDATE `WHERE state='INTENT_READY'`). 🔴 **세션 상태를 다시 확인한다** — A 와 B 사이에 정지가 들어왔으면 여기서 멈추고 **철회**한다(아직 나간 적이 없다). 🔴 **이 전환에 성공한 작업만 C 로 간다** — §4.1 |
| C | **트랜잭션 밖** | 거래소 호출. 결과를 D 에서 기록한다 |
| D | 트랜잭션 | `SUBMITTED`/`UNKNOWN`/`FAILED` 기록 + 정산 |

#### 4.1 🔴 claim 을 얻은 작업자만 최초 제출한다

**`SUBMITTING` 을 읽었다는 이유로 제출하면 안 된다.** 그러면 재기동·복구 작업자가 그 상태를 보고
**재제출**할 수 있다. 규칙은 이렇다:

| 규칙 | 내용 |
|---|---|
| 최초 제출 권한 | `INTENT_READY` → `SUBMITTING` 조건부 전환이 **1행을 돌려받고 그 트랜잭션이 커밋에 성공한** 작업만 외부로 **한 번** 제출한다 |
| 🔴 UPDATE 1행만으로는 부족하다 | 조건부 UPDATE 가 1행을 돌려줘도 **그 트랜잭션은 롤백될 수 있다**(이후 단계 실패, 낙관적 잠금, 커밋 자체 실패). 그때 제출하면 **아무도 claim 하지 않은 주문이 외부로 나간다.** 그래서 **외부 호출은 커밋 이후에** 한다 — `TransactionSynchronization#afterCommit` 또는 커밋 후 별도 단계 |
| 커밋 실패 시 | **제출 0회.** 예약도 롤백되므로 주문은 `INTENT_READY` 로 남거나 사라진다 |
| 재기동·복구 | `SUBMITTING` 을 발견한 복구 작업은 🔴 **조회만 한다.** 제출하지 않는다 — 전환에 성공한 적이 없기 때문이다 |
| 구분 근거 | "전환 성공" 은 **그 트랜잭션의 UPDATE 결과(1행)** 이고, 상태를 읽은 것과는 다르다. 상태는 재기동 후에도 보이지만 **전환 성공은 한 번만 일어난다** |

#### 4.2 🔴 HTTP 클라이언트의 주문 POST 자동 재시도 (확인 결과)

클라이언트가 조용히 재시도하면 위 "한 번만 제출" 이 무너진다. 확인했다:

- `UpbitOrderClient` 는 `HttpClient.newBuilder().connectTimeout(10s).build()` — **애플리케이션 수준의
  재시도 계층이 없다.** 저장소 전체에 `@Retryable`·`RetryTemplate`·spring-retry 사용도 없다.
- 🔴 **`connectTimeout(10s)` 은 응답 대기 전체의 제한이 아니다** — 연결 수립까지의 제한이다. 응답
  대기는 **요청별 타임아웃**이 담당하고, 주문 POST 를 포함한 모든 요청에 `.timeout(Duration.ofSeconds(15))`
  가 걸려 있다(`UpbitOrderClient` 전 메서드). 즉 **접수 후 15초 안에 응답이 없으면 불명이 된다.**
- JDK `HttpClient` 는 연결 수준 실패에서 **멱등 메서드만** 재시도하며, POST 까지 재시도하게 만드는
  `jdk.httpclient.enableAllMethodRetry` 는 **기본값이 꺼짐**이다. 운영 `JAVA_OPTS`
  (`docker-compose.prod.yml`)에도 그 속성이 **없다**.

🔴 **그러므로 현재 설정에서 주문 POST 는 자동 재시도되지 않는다.** 단 이것은 **설정에 달린 사실**이므로
**명세로 고정한다**: `jdk.httpclient.enableAllMethodRetry` 를 켜지 않는다. 프록시·게이트웨이를 앞에
두는 경우에도 그 계층의 재시도를 확인해야 한다.

🔴 **그러나 재시도 설정 확인만으로 "모든 장애 상황에서 전송 중복이 없다" 고 보장하지 않는다.** 재시도가
없어도 중복은 다른 데서 생길 수 있다 — 네트워크 중간 계층의 패킷 재전송과 서버 측 중복 처리, 타임아웃
후 사람·복구 작업의 재호출, 같은 의도에 대해 두 작업자가 claim 을 다투는 경우. **중복 방지의 근거는
재시도 설정이 아니라 §4.1 의 claim 규칙과 `identifier` 의 계정 전체 고유성이다.**

**정지의 동작**: 세션을 `STOPPED` 로 커밋하면 **A·B 가 더는 승인되지 않는다**(둘 다 세션 잠금 안에서
상태를 본다). 🔴 **그러나 이미 `SUBMITTING` 인 주문은 C 로 나갈 수 있다** — 그것을 막을 방법은 없다
(이미 claim 됐고 접수 가능성이 있다). 그래서 **정지는 "신규 승인 차단" 까지만 보장하고, 미해결 주문이
남아 있으면 정리 완료로 표시하지 않는다.**

| 정지 시 | 동작 |
|---|---|
| 신규 진입 | **차단** — A·B 가 세션 잠금 안에서 상태를 확인한다 |
| 🔴 이미 승인된 제출(`SUBMITTING`) | **진행을 막지 않는다.** 그 대신 **세션을 "정리 미완료" 로 표시**하고, 그 주문이 해결될 때까지 **정리 완료로 표시하지 않는다** |
| 매도·청산 | **절대 막지 않는다** (이미 반영) |
| 활성 주문 | UUID 가 있는 주문은 취소를 **시도**하고, 결과가 불명이면 `UNKNOWN` 으로 둔다. 🔴 **취소 요청을 보냈다는 이유로 종결하지 않는다**(이미 반영). 🔴 UUID 가 없는 `INTENT_READY`·`SUBMITTING`·`UNKNOWN` 은 **현행 취소 경로를 건너뛰고 식별자 추적·후속 정리로 넘긴다** — 식별자 취소(`DELETE ?identifier=`)는 가능하지만 미구현 |
| `UNKNOWN` 주문 | **추적을 계속한다.** 세션이 `STOPPED` 여도 폴러는 세션 상태를 보지 않으므로 이어진다(§4.6-5 로 확인) |
| 늦은 체결 | 포지션이 생기면 **관리 주체가 필요하다** → §6 열린 질문 |
| 잔여 포지션 | 🔴 **자동 청산할지 별도 정리 상태로 둘지 아직 정하지 않았다.** 처리가 끝나기 전에 "정리 완료" 로 표시하지 않는다 |
| 🔴 정리 완료의 조건 | 세션의 **모든 주문이 종결**(`FILLED`/`CANCELLED`/`FAILED`)이고 **잔여 포지션의 관리 주체가 정해졌을 때**만. `INTENT_READY`·`SUBMITTING`·`UNKNOWN` 이 하나라도 남아 있으면 **정리 완료가 아니다** |

## 5. 정산의 원자성

**한 트랜잭션에 묶는 단위**: `상태 전이 + 잔액 반영 + 포지션 반영`. 셋 중 하나만 커밋되는 경우를
만들지 않는다.

| 경계 | 방식 |
|---|---|
| `INTENT` 커밋 | 주문 행 + 예약을 **한 트랜잭션** |
| 외부 호출 | **트랜잭션 밖**. 🔴 호출 중 DB 트랜잭션을 열어두지 않는다(커넥션·잠금 점유) |
| 결과 반영 | 조회 결과 1건당 **한 트랜잭션**에서 전이+정산. 실패하면 그 건만 롤백되고 **활성으로 남아 다음 폴링에서 재시도**된다(이미 `checkOrderStatus` 에 적용, §4.6-4) |
| 중복 반영 방지 | 🔴 **상태 전이 가드만으로는 부족하다** — §5.1 을 본다 |
| 🔴 가드와 정산을 같은 트랜잭션에 | 전이는 바깥, 정산은 `REQUIRES_NEW` 로 갈라놓으면 **정산만 커밋되고 바깥이 롤백**돼 재정산이 가능하다. 2026-10-07 에 KRW 복원에서 실제로 그 구조였다 |

### 5.1 🔴 주문 상태만으로 중복 정산을 막을 수 없다

`PARTIAL_FILLED` → `PARTIAL_FILLED` **인 동안에도 체결량은 증가한다.** 상태가 그대로이므로 조건부
UPDATE(`WHERE state = :expected`)는 **같은 전이로 보이고 가드가 되지 않는다.** 그래서 기준을 바꾼다:

| 기준 | 내용 |
|---|---|
| **정산 버전으로 제어** | 🔴 `applied_volume` **하나에만** 가드를 걸면 부족하다 — **체결량이 그대로인데 수수료·체결금액·취소 상태가 갱신될 수 있다.** 주문 행에 **정산 버전**(`settlement_version`)을 두고 `WHERE settlement_version = :expected` 로 조건부 UPDATE 한다. 그 한 UPDATE 에서 **누적 체결량·누적 체결금액·누적 수수료·예약 해제 여부·정산 버전**을 **함께 원자적으로** 갱신한다 |
| **차분 반영** | 보존한 누적값과 조회 결과의 누적값을 비교해 **차분만** 잔액·포지션에 반영한다. 차분이 0 이어도 **수수료·상태 변화는 반영될 수 있다** |

🔴 **`settlement_version` 은 동시 쓰기를 제어할 뿐, 응답의 최신성을 판단하지 않는다.** 오래된 응답이
**최신 로컬 버전을 읽고** 갱신할 수도 있다(조회 → 지연 → 그사이 다른 반영 완료 → 이 응답이 버전을 다시
읽어 통과). 그래서 **최신성 규칙을 따로 둔다**:

| 규칙 | 내용 |
|---|---|
| **누적 단조성** | 조회 결과의 누적 체결량·누적 체결금액이 **이미 반영한 값보다 작으면 거부**한다. 체결은 되돌아가지 않는다 |
| **종결 역행 금지** | 이미 `FILLED`·`CANCELLED` 로 종결된 주문을 **활성 상태로 되돌리지 않는다.** 종결 후 도착한 활성 응답은 오래된 것으로 보고 버린다 |
| **수량 같은 수수료 증가** | 누적 체결량이 **같고** 수수료·체결금액만 증가하는 경우는 **정산 지연으로 실재한다**(시장가 매도의 `trades`·`executed_funds` 가 뒤늦게 채워진다 — 코드 주석에 그 사례가 있다). **받아들인다** |
| 🔴 **수량 같은 수수료 감소** | **자동 반영하지 않는다. 그렇다고 "오래된 응답" 으로 단정해 버리지도 않는다.** 🔴 위의 "뒤늦게 채워진다" 사례는 **증가 방향의 설명**일 뿐이고, 그것만으로 **수수료가 항상 증가만 한다는 보장은 생기지 않는다**(거래소의 정산 정정·수수료 환급·우리 쪽 해석 오류가 모두 후보다). 그래서 **불일치로 보존하고 확인 대상으로 남긴다** — 감소분을 버리지도, 잔액에 반영하지도 않고, 그 응답과 로컬 값의 차이를 기록해 사람이 확인한다 |
| 🔴 적용 순서 | **최신성 규칙으로 먼저 거르고**, 통과한 응답만 `settlement_version` 조건부 UPDATE 로 반영한다. 버전만으로는 오래된 응답을 막을 수 없다 |
| **또는 체결 식별자** | 거래소가 체결(trade) 식별자를 주면 **이미 반영한 식별자 집합**을 기준으로 멱등 처리한다. (업비트 응답의 `trades` 를 쓸 수 있는지는 **확인하지 않았다**) |
| 부분 체결 후 취소 | **미체결분 자금만 해제**한다. 🔴 **보유 수량이 남은 포지션의 슬롯은 유지한다** — 수량이 있으면 그 포지션은 여전히 관리 대상이다 |

🔴 현재 구현은 `syncOrderState` 가 `filledQuantity` 를 **덮어쓰고** 상태 전이로만 가드한다. 위 기준으로
바꾸지 않으면 부분 체결 구간에서 **같은 체결이 두 번 반영될 수 있다.**

### 5.2 측정 결과 — 시험 17·18·19 (2026-10-07, `SettlementIdempotencyTest`)

🔴 **기존 코드가 실패할 것으로 가정하지 않고 돌려서 실제 결과를 봤다.** 둘은 통과했고 하나는
실패했는데, **통과한 이유가 설계가 의도한 가드와 다르다.**

| 시험 | 결과 | 실제 이유 |
|---|---|---|
| 17 반복 응답 | 🟢 통과 | `syncOrderState` 가 `currentState == newState` 면 **조기 반환**하고, `checkOrderStatus` 는 종결 주문을 **조회조차 하지 않는다** |
| 18 종결 후 활성 응답 | 🟢 통과 | 같은 이유 — 종결 주문은 더 보지 않는다. 🔴 **최신성 규칙이 있는 것이 아니다**. `syncOrderState` 를 직접 부르는 경로(`cancelOrder` 의 체결 확인 분기)에는 그 가드가 없어 **미검증**이다 |
| 19 수량 불변·수수료 증가 | 🔴 **실패** | 아래 |

**19 의 측정값**: 1회차와 2회차가 완전히 동일했다 —
`order{state=FILLED filledQty=10 price=300 execFunds=null} pos{size=10 fee=1.50} session{availableKrw=7000}`.

원인이 두 겹이다:

1. **조기 반환이 두 번** — 17·18 을 통과시키는 바로 그 성질이 **유효한 갱신까지 막는다.** 같은
   메커니즘의 양면이므로, 19 를 고치려면 17·18 의 보호를 **다른 수단으로 대체**해야 한다(설계안의
   최신성 규칙 + 정산 버전 가드가 그 수단이다).
2. 🔴 **보존할 자리가 없다** — 응답의 `executedFunds` 는 주문 행에 **필드가 있는데도 채우지 않는다**
   (`execFunds=null`). 수수료는 주문 엔티티에 필드가 없고, 포지션의 `position_fee` 에 남는 값은
   **거래소가 보고한 `paidFee`(1.00)가 아니라 우리가 계산한 값(1.50 = 3000 × 0.0005)** 이다.

🔴 **두 번째가 설계를 보강한다.** §5.1 은 "이미 반영한 누적 체결량·금액·수수료" 를 보존해 차분을
반영하라고 했는데, **지금은 누적 금액·수수료를 거래소 보고값으로 보존하지 않는다.** 그러므로 정산
버전 가드만 추가해서는 19 가 통과하지 않는다 — **보존 필드(`applied_executed_funds`·
`applied_paid_fee`)와 거래소 보고값을 쓰는 경로가 함께 필요하다.** 🔴 그리고 수수료를 자체 계산값에서
거래소 보고값으로 바꾸는 것은 **회계 기준 변경**이므로, 과거 데이터 해석과 함께 따로 판단해야 한다.

### 5.3 회계 기준 변경과 구현 경계 (2026-10-07 승인)

**LIVE·DYNAMIC 실거래 회계는 거래소가 보고한 실제 수수료를 쓴다.** 자체 계산값은 추정·대조용으로
남기고, **PAPER 의 고정 수수료 가정은 유지한다**(모의에는 거래소 보고값이 없다).

| 경계 | 내용 |
|---|---|
| **원본과 반영값 분리** | `reported_executed_funds`·`reported_paid_fee`(거래소가 말한 값) 과 `applied_executed_funds`·`applied_paid_fee`(회계에 이미 반영한 누적값)를 따로 저장한다. 둘을 비교해 **차분만** 반영한다 |
| **누락과 0 의 구분** | 🔴 전부 **NULL** 로 시작한다. **수수료 미보고를 0원으로 처리하지 않는다.** 추정값을 임시 반영하면 `fee_source='ESTIMATED'` 로 **출처와 미확정 상태를 남기고**, 실제값이 오면 **차액만** 정산하며 `REPORTED` 로 올린다 |
| **과거 데이터 보존** | 🔴 기존 행의 새 컬럼은 **NULL 로 남긴다.** 기존 계산 수수료를 실제 수수료였던 것처럼 재해석하지 않는다. `applied_*` 를 0 으로 초기화하면 **이미 반영된 금액을 다시 차감**할 수 있다. 전환 규칙은 **`fee_source IS NULL` 이면 손대지 않는다** |
| **감소 응답 보존** | 🔴 실제 수수료가 추정값보다 **작을 수도 있다.** "증가만 반영" 을 **추정값 → 실측값 전환에 적용하지 않는다.** 실측값끼리 감소하는 경우만 §5.1 의 **불일치 확인 절차**로 처리한다 |
| **종결 주문 재조회** | 🔴 저장 필드와 가드만 추가하면 **시험 19 의 첫 번째 원인이 남는다.** 종결 주문의 후속 정보를 **언제 다시 조회할지**가 구현에 들어가야 한다 — V81 에 `(state, fee_source)` 부분 인덱스를 두어 "보고값과 반영값이 다른 주문" 을 찾는 질의의 출발점을 만들었다. 재조회 정책 자체는 **미구현** |

#### 구현하면서 찾은 것 — 원본이 정상 체결에서 저장되지 않았다

🔴 `order.setExecutedFunds(...)` 는 **"부분 체결 후 취소" 분기에서만** 호출됐다. 정상 전량 체결
(`done`)에서는 저장되지 않아 두 가지가 따라왔다:

- **시장가 매수의 평균단가**가 `executedFunds` 가 없으면 `quantity`(요청 KRW)로 **폴백**한다 →
  실제보다 **과대 계산**된다(실제 사용액 ≤ 요청액).
- **미사용 KRW 복원 조건**(`executedFunds < quantity`)이 `executedFunds == null` 이라 **성립하지 않는다**
  → 시장가 매수에서 남은 KRW 가 복원되지 않을 수 있다.

🔴 **그래서 원본을 새 컬럼(`reported_*`)에 저장하고, 기존 `executed_funds` 와 그것을 쓰는 금액 경로는
건드리지 않았다.** 기존 컬럼을 채우면 위 두 경로가 **조용히 바뀐다** — 평균단가와 KRW 복원은 돈이
움직이는 자리이므로 **차분 정산 규칙과 함께 따로 판단한다.**

#### 1단계 구현 상태 (V81)

| 완료 | 마이그레이션 V81(6개 컬럼 + 부분 인덱스), 엔티티 필드, **모든 응답에서 거래소 보고 원본 보존**, 시험 1건(정상 전량 체결에서 `reported_*` 가 저장되고 `applied_*`·`fee_source` 는 NULL 로 남는다) |
|---|---|
| 🔴 미구현 | 차분 정산(회계 연결), 최신성 규칙, 정산 버전 가드, 종결 주문 재조회 정책, 추정→실측 전환, 불일치 보존 |
| 📌 테스트 환경 | H2 스키마는 `ddl-auto: none` + 손으로 관리하는 `schema-h2.sql` 이다. **컬럼을 추가하면 그 파일도 같이 고쳐야 한다** — 안 고치면 컨텍스트 기동이 깨지고 **다른 테스트 클래스까지 실패한다**(실측) |

### 5.4 2단계 구현 — 추적 정책과 불일치 보존 (V82, 2026-10-12)

#### ① 신규 주문과 기존 주문의 경계

🔴 V81 의 컬럼이 전부 NULL 로 시작하므로 **신규 주문도 그대로 두면 "전환 이전 데이터" 와 구분되지
않는다.** 전환 규칙이 "`fee_source IS NULL` 이면 손대지 않는다" 이므로 신규 주문이 새 경로에서 영원히
빠진다. 그래서 `fee_source` 에 값을 하나 더 뒀다:

| 값 | 뜻 |
|---|---|
| `NULL` | **전환 이전 데이터.** 🔴 자동 재정산에서 제외한다 |
| `PENDING` | 새 경로에 참여한다. 아직 아무것도 반영하지 않았다. **주문 생성 시 명시**한다 |
| `ESTIMATED` | 추정값을 임시 반영했다 |
| `REPORTED` | 거래소 보고값을 반영했다 |

🔴 **아직 미체결인 기존 주문의 전환은 하지 않았다.** 그 주문들은 NULL 로 남아 새 경로에 참여하지
않는다. 어느 시점의 미체결 주문을 `PENDING` 으로 올릴지, 이미 일부 반영된 금액을 어떻게 볼지는
**별도 작업**이며 여기서 섞으면 과거 데이터를 재해석하게 된다.

#### ② 재조회 대상은 '보고값 ≠ 반영값' 보다 넓다

🔴 V81 의 인덱스는 "보고값 ≠ 반영값" 전제였는데 **그것으로는 부족하다** — 보고값과 반영값이 같거나
둘 다 NULL 이어도 나중에 체결금액·수수료가 도착할 수 있다. 대상 조건은 **"정산이 아직 확정되지
않았다"** 다. 세 컬럼으로 표현한다:

| 컬럼 | 역할 |
|---|---|
| `settlement_final` | 확정 여부. `false` 인 동안만 재조회 대상 |
| `settlement_next_check_at` | 다음 조회 시각 — **백오프**를 이 값으로 표현한다(5초 폴러를 그대로 때리지 않는다) |
| `settlement_attempts` | 조회 횟수 — 백오프 계산과 **사람 판정 상향** 기준 |

🔴 **횟수 소진으로 `settlement_final` 이 되지 않는다.** 확정은 ⓐ 거래소 응답으로 결말이 나거나
ⓑ 사람이 판정해 불일치로 보존할 때만 성립한다. 인덱스(`idx_order_settlement_due`)는 **정책을 정하지
않고 받친다.**

#### ③ 감소 응답의 불일치 보존

전용 테이블 `order_settlement_discrepancy` 를 뒀다 — `kind`(`FEE_DECREASE`·`FUNDS_DECREASE`·
`VOLUME_DECREASE`·`STATE_REGRESS`), **이전 값과 수신값**, 상태, 그리고 `resolved_at`·`resolved_by`·
`resolution_note`. 🔴 **덮어쓰기 전에 둘을 함께 남긴다** — 컬럼으로는 "여러 번 어긋난 이력" 을 담을 수
없어 테이블로 뒀다. 확인 전까지 미해결로 남는다.

#### 2단계 구현 상태

| 완료 | V82(3개 컬럼 + 불일치 테이블 + 정책 인덱스), 엔티티 필드, **주문 생성 시 `PENDING`·정산 버전 명시**, 회귀 사례 `MarketBuyUnusedFundsTest`(원본 보존 시험 통과) |
|---|---|
| 🔴 미구현 | 차분 계산과 **회계 연결**(주문·잔액·포지션의 원자적 반영), 최신성 규칙, 정산 버전 가드, 재조회 실행(백오프·종료 조건을 코드로), 추정→실측 전환, 불일치 기록 쓰기 |
| 🔴 보고 기준 | **시험 19 는 여전히 미통과다.** 재조회·최신성·버전 가드만으로는 잔액·포지션이 바뀌지 않는다 — **차분 계산과 원자적 반영까지 들어가야** 통과한다. 지금은 **보존 시험만 통과한 것**으로 본다 |
| 📌 규약 | 🔴 **V78 이후 신규 타임스탬프 컬럼은 예외 없이 `TIMESTAMPTZ`** 다. V82 에서 `TIMESTAMP` 로 썼다가 프로젝트 자체 규약 시험(`TimestampConventionTest`)에 걸렸다 |

### 5.5 3단계 구현 — 차분 계산과 원자적 반영 (2026-10-12)

`OrderSettlementService` 를 두어 **최신성 검사 → 차분 계산 → 원자적 반영**을 한 경로에 넣었다.

| 요소 | 구현 |
|---|---|
| 최신성 | 누적 체결량·체결금액 감소 거부, 종결 역행 거부. 🔴 **버전 가드가 이것을 대신하지 못한다** — 오래된 응답이 최신 버전을 읽고 통과할 수 있다 |
| 추정→실측 전환 | 🔴 **"증가만 반영" 을 전환에 적용하지 않는다.** `ESTIMATED → REPORTED` 는 감소도 반영한다. `REPORTED` 끼리 감소할 때만 불일치로 보존한다 |
| 차분 | 보고값 − 반영값. 차분이 0 이면 금액을 움직이지 않고 **일정만** 미룬다 |
| 원자성 | 주문·잔액이 **한 트랜잭션**. 잔액은 `applyWithin`(같은 트랜잭션)으로 갱신한다 — `apply`(REQUIRES_NEW)를 쓰면 잔액만 커밋돼 재처리에서 두 번 들어간다 |
| 중복 방지 | 조건부 UPDATE(`WHERE settlement_version = :expected`)가 **1을 돌려준 호출만** 금액을 움직인다. 0 이면 아무것도 하지 않는다 |
| 재조회 | 종결 주문도 **정산 미확정이면 다시 조회**한다. 조기 반환을 걷어내고 중복은 위 가드가 막는다 |

#### 🔴 두 번 틀렸고 둘 다 시험이 아니라 재검토로 찾았다

**① 반영한 회차에 확정을 세웠다.** `종결 상태 + 값이 다 있음` 을 확정 근거로 삼았더니, 1회차에
`settlement_final` 이 되어 **2회차의 수수료 증가가 영원히 반영되지 않았다**. 그것은 "done 이후에도
상세가 채워진다" 는 전제를 코드가 부정한 것이다. 확정은 **종결 상태이고 차분이 없음이 확인된
회차**에만 세운다.

**② 잔액 조정 방향이 반대였다.** 매수는 요청액을 **제출 시점에 이미 전액 차감**했으므로 정산이 할
일은 소비액을 다시 빼는 것이 아니라 **미사용액을 복원**하는 것이다. 처음에는 소비액을 또 차감해
요청액만큼 이중 차감했다. 🔴 **반복 동일성만 보던 시험은 그것을 잡지 못했다** — 값이 "반복해도
같다" 는 것은 "옳다" 가 아니다. 그래서 절대값을 보는 시험을 따로 넣었다.

```
요청 3,000 / 체결 2,940 / 수수료 1.47
  원금 차이  = 60      ← 이것을 복원하면 수수료만큼 과다 복원
  미사용액   = 58.53   ← 요청액 − 체결금액 − 수수료
```

🔴 **처음 반영의 기준선**: 아직 반영이 없으면 "이미 복원한 금액" 은 0 이다. 차분 공식에
`applied=0` 을 그대로 넣으면 "요청액 전체를 이미 복원했다" 가 되어 요청액만큼 어긋난다.

#### 3단계 구현 상태

| 🟢 통과 | **시험 17·18·19 전부** + 미사용 금액 복원(58.53) + 반복 응답에 추가 복원 없음 |
|---|---|
| 🔴 범위 밖(미착수) | **지정가 매수**의 잔액 반영(`quantity` 가 코인 수량이라 같은 공식을 쓸 수 없다), **매도** 정산, **DYNAMIC** 세션, **포지션 수수료**를 거래소 보고값으로 전환(지금도 자체 계산값 1.50 이 남는다), **평균단가**를 실제 사용액 기준으로(여전히 요청액 폴백 — `MarketBuyUnusedFundsTest` 의 `@Disabled` 건) |
| 🔴 미구현 | 수동 종결 경로(확정 근거·잔여 위험·조정 기록), 불일치 해소 절차, 동시 반영 시험, 중간 실패·재처리 시험 |

🔴 **그러므로 선행 조건 3·5 는 여전히 미완료다.** 시험 19 와 미사용 금액 시험은 통과했으나 위
"범위 밖" 항목이 남아 있고, 그 각각이 돈이 움직이는 자리다.

### 5.6 확정 조건 정정과 원자성 시험 (2026-10-12)

#### 🔴 `settlement_final` 을 자동으로 세우지 않는다 — 세 번째 수정

확정 조건을 두 번 틀렸다.

| 시도 | 왜 틀렸나 |
|---|---|
| ① 종결 상태 + 값이 다 있음 | 1회차에 확정돼 **2회차의 수수료 증가를 놓쳤다** |
| ② 종결 상태 + 차분 없음이 한 번 확인됨 | 🔴 **같은 값이 한 번 더 왔다는 사실은 이후 변경이 없다는 증거가 아니다.** `첫 응답 → 동일 응답 → 늦은 수수료 증가` 에서 **마지막 갱신을 놓친다** |

**업비트 응답에는 "정산이 끝났다" 는 신호가 없다.** 그러므로 자동 확정의 근거가 없고, 이 서비스는
`settlement_final` 을 **세우지 않는다.** 🔴 **백오프와 확정은 별개다** — 비용은 백오프가 줄이고
(간격을 30초→최대 30분으로 늘린다), 재조회를 영구히 멈추는 것은 확정이 한다. **차분이 없다는 이유로
멈추지 않는다.**

확정은 사람이 **확정 근거 · 잔여 위험 · 회계 조정 기록**과 함께 판정할 때만 성립하며 그 경로는
**미구현**이다. 🔴 사람이 세운 확정도 "거래소 정산이 확인됐다" 는 뜻이 아니므로 그 구분을 기록에
남긴다.

**회귀 시험**: `동일 응답을 거쳐도 늦게 도착한 수수료 증가가 반영된다` — 위 ②를 고정한다.

#### 원자성 시험 (`SettlementAtomicityTest`)

| 확인 | 결과 |
|---|---|
| 조건부 UPDATE 성공 뒤 **잔액 변경 전** 예외 | 🟢 주문의 반영값·버전·확정 표시와 잔액이 **모두 이전 상태** |
| 조건부 UPDATE 성공 뒤 **잔액 변경 후** 예외 | 🟢 같음 |
| 같은 응답 재처리 | 🟢 **예상 절대금액** 반영 — 7000 + 58.53 = 7058.53, 버전 1 |
| 추가 반복 처리 | 🟢 변화 없음 |

🔴 **전제를 시험에 고정했다**: 세션 잔액에서 **정확히 3,000원**이 선차감돼 있고 **별도의 수수료
차감이 없다**(거래소가 그 3,000원 안에서 수수료를 뺀다). 이 전제가 깨지면 미사용액 계산도 달라진다.

📌 **스냅샷의 범위를 좁혀야 했다.** 처음에는 포지션까지 넣고 비교했는데, 같은 `checkOrderStatus`
호출 안에서 **체결 반영이 별도 트랜잭션으로 먼저 돌아** 포지션을 바꾼다. 그것은 정산 실패와 무관하게
커밋되므로, 포지션을 넣으면 **정산의 롤백을 확인하는 대신 체결 반영의 결과를 비교**하게 된다.

#### 🔴 원자성의 범위는 **주문·잔액까지**다

**"주문·잔액·포지션 정산 완료" 로 넓히지 않는다.** 포지션은 정산 경로에 연결되지 않았고, 그 사실을
시험으로 고정했다:

- **포지션 수수료** = 1.50 (자체 계산이 **요청액 3,000 기준**). 거래소 보고값은 1.47 → **0.03 어긋난다.**
- **평균단가** = 306.12 (요청액 폴백). 실제 사용액 기준이면 **300** 이다.

둘 다 같은 뿌리(요청액 폴백)이며 **미착수**다.

#### 미사용 금액 시험의 결과는 둘로 나눠 본다

| 🟢 통과 | **잔액 복원** — 58.53원이 한 번만 복원된다 |
|---|---|
| 🔴 미통과 | **평균단가** — 실제 사용액 기준이 아니다(`@Disabled` 보존) |

### 5.7 🔴 중간 상태가 실재한다 — 시험 범위의 문제가 아니다 (2026-10-12)

앞서 원자성 시험에서 포지션을 스냅샷에서 뺀 것은 **시험을 맞추려는 조치였고, 그 자체가 문제를
드러낸다.** 같은 `checkOrderStatus` 호출에서

```
① 체결 반영(syncTx, REQUIRES_NEW)  → 커밋  : 포지션 수량·평균단가·수수료가 바뀐다
② 정산(settlementTx, REQUIRES_NEW) → 실패  : 주문 반영값·잔액은 그대로
```

🔴 **그러면 "포지션은 바뀌었고 잔액 정산은 남은" 중간 상태가 실제로 존재한다.** 현재 시험이 입증하는
것은 **주문·잔액 정산의 원자성**뿐이다.

**그래서 정해야 하는 것** (🔴 미결정):

| 질문 | 선택지 |
|---|---|
| 중간 상태를 **허용**하는가 | ⓐ 허용하고 **재처리 완료까지 추적**한다(정산 미확정이 그 추적이지만, 포지션이 이미 바뀐 상태라는 표시는 없다) ⓑ 체결 반영과 정산을 **한 트랜잭션**으로 묶는다(실패 시 체결 반영도 롤백 — 주문이 활성으로 남아 다음 폴링에서 재시도) |
| 허용한다면 **거래를 제어**하는가 | 정산 미확정인 포지션에 대해 신규 진입·청산을 그대로 허용할지, 제한할지 |

🔴 **ⓑ 가 단순히 더 안전하지 않다.** 체결 반영까지 롤백하면 거래소에는 체결이 있는데 로컬에는
없는 상태가 반복될 수 있고, 그 사이 평가 루프는 포지션이 없다고 본다. 둘 중 무엇을 택하든
**그 선택을 기록하고 그에 맞는 추적·제어를 함께 넣어야 한다.** 지금은 ⓐ 를 암묵적으로 택한 상태이며
**추적·제어가 없다.**

### 5.8 요청액 폴백의 전달 범위 (2026-10-12, 시험으로 고정)

`RequestedFundsFallbackImpactTest` 로 확인했다.

| 대상 | 전달 | 근거 |
|---|---|---|
| **평균단가** | 🔴 직접 | `avgFillPrice = fundsUsed / filledQty`. 요청 3000 / 9.8 = **306.12**(실제는 300) |
| **손익률** | 🔴 직접 | `pnlPct = (현재가 − avgPrice) / avgPrice`. 평균단가 과대 → **손익률 과소**(현재가 300 에서 0% 가 아니라 −2%) |
| **손절** | 🟡 **폴백 경로에서만** | `stopLossPrice != null` 이면 가격 비교라 무관. **null 이면** `pnlPct ≤ −한도` 로 판단하므로 **조기 손절** 가능 |
| **익절** | 🟢 영향 없음 | `takeProfitPrice` 는 **진입 시점 신호가 기준**이며 평균단가를 쓰지 않는다 |
| **실현손익** | 🔴 직접 | `realizedPnl = 매도대금 − 수수료 − (수량 × avgPrice)` → **실현손익 과소** |

🔴 **손절·익절가 자체는 평균단가에서 오지 않는다.** 그러므로 평균단가를 고쳐도 기존 기준가가 자동으로
바뀌지 않는다 — **그 둘을 별도 규칙으로 다룬다**는 방침과 일치한다.

### 5.10 DYNAMIC 의 정지·회계 가드와 원자적 체결 회계 통합 (2026-10-13)

예약은 공통화됐지만 그 **앞의 승인 조건과 뒤의 체결 처리**가 LIVE 에만 있었다. 체결 후 처리가 갈리면 자금·슬롯이 다시
어긋난다. 같은 규칙으로 모았다.

| 항목 | 종전 DYNAMIC | 지금 (LIVE·DYNAMIC 공통) |
|---|---|---|
| 신규 진입 승인 | 정지·회계 미반영·미해결 제출 어느 것도 보지 않았다 | 세션 행 **배타 잠금**으로 `RUNNING` 확인 + 회계 미반영 체결 0 + 미해결 제출 0 |
| claim 직전 재확인 | 없었다 | 세션 행 잠금 안에서 정지를 보면 `WITHDRAWN_STOPPED` 로 철회 |
| 시장가 매수 체결 회계 | 종전 경로(`handleBuyFill`): 포지션과 잔액을 다른 트랜잭션에 썼다 | 원자 경로(`observeAndApplyBuyFill`): 주문·잔액·포지션 한 트랜잭션, 대기 표시·버전 가드 |
| 미사용액 (요청 3,000 / 체결 2,940 / 수수료 1.47) | 🔴 **전량 체결: 0 복원**(잔액 7,000 에 머묾, 평균단가 306.12 = 요청액 폴백) · **체결 후 취소: 60**(수수료 미반영) — 실측 | **58.53** 한 번, 반복 조회 불변 |
| 정지 시 size=0 포지션 | 🔴 무조건 `CLOSED` — 철회된 매수의 예약이 **영영 복원되지 않고**(고아 정리는 열린 포지션만 본다), 늦은 체결이 반영될 곳이 없었다(재개방 금지) — 실측 | **매수 주문의 상태로 가른다**(LIVE 와 같은 규칙): ① 의도·claim·불명·제출 중 → **열어 둔다**(추적이 체결을 받는다) ② 체결됐는데 수량 0(회계 대기) → 열어 둔다 ③ **확정된 미제출 철회·체결 없는 취소 → 닫기와 예약 복원을 한 트랜잭션으로, 한 번**(닫기에 성공한 쪽만 복원 — 고아 정리와 겹쳐도 한 번) ④ 매수 주문 없음·차감 없던 주문 → 닫기만 |
| 정지 후 미해결 제출 | 알림 없음 | LIVE 와 같이 **정리 미완료** 경고·알림 |

LIVE 쪽에도 같은 공백이 있어 함께 고쳤다:

- **LIVE 정지**: 매수가 진행 중인(의도·claim·불명 — 취소 대상이 아니다) size=0 포지션을 닫던 분기를 막았다.
- **타임아웃 직전 체결·취소 실패 후 체결**: 두 경로가 종전 `syncOrderState` 로 반영했다. 원자 회계 대상 시장가 매수는
  이제 `checkOrderStatus` 하나로 보낸다. 코드 읽기로 고친 뒤 **회귀 시험을 붙였다**(`AtomicPathBypassTest`, LIVE·DYNAMIC
  × 타임아웃 전량 체결 / 타임아웃 체결 후 취소 / 취소 실패 후 체결 = 6건, 각각 반복 처리 3회에서 값 불변). 수정을 끈
  채 돌린 결과(실측):
  - 타임아웃 직전 **전량 체결**: 종전 경로가 반영해 **정산 버전 0, 미사용액 미복원(잔액 7,000)**.
  - 타임아웃 직전 **체결 후 취소**(`cancel` + 체결량 > 0): `FILLED` 판정에 걸리지 않아 **이미 체결된 주문에 거래소
    취소 요청을 보냈다.** 취소가 "성공" 하면 주문은 `CANCELLED` 가 되고 고아 정리가 **예약 전액을 복원**한다 — 산
    코인이 있는데 돈도 돌아오는 경로다.
  - 취소 실패 후 체결: 그 자리에서 종전 경로로 `FILLED` 반영.

#### 시험 기반의 한계 — 시험 JVM 힙 (2026-10-13 실측)

전체 실행이 40분 넘게 끝나지 않았다. 원인은 코드가 아니라 **시험 JVM 힙 고갈**이었다 — 힙 523/524MB(Gradle 작업자
기본 최대 512MB), 스레드 707개, GC 로 CPU 18분, 컨텍스트 적재 실패 처리에서 정지. 목·스파이 조합이 다른 시험 클래스는
**캐시된 컨텍스트를 하나씩 더**(각자 Tomcat·스케줄러 포함) 만들고, 이번에 추가한 `DynamicFillAccountingTest` 의 조합이
21번째 컨텍스트였다. 직전의 세 번 통과도 한계 근처였다는 뜻이다.
- 조치: 그 클래스가 `SettlementAtomicityTest` 와 **같은 조합**을 쓰게 해 컨텍스트를 늘리지 않았다(두 클래스에 상대의
  스파이를 사용하지 않는 필드로 둔다). 힙 설정은 바꾸지 않았다.
- 🔴 남는 위험: 새 조합의 시험 클래스가 하나 더 생기면 같은 정지가 재현될 수 있다. 힙 상향·컨텍스트 캐시 상한·스케줄러
  비활성 프로필 중 무엇을 택할지는 결정이 필요하다.

#### 🔴 시험 10 이 잡은 결함 — 관측 저장이 반영을 되돌렸다

`ConcurrentFillSettlementTest` 에서 **같은 체결이 두 번 반영**됐다(포지션 19.6, 잔액 7,117.06, 주문 버전 1). 폴러+복구
경로에서만, LIVE 1/24·DYNAMIC 1/3 라운드.

- 원인: 원자 경로의 1단계(관측 보존)가 주문을 **엔티티로 읽어 저장**했다. 주문 엔티티에는 `@Version` 도 부분 갱신도
  없어 저장은 **전 열을 쓴다.** 상대 작업자가 회계를 반영하는 동안 그 **이전에 읽은 스냅숏**이 잠금 해제 직후 덮어써
  **정산 버전·반영값을 0·null 로 되돌렸고**, 버전 가드가 같은 체결을 다시 통과시켰다.
- 🔴 버전 가드는 "가드를 쓰는 쪽끼리" 만 직렬화한다 — 가드를 거치지 않는 전 열 저장이 그 값을 되돌리면 가드는
  무력하다.
- 수정: 관측은 **관측 열만 쓰는 조건부 UPDATE**(`recordBuyFillObservation`)로, 종결 전이는 **행 잠금 읽기**
  (`findByIdForUpdate`) 후 저장으로 바꿨다.
- 결과: 360라운드(30 × 4경우 × 3회) 중복 0. 🔴 같은 유형 — 주문 행을 전 열로 저장하는 다른 경로가 원자 경로와
  겹치는 경우 — 는 **이 시험의 범위 밖**이다. 주문 엔티티의 전 열 저장 지점 목록화는 남는다.

### 재폴링·동시 처리·재시작의 기준

- **재폴링**: 조건부 UPDATE 가드로 1회만. (순차 재폴링은 시험으로 확인됨, 동시 반영은 미검증)
- **동시 처리**: 같은 주문을 폴러·WS·reconcile 이 동시에 잡는 경우는 **아직 시험하지 않았다**(§4 동시성 목록).
- **재시작**: `INTENT`·`UNKNOWN` 이 활성이므로 기동 시 추적 대상에 자동 포함된다.

## 6. 추적 주체 — 기존 폴러 확장 vs 별도 작업

| | 기존 `pollActiveOrders()` 확장 | 별도 작업 분리 |
|---|---|---|
| 장점 | 새 스케줄러가 없다. 활성 주문 집합에 `INTENT`·`UNKNOWN` 을 더하면 끝. 재시작 복구가 자동으로 따라온다 | `UNKNOWN` 전용 주기·백오프를 따로 줄 수 있다(조회 실패가 반복될 때 5초 폴링은 과하다) |
| 단점 | `UNKNOWN` 은 조회 실패가 반복될 수 있어 **5초 주기로 계속 때리면 레이트리밋을 먹는다**. 지금도 앱이 분당 22코인을 호출한다 | 스케줄러가 34개에서 35개가 된다. 같은 주문을 두 작업이 동시에 잡을 위험이 새로 생긴다 |

**제안**: **기존 폴러를 확장**하되 `UNKNOWN` 에만 **백오프**를 둔다(예: 마지막 조회 후 n초 경과한 건만).
스케줄러를 늘리지 않고 레이트리밋 문제를 피한다. 🔴 이것은 제안이고, 결정은 아니다.

## 8. 확인 항목 — 중첩 잠금 대기

🔴 **원자성을 확보했어도 중첩 잠금 대기가 다시 생길 수 있다.** `REQUIRES_NEW` 는 새 커넥션을 쓰지만
같은 스레드의 동기 호출이므로, **바깥 트랜잭션이 이미 그 행의 잠금을 쥐고 있으면 안쪽이 대기한다** —
그 대기는 **설정된 제한 시간(잠금 타임아웃·트랜잭션 타임아웃)에 실패할 수 있다.** 2026-08-25 DYNAMIC
사고에서는 타임아웃이 없는 설정이어서 동적 세션 16개가 29시간 무응답이었다. 🔴 즉 "영원히" 는 그때의
설정에 달린 결과이고 일반 명제가 아니다.

**현재 `restorePositionKrwAtomically` 호출 시점의 점검 결과** — 바깥(`stopSessionOnce`)이 쥔 잠금:

| 행 | 바깥이 UPDATE 하는가 | 안쪽이 건드리는가 | 판정 |
|---|---|---|---|
| 세션 | **아니다**(직접 쓰기를 제거했다. 최종 상태 쓰기는 이 호출 **뒤**의 `REQUIRES_NEW`) | 예 | 🟢 대기 없음 |
| 그 포지션 | 아니다(`size=0` 분기는 `markClosingIfOpen` 을 타지 않는다) | 예 | 🟢 대기 없음 |
| 다른 포지션 | 예(`size>0` 분기의 `markClosingIfOpen`) | 아니다(다른 행) | 🟢 무관 |
| 주문 | 예(`cancelSessionActiveOrders` 의 `transitionState`) | 아니다 | 🟢 무관 |

🔴 **그러나 이것은 지금 코드에 대한 판정이고 보장이 아니다.** 다음 중 하나라도 생기면 **즉시 대기·
데드락이 된다**:

- 바깥이 **세션 행을 직접 UPDATE** 하도록 되돌아간다(제거한 그 코드가 복구되는 경우),
- 바깥이 `findByIdForUpdate` 로 세션 행을 **잠근 뒤** 이 메서드를 부른다,
- `size=0` 분기 앞에 그 포지션 행을 UPDATE 하는 코드가 추가된다.

그 경우 **중첩 잠금 대기가 발생하며, 설정된 제한 시간에 실패할 수 있다.**

**그러므로 설계에 규칙으로 못박는다**: `REQUIRES_NEW` 로 들어가는 메서드를 부르기 전에 **바깥
트랜잭션이 그 메서드가 쓸 행을 이미 UPDATE/잠금했는지 확인한다.** 어긋나면 `REQUIRES_NEW` 를 쓰지
말고 바깥 트랜잭션 안에서 처리하거나, 그 쓰기를 모두 한 경계로 모은다.

🔴 **이 규칙의 범위는 같은 스레드의 중첩 트랜잭션이다 (2026-10-13).** **서로 다른 스레드 사이의 잠금 순서와 제한
시간은 검증되지 않았다.** 현재 잠금을 잡는 행은 계좌 자본 잠금 행·세션 행(LIVE·DYNAMIC)·주문 행(§5.10 의 잠금
읽기)·포지션 행이고, 경로마다 잡는 순서가 같다는 확인이 없다 — 예를 들어 틱은 계좌 잠금 → 세션 행 순이고, 정지는
세션 행을 먼저 쓴다. 두 스레드가 반대 순서로 잡으면 교착이 가능하며, 그때의 결과(어느 쪽이 얼마 만에 실패하는가)는
DB 의 교착 탐지와 잠금 제한 시간 설정에 달려 있다. 운영 PostgreSQL 의 `lock_timeout`·`deadlock_timeout` 값과 경로별
잠금 순서표는 **별도 확인 항목으로 남긴다.**

## 9. 해결 목표와 남는 것

🔴 **아래는 "닫는다" 가 아니라 해결 목표다.** §4 의 승인·정지 순서를 확정하고 §7 의 실패 시험을
통과하기 전까지는 어느 것도 닫히지 않는다.

**해결 목표**: 응답 불명과 확정 실패의 분리, 불명 주문의 자금·슬롯 성급 해제 방지, 재기동 복구,
`identifier` 기반 추적, 한도 확인+예약+의도 저장의 원자화.

🔴 **남는 것**:

- **`SUBMITTING` 안에서 "아직 안 나갔다" 와 "나갔을 수 있다" 의 구분** — claim 을 커밋한 뒤 호출
  직전에 죽은 경우와 호출 도중 죽은 경우를 구분할 단서가 없다. 그래서 **보수적으로 둘 다 불명으로
  다룬다**(자동 재제출 금지). 🔴 **그 결과 실제로 나가지 않은 주문의 자금·슬롯이 불명 해소까지
  묶인다 — 이것은 알려진 가용성 한계로 받아들인다.** 미접수로 추정해 해제하는 선택은 §0 의 원칙과
  충돌하므로 택하지 않는다.
- **장기 `UNKNOWN` 의 종결** — 자동 종결 규칙을 두지 않고, 수동 조정은 `FAILED` 로 바꾸지 않는다(§1.1).
- **늦은 체결 포지션의 관리 주체**(③-2) — 자동 청산 vs 별도 정리 상태는 미결정.
- **동시 반영** — 같은 주문을 여러 경로가 동시에 처리하는 경우(§5.1 의 조건부 UPDATE 로 다루려 하나
  시험 전이다).
- **기존 `FAILED` 데이터의 재해석** — 과거 행에는 응답 불명이 섞여 있어 새 의미로 일괄 해석할 수 없다.

**따라서 이 설계안을 구현해도 선행 조건 3번과 5번은 닫히지 않는다.** 위 경계를 확정하고 실패 시험을
통과해야 한다. 위 네 가지가 남는다.
