# 불명 주문 상태·예약·복구 설계안 (2026-10-07)

> **이 문서는 설계안이고 구현이 아니다.** 아직 코드로 옮기지 않았다. 검증 66세션은 그대로
> 유지하며, 운영 재배포는 보류 상태다. 선행 조건 5번은 미완료다.
>
> 근거가 되는 재현·측정은 [`LIVE_RISK_IMPLEMENTATION_REVIEW.md`](LIVE_RISK_IMPLEMENTATION_REVIEW.md)
> §4.6 에 있다. 여기서는 그 결과를 전제로 **무엇을 어떻게 바꿀지**만 적는다.

## 0. 해결하려는 문제 하나

**지금 코드는 "확정 실패" 와 "응답 불명" 을 같은 상태로 다룬다.** 거래소 접수 후 응답이 오지 않으면
주문은 `FAILED` 로 기록되고 `exchangeOrderId` 는 `null` 이다. 그러면

- `pollActiveOrders()` 는 활성 주문만 보므로 **그 주문을 더 쫓지 않는다**,
- 정지는 `FAILED` 매수를 보고 **KRW 를 복원하고 슬롯을 해제한다** — 실제로는 쓰인 자금일 수 있다.

🔴 **이 문서가 바꾸려는 것은 그 한 가지다.** 중복 복원·버전 충돌은 이미 따로 고쳤고(§4.6), 그것들이
이 문제를 해결하지 않는다.

### 전제 — 업비트 식별자 규칙 (확인됨)

`POST /v1/orders` 의 `identifier`(≤64자, 계정 전체 고유, **재사용 불가**)로 제출하고,
`GET`/`DELETE /v1/order?identifier=...` 로 **응답 UUID 없이도** 조회·취소할 수 있다.

🔴 **멱등 API 가 아니다.** 같은 키로 재요청하면 기존 응답을 준다는 보장이 없다. 🔴 **조회 가능 보존
기간**과 **"조회 실패 = 미접수"** 보장도 문서에 없다. 그래서 **조회 실패는 "없다" 가 아니라 "모른다"**
로 다룬다.

## 1. 상태 전이표

현재 `order.state` 는 `PENDING · SUBMITTED · PARTIAL_FILLED · FILLED · CANCELLED · FAILED` 다.
여기에 **두 상태를 추가**한다 — 기존 값의 의미는 바꾸지 않는다(기존 데이터 해석을 보존한다).

| 상태 | 뜻 | 활성? | 자금·슬롯 |
|---|---|---|---|
| `INTENT` | **신규** — 제출 의도가 커밋됐고 아직 외부로 보내지 않았다 | 예 | **예약** |
| `SUBMITTED` | 거래소가 접수했음을 **응답으로 확인**했다 | 예 | 예약 유지 |
| `UNKNOWN` | **신규** — 보냈으나 **결과를 모른다**(시간 초과·연결 끊김·응답 파싱 실패) | 예 | **예약 유지** |
| `PARTIAL_FILLED` | 일부 체결을 확인했다 | 예 | 체결분 확정 + 잔량 예약 유지 |
| `FILLED` | 전량 체결을 확인했다 | 아니오 | 확정 |
| `CANCELLED` | **거래소 응답으로** 취소를 확인했다 | 아니오 | 해제 |
| `FAILED` | **거래소가 거절했음을 응답으로 확인**했다(검증 오류 등) | 아니오 | 해제 |

🔴 **`FAILED` 의 의미를 좁힌다**: "보냈는데 결과를 모른다" 는 더 이상 `FAILED` 가 아니라 `UNKNOWN` 이다.
해제가 일어나는 두 상태(`CANCELLED`·`FAILED`)는 **거래소 응답이라는 근거가 있을 때만** 쓴다.

### 전이와 그 근거

| 전이 | 근거 |
|---|---|
| (없음) → `INTENT` | 제출 결정. `identifier` 를 만들어 **외부 호출 전에** 함께 커밋한다 |
| `INTENT` → `SUBMITTED` | 주문 생성 API 가 **성공 응답**을 돌려줬다(uuid 확보) |
| `INTENT` → `UNKNOWN` | 호출이 **시간 초과·연결 오류·응답 해석 실패**로 끝났다 |
| `INTENT` → `FAILED` | 거래소가 **명시적 거절**을 응답했다(검증 오류 등). 🔴 네트워크 오류는 여기 오지 않는다 |
| `UNKNOWN` → `SUBMITTED`/`PARTIAL_FILLED`/`FILLED`/`CANCELLED` | `GET /v1/order?identifier=` **조회 결과** |
| `UNKNOWN` → `UNKNOWN` | **조회 실패 또는 미발견.** 🔴 머문다. 미접수로 단정하지 않는다 |
| `SUBMITTED` → `PARTIAL_FILLED`/`FILLED`/`CANCELLED` | 폴링·조회 결과 (현행과 동일) |
| 🔴 `UNKNOWN` → `FAILED` | **자동 전이를 두지 않는다.** 조회로 "없음" 을 확정할 근거가 없다. 장기 미해결은 **사람이 판정**하고 그 판정을 기록한다 |

🔴 **마지막 줄이 이 설계의 핵심이다.** `UNKNOWN` 을 자동으로 종결시키면 지금과 같은 문제가 이름만 바꿔
돌아온다. 종결에는 **조회로 확인한 결과** 또는 **사람의 명시적 판정**이 필요하다.

## 2. 영속화·복구

```
① INTENT 커밋 (identifier + 주문 의도 + 자금·슬롯 예약)   ← 외부 호출 전
② 외부 호출 (POST /v1/orders, identifier 포함)
③ 결과 기록 (SUBMITTED | UNKNOWN | FAILED)
```

**어느 지점에서 프로세스가 죽어도 복구된다**:

| 죽은 지점 | 재기동 후 상태 | 복구 방법 |
|---|---|---|
| ① 전 | 아무것도 없다 | 복구 불필요 |
| ① 후 ② 전 | `INTENT` | **`identifier` 로 조회** → 없으면 미제출로 보고 **같은 identifier 로 재제출**(재사용 금지에 걸리지 않는다 — 아직 쓰이지 않았다). 🔴 다만 "조회 실패" 와 "조회 성공 + 미발견" 을 구분해야 하며, 조회 실패면 `UNKNOWN` 과 같게 다룬다 |
| ② 중 (호출 도중) | `INTENT` | 위와 같다. 🔴 **이 경우 접수됐을 수 있으므로 조회 결과 없이 재제출하지 않는다** — ①의 `INTENT` 와 구분이 안 되는 것이 이 설계의 약한 지점이다(§6 열린 질문) |
| ③ 전 | `INTENT` | 같다 |
| ③ 후 | `SUBMITTED`/`UNKNOWN`/`FAILED` | 활성 상태면 기존 추적 경로가 잇는다 |

🔴 **`INTENT` 는 활성 상태로 취급한다.** 재기동 후에도 추적 대상에 남아야 하므로 `ACTIVE_STATES` 에
포함한다.

## 3. 자금·슬롯

| 시점 | 자금 | 슬롯(포지션 수) |
|---|---|---|
| `INTENT` 커밋 | **예약**(차감) | **예약**(점유로 계산) |
| `SUBMITTED`·`UNKNOWN`·`PARTIAL_FILLED` | 예약 유지 | 예약 유지 |
| `FILLED` | 체결 금액으로 **확정**, 차액만 정산 | 포지션으로 전환 |
| `CANCELLED`(응답 확인) | 미체결분 **해제** | 미체결분 해제 |
| `FAILED`(명시적 거절) | **해제** | 해제 |
| 🔴 `UNKNOWN` | **해제하지 않는다** | **해제하지 않는다** |

🔴 **현재 구조와의 차이**: 지금은 자금 차감이 **주문 제출 뒤**에 오고, 슬롯은 `size > 0` 만 세므로
**체결 전에는 점유로 보이지 않는다**(§1.5-2). 이 설계는 **`INTENT` 시점에 둘 다 예약**한다. 그래야
동시 상한(선행 조건 3번)도 의미를 갖는다 — 두 선행 조건이 같은 변경으로 닫힌다.

## 4. 정지와의 관계

**신규 진입 차단과 기존 주문 추적은 분리한다.**

| 정지 시 | 동작 |
|---|---|
| 신규 진입 | **차단**. 세션 행 잠금으로 순서를 강제한다(이미 구현, §4.6 ③-1). `INTENT` 생성도 이 가드 뒤로 보낸다 |
| 매도·청산 | **절대 막지 않는다** (이미 반영) |
| 활성 주문 | 취소를 **시도**하고, 결과가 불명이면 `UNKNOWN` 으로 둔다. 🔴 **취소 요청을 보냈다는 이유로 종결하지 않는다**(이미 반영) |
| `UNKNOWN` 주문 | **추적을 계속한다.** 세션이 `STOPPED` 여도 폴러는 세션 상태를 보지 않으므로 이어진다(§4.6-5 로 확인) |
| 늦은 체결 | 포지션이 생기면 **관리 주체가 필요하다** → §6 열린 질문 |
| 잔여 포지션 | 🔴 **자동 청산할지 별도 정리 상태로 둘지 아직 정하지 않았다.** 처리가 끝나기 전에 "정리 완료" 로 표시하지 않는다 |

## 5. 정산의 원자성

**한 트랜잭션에 묶는 단위**: `상태 전이 + 잔액 반영 + 포지션 반영`. 셋 중 하나만 커밋되는 경우를
만들지 않는다.

| 경계 | 방식 |
|---|---|
| `INTENT` 커밋 | 주문 행 + 예약을 **한 트랜잭션** |
| 외부 호출 | **트랜잭션 밖**. 🔴 호출 중 DB 트랜잭션을 열어두지 않는다(커넥션·잠금 점유) |
| 결과 반영 | 조회 결과 1건당 **한 트랜잭션**에서 전이+정산. 실패하면 그 건만 롤백되고 **활성으로 남아 다음 폴링에서 재시도**된다(이미 `checkOrderStatus` 에 적용, §4.6-4) |
| 중복 반영 방지 | **상태 전이를 가드로 쓴다** — `@Modifying` 조건부 UPDATE(`... WHERE state = :expected`)가 1을 돌려준 쪽만 정산한다. `closeIfOpen`·`markClosingIfOpen` 과 같은 패턴 |
| 🔴 가드와 정산을 같은 트랜잭션에 | 전이는 바깥, 정산은 `REQUIRES_NEW` 로 갈라놓으면 **정산만 커밋되고 바깥이 롤백**돼 재정산이 가능하다. 2026-10-07 에 KRW 복원에서 실제로 그 구조였다 |

### 재폴링·동시 처리·재시작의 기준

- **재폴링**: 조건부 UPDATE 가드로 1회만. (순차 재폴링은 시험으로 확인됨, 동시 반영은 미검증)
- **동시 처리**: 같은 주문을 폴러·WS·reconcile 이 동시에 잡는 경우는 **아직 시험하지 않았다**(§4 동시성 목록).
- **재시작**: `INTENT`·`UNKNOWN` 이 활성이므로 기동 시 추적 대상에 자동 포함된다.

## 6. 추적 주체 — 기존 폴러 확장 vs 별도 작업

| | 기존 `pollActiveOrders()` 확장 | 별도 작업 분리 |
|---|---|---|
| 장점 | 새 스케줄러가 없다. 활성 주문 집합에 `INTENT`·`UNKNOWN` 을 더하면 끝. 재시작 복구가 자동으로 따라온다 | `UNKNOWN` 전용 주기·백오프를 따로 줄 수 있다(조회 실패가 반복될 때 5초 폴링은 과하다) |
| 단점 | `UNKNOWN` 은 조회 실패가 반복될 수 있어 **5초 주기로 계속 때리면 레이트리밋을 먹는다**. 지금도 앱이 분당 22코인을 호출한다 | 스케줄러가 34개에서 35개가 된다. 같은 주문을 두 작업이 동시에 잡을 위험이 새로 생긴다 |

**제안**: **기존 폴러를 확장**하되 `UNKNOWN` 에만 **백오프**를 둔다(예: 마지막 조회 후 n초 경과한 건만).
스케줄러를 늘리지 않고 레이트리밋 문제를 피한다. 🔴 이것은 제안이고, 결정은 아니다.

| # | 실패 지점 | 시험 | 현재 |

| 4 | 조회에서 체결 확인 | 정산이 **정확히 한 번** 반영되는가 | 🟡 순차 재폴링만 확인(`FillProcessingFailureTest`) |

| 7 | 정지 중 `UNKNOWN` 존재 | 신규 진입은 막히고 **추적은 이어지는가** | 🟡 추적 지속은 코드로 확인, 시험 미작성 |
| 8 | 정지 롤백 후 재시도 | 복원·정산이 **한 번만** 일어나는가 | 🟡 불변식만 확인(`KrwRestoreRollbackRetryTest`, 한계 명시) |

| 10 | 같은 주문의 동시 반영 | 중복 정산 0건 | 🔴 미작성 |

## 8. 확인 항목 — 중첩 잠금 대기

🔴 **원자성을 확보했어도 중첩 잠금 대기가 다시 생길 수 있다.** `REQUIRES_NEW` 는 새 커넥션을 쓰지만
같은 스레드의 동기 호출이므로, **바깥 트랜잭션이 이미 그 행의 잠금을 쥐고 있으면 안쪽이 영원히
기다린다**(2026-08-25 DYNAMIC 자기 데드락: 동적 세션 16개가 29시간 무응답).

**현재 `restorePositionKrwAtomically` 호출 시점의 점검 결과** — 바깥(`stopSessionOnce`)이 쥔 잠금:

| 행 | 바깥이 UPDATE 하는가 | 안쪽이 건드리는가 | 판정 |
|---|---|---|---|
| 세션 | **아니다**(직접 쓰기를 제거했다. 최종 상태 쓰기는 이 호출 **뒤**의 `REQUIRES_NEW`) | 예 | 🟢 대기 없음 |
| 그 포지션 | 아니다(`size=0` 분기는 `markClosingIfOpen` 을 타지 않는다) | 예 | 🟢 대기 없음 |
| 다른 포지션 | 예(`size>0` 분기의 `markClosingIfOpen`) | 아니다(다른 행) | 🟢 무관 |
| 주문 | 예(`cancelSessionActiveOrders` 의 `transitionState`) | 아니다 | 🟢 무관 |

🔴 **그러나 이것은 지금 코드에 대한 판정이고 보장이 아니다.** 다음 중 하나라도 생기면 **즉시 대기·
데드락이 된다**:

- 바깥이 **세션 행을 직접 UPDATE** 하도록 되돌아간다(제거한 그 코드가 복구되는 경우),
- 바깥이 `findByIdForUpdate` 로 세션 행을 **잠근 뒤** 이 메서드를 부른다,
- `size=0` 분기 앞에 그 포지션 행을 UPDATE 하는 코드가 추가된다.

**그러므로 설계에 규칙으로 못박는다**: `REQUIRES_NEW` 로 들어가는 메서드를 부르기 전에 **바깥
트랜잭션이 그 메서드가 쓸 행을 이미 UPDATE/잠금했는지 확인한다.** 어긋나면 `REQUIRES_NEW` 를 쓰지
말고 바깥 트랜잭션 안에서 처리하거나, 그 쓰기를 모두 한 경계로 모은다.

## 9. 이 설계안이 닫는 것과 닫지 못하는 것

**닫는다**: 응답 불명과 확정 실패의 분리, 불명 주문의 자금·슬롯 성급 해제, 재기동 복구,
`identifier` 기반 추적. 선행 조건 **3번**(슬롯·자금 예약)도 같은 변경으로 함께 닫힌다.

🔴 **닫지 못한다**:

- **`INTENT` 와 "호출 도중 죽음" 의 구분** — 둘 다 `INTENT` 로 보인다. 재제출 가능 여부가 갈리는데
  구분할 단서가 없다. 호출 직전에 "보냄" 표시를 한 번 더 커밋하면 구분되지만 쓰기가 한 번 더 늘고,
  그 표시 자체가 또 같은 문제를 갖는다(표시 후 죽음). **해결하지 못했다.**
- **장기 `UNKNOWN` 의 종결** — 사람 판정에 맡긴다. 자동 종결 규칙을 두지 않는다.
- **늦은 체결 포지션의 관리 주체**(③-2) — 자동 청산 vs 별도 정리 상태는 미결정.
- **동시 반영** — 같은 주문을 여러 경로가 동시에 처리하는 경우.

**따라서 이 설계안을 구현해도 선행 조건 5번은 닫히지 않는다.** 위 네 가지가 남는다.
