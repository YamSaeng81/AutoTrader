# 불명 주문 상태·예약·복구 설계안 (2026-10-07)

> **이 문서는 설계안이고 구현이 아니다.** 아직 코드로 옮기지 않았다. 검증 66세션은 그대로
> 유지하며, 운영 재배포는 보류 상태다. 선행 조건 5번은 미완료다.
>
> 근거가 되는 재현·측정은 [`LIVE_RISK_IMPLEMENTATION_REVIEW.md`](LIVE_RISK_IMPLEMENTATION_REVIEW.md)
> §4.6 에 있다. 여기서는 그 결과를 전제로 **무엇을 어떻게 바꿀지**만 적는다.

## 0. 해결하려는 문제 하나

**지금 코드는 "확정 실패" 와 "응답 불명" 을 같은 상태로 다룬다.** 거래소 접수 후 응답이 오지 않으면
주문은 `FAILED` 로 기록되고 `exchangeOrderId` 는 `null` 이다. 그러면

- `pollActiveOrders()` 는 활성 주문만 보므로 **그 주문을 더 쫓지 않는다**,
- 정지는 `FAILED` 매수를 보고 **KRW 를 복원하고 슬롯을 해제한다** — 실제로는 쓰인 자금일 수 있다.

🔴 **이 문서가 바꾸려는 것은 그 한 가지다.** 중복 복원·버전 충돌은 이미 따로 고쳤고(§4.6), 그것들이
이 문제를 해결하지 않는다.

### 전제 — 업비트 식별자 규칙 (확인됨)

`POST /v1/orders` 의 `identifier`(≤64자, 계정 전체 고유, **재사용 불가**)로 제출하고,
`GET`/`DELETE /v1/order?identifier=...` 로 **응답 UUID 없이도** 조회·취소할 수 있다.

🔴 **멱등 API 가 아니다.** 같은 키로 재요청하면 기존 응답을 준다는 보장이 없다. 🔴 **조회 가능 보존
기간**과 **"조회 실패 = 미접수"** 보장도 문서에 없다. 그래서 **조회 실패는 "없다" 가 아니라 "모른다"**
로 다룬다.

## 1. 상태 전이표

현재 `order.state` 는 `PENDING · SUBMITTED · PARTIAL_FILLED · FILLED · CANCELLED · FAILED` 다.
여기에 **두 상태를 추가**한다 — 기존 값의 의미는 바꾸지 않는다(기존 데이터 해석을 보존한다).

| 상태 | 뜻 | 활성? | 자금·슬롯 |
|---|---|---|---|
| `INTENT_READY` | **신규** — 의도가 커밋됐고 **제출 작업자가 아직 가져가지 않았다.** 외부로 나간 적이 없음이 확정된다 | 예 | **예약** |
| `SUBMITTING` | **신규** — 제출 작업자가 **가져갔다**(claim). 외부 호출이 시작됐거나 시작될 수 있으므로 **접수 가능성이 있다** | 예 | 예약 유지 |
| `SUBMITTED` | 거래소가 접수했음을 **응답으로 확인**했다 | 예 | 예약 유지 |
| `UNKNOWN` | **신규** — 보냈으나 **결과를 모른다**(시간 초과·연결 끊김·응답 파싱 실패) | 예 | **예약 유지** |
| `PARTIAL_FILLED` | 일부 체결을 확인했다 | 예 | 체결분 확정 + 잔량 예약 유지 |
| `FILLED` | 전량 체결을 확인했다 | 아니오 | 확정 |
| `CANCELLED` | **거래소 응답으로** 취소를 확인했다 | 아니오 | 해제 |
| `FAILED` | **거래소가 거절했음을 응답으로 확인**했다(검증 오류 등) | 아니오 | 해제 |

🔴 **`FAILED` 의 의미를 좁힌다**: "보냈는데 결과를 모른다" 는 더 이상 `FAILED` 가 아니라 `UNKNOWN` 이다.
해제가 일어나는 두 상태(`CANCELLED`·`FAILED`)는 **거래소 응답이라는 근거가 있을 때만** 쓴다.

### 전이와 그 근거

| 전이 | 근거 |
|---|---|
| (없음) → `INTENT` | 제출 결정. `identifier` 를 만들어 **외부 호출 전에** 함께 커밋한다 |
| `INTENT` → `SUBMITTED` | 주문 생성 API 가 **성공 응답**을 돌려줬다(uuid 확보) |
| `INTENT` → `UNKNOWN` | 호출이 **시간 초과·연결 오류·응답 해석 실패**로 끝났다 |
| `INTENT` → `FAILED` | 거래소가 **명시적 거절**을 응답했다(검증 오류 등). 🔴 네트워크 오류는 여기 오지 않는다 |
| `UNKNOWN` → `SUBMITTED`/`PARTIAL_FILLED`/`FILLED`/`CANCELLED` | `GET /v1/order?identifier=` **조회 결과** |
| `UNKNOWN` → `UNKNOWN` | **조회 실패 또는 미발견.** 🔴 머문다. 미접수로 단정하지 않는다 |
| `SUBMITTED` → `PARTIAL_FILLED`/`FILLED`/`CANCELLED` | 폴링·조회 결과 (현행과 동일) |
| `INTENT_READY` → `SUBMITTING` | 제출 작업자가 **claim 을 커밋**했다. 🔴 이 커밋이 "외부로 나갔을 수 있다" 의 경계다 |
| `INTENT_READY` → (철회) | 아직 나간 적이 없으므로 **안전하게 철회**하고 예약을 해제할 수 있다 |
| `SUBMITTING` → `UNKNOWN` | 호출이 시간 초과·연결 오류로 끝났다. **또는 재기동 후 `SUBMITTING` 으로 남아 있었다** — 호출 직전에 죽었더라도 **보수적으로 불명 처리한다** |
| 🔴 `UNKNOWN` → `FAILED` | **자동 전이도, 사람에 의한 전이도 두지 않는다.** §1.1 을 본다 |

🔴 **`INTENT` 를 둘로 쪼갠 이유**: 초판에는 `INTENT` 하나만 두고 "재기동 후 조회해서 없으면 같은
`identifier` 로 재제출" 이라고 적었다. **그것은 "미발견은 미접수의 증거가 아니다" 와 정면으로
충돌한다** — 삭제했다. 대신 **아직 가져가지 않은 의도**(`INTENT_READY`)와 **제출 시도가 시작돼 접수
가능성이 있는 의도**(`SUBMITTING`)를 영속 상태로 구분한다. 전자만 안전하게 제출·철회할 수 있고,
후자는 **호출 직전에 죽었더라도 보수적으로 불명 처리한다.**

### 1.1 🔴 사람의 판단도 "거래소 거절" 의 증거가 아니다

장기 `UNKNOWN` 을 수동 처리할 때 **`FAILED` 로 바꾸지 않는다.** `FAILED` 는 이 설계에서 "거래소가
거절했음을 응답으로 확인" 이라는 뜻이고, 사람의 판단은 그 증거가 아니다. 대신 **수동 조정을 별도로
보존한다**: 조정의 **근거 · 금액 · 책임자 · 조정 시각**, 그리고 **그 주문이 여전히 미해결이라는
위험**을 함께 남긴다. 주문 상태는 `UNKNOWN` 으로 두고, 회계만 수동 조정으로 맞춘다.

🔴 **기존 `FAILED` 데이터를 새 의미로 일괄 해석하지 않는다.** 과거의 `FAILED` 에는 **응답 불명이 섞여
있다**(지금까지 시간 초과를 `FAILED` 로 기록해 왔다). 마이그레이션에서 과거 행을 "확정 실패" 로 읽으면
그 자체가 오판이 된다 — 새 의미는 **전이 시점 이후**에만 적용하고, 과거 행은 **의미 불명으로 표시**하거나
적어도 구분 가능하게 남긴다.

## 2. 영속화·복구

```
① INTENT 커밋 (identifier + 주문 의도 + 자금·슬롯 예약)   ← 외부 호출 전
② 외부 호출 (POST /v1/orders, identifier 포함)
③ 결과 기록 (SUBMITTED | UNKNOWN | FAILED)
```

**어느 지점에서 프로세스가 죽어도 복구된다**:

| 죽은 지점 | 재기동 후 상태 | 복구 방법 |
|---|---|---|
| ① 전 | 아무것도 없다 | 복구 불필요 |
| ① 후, claim 전 | `INTENT_READY` | **외부로 나간 적이 없음이 확정된다.** 그대로 제출하거나, 정지 등으로 필요 없어졌으면 **철회하고 예약을 해제**한다. 🔴 조회에 의존하지 않는다 |
| claim 후 ② 전 (호출 직전) | `SUBMITTING` | 🔴 **보수적으로 `UNKNOWN` 으로 넘긴다.** 실제로 나가지 않았을 수 있지만 **구분할 근거가 없으므로 접수 가능성이 있다고 다룬다** — 자금·슬롯을 유지하고 `identifier` 로 조회를 시작한다. **자동 재제출하지 않는다** |
| ② 중 (호출 도중) | `SUBMITTING` | 위와 같다 |
| ③ 전 | `SUBMITTING` | 위와 같다 |
| ③ 후 | `SUBMITTED`/`UNKNOWN`/`FAILED` | 활성 상태면 추적 경로가 잇는다 |

🔴 **`INTENT_READY`·`SUBMITTING`·`UNKNOWN` 은 모두 활성으로 취급한다**(`ACTIVE_STATES` 포함). 🔴 단
**활성 상태를 추가하는 것만으로 복구가 완성되지 않는다** — 아래 제출 승인(§4)과 정산(§5) 규칙이
먼저다. 상태만 늘리고 그 규칙이 없으면 추적 대상만 늘어난다.

## 3. 자금·슬롯

| 시점 | 자금 | 슬롯(포지션 수) |
|---|---|---|
| `INTENT_READY` 커밋 | **예약**(차감) | **예약**(점유로 계산) |
| `SUBMITTING`·`SUBMITTED`·`UNKNOWN` | 예약 유지 | 예약 유지 |
| `PARTIAL_FILLED` | 체결분 확정 + **잔량 예약 유지** | 유지 |
| `FILLED` | 체결 금액으로 **확정**, 차액만 정산 | 포지션으로 전환 |
| `CANCELLED`(응답 확인) | 미체결분 **해제** | 미체결분 해제 |
| `FAILED`(명시적 거절) | **해제** | 해제 |
| 🔴 `UNKNOWN` | **해제하지 않는다** | **해제하지 않는다** |

🔴 **현재 구조와의 차이**: 지금은 자금 차감이 **주문 제출 뒤**에 오고, 슬롯은 `size > 0` 만 세므로
**체결 전에는 점유로 보이지 않는다**(§1.5-2). 이 설계는 **`INTENT_READY` 시점에 둘 다 예약**한다.

### 3.1 🔴 예약을 추가하는 것만으로 선행 조건 3번이 닫히지 않는다

**한도 확인 · 자금·슬롯 예약 · 의도 저장이 하나의 원자적 작업이어야 한다.** 셋이 갈라지면 지금과 같은
TOCTOU 가 이름만 바꿔 돌아온다 — 각자는 한도 안인데 **합계가 상한을 넘는다**.

| 요구 | 내용 |
|---|---|
| 원자성 | `공유 풀 한도 확인 → 예약 → 의도 저장` 을 **한 트랜잭션**에서, **직렬화가 보장되는 방식**으로 수행한다(공유 풀 행 잠금 또는 예약 합계에 대한 제약) |
| 시험 | 🔴 **서로 다른 세션의 동시 요청에서도 합계가 상한을 넘지 않아야 한다.** 세션 N개가 동시에 진입을 시도할 때 예약 합계 ≤ 상한, 초과 승인 0건 |
| 판정 | **이 시험을 통과하기 전까지 선행 조건 3번은 미완료다.** 예약 코드를 넣은 것만으로는 닫히지 않는다 |

## 4. 정지와의 관계

**신규 진입 차단과 기존 주문 추적은 분리한다.**

🔴 **먼저 짚을 문제 — 외부 호출을 트랜잭션 밖으로 옮기면 기존 정지 가드가 그대로 성립하지 않는다.**
지금 구현된 가드는 `submitOrder` 의 트랜잭션 안에서 세션 행을 잠근 채 거래소를 호출하므로 "정지 커밋
후 제출 0회" 가 성립한다(§4.6 ③-1). 그런데 §5 는 **외부 호출을 트랜잭션 밖으로** 빼라고 한다(커넥션·
잠금 점유를 피하려고). 그러면 **의도 커밋 → 잠금 해제 → 정지 완료 → 외부 제출** 이 가능해진다.
**둘을 동시에 만족시키는 순서를 다시 설계해야 한다.**

**제안하는 순서** (🔴 검토 대상이며 확정이 아니다):

| 단계 | 경계 | 내용 |
|---|---|---|
| A | 트랜잭션 + 세션 행 잠금 | 한도 확인 → 예약 → `INTENT_READY` 커밋. **세션이 `RUNNING` 이 아니면 여기서 거절**한다 |
| B | 트랜잭션 + 세션 행 잠금 | `INTENT_READY` → `SUBMITTING` **claim 커밋**(조건부 UPDATE `WHERE state='INTENT_READY'`). 🔴 **세션 상태를 다시 확인한다** — A 와 B 사이에 정지가 들어왔으면 여기서 멈추고 **철회**한다(아직 나간 적이 없다). 🔴 **이 전환에 성공한 작업만 C 로 간다** — §4.1 |
| C | **트랜잭션 밖** | 거래소 호출. 결과를 D 에서 기록한다 |
| D | 트랜잭션 | `SUBMITTED`/`UNKNOWN`/`FAILED` 기록 + 정산 |

#### 4.1 🔴 claim 을 얻은 작업자만 최초 제출한다

**`SUBMITTING` 을 읽었다는 이유로 제출하면 안 된다.** 그러면 재기동·복구 작업자가 그 상태를 보고
**재제출**할 수 있다. 규칙은 이렇다:

| 규칙 | 내용 |
|---|---|
| 최초 제출 권한 | `INTENT_READY` → `SUBMITTING` 조건부 전환이 **1행을 돌려받고 그 트랜잭션이 커밋에 성공한** 작업만 외부로 **한 번** 제출한다 |
| 🔴 UPDATE 1행만으로는 부족하다 | 조건부 UPDATE 가 1행을 돌려줘도 **그 트랜잭션은 롤백될 수 있다**(이후 단계 실패, 낙관적 잠금, 커밋 자체 실패). 그때 제출하면 **아무도 claim 하지 않은 주문이 외부로 나간다.** 그래서 **외부 호출은 커밋 이후에** 한다 — `TransactionSynchronization#afterCommit` 또는 커밋 후 별도 단계 |
| 커밋 실패 시 | **제출 0회.** 예약도 롤백되므로 주문은 `INTENT_READY` 로 남거나 사라진다 |
| 재기동·복구 | `SUBMITTING` 을 발견한 복구 작업은 🔴 **조회만 한다.** 제출하지 않는다 — 전환에 성공한 적이 없기 때문이다 |
| 구분 근거 | "전환 성공" 은 **그 트랜잭션의 UPDATE 결과(1행)** 이고, 상태를 읽은 것과는 다르다. 상태는 재기동 후에도 보이지만 **전환 성공은 한 번만 일어난다** |

#### 4.2 🔴 HTTP 클라이언트의 주문 POST 자동 재시도 (확인 결과)

클라이언트가 조용히 재시도하면 위 "한 번만 제출" 이 무너진다. 확인했다:

- `UpbitOrderClient` 는 `HttpClient.newBuilder().connectTimeout(10s).build()` — **애플리케이션 수준의
  재시도 계층이 없다.** 저장소 전체에 `@Retryable`·`RetryTemplate`·spring-retry 사용도 없다.
- 🔴 **`connectTimeout(10s)` 은 응답 대기 전체의 제한이 아니다** — 연결 수립까지의 제한이다. 응답
  대기는 **요청별 타임아웃**이 담당하고, 주문 POST 를 포함한 모든 요청에 `.timeout(Duration.ofSeconds(15))`
  가 걸려 있다(`UpbitOrderClient` 전 메서드). 즉 **접수 후 15초 안에 응답이 없으면 불명이 된다.**
- JDK `HttpClient` 는 연결 수준 실패에서 **멱등 메서드만** 재시도하며, POST 까지 재시도하게 만드는
  `jdk.httpclient.enableAllMethodRetry` 는 **기본값이 꺼짐**이다. 운영 `JAVA_OPTS`
  (`docker-compose.prod.yml`)에도 그 속성이 **없다**.

🔴 **그러므로 현재 설정에서 주문 POST 는 자동 재시도되지 않는다.** 단 이것은 **설정에 달린 사실**이므로
**명세로 고정한다**: `jdk.httpclient.enableAllMethodRetry` 를 켜지 않는다. 프록시·게이트웨이를 앞에
두는 경우에도 그 계층의 재시도를 확인해야 한다.

🔴 **그러나 재시도 설정 확인만으로 "모든 장애 상황에서 전송 중복이 없다" 고 보장하지 않는다.** 재시도가
없어도 중복은 다른 데서 생길 수 있다 — 네트워크 중간 계층의 패킷 재전송과 서버 측 중복 처리, 타임아웃
후 사람·복구 작업의 재호출, 같은 의도에 대해 두 작업자가 claim 을 다투는 경우. **중복 방지의 근거는
재시도 설정이 아니라 §4.1 의 claim 규칙과 `identifier` 의 계정 전체 고유성이다.**

**정지의 동작**: 세션을 `STOPPED` 로 커밋하면 **A·B 가 더는 승인되지 않는다**(둘 다 세션 잠금 안에서
상태를 본다). 🔴 **그러나 이미 `SUBMITTING` 인 주문은 C 로 나갈 수 있다** — 그것을 막을 방법은 없다
(이미 claim 됐고 접수 가능성이 있다). 그래서 **정지는 "신규 승인 차단" 까지만 보장하고, 미해결 주문이
남아 있으면 정리 완료로 표시하지 않는다.**

| 정지 시 | 동작 |
|---|---|
| 신규 진입 | **차단** — A·B 가 세션 잠금 안에서 상태를 확인한다 |
| 🔴 이미 승인된 제출(`SUBMITTING`) | **진행을 막지 않는다.** 그 대신 **세션을 "정리 미완료" 로 표시**하고, 그 주문이 해결될 때까지 **정리 완료로 표시하지 않는다** |
| 매도·청산 | **절대 막지 않는다** (이미 반영) |
| 활성 주문 | 취소를 **시도**하고, 결과가 불명이면 `UNKNOWN` 으로 둔다. 🔴 **취소 요청을 보냈다는 이유로 종결하지 않는다**(이미 반영) |
| `UNKNOWN` 주문 | **추적을 계속한다.** 세션이 `STOPPED` 여도 폴러는 세션 상태를 보지 않으므로 이어진다(§4.6-5 로 확인) |
| 늦은 체결 | 포지션이 생기면 **관리 주체가 필요하다** → §6 열린 질문 |
| 잔여 포지션 | 🔴 **자동 청산할지 별도 정리 상태로 둘지 아직 정하지 않았다.** 처리가 끝나기 전에 "정리 완료" 로 표시하지 않는다 |
| 🔴 정리 완료의 조건 | 세션의 **모든 주문이 종결**(`FILLED`/`CANCELLED`/`FAILED`)이고 **잔여 포지션의 관리 주체가 정해졌을 때**만. `INTENT_READY`·`SUBMITTING`·`UNKNOWN` 이 하나라도 남아 있으면 **정리 완료가 아니다** |

## 5. 정산의 원자성

**한 트랜잭션에 묶는 단위**: `상태 전이 + 잔액 반영 + 포지션 반영`. 셋 중 하나만 커밋되는 경우를
만들지 않는다.

| 경계 | 방식 |
|---|---|
| `INTENT` 커밋 | 주문 행 + 예약을 **한 트랜잭션** |
| 외부 호출 | **트랜잭션 밖**. 🔴 호출 중 DB 트랜잭션을 열어두지 않는다(커넥션·잠금 점유) |
| 결과 반영 | 조회 결과 1건당 **한 트랜잭션**에서 전이+정산. 실패하면 그 건만 롤백되고 **활성으로 남아 다음 폴링에서 재시도**된다(이미 `checkOrderStatus` 에 적용, §4.6-4) |
| 중복 반영 방지 | 🔴 **상태 전이 가드만으로는 부족하다** — §5.1 을 본다 |
| 🔴 가드와 정산을 같은 트랜잭션에 | 전이는 바깥, 정산은 `REQUIRES_NEW` 로 갈라놓으면 **정산만 커밋되고 바깥이 롤백**돼 재정산이 가능하다. 2026-10-07 에 KRW 복원에서 실제로 그 구조였다 |

### 5.1 🔴 주문 상태만으로 중복 정산을 막을 수 없다

`PARTIAL_FILLED` → `PARTIAL_FILLED` **인 동안에도 체결량은 증가한다.** 상태가 그대로이므로 조건부
UPDATE(`WHERE state = :expected`)는 **같은 전이로 보이고 가드가 되지 않는다.** 그래서 기준을 바꾼다:

| 기준 | 내용 |
|---|---|
| **정산 버전으로 제어** | 🔴 `applied_volume` **하나에만** 가드를 걸면 부족하다 — **체결량이 그대로인데 수수료·체결금액·취소 상태가 갱신될 수 있다.** 주문 행에 **정산 버전**(`settlement_version`)을 두고 `WHERE settlement_version = :expected` 로 조건부 UPDATE 한다. 그 한 UPDATE 에서 **누적 체결량·누적 체결금액·누적 수수료·예약 해제 여부·정산 버전**을 **함께 원자적으로** 갱신한다 |
| **차분 반영** | 보존한 누적값과 조회 결과의 누적값을 비교해 **차분만** 잔액·포지션에 반영한다. 차분이 0 이어도 **수수료·상태 변화는 반영될 수 있다** |

🔴 **`settlement_version` 은 동시 쓰기를 제어할 뿐, 응답의 최신성을 판단하지 않는다.** 오래된 응답이
**최신 로컬 버전을 읽고** 갱신할 수도 있다(조회 → 지연 → 그사이 다른 반영 완료 → 이 응답이 버전을 다시
읽어 통과). 그래서 **최신성 규칙을 따로 둔다**:

| 규칙 | 내용 |
|---|---|
| **누적 단조성** | 조회 결과의 누적 체결량·누적 체결금액이 **이미 반영한 값보다 작으면 거부**한다. 체결은 되돌아가지 않는다 |
| **종결 역행 금지** | 이미 `FILLED`·`CANCELLED` 로 종결된 주문을 **활성 상태로 되돌리지 않는다.** 종결 후 도착한 활성 응답은 오래된 것으로 보고 버린다 |
| **수량 같은 수수료 증가** | 누적 체결량이 **같고** 수수료·체결금액만 증가하는 경우는 **정산 지연으로 실재한다**(시장가 매도의 `trades`·`executed_funds` 가 뒤늦게 채워진다 — 코드 주석에 그 사례가 있다). **받아들인다** |
| 🔴 **수량 같은 수수료 감소** | **자동 반영하지 않는다. 그렇다고 "오래된 응답" 으로 단정해 버리지도 않는다.** 🔴 위의 "뒤늦게 채워진다" 사례는 **증가 방향의 설명**일 뿐이고, 그것만으로 **수수료가 항상 증가만 한다는 보장은 생기지 않는다**(거래소의 정산 정정·수수료 환급·우리 쪽 해석 오류가 모두 후보다). 그래서 **불일치로 보존하고 확인 대상으로 남긴다** — 감소분을 버리지도, 잔액에 반영하지도 않고, 그 응답과 로컬 값의 차이를 기록해 사람이 확인한다 |
| 🔴 적용 순서 | **최신성 규칙으로 먼저 거르고**, 통과한 응답만 `settlement_version` 조건부 UPDATE 로 반영한다. 버전만으로는 오래된 응답을 막을 수 없다 |
| **또는 체결 식별자** | 거래소가 체결(trade) 식별자를 주면 **이미 반영한 식별자 집합**을 기준으로 멱등 처리한다. (업비트 응답의 `trades` 를 쓸 수 있는지는 **확인하지 않았다**) |
| 부분 체결 후 취소 | **미체결분 자금만 해제**한다. 🔴 **보유 수량이 남은 포지션의 슬롯은 유지한다** — 수량이 있으면 그 포지션은 여전히 관리 대상이다 |

🔴 현재 구현은 `syncOrderState` 가 `filledQuantity` 를 **덮어쓰고** 상태 전이로만 가드한다. 위 기준으로
바꾸지 않으면 부분 체결 구간에서 **같은 체결이 두 번 반영될 수 있다.**

### 5.2 측정 결과 — 시험 17·18·19 (2026-10-07, `SettlementIdempotencyTest`)

🔴 **기존 코드가 실패할 것으로 가정하지 않고 돌려서 실제 결과를 봤다.** 둘은 통과했고 하나는
실패했는데, **통과한 이유가 설계가 의도한 가드와 다르다.**

| 시험 | 결과 | 실제 이유 |
|---|---|---|
| 17 반복 응답 | 🟢 통과 | `syncOrderState` 가 `currentState == newState` 면 **조기 반환**하고, `checkOrderStatus` 는 종결 주문을 **조회조차 하지 않는다** |
| 18 종결 후 활성 응답 | 🟢 통과 | 같은 이유 — 종결 주문은 더 보지 않는다. 🔴 **최신성 규칙이 있는 것이 아니다**. `syncOrderState` 를 직접 부르는 경로(`cancelOrder` 의 체결 확인 분기)에는 그 가드가 없어 **미검증**이다 |
| 19 수량 불변·수수료 증가 | 🔴 **실패** | 아래 |

**19 의 측정값**: 1회차와 2회차가 완전히 동일했다 —
`order{state=FILLED filledQty=10 price=300 execFunds=null} pos{size=10 fee=1.50} session{availableKrw=7000}`.

원인이 두 겹이다:

1. **조기 반환이 두 번** — 17·18 을 통과시키는 바로 그 성질이 **유효한 갱신까지 막는다.** 같은
   메커니즘의 양면이므로, 19 를 고치려면 17·18 의 보호를 **다른 수단으로 대체**해야 한다(설계안의
   최신성 규칙 + 정산 버전 가드가 그 수단이다).
2. 🔴 **보존할 자리가 없다** — 응답의 `executedFunds` 는 주문 행에 **필드가 있는데도 채우지 않는다**
   (`execFunds=null`). 수수료는 주문 엔티티에 필드가 없고, 포지션의 `position_fee` 에 남는 값은
   **거래소가 보고한 `paidFee`(1.00)가 아니라 우리가 계산한 값(1.50 = 3000 × 0.0005)** 이다.

🔴 **두 번째가 설계를 보강한다.** §5.1 은 "이미 반영한 누적 체결량·금액·수수료" 를 보존해 차분을
반영하라고 했는데, **지금은 누적 금액·수수료를 거래소 보고값으로 보존하지 않는다.** 그러므로 정산
버전 가드만 추가해서는 19 가 통과하지 않는다 — **보존 필드(`applied_executed_funds`·
`applied_paid_fee`)와 거래소 보고값을 쓰는 경로가 함께 필요하다.** 🔴 그리고 수수료를 자체 계산값에서
거래소 보고값으로 바꾸는 것은 **회계 기준 변경**이므로, 과거 데이터 해석과 함께 따로 판단해야 한다.

### 5.3 회계 기준 변경과 구현 경계 (2026-10-07 승인)

**LIVE·DYNAMIC 실거래 회계는 거래소가 보고한 실제 수수료를 쓴다.** 자체 계산값은 추정·대조용으로
남기고, **PAPER 의 고정 수수료 가정은 유지한다**(모의에는 거래소 보고값이 없다).

| 경계 | 내용 |
|---|---|
| **원본과 반영값 분리** | `reported_executed_funds`·`reported_paid_fee`(거래소가 말한 값) 과 `applied_executed_funds`·`applied_paid_fee`(회계에 이미 반영한 누적값)를 따로 저장한다. 둘을 비교해 **차분만** 반영한다 |
| **누락과 0 의 구분** | 🔴 전부 **NULL** 로 시작한다. **수수료 미보고를 0원으로 처리하지 않는다.** 추정값을 임시 반영하면 `fee_source='ESTIMATED'` 로 **출처와 미확정 상태를 남기고**, 실제값이 오면 **차액만** 정산하며 `REPORTED` 로 올린다 |
| **과거 데이터 보존** | 🔴 기존 행의 새 컬럼은 **NULL 로 남긴다.** 기존 계산 수수료를 실제 수수료였던 것처럼 재해석하지 않는다. `applied_*` 를 0 으로 초기화하면 **이미 반영된 금액을 다시 차감**할 수 있다. 전환 규칙은 **`fee_source IS NULL` 이면 손대지 않는다** |
| **감소 응답 보존** | 🔴 실제 수수료가 추정값보다 **작을 수도 있다.** "증가만 반영" 을 **추정값 → 실측값 전환에 적용하지 않는다.** 실측값끼리 감소하는 경우만 §5.1 의 **불일치 확인 절차**로 처리한다 |
| **종결 주문 재조회** | 🔴 저장 필드와 가드만 추가하면 **시험 19 의 첫 번째 원인이 남는다.** 종결 주문의 후속 정보를 **언제 다시 조회할지**가 구현에 들어가야 한다 — V81 에 `(state, fee_source)` 부분 인덱스를 두어 "보고값과 반영값이 다른 주문" 을 찾는 질의의 출발점을 만들었다. 재조회 정책 자체는 **미구현** |

#### 구현하면서 찾은 것 — 원본이 정상 체결에서 저장되지 않았다

🔴 `order.setExecutedFunds(...)` 는 **"부분 체결 후 취소" 분기에서만** 호출됐다. 정상 전량 체결
(`done`)에서는 저장되지 않아 두 가지가 따라왔다:

- **시장가 매수의 평균단가**가 `executedFunds` 가 없으면 `quantity`(요청 KRW)로 **폴백**한다 →
  실제보다 **과대 계산**된다(실제 사용액 ≤ 요청액).
- **미사용 KRW 복원 조건**(`executedFunds < quantity`)이 `executedFunds == null` 이라 **성립하지 않는다**
  → 시장가 매수에서 남은 KRW 가 복원되지 않을 수 있다.

🔴 **그래서 원본을 새 컬럼(`reported_*`)에 저장하고, 기존 `executed_funds` 와 그것을 쓰는 금액 경로는
건드리지 않았다.** 기존 컬럼을 채우면 위 두 경로가 **조용히 바뀐다** — 평균단가와 KRW 복원은 돈이
움직이는 자리이므로 **차분 정산 규칙과 함께 따로 판단한다.**

#### 1단계 구현 상태 (V81)

| 완료 | 마이그레이션 V81(6개 컬럼 + 부분 인덱스), 엔티티 필드, **모든 응답에서 거래소 보고 원본 보존**, 시험 1건(정상 전량 체결에서 `reported_*` 가 저장되고 `applied_*`·`fee_source` 는 NULL 로 남는다) |
|---|---|
| 🔴 미구현 | 차분 정산(회계 연결), 최신성 규칙, 정산 버전 가드, 종결 주문 재조회 정책, 추정→실측 전환, 불일치 보존 |
| 📌 테스트 환경 | H2 스키마는 `ddl-auto: none` + 손으로 관리하는 `schema-h2.sql` 이다. **컬럼을 추가하면 그 파일도 같이 고쳐야 한다** — 안 고치면 컨텍스트 기동이 깨지고 **다른 테스트 클래스까지 실패한다**(실측) |

### 5.4 2단계 구현 — 추적 정책과 불일치 보존 (V82, 2026-10-12)

#### ① 신규 주문과 기존 주문의 경계

🔴 V81 의 컬럼이 전부 NULL 로 시작하므로 **신규 주문도 그대로 두면 "전환 이전 데이터" 와 구분되지
않는다.** 전환 규칙이 "`fee_source IS NULL` 이면 손대지 않는다" 이므로 신규 주문이 새 경로에서 영원히
빠진다. 그래서 `fee_source` 에 값을 하나 더 뒀다:

| 값 | 뜻 |
|---|---|
| `NULL` | **전환 이전 데이터.** 🔴 자동 재정산에서 제외한다 |
| `PENDING` | 새 경로에 참여한다. 아직 아무것도 반영하지 않았다. **주문 생성 시 명시**한다 |
| `ESTIMATED` | 추정값을 임시 반영했다 |
| `REPORTED` | 거래소 보고값을 반영했다 |

🔴 **아직 미체결인 기존 주문의 전환은 하지 않았다.** 그 주문들은 NULL 로 남아 새 경로에 참여하지
않는다. 어느 시점의 미체결 주문을 `PENDING` 으로 올릴지, 이미 일부 반영된 금액을 어떻게 볼지는
**별도 작업**이며 여기서 섞으면 과거 데이터를 재해석하게 된다.

#### ② 재조회 대상은 '보고값 ≠ 반영값' 보다 넓다

🔴 V81 의 인덱스는 "보고값 ≠ 반영값" 전제였는데 **그것으로는 부족하다** — 보고값과 반영값이 같거나
둘 다 NULL 이어도 나중에 체결금액·수수료가 도착할 수 있다. 대상 조건은 **"정산이 아직 확정되지
않았다"** 다. 세 컬럼으로 표현한다:

| 컬럼 | 역할 |
|---|---|
| `settlement_final` | 확정 여부. `false` 인 동안만 재조회 대상 |
| `settlement_next_check_at` | 다음 조회 시각 — **백오프**를 이 값으로 표현한다(5초 폴러를 그대로 때리지 않는다) |
| `settlement_attempts` | 조회 횟수 — 백오프 계산과 **사람 판정 상향** 기준 |

🔴 **횟수 소진으로 `settlement_final` 이 되지 않는다.** 확정은 ⓐ 거래소 응답으로 결말이 나거나
ⓑ 사람이 판정해 불일치로 보존할 때만 성립한다. 인덱스(`idx_order_settlement_due`)는 **정책을 정하지
않고 받친다.**

#### ③ 감소 응답의 불일치 보존

전용 테이블 `order_settlement_discrepancy` 를 뒀다 — `kind`(`FEE_DECREASE`·`FUNDS_DECREASE`·
`VOLUME_DECREASE`·`STATE_REGRESS`), **이전 값과 수신값**, 상태, 그리고 `resolved_at`·`resolved_by`·
`resolution_note`. 🔴 **덮어쓰기 전에 둘을 함께 남긴다** — 컬럼으로는 "여러 번 어긋난 이력" 을 담을 수
없어 테이블로 뒀다. 확인 전까지 미해결로 남는다.

#### 2단계 구현 상태

| 완료 | V82(3개 컬럼 + 불일치 테이블 + 정책 인덱스), 엔티티 필드, **주문 생성 시 `PENDING`·정산 버전 명시**, 회귀 사례 `MarketBuyUnusedFundsTest`(원본 보존 시험 통과) |
|---|---|
| 🔴 미구현 | 차분 계산과 **회계 연결**(주문·잔액·포지션의 원자적 반영), 최신성 규칙, 정산 버전 가드, 재조회 실행(백오프·종료 조건을 코드로), 추정→실측 전환, 불일치 기록 쓰기 |
| 🔴 보고 기준 | **시험 19 는 여전히 미통과다.** 재조회·최신성·버전 가드만으로는 잔액·포지션이 바뀌지 않는다 — **차분 계산과 원자적 반영까지 들어가야** 통과한다. 지금은 **보존 시험만 통과한 것**으로 본다 |
| 📌 규약 | 🔴 **V78 이후 신규 타임스탬프 컬럼은 예외 없이 `TIMESTAMPTZ`** 다. V82 에서 `TIMESTAMP` 로 썼다가 프로젝트 자체 규약 시험(`TimestampConventionTest`)에 걸렸다 |

### 재폴링·동시 처리·재시작의 기준

- **재폴링**: 조건부 UPDATE 가드로 1회만. (순차 재폴링은 시험으로 확인됨, 동시 반영은 미검증)
- **동시 처리**: 같은 주문을 폴러·WS·reconcile 이 동시에 잡는 경우는 **아직 시험하지 않았다**(§4 동시성 목록).
- **재시작**: `INTENT`·`UNKNOWN` 이 활성이므로 기동 시 추적 대상에 자동 포함된다.

## 6. 추적 주체 — 기존 폴러 확장 vs 별도 작업

| | 기존 `pollActiveOrders()` 확장 | 별도 작업 분리 |
|---|---|---|
| 장점 | 새 스케줄러가 없다. 활성 주문 집합에 `INTENT`·`UNKNOWN` 을 더하면 끝. 재시작 복구가 자동으로 따라온다 | `UNKNOWN` 전용 주기·백오프를 따로 줄 수 있다(조회 실패가 반복될 때 5초 폴링은 과하다) |
| 단점 | `UNKNOWN` 은 조회 실패가 반복될 수 있어 **5초 주기로 계속 때리면 레이트리밋을 먹는다**. 지금도 앱이 분당 22코인을 호출한다 | 스케줄러가 34개에서 35개가 된다. 같은 주문을 두 작업이 동시에 잡을 위험이 새로 생긴다 |

**제안**: **기존 폴러를 확장**하되 `UNKNOWN` 에만 **백오프**를 둔다(예: 마지막 조회 후 n초 경과한 건만).
스케줄러를 늘리지 않고 레이트리밋 문제를 피한다. 🔴 이것은 제안이고, 결정은 아니다.

## 8. 확인 항목 — 중첩 잠금 대기

🔴 **원자성을 확보했어도 중첩 잠금 대기가 다시 생길 수 있다.** `REQUIRES_NEW` 는 새 커넥션을 쓰지만
같은 스레드의 동기 호출이므로, **바깥 트랜잭션이 이미 그 행의 잠금을 쥐고 있으면 안쪽이 대기한다** —
그 대기는 **설정된 제한 시간(잠금 타임아웃·트랜잭션 타임아웃)에 실패할 수 있다.** 2026-08-25 DYNAMIC
사고에서는 타임아웃이 없는 설정이어서 동적 세션 16개가 29시간 무응답이었다. 🔴 즉 "영원히" 는 그때의
설정에 달린 결과이고 일반 명제가 아니다.

**현재 `restorePositionKrwAtomically` 호출 시점의 점검 결과** — 바깥(`stopSessionOnce`)이 쥔 잠금:

| 행 | 바깥이 UPDATE 하는가 | 안쪽이 건드리는가 | 판정 |
|---|---|---|---|
| 세션 | **아니다**(직접 쓰기를 제거했다. 최종 상태 쓰기는 이 호출 **뒤**의 `REQUIRES_NEW`) | 예 | 🟢 대기 없음 |
| 그 포지션 | 아니다(`size=0` 분기는 `markClosingIfOpen` 을 타지 않는다) | 예 | 🟢 대기 없음 |
| 다른 포지션 | 예(`size>0` 분기의 `markClosingIfOpen`) | 아니다(다른 행) | 🟢 무관 |
| 주문 | 예(`cancelSessionActiveOrders` 의 `transitionState`) | 아니다 | 🟢 무관 |

🔴 **그러나 이것은 지금 코드에 대한 판정이고 보장이 아니다.** 다음 중 하나라도 생기면 **즉시 대기·
데드락이 된다**:

- 바깥이 **세션 행을 직접 UPDATE** 하도록 되돌아간다(제거한 그 코드가 복구되는 경우),
- 바깥이 `findByIdForUpdate` 로 세션 행을 **잠근 뒤** 이 메서드를 부른다,
- `size=0` 분기 앞에 그 포지션 행을 UPDATE 하는 코드가 추가된다.

그 경우 **중첩 잠금 대기가 발생하며, 설정된 제한 시간에 실패할 수 있다.**

**그러므로 설계에 규칙으로 못박는다**: `REQUIRES_NEW` 로 들어가는 메서드를 부르기 전에 **바깥
트랜잭션이 그 메서드가 쓸 행을 이미 UPDATE/잠금했는지 확인한다.** 어긋나면 `REQUIRES_NEW` 를 쓰지
말고 바깥 트랜잭션 안에서 처리하거나, 그 쓰기를 모두 한 경계로 모은다.

## 9. 해결 목표와 남는 것

🔴 **아래는 "닫는다" 가 아니라 해결 목표다.** §4 의 승인·정지 순서를 확정하고 §7 의 실패 시험을
통과하기 전까지는 어느 것도 닫히지 않는다.

**해결 목표**: 응답 불명과 확정 실패의 분리, 불명 주문의 자금·슬롯 성급 해제 방지, 재기동 복구,
`identifier` 기반 추적, 한도 확인+예약+의도 저장의 원자화.

🔴 **남는 것**:

- **`SUBMITTING` 안에서 "아직 안 나갔다" 와 "나갔을 수 있다" 의 구분** — claim 을 커밋한 뒤 호출
  직전에 죽은 경우와 호출 도중 죽은 경우를 구분할 단서가 없다. 그래서 **보수적으로 둘 다 불명으로
  다룬다**(자동 재제출 금지). 🔴 **그 결과 실제로 나가지 않은 주문의 자금·슬롯이 불명 해소까지
  묶인다 — 이것은 알려진 가용성 한계로 받아들인다.** 미접수로 추정해 해제하는 선택은 §0 의 원칙과
  충돌하므로 택하지 않는다.
- **장기 `UNKNOWN` 의 종결** — 자동 종결 규칙을 두지 않고, 수동 조정은 `FAILED` 로 바꾸지 않는다(§1.1).
- **늦은 체결 포지션의 관리 주체**(③-2) — 자동 청산 vs 별도 정리 상태는 미결정.
- **동시 반영** — 같은 주문을 여러 경로가 동시에 처리하는 경우(§5.1 의 조건부 UPDATE 로 다루려 하나
  시험 전이다).
- **기존 `FAILED` 데이터의 재해석** — 과거 행에는 응답 불명이 섞여 있어 새 의미로 일괄 해석할 수 없다.

**따라서 이 설계안을 구현해도 선행 조건 3번과 5번은 닫히지 않는다.** 위 경계를 확정하고 실패 시험을
통과해야 한다. 위 네 가지가 남는다.
