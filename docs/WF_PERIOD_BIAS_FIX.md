## 1. 문제

[`WalkForwardTestRunner.java:136-151`](../core-engine/src/main/java/com/cryptoautotrader/core/backtest/WalkForwardTestRunner.java) 은 윈도우마다 IS·OOS **누적 수익률**을 그대로 비교한다.

```
drop_w = max(0, (R_IS − R_OOS) / R_IS)      (R_IS > 0 인 윈도우만)
score  = 평균(drop_w)        → > 0.5 OVERFITTING · > 0.3 CAUTION · 나머지 ACCEPTABLE
```

ROLLING · 학습 비율 r 이면 IS 는 OOS 의 r/(1−r) 배 길다. 시간당 성과가 같으면 누적 수익률은 길이에 비례하므로(단리 근사)

```
drop = 1 − (1−r)/r      r = 0.7 → 0.571 (OVERFITTING) · r = 0.6 → 0.333 (CAUTION) · r = 0.5 → 0
```

**성과 저하가 전혀 없어도 r > 2/3 이면 OVERFITTING 이다.** 복리와 구간 첫머리의 지표 준비 봉(`minCandles`, 거래 불가)이 더해지면 편향은 더 커진다 — 준비 봉은 두 구간에서 같은 수만큼 빠지므로 짧은 OOS 쪽 비중이 더 줄어든다.

### 영향 범위 (코드에서 확인한 것만)

|---|---|

| `WalkForwardValidationGate` (LIVE 진입 게이트) | `OVERFITTING` 이면 차단한다(`:248`). 운영 WF 실행의 비율이 0.7 이면 같은 편향으로 **과하게 차단**된다 — 운영 기록의 실제 비율은 확인하지 않았다 |
| 화면·리포트(`overfittingScore`, `verdict`) | 같은 값을 표시한다 |
| 다음 후보 1단계(504 판정) | 그대로 쓰면 선별을 왜곡한다 — 리뷰 11차 지적 |

## 2. 가짜 자료 시험 — 실제 `run()` 경로

[`WalkForwardPeriodBiasTest`](../core-engine/src/test/java/com/cryptoautotrader/core/backtest/WalkForwardPeriodBiasTest.java) · 4건 통과(2026-10-28 로컬).

- 자료: 5,000봉 H1, 매끈한 지수 추세. ROLLING · 0.7 · 창 5 → 윈도우마다 IS 700봉 · OOS 300봉, 준비 봉 20.
- 탐침 전략: 시각만 보고 20시간마다 매수, 12시간 뒤 매도. 추세가 일정하면 언제 거래해도 거래당 성과가 같다.

| 가짜 자료 | 윈도우 수익률 IS / OOS | 현재 점수 → 판정 | 후보 LOG → 판정 | 후보 LINEAR |
|---|---|---|---|---|
| 정상: 전 구간 같은 추세 (시간당 성과 OOS/IS 0.95~1.05 확인) | +8.52% / +3.42% (5윈도우 같음) | 0.5986 → **OVERFITTING** | 0.0000 → ACCEPTABLE | 0.0231 |
| OOS 추세만 10% 낮춤 | — | 0.6796 → **OVERFITTING** | 0.1983 → ACCEPTABLE | — |

- 정상 자료에서 현재 식은 **성과 저하 없이 OVERFITTING** 이다(리뷰 지적 재현).
- 후보는 정상 자료를 ACCEPTABLE 로, **실제 큰 저하는 여전히 OVERFITTING** 으로 낸다. 보정이 저하를 가리지 않는다.
- 추세 10% 저하가 시간당 성과로는 약 20% 저하가 된 것은 거래당 고정 비용 때문이다(가짜 자료의 성질이지 식의 성질이 아니다).
- 시험의 첫 단언(현재 식 = OVERFITTING)은 **현재 동작의 특성 시험**이다. 수정이 반영되면 그 단언을 새 동작으로 바꾸고, 바꾼 사실을 개정 기록에 남긴다(시험을 지우지 않는다).

## 3. 수정 안

| 안 | 내용 | 정상 자료 | 판단 |
|---|---|---|---|
| **(가) 권장 → 채택(F1)** | 윈도우마다 **평가 봉 1개당 로그 성장률**로 바꿔 비교: `g = ln(1 + R/100) / n_eff`. `drop = max(0, (g_IS − g_OOS) / g_IS)`. `n_eff` 는 **엔진이 센 평가 대상 봉 수**(§7) — 초안의 "구간 봉 수 − minCandles − 1" 공식은 철회 | 0.0000 | 길이·복리·준비 봉을 모두 보정한다 |
| (나) | 단리 환산: `R / n_eff` | 0.0231 | 단순하지만 복리 편향이 남는다 |
| (다) | 거래당 기대값 비교 | — | 길이는 없어지지만 거래 빈도 저하(신호가 끊기는 과적합)를 못 잡는다. 대체로 쓰지 않는다 |
| (라) | 학습 비율을 0.5 로 | — | WF 설정을 바꾸는 것이다. B 와 계획서가 고정한 0.7 을 결과 뒤에 바꾸게 된다. **채택하지 않는다** |

(가) 에서 **바꾸지 않는 것**: 하락률 계산 대상(IS > 0 윈도우)·0 하한·윈도우 평균·임계값 0.5/0.3·표본 하한(`INSUFFICIENT_DATA`)·홀드아웃 게이트. 바꾸는 것은 비교 단위 하나다.
- ~~`R ≤ −100%` 는 `g = −∞` 로 둔다~~ — **철회(리뷰 12차 지적 1).** 평가 봉 0 · `R ≤ −100%` 처럼 `g` 를 정의할 수 없는 윈도우가 (점수 대상 중) 하나라도 있으면 비유한 값을 저장하지 않고 점수 `null` · 판정 `INSUFFICIENT_DATA` 로 둔다. 그 윈도우를 빼고 평균을 내면 최악 구간이 점수에서 사라지기 때문이다.
- ANCHORED 는 윈도우마다 IS 길이가 달라 편향이 더 크다. 같은 식으로 보정된다.

### 구현 방식 (초안 계획 — 실제 구현은 §7)

1. `evaluateWindow` 가 두 구간의 평가 봉 수를 `WindowResult` 에 싣는다.
2. 점수 계산을 (가) 로 바꾸고, **기존 점수를 `rawOverfittingScore` 로 함께 남긴다** — 과거 결과와 비교·감사할 수 있게.
3. 결과 CSV·화면에 어느 식인지 적는다(`scoreMethod = PER_BAR_LOG_V1`).
4. 시험: 위 4건 + 기존 WF 시험 전부. 특성 시험 단언은 새 동작으로 바꾸고 개정 기록에 남긴다.
5. **운영 영향**: `core-engine` 변경은 배포되면 LIVE 진입 게이트 판정을 바꾼다(지금보다 덜 막는다). 배포는 별도 승인이며, 이 수정의 범위가 아니다. 운영은 `2eb4225` 를 유지한다.
   - 다음 후보 1단계는 로컬 러너로 돌리므로 배포 없이 수정된 판정식을 쓸 수 있다. 이때 "전략 코드는 `2eb4225` 와 같고, WF 판정식만 수정본"이라고 결과에 적는다.

## 4. 이 수정이 다루지 않는 것 (관찰만, 바꾸지 않음)

- IS ≤ 0 인 윈도우는 점수에서 빠진다 — IS·OOS 둘 다 손실인 윈도우가 많아도 점수가 낮을 수 있다.
- IS 수익이 아주 작으면 비율이 크게 흔들린다(상한 없음).
- 임계값 0.5/0.3 에는 통계적 근거가 적혀 있지 않다.
- 이 세 가지는 별도 리뷰 없이 이번 수정에 섞지 않는다.

## 5. B 결과 처리

- B WF 원본(0/21, `OVERFITTING 20 · INSUFFICIENT_DATA 1`)·결과 CSV·로그·리뷰 9차 판정과 **전향 검증 미시작 결정을 그대로 보존**한다. 이 문서는 B 를 재판정하지 않는다.
- B 는 사전 등록 기준에 OOS 기대값 > 0 도 있었고, 그 조건을 만족한 코인은 11/21 이었다. 판정식만 바꿔도 B 가 통과로 바뀐다고 말할 수 없다.
- B 를 수정 식으로 다시 계산해 볼지는 리뷰 결정이다. 하더라도 결과 뒤 재계산이므로 **참고 값일 뿐 독립 검증이 아니다.**
