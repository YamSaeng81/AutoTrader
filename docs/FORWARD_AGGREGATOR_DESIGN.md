## 3. 회계 — 수수료·슬리피지

### 3-1. 엔진이 실제로 하는 계산 (모의, `PaperTradingService`)

| | 식 | 위치 |
|---|---|---|
| 매수 금액 | `invest = 가용현금 × investRatio`(소수 2자리 버림) | `:937-940` |
| 매수 체결가 | `신호가 × (1 + 0.001)` — 슬리피지 0.1% | `:950`, `TradingConstants.PAPER_SLIPPAGE_PCT` |
| 매수 수수료 | `invest × 0.0005` | `:953`, `TradingConstants.FEE_RATE` |
| 수량 | `(invest − 수수료) / 체결가`(8자리 버림) | `:955` |
| 기록 | 포지션 `invested_krw = invest` · `entry_price = 체결가` · `avg_price = invest / 수량` · `position_fee = 매수 수수료`. 현금 `−invest` | `:986-1023` |
| 매도 체결가 | `신호가 × (1 − 0.001)` | `:1044` |
| 매도 | `proceeds = 수량 × 매도 체결가`, 수수료 `proceeds × 0.0005`, 현금 `+(proceeds − 수수료)` | `:1047-1079` |
| 실현 손익 | `realized_pnl = (proceeds − 매도 수수료) − 수량 × avg_price` = 양쪽 수수료·슬리피지가 모두 빠진 값 | `:1051-1054` |
| 엔진의 평가자산 | `total_krw = 가용현금 + 보유수량 × 현재가` — 매도 비용을 미리 빼지 않는다 | `:1104-1118` |

📌 매도 체결가는 포지션 행에 없다 — **매도 주문 행**(`paper_trading."order"`, `side='SELL'`, `position_id`)의 `price` 에서 얻는다.
모의 엔진에 부분 매도 경로는 없다(포지션 하나 = 매수 하나 + 매도 하나). 구현 시 위반이 나오면 계산하지 않고 중단한다(§9 F12).

### 3-2. 집계기가 하는 계산

- **현금** = 1,000,000 − Σ(그 시점까지 매수의 `invested_krw`) + Σ(그 시점까지 매도의 `수량 × 매도가 × (1 − 0.0005)`)
- **평가자산** = 현금 + Σ(열린 포지션 `size`) × 평가 가격 — PREREG §3 정의 그대로. 엔진 `total_krw` 와 같은 방식이다.
- 🔴 **슬리피지는 체결가에 이미 들어 있다. 다시 빼지 않는다**(역사적 러너 `SupertrendValidationRunner.java:265` 와 같은 원칙).
- **순수익(코인·팔)** = `(E[T_end] − 1,000,000) / 1,000,000 × 100`
- **거래당 순수익률(왕복 하나)** = `realized_pnl / (size × entry_price) × 100`
  - 분모 = 체결가 기준 진입 금액(수수료 제외) — 역사적 러너의 `entryAmount = 체결가 × 수량`(`:292`)과 같은 정의
  - 분자 = 양쪽 수수료·슬리피지를 뺀 값 → **R4**

### 3-3. 🔴 역사적 러너에서 발견한 불일치 — 기록만 한다

역사적 검사의 왕복 순손익은 `net = 청산 체결금액 − 진입 체결금액 − fee` 인데, 여기서 `fee` 는 **매도 수수료 하나**다(`SupertrendValidationRunner.java:302`).
바로 위 주석은 "(양쪽 수수료)" 라고 적었다(`:301`). 백테스트 엔진은 매수 수수료를 따로 기록하므로(`BacktestEngine.java:370·394`) 현금·평가자산에는 빠짐없이 반영됐고, **거래당 순수익률에서만 매수 수수료가 빠졌다.**

- 매수 수수료는 진입 체결금액의 정확히 0.05% 이므로, 계산상 거래당 순수익률이 **0.05%p 높게** 나온 것으로 보인다(주 +0.7121% → 약 +0.66%, 스트레스 +0.4884% → 약 +0.44%). 두 값 모두 기준(≥ 0.10% / > 0)을 넘으므로 **(나) 판정은 바뀌지 않는 것으로 보인다.** 🔴 **재실행으로 확인하지 않았다.**
- 순수익·자산곡선·(가) 는 영향이 없다(현금 경로는 매수 수수료를 뺐다).
- 전향 집계기는 **문서 정의(수수료 양쪽)** 를 따른다. 역사적 결과를 고칠지는 별도 판단이다 → **R4**

| 검증 | 기준 |
|---|---|

| Σ 포지션 `realized_pnl` ↔ `virtual_balance.realized_pnl` | 같음(허용오차 내) |

- ② 와 ⑤ 의 경계: **주문 0 이면서 평가 기록도 거의 없으면**, "거래가 없었다" 가 아니라 "작동하지 않았다" 일 수 있다(PREREG '시작 전 확인' — 워밍업 부족이면 팔이 조용히 아무것도 안 한다). 집계기는 세션별 일평균 평가 기록 수를 함께 출력한다. 몇 건 미만을 ④ 로 볼지는 → **R7**
- 평가 가격 결측의 처리 순서:
  1. 보유 0 이면 가격이 필요 없다 — 결측이 아니다(E = 현금).
  2. 캐시에 그 봉이 있으면 쓴다.
  3. 캐시에 없고, **거래소에도 그 봉이 없음**(무거래 시간 — 업비트는 체결이 없는 봉을 만들지 않는다. 개입 #2 의 HIVE·DKA·ELF·GLM 5봉 사례)이 확인되면 직전 종가를 잇는다. 확인 근거(조회 시각·응답)를 출력에 남긴다.
  4. 확인할 수 없으면 ④. 🔴 거래지원이 끝난 코인은 거래소가 과거 봉도 주지 않는다(BLAST `candles` 404, 10-27 확인) — 그 코인은 캐시가 유일한 출처다.
- BLAST 의 정지 전 구간(T0 ~ 10-27 04:05Z)은 주문 0·포지션 0 이 대조로 확인됐으므로(PREREG 집행표) 평가 가격 없이 E = 1,000,000 이다. 10-26 02:00Z 이후 BLAST 봉이 캐시에 없어도 결측이 아니다(보유 0).

## 11. 이 설계가 하지 않는 것

- 검증 기간·종료 조건·판정 기준·분모·T0 를 다시 정하지 않는다.
- 운영 DB 를 조회하지 않았고, 중간 성과를 계산하지 않았다. 구현 후에도 `final` 은 종료 뒤 한 번만 돌린다(PREREG §7).
- 개입 구간을 잘라내는 옵션을 두지 않는다.
- R4·R12·R13 처럼 결과에 직접 영향을 주는 선택은 **결과를 보기 전에** 리뷰에서 정하고 이 문서에 고정한다.
