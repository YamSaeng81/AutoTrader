## 2. 시각 규칙 — 일별 평가와 종료점

### 2-1. 기준 시각은 매도·매수 **주문의 `filled_at`** 하나다

모의 엔진은 청산 때 포지션 `closed_at`(`PaperTradingService.java:1059`)과 매도 주문 `filled_at`(`:1075`)을 **서로 다른 `Instant.now()`** 로 기록한다. 두 값은 같은 순간이 아니다.
집계기는 **주문의 `filled_at` 만** 쓴다 — 매수 체결 = 매수 주문 `filled_at`, 왕복 완료 = 그 포지션의 **검증된**(§3-4 짝 검사를 통과한) 매도 주문 `filled_at`. 포지션의 `opened_at`·`closed_at`·현재 `status` 는 시각 판단에 쓰지 않는다(대조용으로만 출력).

### 2-2. 두 가지 포함 규칙 — 섞지 않는다

| | 규칙 | 쓰는 곳 |
|---|---|---|
| **일별 경계** | `filled_at < 경계` 인 체결을 그날까지에 넣는다. 경계 = 매일 **00:00:00Z** | `E[d]` (d 일 다음 날 00:00Z 시점) |
| **최종 종료점** | `filled_at ≤ T_end` 인 체결을 모두 넣는다 | `E[T_end]`, 순수익, 거래 수, 거래당 순수익률 |

- 200거래 종료이면 `T_end` = **종료를 결정한 200번째 청산의 매도 `filled_at`** 이고, 그 청산은 `≤` 규칙으로 **최종 집계에 포함된다.** 같은 `filled_at` 이 여럿이면 주문 id 오름차순으로 순서를 정한다(200번째를 특정하기 위함). 같은 시각의 다른 체결도 `≤` 로 함께 들어간다.
- 6개월 종료이면 `T_end` = **2027-04-01T06:16:12.634313Z**(R9), 같은 `≤` 규칙.
- `T_end` 가 날짜 경계와 겹치면 `E[마지막 날]` 과 `E[T_end]` 는 포함 규칙이 달라 다를 수 있다 — 최종 점은 항상 `E[T_end]` 로 따로 계산하고 마지막 일별 변화는 `E[T_end] − E[직전 경계]` 로 잇는다.

## 3. 회계 — 수수료·슬리피지

### 3-1. 엔진이 실제로 하는 계산 (모의, `PaperTradingService`)

| | 식 | 위치 |
|---|---|---|
| 매수 금액 | `invest = 가용현금 × investRatio`(소수 2자리 버림) | `:937-940` |
| 매수 체결가 | `신호가 × (1 + 0.001)` — 슬리피지 0.1% | `:950`, `TradingConstants.PAPER_SLIPPAGE_PCT` |
| 매수 수수료 | `invest × 0.0005` | `:953`, `TradingConstants.FEE_RATE` |
| 수량 | `(invest − 수수료) / 체결가`(8자리 버림) | `:955` |
| 기록 | 포지션 `invested_krw = invest` · `entry_price = 체결가` · `avg_price = invest / 수량` · `position_fee = 매수 수수료`. 현금 `−invest` | `:986-1023` |
| 매도 체결가 | `신호가 × (1 − 0.001)` | `:1044` |
| 매도 | `proceeds = 수량 × 매도 체결가`, 수수료 `proceeds × 0.0005`, 현금 `+(proceeds − 수수료)` | `:1047-1079` |
| 실현 손익 | `realized_pnl = (proceeds − 매도 수수료) − 수량 × avg_price` = 양쪽 수수료·슬리피지가 모두 빠진 값 | `:1051-1054` |
| 엔진의 평가자산 | `total_krw = 가용현금 + 보유수량 × 현재가` — 매도 비용을 미리 빼지 않는다 | `:1104-1118` |

📌 매도 체결가는 포지션 행에 없다 — **매도 주문 행**(`paper_trading."order"`, `side='SELL'`, `position_id`)의 `price` 에서 얻는다.
모의 엔진에 부분 매도 경로는 없다(포지션 하나 = 매수 하나 + 매도 하나). 위반이 나오면 계산하지 않고 중단한다(§9 F12).

### 3-2. 집계기가 하는 계산 (시각 t 기준, 포함 규칙은 §2-2)

- **현금(t)** = 1,000,000 − Σ(t 까지 매수의 `invested_krw`) + Σ(t 까지 매도의 `수량 × 매도가 × (1 − 0.0005)`)
- **평가자산(t)** = 현금(t) + Σ(t 에 보유 중인 포지션 `size`) × 평가 가격 — PREREG §3 정의, 엔진 `total_krw` 와 같은 방식
- 🔴 **슬리피지는 체결가에 이미 들어 있다. 다시 빼지 않는다**(역사적 러너 `SupertrendValidationRunner.java:265` 와 같은 원칙)
- **순수익(코인·팔)** = `(E[T_end] − 1,000,000) / 1,000,000 × 100`
- **거래당 순수익률(왕복 하나)** = `realized_pnl / (size × entry_price) × 100` — 매도 `filled_at ≤ T_end` 인 왕복만
  - 분모 = 체결가 기준 진입 금액(수수료 제외) — 역사적 러너의 `entryAmount = 체결가 × 수량`(`:292`)과 같은 정의
  - 분자 = **양쪽 수수료**·슬리피지를 뺀 값 — **R4 승인**

### 3-3. 역사적 러너의 매수 수수료 누락 — 확인됨, 정정은 분석층에서

역사적 검사의 왕복 순손익은 `net = 청산 체결금액 − 진입 체결금액 − fee` 이고, 여기서 `fee` 는 **매도 수수료 하나**다(`SupertrendValidationRunner.java:302`). 바로 위 주석은 "(양쪽 수수료)" 라고 적었다(`:301`). 백테스트 엔진은 매수 수수료를 따로 기록하므로(`BacktestEngine.java:370·394`) 현금·평가자산에는 반영됐고, **거래당 순수익률에서만 매수 수수료가 빠졌다.** 리뷰가 코드에서 확인했다(2026-10-27).

- 영향 범위: 거래당 순수익률(§4(나) 의 한 항목). 순수익·자산곡선·(가) 는 현금 경로가 매수 수수료를 뺐으므로 해당하지 않는다.
- 🔴 **정정 수치와 (나) 판정이 그대로인지는 아직 적지 않는다** — 재확인 전이다(리뷰 1차). 초안 `86a10f8` 에 적었던 근사치는 철회한다.
- 처리 방식(리뷰 1차): **원본 산출물은 보존**한다(PREREG '결과 (2026-09-24)' 의 수치와 `d:/tmp/stval_out` 을 고치거나 덮어쓰지 않는다). 정정은 **분석층**에서 — 러너의 왕복 계산을 고치고 정정본을 별도 산출물로 낸 뒤, 두 값을 나란히 기록한다. 이 정정은 집계기 구현과 별개 작업이며 아직 하지 않았다.

### 3-4. 추출 스냅샷과 두 종류의 대조

🔴 **한 번의 추출 = 하나의 스냅샷.** 모든 조회를 `BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY;` 한 트랜잭션 안에서 실행하고 `ROLLBACK` 으로 끝낸다. 엔진은 계속 쓰고 있으므로, 세션·포지션·주문을 서로 다른 시점에 읽으면 짝이 어긋난다. 스냅샷 시각(`transaction_timestamp()`)을 출력에 남긴다.

| | ① 추출 시점 잔액 검산 | ② `T_end` 성과 계산 |
|---|---|---|
| 목적 | 재구성 로직과 원자료가 **엔진 장부와 맞는가** | 판정 입력 |
| 대상 체결 | 스냅샷에 보이는 **전부** | `filled_at ≤ T_end` 만 (일별은 `< 경계`) |
| 비교 | 재구성 현금 ↔ `virtual_balance.available_krw` · Σ 포지션 `realized_pnl` ↔ `virtual_balance.realized_pnl` · Σ 수수료 ↔ `virtual_balance.total_fee` | `Σ r × 초기자본 = E[T_end] − 1,000,000`(망원합 — 집계 누락만 잡는다) |
| 보유 판단 | 스냅샷의 `status` 와 재구성 결과가 같은가(대조) | `filled_at` 으로만(§2-3) |

공통 구조 검사: 모든 포지션에 매수 주문 1 · CLOSED 포지션에 매도 주문 1 · 짝 없는 주문 0 · T0 이전 주문 0 · 확인된 종료 세션은 정지 시각 이후 주문 0·정지 시각에 보유 0.

하나라도 실패하면 **판정을 출력하지 않는다.**

### 3-5. 잔액 검산 허용오차 — 반올림 위치·횟수에서 나온 상한 (R5, 리뷰 2차)

🔴 초안의 "세션당 1원" 은 **철회**한다 — 근거가 없었고, 아래 상한으로 보면 왕복 300건에서 정상 장부를 실패시킬 수 있다.
허용오차는 **시험에서 관측한 최대 차이가 아니라** 반올림이 어디서 몇 번 일어나는지에서 정한다. 1·50·300건 시험은 이 규칙을 **검증하는 자료**다.

**① 반올림이 일어나는 곳 — 세션 행 세 컬럼뿐이다**

| 값 | 저장 형식 | 저장 때 바뀌는가 |
|---|---|---|
| 세션 `available_krw`·`total_fee`·`realized_pnl` | `NUMERIC(20,2)` (`V8`·`V18`) | **바뀐다** — 엔진 값은 소수 2자리를 넘는다(수수료 `× 0.0005`, 매도 금액 `수량 × 가격`) |
| 포지션 `invested_krw` | `NUMERIC(20,8)` (`V73:25`) | 아니다 — 엔진이 이미 2자리로 버림(`:939-940`) |
| 포지션 `size`·`entry_price`·`avg_price`, 주문 `price`·`quantity` | `NUMERIC(20,8)` | 아니다 — 엔진이 이미 8자리로 맞춤(`:951·955·962·1045`) |

재구성은 둘째·셋째 줄의 값만 쓰므로 **재구성 쪽 오차는 0** 이다 — 엔진이 계산한 반올림 전 값을 그대로 다시 만든다(시험 720회 전부 차이 0).

**② 저장 한 번의 오차 ≤ 0.005원** — PostgreSQL 은 `NUMERIC(p,2)` 저장 때 가장 가까운 값으로, 정확히 절반이면 0 에서 먼 쪽으로 반올림한다(로컬 PostgreSQL 15.13 에서 확인: `2.505 → 2.51`, `−2.505 → −2.51`, `2.50499999 → 2.50`).

**③ 오차가 남는 횟수** — 세션 잔액을 쓰는 코드는 `PaperTradingService` 의 매수(`:1021-1023`)와 청산(`:1079-1083`)뿐이다(다른 서비스는 모의 세션을 읽기만 한다 — 코드 확인). 엔진은 저장한 뒤에도 반올림 전 값을 들고 있다가 **다음 틱에 다시 읽을 때** 반올림된 값을 받는다. 같은 틱에 이어진 계산(청산 직후 매수)은 반올림 없이 이어지고 마지막 저장만 남으므로, **남는 반올림 수는 저장 횟수를 넘지 않는다.**

| 컬럼 | 상한 | 이유 |
|---|---|---|
| `available_krw` | **0.005 × 매도 수** | 다시 읽은 값(2자리)에서 출발한 매수는 `2자리 − 2자리` 라 반올림이 없다. 같은 틱 청산 직후 매수는 반올림 전 값에서 출발해 그 저장에 반올림이 생기지만, 직전 매도 저장의 반올림을 덮어쓴다 → 매도 하나당 최대 한 번 |
| `total_fee` | **0.005 × (매수 수 + 매도 수)** | 매수 수수료(`투자금 × 0.0005`, 최대 6자리)·매도 수수료 모두 2자리를 넘는다 |
| `realized_pnl`(세션) | **0.005 × 매도 수** | 매도 때만 바뀐다 |

판정: `|세션 값 − 재구성 값| ≤ 상한`(같으면 통과). 거래 0건이면 상한 0 — 정확히 같아야 한다. 왕복 300건이면 잔액 1.5원·수수료 3.0원·실현손익 1.5원이다.

**④ 상한은 원리상 도달 가능하다** — 엔진 식 한 번으로 상한에 닿는 값이 있다(가용 6,262.50원 × 0.80 = 투자 5,010.00원 → 수수료 2.505원 → 저장 2.51원, 차이 +0.005). 같은 방향의 끝자리 5 가 반복되면 저장마다 0.005 씩 선형으로 쌓인다(300번 → 1.5원). 🔴 엔진이 실제로 300번 연속 같은 방향을 만드는지는 보이지 않았다 — **원리상 가능한 최대**라는 것까지다.

**⑤ 시험 결과(F20, `scripts/forward_aggregate/test_ledger_rounding.py`, 10/10)** — 가격대 3(5원·1,000원·700,000원) × 투자비율 2(0.80·1.00) × 같은 틱 이어짐 2 × 시드 20 = 건수마다 240회:

| 왕복 | 관측 최대 \|차이\| (잔액 / 수수료 / 실현손익) | 상한 | 최대 차이 ÷ 상한 |
|---|---|---|---|
| 1 | 0.004997 / 0.004973 / 0.004997 | 0.005 / 0.010 / 0.005 | 0.999 |
| 50 | 0.064 / 0.077 / 0.056 | 0.25 / 0.50 / 0.25 | 0.257 |
| 300 | 0.121 / 0.212 / 0.121 | 1.5 / 3.0 / 1.5 | 0.081 |

관측값은 무작위 오차가 상쇄돼 상한보다 훨씬 작다 — 🔴 **그래서 관측 최대를 허용오차로 쓰지 않는다.** 엔진이 실제로 만들 수 있는 정상 장부를 실패시킬 수 있기 때문이다.
변이 검증 4건 — 허용오차 절반 · 재구성에서 매도 수수료 누락 · DB 가 반올림 대신 버림 · 수수료 상한을 매도 수로만 — 모두 시험이 실패로 잡았다.

**⑥ 이 규칙의 전제 — 남은 확인**

- 🔴 **Hibernate·JDBC 가 `BigDecimal` 을 자르지 않고 그대로 DB 에 넘긴다**는 전제다. 중간에서 버림이 일어나면 저장 한 번 오차가 0.01원 가까이 되어 규칙이 깨진다(변이 '버림' 이 그 경우다). → **구현 단계에서 로컬 DB 에 엔진 경로로 저장해 확인한다.** 운영에서 시험하지 않는다.
- 세션 잔액을 쓰는 경로가 위 두 곳뿐이라는 전제 — 다른 경로가 생기면 규칙을 다시 본다.
- 부분 매도가 없다는 전제(§3-1).
- 🔴 **검출 한계**: 상한 이내의 불일치는 원리상 잡지 못한다. 상한의 2배를 넘는 조작은 60/60 검출됐다.
- 🔴 실제 추출에서 상한을 넘으면 **허용오차를 넓히지 않고 원인을 찾는다.**

## 4. 두 축으로 기록한다 — 자산을 계산할 수 있는가 / 운용 공백이 있었는가

🔴 두 질문은 서로를 대신하지 않는다(리뷰 1차 R7). 집계기는 세션·일자마다 **측정 분류 하나**와 **운용 공백 표시**를 따로 출력한다.

### 4-1. 측정 축 — 판정 입력

| 분류 | 조건 | 자산곡선 처리 | 판정에서 |
|---|---|---|---|
| ① 정상 관측 | 회계 검증 통과, 보유 중이면 그날 평가 가격 있음. **그날 체결이 있었는지와 무관하다** | `E = 그 시점까지의 재구성 현금 + 그 시점 보유수량 × 평가 가격`. 🔴 **무체결일도 이 식으로 계산한다** — 이전부터 보유 중이면 가격 변화로 E 가 바뀌고, 실현손익이 생긴 뒤 현금만 들고 있으면 E = **그 현금**(100만원이 아니다) | 그대로 |
| ② **T0 이후 체결 0건 세션** | ① 의 특수한 경우. 그 세션의 주문이 **T0 부터 `T_end` 까지 0건**이고, 추출 스냅샷 잔액 검산에서 `available_krw = 1,000,000`(이 경우 허용오차 0, §3-4)이 확인된 경우**에만** | 1,000,000 유지 — 재구성 결과가 그 값이라는 뜻이지, 주문이 없으니 100만원으로 놓는다는 뜻이 아니다 | 순수익 0. 양수 코인·개선 코인으로 **세지 않는다**(0 은 > 0 이 아님) |
| ③ **확인된 종료 — 현금 연장** | 집계기 **입력 파일에 명시된** 세션만(현재 576·577·578). 정지 시각·정지 시 현금·근거 기록(PREREG 📌 KRW-BLAST 집행표)이 있어야 한다 | 정지 시각 이후 `T_end` 까지 확인된 현금으로 잇는다. 가상 체결 없음 | 22·66 에 포함. 정지 전 구간은 ① 또는 ② |
| ④ **측정 결측** | 보유 중인데 평가 가격을 확정할 수 없음 · 회계 불일치 · 세션·주문·포지션 행 누락 · 입력 파일에 없는 세션이 RUNNING 이 아님 | **채우지 않는다.** 0 수익·현금·직전 값으로 메우지 않는다 | 해소되지 않으면 **판정 불가** — **R6 동의** |

- 🔴 **③ 은 상태값으로 추론하지 않는다.** `status='STOPPED'` 만 보고 현금 연장을 적용하면 정지 사유·정지 시 보유가 확인되지 않은 세션까지 조용히 0 수익이 된다.
- 평가 가격 결측의 처리 순서:
  1. 보유 0 이면 가격이 필요 없다 — 결측이 아니다(E = 현금).
  2. 캐시에 그 봉이 있으면 쓴다.
  3. 캐시에 없고 **거래소에도 그 봉이 없음**(무거래 시간 — 업비트는 체결이 없는 봉을 만들지 않는다. 개입 #2 의 HIVE·DKA·ELF·GLM 5봉 사례)이 확인되면 직전 종가를 잇는다. 확인 근거(조회 시각·응답)를 출력에 남기고 데이터 복구로 기록한다.
  4. 확인할 수 없으면 ④. 거래지원이 끝난 코인은 거래소가 과거 봉도 주지 않는다(BLAST `candles` 404, 10-27 확인) — 캐시가 유일한 출처다.
- BLAST 의 정지 전 구간(T0 ~ 10-27 04:05Z)은 주문 0·포지션 0 이 대조로 확인됐으므로(PREREG 집행표) 평가 가격 없이 E = 1,000,000 이다.

## 6. 판정 계산

| 지점 | 역사적 구현 | 전향 설계 |
|---|---|---|
| 블록 나누기 | 첫 날부터 L일씩, 마지막 짧은 블록도 하나의 블록(`validation_analysis.py:61-64`) | 같게. 출발 = T0 가 속한 UTC 날짜. 6개월(UTC 날짜 183개, 첫날·끝날 부분일)이면 30일 블록 **7개**(마지막 3일)뿐이다 — 사실로 보고하고 바꾸지 않는다 |
| (가) 코인 집합 | 22 | **22 고정** — BLAST 는 A−B = 0 으로 들어가고 '개선 코인' 으로 세지 않는다(사후 규칙 5 의 결과) |
| (나) 평균·중앙값 순수익, 양수 코인 | 22 기준 | **22 고정.** 거래 0건 코인·BLAST 는 순수익 0, 양수 아님 |
| (나) 거래당 순수익률 | 왕복이 있는 코인만 평균(`validation_analysis.py:137`) | **R12 확정 — 거래가 있는 N코인의 평균.** 왕복 0 코인은 그 지표가 **정의되지 않으므로 0 을 만들지 않는다.** 출력에 **N/22 와 코인별 왕복 수**를 함께 표시. N=0 이면 **NA**. 🔴 코인을 검증에서 빼는 것이 아니다 — 같은 코인이 순수익·A−B·양수 코인 수에는 그대로 들어간다 |
| (나) 스트레스 열 | 슬리피지 0.2% 로 **엔진을 다시 실행**(PREREG §2 "사후 차감이 아니다") | **R13 확정 — 미검증이면 NA.** 66세션은 0.1% 로만 돌았으므로 현재 설계로는 NA 다 |

📌 **N=0 이 판정에 나타나는 경우**: 종료 조건이 팔마다 왕복 ≥ 100 을 요구하므로, 판정이 성립하는 종료에서 A 의 N 은 1 이상이다. NA 는 건수 미달(판정 불가)이나 진단 출력에서만 생긴다.

### 6-1. 스트레스가 NA 일 때 (나) 의 결과 표시 (R13)

| 주 비용 네 항목 | 스트레스 | (나) 표시 |
|---|---|---|
| 하나라도 미달 | (무관) | **미충족** — 주 비용 미달만으로 결론이 난다 |
| 모두 충족 | NA | **미확정(스트레스 미검증)** — 🔴 **'충족' 으로 쓰지 않는다.** 선택지 ①(주 비용만으로 충족) 반려 |
| 모두 충족 | 검증됨 | 사전 등록 그대로 |

- 사후 차감 근사(체결가에 편당 0.1%p 를 더 얹은 재계산)는 **참고값으로만** 출력하고 표시명에 "참고·사후 차감, 판정 아님" 을 붙인다.
- 🔴 **후속 표시는 "미확정 유지 · 실전 진입 불가"** 다(리뷰 2차). 사전 등록의 네 결과 표(PREREG §4, `LIVE_ENTRY_PREREG.md` §1)에는 이 칸이 없으므로 그대로 적는다 — **'미충족' 으로 바꿔 쓰지 않고, 주 비용만으로 통과시키지도 않는다.**
- 종료 후 **별도 재실행**으로 스트레스를 검증할 수 있는지는 재현 범위(같은 구간·같은 캔들·같은 전략 상태 초기화 방식)와 엔진(모의 엔진 재현인지 백테스트 엔진인지)을 정한 **별도 설계**를 먼저 리뷰받는다. 그 설계 전에는 NA 다.
- 실전 단계의 실측 비용 재계산(`LIVE_ENTRY_PREREG.md` §4)은 **실전 진입의 별도 관문**이며 이 스트레스 검증을 대신하지도, 이것과 모순되지도 않는다(리뷰 1차 — 초안의 "두 문서의 방식이 다르다" 는 철회).

```
① 고정 설정 (저장소 커밋, SHA 로 고정)
     sessions: 66개 id → (coin, arm)   ← PREREG 표에서. RUNNING 조회나 CSV 의 코인 목록에서 만들지 않는다
     t0, initial_capital, fee_rate 0.0005, slippage 0.001(검산용), 허용오차 규칙(§3-5 — 숫자가 아니라 저장 횟수 × 0.005)
     confirmed_ends: [{id, stopped_at, cash, 근거 문서 위치}]   ← 현재 576·577·578
     t_end: 종료 시각(종료 판단 뒤 기록)
② 추출 SQL (운영자 실행)
     BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY;  … 전부 한 스냅샷 …  ROLLBACK;
     세션 66행 · 포지션 · 주문 · H1 캔들 22코인 · 신호 기록 일별 건수 · transaction_timestamp()
③ 계산기 (로컬 Python, CSV 입력만, 네트워크 없음)
     count   — 팔별 청산 왕복 수만 (손익 계산 안 함)
     verify  — §3-4 ① 잔액 검산 + 구조 검사 + §4 측정 분류. 실패 시 종료 코드 ≠ 0
     final   — verify 통과 시에만: §2-2 규칙으로 일별 E·E[T_end], (가)(나), 부트스트랩, 운용 공백 목록
```

- 🔴 **입력 검증이 먼저다**: 66개 id 가 정확히 한 번씩, 코인·팔이 고정 설정과 같고, 22코인 × 3팔. 어긋나면 계산하지 않는다(**fail closed**).

- 출력에 입력 파일 해시·설정 SHA·스냅샷 시각·실행 시각을 남긴다.

## 11. 이 설계가 하지 않는 것

- 검증 기간·종료 조건·판정 기준·분모·T0 를 다시 정하지 않는다.
- 운영 DB 를 조회하지 않았고, 중간 성과를 계산하지 않았다. 구현 후에도 `final` 은 종료 뒤 한 번만 돌린다(PREREG §7).
- 개입 구간을 잘라내는 옵션을 두지 않는다. 운용 공백 축에 수치 기준을 두지 않는다.
- 역사적 결과의 원본 수치를 고치지 않는다.
- 초기화 서비스를 호출하지 않는다. 서버 자동화를 설치하지 않는다.
