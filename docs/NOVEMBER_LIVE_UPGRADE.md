수익 목표는 기존 결정인 **허용한 위험 안에서 거래 비용을 뺀 절대수익**이다. 실제 성과는 현금·보유 평가액·수수료·슬리피지를 함께 기록해 판단한다. 현재 승인된 56일 제한시험의 목적과 진입 조건을 수익성 입증 조건으로 바꾸지 않는다. 시작 전 HOLD나 관문 차단도 규칙에 맞으면 정상이며, 거래 건수를 늘리려고 신호·위험 한도를 바꾸지 않는다.

## 1. 총괄의 운영 방식

- 총괄: 운영 보고와 코드·시험을 대조해 위험을 찾고, 우선순위·담당·완료 조건을 정한다. 결과를 확인해 완료·추가 보완·보류를 판정한 뒤 다음 작업을 지정한다.
- 개발: 재현 자료, 변경 범위, 관련 시험의 원문, 실패 이력, 고정 SHA를 남긴다. 운영 반영이 필요한 변경은 배포 후보·복구 방법·F1 기대값까지 준비한다.
- 운영자 확인이 필요한 계좌·휴대폰 수신·서버 실행은 구체적인 명령과 기대값으로 전달한다. 실제로 받지 못한 결과는 확인됐다고 쓰지 않는다.
- 로컬 검토·보완·관련 시험은 지시한 범위 안에서 진행한다. 이미 통과한 시험은 새 실패·변경·공백과 관계가 있을 때만 다시 돌린다. 확인만을 위한 회신·커밋을 반복하지 않는다.
- 다음 보고마다 이 목록의 상태와 근거를 갱신한다. 자동 감시·서버 조회를 수행하지 않은 동안에도 확인했다고 기록하지 않는다.

### N01. 거래소 DOWN → UP이 제한시험을 다시 여는지

**코드로 확인한 접점**: 운영 `cad3939`의 `LiveTradingService.onExchangeDown`은 RUNNING 세션을 복구 대상에 넣는다. `onExchangeRecovered` → `restartAfterExchangeRecovery` → `startLocked`는 비상정지 세션을 RUNNING으로 만들고 `started_at`을 현재로 다시 쓴다. 기존 `ExchangeRecoveryRestartTest`는 일반 세션의 자동 복구를 정상 동작으로 검증한다. SMA20 제한시험의 중단 후 재개 금지·최초 시작 + 56일과 연결한 검증은 확인되지 않았다.

**개발 지시**:

1. SID 203과 같은 설정의 로컬 시험 세션으로 매수·정산 → DOWN → UP → 반복 UP을 이어 재현한다. 운영 세션이나 API는 사용하지 않는다.
2. 비상정지 유지, 최초 `started_at`과 종료 시각 보존, 추가 매수 0, 청산·정리 작업 비중복을 확인한다. 주문 접수만으로 청산 완료를 쓰지 않는다.
3. 기존 코드가 이 기대와 다르면 실패를 먼저 남기고, 제한시험의 재개 금지 정책을 명시적으로 연결하는 최소 수정을 준비한다. 일반 세션의 승인된 자동 복구 동작과 혼합하지 않는다. 판별 정책과 영향 범위를 총괄에게 제시한다.
4. 기존 일반 세션 복구 시험과 변경 경로만 회귀한다. 재현 결과·실패/수정 후 원문·대상 파일·고정 SHA·배포 필요 여부를 보고한다.

이는 새로운 손실 한도나 시작 조건을 만드는 작업이 아니라 이미 정한 중단·기간 규칙을 실제 이벤트 경로와 맞추는 작업이다. 현재 운영 SID 203은 CREATED이므로 이 확인을 위해 운영을 시작하거나 재기동하지 않는다.

### N02. 낡은 시세가 실시간 손절 주문으로 이어지는지

**코드로 확인한 접점**: 운영 `cad3939`의 LIVE·DYNAMIC 실시간 이벤트 처리기는 이벤트의 가격을 사용하며 관측 시각을 직접 확인하지 않는다. 반면 기존 `CandleGapExitTest`와 `PoolLossLimitTest`는 시세 장부·캔들 없는 평가에서 낡은 값이 거절되는 경로를 검증한다. 보유 세션의 실제 이벤트 처리 → 보호 매도까지 잇는 검증은 확인되지 않았다.

**개발 지시**:

1. 기존 시세 유효기간 정의를 확인한 뒤, 진입가 300·손절가 285인 보유 시험 세션에 121초 전 가격 280 이벤트를 넣는다. 매도 0·OPEN 유지와 보호 점검 시각·가격 이력이 최신처럼 갱신되지 않는지 본다.
2. 같은 가격의 신선한 이벤트는 보호 매도 1회로 연결돼야 한다. 기존 중복 매도 방지 시험과 대조한다. LIVE·DYNAMIC 공통 영향 범위를 구분한다.
3. 실패하면 누락된 유효성 검사를 기존 정의에 맞게 연결한다. 관측 시각·발행 시각·수신 시각을 구분하고, 새 시간 한도를 임의로 만들지 않는다.
4. 재현과 수정 후 결과, 기존 정상·장애 복구 경로 영향, 배포 필요 여부를 보고한다. 전체 회귀·격리 리허설부터 반복하지 않는다.

## 4. 결과 확인 기준

- 코드에서 보이는 위험은 **검토 결과**, 실제로 실패한 시나리오는 **재현 확인**, 수정 뒤 해당 시나리오가 통과한 것은 **로컬 검증**, 운영 출력까지 맞은 것은 **운영 반영 확인**으로 구분한다.
- 완료 보고에는 문제·원인·바뀐 동작·영향 범위·실행한 시험·실패 이력·SHA·운영 반영 여부를 포함한다. 총괄은 같은 문제를 잡는 시험인지와 실제 적용본이 일치하는지 확인한다.
- 수익은 실제 순손익과 비용으로 확인한다. 시험 수·커밋 수·매수 횟수를 수익 성과로 세지 않는다. 추가 입금·증액·자동 연장, 종료 후보 재개·결과를 본 뒤 전략 파라미터 탐색은 이 작업 목록에 포함하지 않는다.
- 운영 배포·활성화는 구체적인 후보와 검증 결과를 갖춰 기존 절차대로 판단한다. 확인하지 않은 서버 상태나 수익을 완료로 기록하지 않는다.
