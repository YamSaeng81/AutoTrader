## 1. 코드에서 확인한 사실

### 1.1 위험 판정의 호출 경로

| | |
|---|---|
| 호출부 | `LiveTradingService:1159`(매수 직전), `OrderExecutionEngine:212` |

### 1.2 🟢 검증 세션은 실전 위험 판정을 오염시키지 않는다

`trade_log` 에 쓰는 곳은 **`OrderExecutionEngine` 하나뿐**이고 `PaperTradingService` 는 쓰지 않는다.
분모도 `LiveTradingSessionEntity` 만 합산한다. 따라서 **PAPER 66세션의 손익이 실전 일일 손실
판정에 섞이지 않는다.** 이것은 확인된 사실이다.

### 1.3 🔴 확인된 공백 다섯

| # | 공백 | 근거 |
|---|---|---|
| ① | **분모가 고정값이 아니다.** `LIVE_ENTRY_PREREG.md` §6 은 1단계 분모를 "그 단계 총 투입 자본(공유 풀 초기 잔액) = 100,000" 으로 등록했는데, 구현은 **RUNNING 세션 합계**다. 3세션 × 20,000 운용이면 분모 60,000 → 누적 −15% 는 **−9,000**(등록값 −15,000 이 아니다). 세션이 하나 멈추면 40,000 → **−6,000**. **등록 금액과 실제 임계가 다르고, 운용 중에 변한다** | `RiskManagementService.resolvePortfolioLimit` |
| ② | **RUNNING 세션의 `initialCapital` 합이 0 이면** 분모가 **1,000만원으로 폴백**한다(세션이 없거나 값이 null/0 인 경우). 그 경우 1일 한도 3% 는 **300,000원**이 되므로 1단계에 등록된 **−3,000원에서는 발동하지 않는다** — 한도가 100배로 희석된다. 코드 주석이 바로 이 희석 문제를 경고하는데 폴백 경로는 남아 있다. 🔴 **다만 "새 세션은 폴백 분모로 시작한다" 는 성립하지 않는다** — 세션은 `CREATED` 로 저장돼 `LiveTradingService:466` 에서 `RUNNING` 이 되고, 평가 스케줄러는 `findByStatus("RUNNING")` 만 순회하므로 평가 경로의 `checkRisk()` 시점에는 이미 분모에 포함돼 있다. **폴백이 실제로 걸리는 경로는 시험으로 가려야 한다**(§4-4) | 같은 메서드의 최종 폴백 |
| ③ | **1일 손실이 총손실(gross)이다** — `pnl < 0` 인 체결만 합산하고 이익으로 상쇄하지 않는다(의도적이며 쿼리 주석에 명시돼 있다). §6 의 "1일 손실 ≤ −3%" 는 순손익으로 읽히므로 **등록 문서와 구현의 의미가 다르다.** 구현이 더 엄격한 쪽이지만 숫자의 뜻이 같지 않다 | `TradeLogRepository.sumRealizedLossSince` |
| ④ | 구간이 **달력 하루가 아니라 직전 24시간 롤링**이다 | `checkRisk`: `now.minus(1, ChronoUnit.DAYS)` |
| ⑤ | **동시 보유 ≤ 3 이 어디에도 설정돼 있지 않다.** `maxPositions` 기본값은 **8** 이고, 주 제어는 자본 사용률이며 포지션 수는 "안전망"으로 설계돼 있다. LIVE 세션 수 상한 `MAX_CONCURRENT_SESSIONS = 10` 은 **세션 수**이지 포지션 수가 아니다 | `RiskConfigEntity:164`, `RiskEngine.check`, `LiveTradingService:94` |

### 1.4 🔴 선행 조건 3 — **초과 진입 가능성이 있는 구조**

`checkRisk()` 는 `@Transactional(readOnly = true)` 로 **승인만 돌려주고**, 매수는 그 트랜잭션
**밖에서** `executeSessionBuy` 가 따로 수행한다. 확인과 사용 사이에 간격이 있다(TOCTOU).
비관적 잠금, 원자적 카운터, 단일 직렬화 지점이 **없다.**

유일한 보호는 `OrderExecutionEngine:179` 의 중복 주문 거부인데, 이는 **같은 세션 · 같은 코인 ·
같은 방향**만 막는다. **서로 다른 세션이 각각 한도 안이면서 합계로 상한을 넘기는 것은 막지
못한다.**

🔴 **이것은 "초과 진입 가능성이 있는 구조" 라는 뜻이며, 실제로 초과가 발생한다는 확정이 아니다.**
실제 발생 여부는 스케줄러 스레드 수·트랜잭션 경계·틱 정렬에 달렸고 **동시성 시험으로만**
확인된다(§4).

## 1.5 추가 읽기 — 미확인 3건의 결과 (2026-10-06)

### (1) A군 분모 — 🔴 등록 사양과 다르다

`StrategyKillCriteriaService.decide()` (순수 함수, DB 접근 없음):

| 기준 | 구현된 식 | 등록 사양(`LIVE_ENTRY_PREREG.md` §6) |
|---|---|---|
| `CAPITAL_LOSS` | `pct(st.initialCapital(), st.totalAsset())` — **세션 초기자본** 대비 **세션 총자산** | "그 포지션에 투입한 금액(**진입 시 배정액**)" |
| `MAX_DRAWDOWN` | `pct(st.mddPeakCapital(), st.totalAsset())` — **세션 고점 자본** 대비 세션 총자산 | "그 포지션의 고점 평가액" |

🔴 **둘 다 세션 단위이고 포지션 단위가 아니다.** 따라서:

- **초기화되지 않는다.** 포지션이 닫히고 새로 열려도 분모(`initialCapital`)는 그대로이므로 판정은
  **세션 생애 전체의 누적**을 본다. 🔴 **방향을 혼동하지 않는다**: §6 은 분모를 진입 배정액으로
  바꾸면 "포지션이 닫히면 기준이 초기화되어 연속 손실의 누적은 잡지 못한다" 고 적었다 — 그것은
  **바꾼 뒤에 생기는 성질**이다. **현재 구현은 세션 생애 누적을 보므로 연속 손실을 오히려 잡는다.**
  즉 §6 의 변경은 한 포지션 안의 사고를 더 민감하게 잡는 대신 **연속 손실 감지를 포기하는
  교환**이며, 그 공백을 누적 −15%·24시간 −3% 가 메우도록 설계된 것이다.
  → §6 의 분모 변경은 **요구사항이며 아직 구현되지 않았다.** 지금 1단계를 돌리면 §6 금액표
  (`20,000 → −3,000`)가 아니라 세션 초기자본 기준으로 발동한다.
- **고점(`mddPeakCapital`)의 갱신 경로를 읽기로 확정하지 못했다.** 🔴 **고점은 원래 내려가지 않는
  값이므로 `DynamicTradingService:1165` 의 "내려가지 않는다" 주석만으로 결함을 확정하지 않는다.**
  확인해야 할 것은 그 반대 방향이다 — **평가이익이 생길 때 고점이 제대로 상승하는가.** 원가로만
  갱신되면 고점이 실제 최고 평가액보다 낮게 머물러 낙폭이 **과소 계산**된다. 실행 시험으로 넘긴다.
- 🔴 **PAPER 는 `MAX_DRAWDOWN` 판정이 아예 생략된다** — `virtual_balance` 에 `mddPeakCapital` 이
  없어 `null` 을 넘긴다(`StrategyKillCriteriaService:225` 주석). **검증 66세션에는 MDD 기준이 걸려
  있지 않다.** 이것은 검증 설계의 사실이므로 그대로 기록한다(기준을 바꾸지 않는다).

### (2) 미체결 주문의 자금·슬롯 예약 — 🔴 예약되지 않는다

LIVE(`LiveTradingService.executeSessionBuy`)와 DYNAMIC(`DynamicTradingService`) 의 순서가 같다:

```
① 잔액 확인(읽기)  →  ② 포지션 save(size = 0, status = "OPEN")
→ ③ orderExecutionEngine.submitOrderAfterCommit(order)
→ ④ availableKrw 차감 (balanceUpdater, 낙관적 잠금 + 재시도)
```

- **자금은 주문 제출 *뒤*에 차감된다.** 승인·제출 시점에 예약되지 않으므로, ①의 잔액 확인과 ④의
  차감 사이에 다른 세션이 같은 잔액을 보고 통과할 수 있다.
- **슬롯(포지션 수)은 미체결 상태에서 예약되지 않는다.** 포지션은 `size = 0` 으로 먼저 생기고,
  한도 계산에 쓰이는 `countRealPositionsByStatus("OPEN")` 은 **`size > 0` 만** 센다
  (`PositionRepository:49`). 즉 **체결 전에는 포지션 수에 보이지 않는다** — 주문 여러 건이 동시에
  떠 있어도 한도는 0 으로 보이고, 그것들이 함께 체결되면 상한을 넘는다.
- **유일한 예약은** `OrderExecutionEngine:179` 의 `ACTIVE_STATES`(PENDING·SUBMITTED·PARTIAL_FILLED)
  중복 거부이며, **같은 세션 · 같은 코인 · 같은 방향** 하나만 막는다.
- **해제 경로(취소·실패 시 자금 복원)를 읽기로 확정하지 못했다.** `OrderExecutionEngine` 에서
  `FAILED`·취소 시 `availableKrw` 를 되돌리는 코드를 찾지 못했고, 차감 쪽 주석은 "reconcile
  스케줄러와의 동시 쓰기 race" 를 언급한다 — 복원을 그 스케줄러가 맡는 것으로 보이나 **확인하지
  못했다.** 실행 시험으로 남긴다.

### (3) DYNAMIC 손익 합산 — 🔴 분자와 분모의 대상이 다르다

- **페이퍼는 섞이지 않는다(확인됨).** `DynamicTradingService:1489` 에서 `session.isPaper()` 면
  `executePaperBuy` 로 빠져 **`orderExecutionEngine` 에 도달하지 않는다.** `PaperTradingService` 도
  `trade_log` 에 쓰지 않는다. 따라서 PAPER·DYN_PAPER 의 손익은 실전 위험 판정에 들어가지 않는다.
- 🔴 **그러나 `trade_log` 는 실거래 **LIVE 와 DYNAMIC 을 구분하지 않는다.** `recordTradeLog` 는
  `orderId`·`eventType`·`detailJson` 만 남기고 `sessionKind` 를 기록하지 않으며,
  `sumRealizedLossSince` 도 구간 조건만 걸고 세션 종류·세션 상태를 걸지 않는다.
- 🔴 **중지된 세션의 손익도 분자에 들어간다.** 구간(24시간) 안의 `FILL` 이면 그 세션이 이미
  STOPPED 여도 합산된다. 반면 분모(`resolvePortfolioLimit`)는 **RUNNING LIVE 세션만** 합한다.
- **특정 조건에서는 조기 차단을 만든다** — 분자가 넓고 분모가 좁으면 손실률이 과대 계산된다.
  🔴 **그러나 이것을 "안전하다" 는 보증으로 읽지 않는다.** §1.3-② 의 **1,000만원 분모 폴백**과
  겹치면 방향이 반대로 뒤집힌다 — 분모가 100배로 커지면 같은 손실이 1/100 로 희석되어 차단이
  **늦어진다.** 두 어긋남이 함께 있으므로 **항상 보수적이라고 말할 수 없고**, 어느 쪽으로 틀리는지는
  그때의 세션 구성에 달렸다. 확실한 것은 **등록된 "1일 −3%" 의 발동 지점이 숫자와 다르다**는 것뿐이다.

### 지금 할 일 — 사람이 대신 판정한다

자동 판정이 빠져 있으므로 **읽기로 자산 곡선을 복원해 사람이 기준을 적용한다**(자동정지 OFF 에서
사람이 집행하는 기존 개입 절차와 같은 방식이다). `paper_trading.position` 의 `CLOSED` 행을
`closed_at` 순으로 누적해 세션별 고점과 현재값을 구하고, `(현재 − 고점) / 고점 ≤ −20%` 를 본다.

🔴 **이 복원의 한계를 집행 전에 명시한다 — 오차가 양방향이다.**

- **실현손익만 본다.** 미실현(보유 중 손실)이 빠져 열린 손실 포지션이 있으면 낙폭이 **작게** 나온다.
- **고점도 실현 기준**이라 평가이익으로만 올랐던 고점은 잡히지 않아 낙폭이 **작게** 나온다.
- 따라서 **−20% 근처 값은 이 방법으로 확정할 수 없다.** 명확히 넘는 세션은 실현 기준으로도 넘은
  것이므로 확정적이며, 그때는 사전 규칙대로 정지하고 **판정 시각·집행 시각·사유**를 남긴다.
- 🔴 **중간 성과를 보고 기준을 바꾸라는 뜻이 아니다.** 기준은 `KILL_CRITERIA.md` 에 등록된 −20%
  그대로이고, 바뀌는 것은 **그것을 평가하는 주체(자동 → 사람)** 뿐이다.

🔴 **범위를 한정한다 — 이것은 2026-10-06 대조 시점의 결과다.**

- 한도 −20% 에서 13%p 이상 떨어져 있으므로, **이 시점의 판단은** 복원의 양방향 오차와 무관하게
  확정적이다.
- 🔴 **그러나 "과거에 임계를 넘은 적이 없다" 는 뜻이 아니다.** 이 대조는 **현재 고점과 현재
  평가자산**만 비교한다. 자동 판정이 없던 구간에 **순간적으로 −20% 를 지나갔다가 회복한 세션이
  있었는지는 알 수 없다** — 그 시점의 평가 스냅샷이 남아 있지 않다. 확인된 것은 **지금 집행
  대상이 0건**이라는 사실뿐이다.
- 🔴 **정기 대조에는 매번 다음을 남긴다** — 사용한 **평가자산**(실현 기준인지 `total_krw` 인지),
  **고점**, **기준 시각**(UTC), **대상 세션**(어떤 상태·어떤 ID 범위를 대조했는지). 남기지 않으면
  나중에 같은 대조를 재현할 수 없고, "그때는 괜찮았다" 를 입증할 수 없다.

🔴 **공백은 해소되지 않았다.** 판정이 돌지 않으므로 **앞으로도 자동으로는 아무 일도 생기지
않는다.** 따라서 자동 판정이 복구되거나 검증이 끝날 때까지 **이 대조를 사람의 정기 점검에
포함한다** — 점검 시각은 이미 확정된 **매일 10:00 · 22:00 KST**
(`SUPERTREND_VALIDATION_PREREG.md` 의 경보 확인·집행 책임 조항)이며, 그 점검에서 **KILL 경보
확인과 함께 이 쿼리를 돌린다.** `CAPITAL_LOSS` 는 자동 판정이 살아 있으므로 추가 대조가 필요
없고, 대조 대상은 **`MAX_DRAWDOWN` 하나**다.

### 남는 선택

PAPER 에 `mddPeakCapital` 을 추가해 자동 판정을 살리는 것은 **운영 코드·스키마 변경**이다.
검증 중 동결 대상이며, **수동 대조로 등록된 중단 규칙을 계속 집행할 수 있는 동안에는 보류한다.**

🔴 **보류의 조건을 명시한다.** 다음 중 하나라도 성립하면 **검증 종료를 기다리지 않고 운영 개입
규칙을 적용한다**(개입 #1~#4 와 같은 경로):

- **수동 계산이 불가능해진다** — 대조 쿼리가 더는 고점을 복원하지 못하거나(스키마 변경·데이터
  누락), 결과가 −20% 근처로 들어와 복원 오차 때문에 판정할 수 없게 된다.
- **적시 집행이 불가능해진다** — 정해진 점검 시각에 대조를 수행할 수 없는 기간이 생긴다
  (부재 기간 등), 또는 대조에서 초과가 나왔는데 집행이 즉시 되지 않는다.

🔴 실전에서는 사람 집행으로 메울 수 없으므로 **선행 조건으로도 남긴다.**

## 4.5 🔴 배포 영향 검증은 세션 수로 끝나지 않는다 (2026-10-07)

개입 #1·#5 에서 재배포 후 **검증 66/66 RUNNING** 을 확인했다. 그것은 **세션이 죽지 않았다**는
뜻일 뿐이며 **그 구간에 평가가 빠지지 않았다는 증거가 아니다.** 프로세스 재시작은 다음을 바꾼다:

- **인메모리 상태 초기화** — 평가 중복 방지용 `lastEvaluatedClosedCandle`, 전략 인스턴스 캐시,
  `RulesetRegistry.known`, BLACK_SWAN 쿨다운 등. 복원 로직이 있는 것과 없는 것이 섞여 있다.
- **평가 공백** — 재시작에 걸린 시간만큼 60초 주기가 건너뛰어진다. `initialDelay` 가 걸린
  스케줄러는 기동 후에도 수십 초를 더 기다린다.
- **공유 자원** — DB 커넥션 풀, 스케줄러 스레드, 웹소켓 구독이 모두 새로 맺어진다.

🔴 **그러므로 "건드린 파일이 검증 경로와 겹치지 않는다" 로 배포 영향을 한정할 수 없다.** 파일
단위가 아니라 **프로세스 단위로 영향이 생긴다.** 배포는 그 자체로 개입이며, 코드 변경 범위와
무관하게 시각·사유를 기록한다.

📌 이 한계를 줄이는 방법은 **배포 횟수를 줄이는 것**이지 영향을 작게 보는 것이 아니다. 수정은
별도 브랜치·시험 환경에서 합성 데이터로 진행하고, **운영 재배포는 필요성과 검증 영향을 그때 따로
판단한다** — 수정 완료가 곧 재배포일 필요는 없다.

## 4.6 선행 조건 5번 진행 상황 (2026-10-07, 브랜치 `fix/stop-reliability` — **미배포**)

🔴 **5번 전체는 여전히 미완료다.** 아래는 어디까지 닫혔고 무엇이 남았는지다. 모든 작업은 별도
브랜치·시험 환경에서 합성 데이터로 했고 **운영 재배포는 하지 않았다.**

|---|---|---|
| ① | **동시 쓰기 중 정지가 성공하는가** | 🟡 재현·수정을 세 번 했다(PAPER 전체 재시도 / LIVE 상태 쓰기만 / `closeSessionPositions` 의 직접 쓰기 제거). 🔴 **닫지 않는다** — 정지 경로에 바깥 엔티티를 직접 쓰는 다른 자리가 남아 있는지 전수로 보지 않았다. 아래는 진행 내역이다: PAPER·LIVE 모두 재현 테스트 작성 후 수정. | ② | **미체결 주문 처리** | 🟡 **취소 결과를 거짓으로 종결하던 분기들을 고쳤다**(아래). `done → CANCELLED` 미해결도 **가려서 닫았다**. 다만 **정지가 미결 주문을 남긴 채 완료되는 정책**은 그대로다 |
| ③-1 | **늦은 신규 제출 차단** | 🟡 늦은 제출은 막힌다(거래소 신규 매수 0회). 🔴 **응답 불명 경로에서 추적 단서 없음·정지 실패**가 확인돼 ③-1 은 미완료다(아래) |

| (옛 표기) | **정지 이후 신규 매수 차단** | 🔴 **미착수.** `STOPPED` 재정지 거부만 테스트했고 그것은 다른 질문이다 — **정지 전에 `RUNNING` 을 읽어둔 평가 작업이 정지 완료 후 매수를 제출하는 경우**를 시험해야 한다. 🔴 기준: **신규 진입 차단과 기존 주문·포지션 정리는 별개 상태다.** 미결 주문이 있어도 신규 매수는 차단돼야 하고, 세션 정지가 주문 추적을 끊어서도 안 된다. §4.6-4 에서 확인한 "정지 후 체결이 관리 주체 없는 포지션을 만든다" 가 이 항목의 핵심이다 |

### ② 에서 고친 것 — 취소를 거짓으로 종결하지 않는다

`OrderExecutionEngine.cancelOrder` 의 두 분기가 틀려 있었다. 둘 다 **주문이 거래소에 살아 있을 수
있는데 로컬을 `CANCELLED` 로 박았다.** `pollActiveOrders()`(5초 주기)는 **활성 주문만** 거래소와
동기화하므로, 취소로 기록된 주문은 **추적 대상에서 빠져 영구 미해결**이 된다. 나중에 체결되면
관리 주체 없는 포지션과 어긋난 KRW 가 남는다.

| 분기 | 종전 | 지금 |
|---|---|---|
| 취소 실패 + **상태 재조회도 실패**(결과 불명) | `CANCELLED` 전이 | 상태 유지 + 예외로 호출부에 알림 |
| 취소 실패 + 재조회 성공인데 **거래소에서 아직 활성**(`wait`/`watch`) | `CANCELLED` 전이 | 상태 유지 + 예외 |
| 취소 실패 + 재조회에서 취소 확인 | `CANCELLED` | 그대로 |

**거짓 종결보다 미결이 낫다** — 미결은 5초 폴러가 자동으로 해소하지만 거짓 종결은 영구히 남는다.
🔴 **취소를 요청했다는 사실은 주문이 사라졌다는 증거가 아니다.**

점에서** 유지한다. 🔴 **네이티브 잠금에서도 재현된다는 사실은 "엔티티 조회만의 문제가 아니다" 는
근거이지, 잠금이 실행 순서에 미치는 영향까지 배제한 것은 아니다.** 🔴 **"한 행만 잠그므로 영향은 그 세션뿐" 이라고 확정하지 않는다** —
거래소 호출 동안 **DB 커넥션과 작업 스레드도 점유**하며, 타임아웃 후 잠금·커넥션 반환과 정지 작업의
회복은 ③에서 보듯 아직 성립하지 않는다.

---

### ③ 다음 작업 순서와 지금 열려 있는 것 (2026-10-07)

🔴 **`balanceUpdater.apply` 로 옮긴 것은 버전 충돌의 해결이지, 복원의 정당성이나 중복 방지까지
보장하는 것이 아니다.** 그 둘은 별개 문제이고 아래에 적는다.

#### 🔴 복원의 정당성 — 불명 주문의 자금을 성급히 해제하고 있다

`closeSessionPositions` 는 매수 주문이 `FAILED`·`CANCELLED` 이면 KRW 를 복원한다. 🔴 **그런데 응답
불명 경로에서 `FAILED` 는 "거래소가 거절했다" 는 뜻이 아니다** — 접수됐는데 응답만 오지 않은 경우도
같은 `FAILED` 다(§4.6 ① 참조). 그 상태에서 KRW 를 복원하면 **실제로는 쓰인 자금을 되돌려 놓는다.**
슬롯도 같이 해제된다(포지션을 `CLOSED` 로 전환하므로).

즉 **"확정 실패" 와 "응답 불명" 을 같은 상태로 다루는 것이 문제의 뿌리다.** 이것은 상태 설계 없이는
고칠 수 없다 — 복원 여부를 판단할 근거(거래소 조회 결과)가 없기 때문이다.

#### 🟢 중복 방지 — 원자적 전환을 가드로 쓰도록 맞췄다 (2026-10-07)

종전에는 가드 없이 복원하고 그 뒤에 `setStatus("CLOSED") + save` 했다. 그러면
`reconcileOrphanBuyPositions`(30초)가 같은 포지션을 동시에 처리할 때 **같은 KRW 가 두 번 복원된다** —
그쪽은 `closeIfOpen` 이 0 이면 복원을 건너뛰는데, 이쪽이 전환을 늦게 하므로 둘 다 "내가 먼저" 로
본다. `executeSessionSell` 의 매수 취소 분기와 reconcile 이 이미 쓰는 패턴(**전환에 성공한 쪽만
복원한다**)을 여기에도 맞췄다.

🔴 **이것은 두 경로 사이의 중복만 막는다.** 늦은 체결·취소 확인·정지 재시도를 포함한 전체 경로에서
정산·자금 복원이 **정확히 한 번**인지는 아래 3번에서 검증해야 한다.

### 업비트 고객 주문 식별자 — 확인된 규칙과 그 한계 (2026-10-07)

| 항목 | 확인 결과 |
|---|---|
| 제출 | `POST /v1/orders` 의 **`identifier`** 로 고객 주문 식별자를 전달한다 |
| 제약 | 최대 **64자**, **계정 전체 주문에서 고유**해야 하고 **사용한 값은 재사용 불가** |
| 조회 | `GET /v1/order?identifier=...` — **응답 UUID 를 받지 못해도 조회할 수 있다** |
| 취소 | `DELETE /v1/order?identifier=...` |

🔴 **멱등 API 로 해석하지 않는다.** 문서가 명시한 것은 **식별자의 고유성과 재사용 금지**이며, 같은 키로
재요청하면 기존 성공 응답을 돌려준다는 보장이 아니다. 🔴 또한 확인한 문서에는 **조회 가능 보존 기간**이
없고, **제출 직후의 조회 실패가 미접수를 확정한다는 보장도 없다.**

#### 그래서 설계 방향은 이렇다

1. **외부 제출 전에 주문 의도와 `identifier` 를 영속화**한다.
2. **시간 초과는 확정 실패와 분리**하고, **자금·슬롯을 유지한 채** 그 식별자로 조회한다.
3. 🔴 **조회 실패만으로 새 식별자를 만들어 재주문하거나 자금을 복원하지 않는다**(재사용 금지 + 보존
   기간 미보장 때문에, 조회 실패는 "없다" 가 아니라 "모른다" 다).
4. 확인된 체결·취소 결과에 따라 정산하고, **재시작 후에도 미해결 주문 추적을 이어간다.**

### 🟡 KRW 복원의 원자성 — 전환과 잔액 반영을 한 트랜잭션으로 묶었다 (2026-10-07)

2041eb3 의 가드는 **동시 실행만** 막고 **롤백에는 무력했다**: `closeIfOpen` 은 바깥 트랜잭션에 참여
(REQUIRED)하고 복원은 `balanceUpdater`(REQUIRES_NEW)로 독립 커밋되므로 **복원 커밋 → 바깥 롤백 →
포지션 `OPEN` 복귀 → 재복원** 이 가능하다. DYNAMIC 세션 49 가 그 유형이었다.

고친 방식: `restorePositionKrwAtomically` 를 두어 **전환과 잔액 반영을 하나의 REQUIRES_NEW
트랜잭션**에 넣고, 세션 엔티티도 그 안에서 다시 읽는다. 둘은 함께 커밋되거나 함께 롤백되므로 바깥이
롤백돼도 쌍이 깨지지 않고, 재시도는 `closeIfOpen == 0` 으로 건너뛴다.

🔴 **시험의 한계를 적는다.** `KrwRestoreRollbackRetryTest` 는 **수정 후 불변식(잔액 증가 1회)** 을
확인한다. 수정 전 코드에 돌려 실패를 보이려 했으나 **다른 이유로 실패했다** — 수정 전에는 복원도
`balanceUpdater` 를 거치므로 실패 주입 지점이 복원 자체를 깨뜨려 "복원은 되고 바깥만 롤백" 시나리오가
만들어지지 않았다. **즉 이 시험은 결함을 재현해 보인 것이 아니다.** 중복 복원 가능성의 근거는 코드
구조와 세션 49 의 실측 전례다.

🔴 **그리고 이것은 중복 복원만 막는다 — 복원의 정당성은 여전히 열려 있다**(위 "복원의 정당성" 항).

1번은 분모 정의·폴백·상한 설정에서 공백 다섯이 확인됐고, 3번은 초과 진입 가능성이 있는 구조가
