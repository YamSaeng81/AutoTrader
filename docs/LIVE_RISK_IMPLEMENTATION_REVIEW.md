# 실전 위험 통제 구현 검토 — 선행 조건 1·3 (2026-10-06)

> **결론: 선행 조건 1·3 미충족. 실거래 진입 불가.**
>
> 이 문서는 [`LIVE_ENTRY_PREREG.md`](LIVE_ENTRY_PREREG.md) §7 의 선행 조건 **1번(위험 한도가
> 1단계에도 적용되는가)** 과 **3번(공유 자본·동시 상한이 실제로 강제되는가)** 을 **코드 읽기로만**
> 검토한 결과다. 운영 코드·설정·검증 세션을 **아무것도 바꾸지 않았다.** 66세션 전향 검증의
> 코드 동결은 유지한다.
>
> 🔴 **읽기로는 선행 조건을 닫을 수 없다.** 구현 경로와 공백은 읽기로 확인되지만, 동시성에서
> 상한이 지켜지는지는 **실행 시험**으로만 확인된다(§4).

## 1. 코드에서 확인한 사실

### 1.1 위험 판정의 호출 경로

| | |
|---|---|
| 호출부 | `LiveTradingService:1159`(매수 직전), `OrderExecutionEngine:212` |
| 판정 | `RiskManagementService.checkRisk()` → `RiskEngine.check(일일·주간·월간 손실률, 포지션 수, 자본사용률, 포트폴리오 낙폭)` |
| 분모 | `resolvePortfolioLimit()` = **RUNNING LIVE 세션들의 `initialCapital` 합** |
| 손실 원천 | `tradeLogRepository.sumRealizedLossSince(since)` — `trade_log` 의 `FILL` 이벤트 |

### 1.2 🟢 검증 세션은 실전 위험 판정을 오염시키지 않는다

`trade_log` 에 쓰는 곳은 **`OrderExecutionEngine` 하나뿐**이고 `PaperTradingService` 는 쓰지 않는다.
분모도 `LiveTradingSessionEntity` 만 합산한다. 따라서 **PAPER 66세션의 손익이 실전 일일 손실
판정에 섞이지 않는다.** 이것은 확인된 사실이다.

### 1.3 🔴 확인된 공백 다섯

| # | 공백 | 근거 |
|---|---|---|
| ① | **분모가 고정값이 아니다.** `LIVE_ENTRY_PREREG.md` §6 은 1단계 분모를 "그 단계 총 투입 자본(공유 풀 초기 잔액) = 100,000" 으로 등록했는데, 구현은 **RUNNING 세션 합계**다. 3세션 × 20,000 운용이면 분모 60,000 → 누적 −15% 는 **−9,000**(등록값 −15,000 이 아니다). 세션이 하나 멈추면 40,000 → **−6,000**. **등록 금액과 실제 임계가 다르고, 운용 중에 변한다** | `RiskManagementService.resolvePortfolioLimit` |
| ② | `initialCapital` 이 `null` 이거나 0 이면 분모가 **1,000만원으로 폴백**한다. 그 경우 1일 한도 3% 는 **300,000원**이 되므로, 1단계에 등록된 **−3,000원에서는 발동하지 않는다** — 한도가 100배로 희석된다. 코드 주석이 바로 이 희석 문제를 경고하는데 폴백 경로는 남아 있다 | 같은 메서드의 최종 폴백 |
| ③ | **1일 손실이 총손실(gross)이다** — `pnl < 0` 인 체결만 합산하고 이익으로 상쇄하지 않는다(의도적이며 쿼리 주석에 명시돼 있다). §6 의 "1일 손실 ≤ −3%" 는 순손익으로 읽히므로 **등록 문서와 구현의 의미가 다르다.** 구현이 더 엄격한 쪽이지만 숫자의 뜻이 같지 않다 | `TradeLogRepository.sumRealizedLossSince` |
| ④ | 구간이 **달력 하루가 아니라 직전 24시간 롤링**이다 | `checkRisk`: `now.minus(1, ChronoUnit.DAYS)` |
| ⑤ | **동시 보유 ≤ 3 이 어디에도 설정돼 있지 않다.** `maxPositions` 기본값은 **8** 이고, 주 제어는 자본 사용률이며 포지션 수는 "안전망"으로 설계돼 있다. LIVE 세션 수 상한 `MAX_CONCURRENT_SESSIONS = 10` 은 **세션 수**이지 포지션 수가 아니다 | `RiskConfigEntity:164`, `RiskEngine.check`, `LiveTradingService:94` |

### 1.4 🔴 선행 조건 3 — **초과 진입 가능성이 있는 구조**

`checkRisk()` 는 `@Transactional(readOnly = true)` 로 **승인만 돌려주고**, 매수는 그 트랜잭션
**밖에서** `executeSessionBuy` 가 따로 수행한다. 확인과 사용 사이에 간격이 있다(TOCTOU).
비관적 잠금, 원자적 카운터, 단일 직렬화 지점이 **없다.**

유일한 보호는 `OrderExecutionEngine:179` 의 중복 주문 거부인데, 이는 **같은 세션 · 같은 코인 ·
같은 방향**만 막는다. **서로 다른 세션이 각각 한도 안이면서 합계로 상한을 넘기는 것은 막지
못한다.**

🔴 **이것은 "초과 진입 가능성이 있는 구조" 라는 뜻이며, 실제로 초과가 발생한다는 확정이 아니다.**
실제 발생 여부는 스케줄러 스레드 수·트랜잭션 경계·틱 정렬에 달렸고 **동시성 시험으로만**
확인된다(§4).

## 2. 미확인 항목

| | 항목 | 왜 미확인인가 |
|---|---|---|
| 1 | `CAPITAL_LOSS`·`MAX_DRAWDOWN` 의 분모가 실제로 **진입 배정액**인가(§6 등록값) | `StrategyKillCriteriaService.decide()` 를 아직 읽지 않았다 |

| 3 | DYNAMIC(비-PAPER) 세션이 `trade_log` 에 남기는 손익이 실전 일일 손실에 합산되는지 | 1.2 는 PAPER 만 확인했다. DYNAMIC 운영 중이면 분모·분자 범위를 다시 봐야 한다 |

## 3. 필요한 결정

🔴 **아래는 지금 결정할 수 있다.** 현재 66세션의 판정 기준과 운영 코드를 바꾸지 않고, **실전 사양의
개정으로 기록**하면 된다. 🔴 **다만 결정 없이 기존 숫자를 임의로 재해석하면 안 된다** — 지금
§6 에 적힌 "−3,000" 이 gross 인지 net 인지 정해지지 않은 상태다.

| # | 결정할 것 | 선택지 |
|---|---|---|
| 1 | 1일 손실을 **gross(총손실)** 로 볼지 **net(순손익)** 으로 볼지 | 구현은 gross. 등록 문구는 net 으로 읽힌다. 어느 쪽이든 **문서와 구현을 일치**시킨다 |
| 2 | 손실 구간을 **달력일**로 할지 **직전 24시간 롤링**으로 할지 | 구현은 롤링 24시간 |
| 3 | 1단계 분모를 **고정 100,000** 으로 할지, **RUNNING 세션 합계**를 사양으로 받아들일지 | 고정으로 하려면 구현 변경이 필요하다. 합계를 받아들이면 §6 의 금액표를 다시 써야 한다 |

이 결정들은 **실전 사양 개정**이며 검증 임계값 변경이 아니다. 결정 시점과 근거를 개정 이력에 적는다.

## 4. 실행 시험 — 읽기로 닫을 수 없는 것

| # | 시험 | 닫는 조건 |
|---|---|---|
| 1 | **같은 틱 동시 신호 N > 상한** — 스레드 N 개가 동시에 매수 시도 | **초과 주문 0건** |
| 2 | **미체결 매수 주문의 슬롯·자금 예약** — 주문 접수 후 체결 전에 같은 슬롯·자금으로 또 진입되는가 | 이중 사용 0건 |
| 3 | **분모 고정** — 세션 하나를 멈춰도 누적·1일 임계 **금액이 변하지 않는가** | §3-3 결정에 맞는 동작 |
| 4 | **`initialCapital` null/0 경로** | 폴백이 발생하지 않거나, 발생하면 진입을 차단한다 |
| 5 | **`maxPositions = 3` 이 4번째 진입을 막는가** | 실제 차단 |
| 6 | **동시 평가 중 정지**(선행 조건 5) — 🔴 HTTP 500 이 없는 것만으로 끝나지 않는다 | ① 최종 **정지 상태**가 남는다 ② **미체결 주문이 처리**된다(취소 또는 체결 후 정리) ③ **정지 이후 신규 매수가 차단**된다 |

🔴 이 시험들은 **운영 코드 수정을 수반**하므로 **검증 종료 후**에 한다. 단, 실제 정지 실패나 데이터
장애가 발생하면 방치하지 않고 기존 운영 오류·위험 대응 예외(개입 규칙)를 적용한다.

## 5. 결론

**선행 조건 1·3 미충족 — 실거래 진입 불가.**

1번은 분모 정의·폴백·상한 설정에서 공백 다섯이 확인됐고, 3번은 초과 진입 가능성이 있는 구조가
확인됐다. 두 조건 모두 **읽기로는 닫히지 않으며 §4 의 실행 시험이 필요하다.** 선행 조건 2(표본
부족 처리)·4(손실 감내 확인)·5(정지 신뢰성)도 미완료이므로, 다섯이 모두 닫히기 전에는 1단계
(체결 검증용 제한 실거래)에 진입하지 않는다.
