# 후속 개발 목록

2026-11-23, 사용자의 **“프로젝트 전반의 추가 개발 내용을 추후 작업에 반영”** 요청을 등록했다. 이 목록은 현재까지 확인한 근거와 개선 제안을 모은 것이며 프로젝트 전체의 코드 감사를 완료했다는 뜻은 아니다. 개별 항목은 **후속 후보·미착수**다. 담당은 개발 제안 → 총괄 범위/결과 검토 → 운영자 실행/인수 확인이며 실제 담당자와 일정은 착수 때 정한다.

## 1. 현재 작업과의 관계

11-28 실제 설정 읽기에서 DYNAMIC의 상승추세·급락 제외 저장값이 둘 다false이고, 제안서가 인용한true 기본값과 달랐다. [운영 근거](evidence/dynamic-runtime-read-20261128/README.md)를 FD13·FD15 후속에 연결한다. **판단 당시 적용된 설정값·출처·기본값 여부를 기록/표시**하고, 세션별 품질 필터를 고정할 수 있을지 검토한다. 기존66세션과 공유하는 전역 값을 새 실전 준비 과정에서 조용히 바꾸지 않는다. 구현은 현재 시험/고정1 인수를 끝낸 뒤 별도 선정한다.

- 당장 수행할 범위는 [현재 계획](LIMITED_LIVE_TEST_PLAN.md)과 [v1.229](evidence/review-825d7efd/README.md)다. 후속 목록 등록은 제품 수정·운영 조회·배포·자금 이동·세션 생성·매매 시작 승인이 아니다.
- 현재 읽기 범위/실패 처리 보정, 비용 보완 배포 판정, 계좌 대조, 휴대폰 수신/대응자, 관리자 보안 확인 등 기존 시작 조건은 그대로 남는다. 아래 목록으로 옮겨 미뤄도 된다는 뜻이 아니다. 새로 확인된 운영 안전 결함도 후속 목록에만 넣고 넘기지 않는다.
- 12월 시작 전 모든 후속 기능을 완성할 조건을 추가하지 않는다. 특히 A3 변화 없음 근거를 만들기 위한 이력/시계 기능은 현재 범위에서 착수하지 않는다. 후속 구현으로 과거 미관측 구간이나 월말 값을 소급 확정하지 않는다.
- 사용자 예산 100,000원·12월 허용손실 40,000원과 더 엄격한 기존 보호는 유지한다. 후속 기능을 이유로 한도를 완화하거나 1월 운용을 자동 승인하지 않는다.

## 4. 우선 C — 전략 확장과 프런트엔드

전략 선택형의 선행 자료와 프런트엔드 착수 시점은 다르다. **FD15는 사용자11-23 추가 요청에 따라 12월1일 실운영 개시 이후 초기 안정성을 확인하고 선정한다.** 디자인·세션 상세 개선이 FD14의 전략 검증 완료를 기다릴 필요는 없다. 상세 방향과 FE01~FE06 작업은 [프런트엔드 후속 계획](FRONTEND_DEVELOPMENT_PLAN.md)에 모았다.

| ID · 후보 | 방향 | 후속 완료 조건 |

## 5. 다음 지시서에 반영하는 방법

1. 매 차수 검토에서 새 공백을 발견하면 **기존 FD 항목에 연결하거나 새 ID를 부여**한다. 확인한 사실·고정 SHA/근거·미확정 부분·예상 영향·현재 관문인지 후속 후보인지를 짧게 남긴다. 이미 수용된 보완을 미구현 결함으로 다시 등록하지 않는다.
2. 현재 승인 범위와 독립 작업을 우선 마친다. 이후 안전/정산 영향, 원천의 선행 필요성, 운영 부담 감소, 구현 위험 순으로 **작은 한 범위씩** 선정한다. 본문 상태는 제안 → 범위 확정 → 구현 → 검증 → 운영 반영 → 인수 완료로 바꾸며 제출/수용/배포를 구분한다.
3. 착수 지시에는 선택한 FD ID·기점 SHA·변경 파일/동작·종료 조건·새 검증 이유·운영 승인 경계를 쓴다. 성능/용량 문제는 측정부터, 정책/전략 선택은 결정부터 한다. 번호가 있다는 이유만으로 작업 시간을 채우거나 범위를 늘리지 않는다.
4. 같은 입력 회귀·PG·빌드 반복과 장황한 로그 재독을 피한다. 관련 고정 근거를 재사용하고 새 실패/경계만 보존한다. 계획/인계에는 상태와 이 파일 링크만 두며 상세 내용을 여러 문서에 복사하지 않는다.

현재 목록의 등록은 끝났으며 각 항목의 구현 일정·인력·운영 적용은 아직 확정하지 않았다. 12월 운영 판단과 1월 재검토에서 우선순위를 실제 관측 결과로 갱신한다.
