## 3. 🔴 불확실성 — 패널 시간블록 부트스트랩

**코인을 독립적으로 재표집하지 않는다.** 22코인은 같은 시장 움직임을 공유하므로
코인 단위 재표집은 불확실성을 **과소평가**한다.

### 🔴 거래 손익 합이 아니라 **자산가치 변화**로 집계한다

청산일에 거래 손익 전부를 넣으면 **여러 블록에 걸친 보유 손익이 마지막 블록으로 몰리고,
미청산 손익은 아예 빠진다.** 그래서 평가(mark-to-market) 자산곡선을 쓴다.

```
1) 코인·팔별로 **동일 시점의 일별 평가 자산곡선** E[coin, arm, d] 를 저장한다
       E = 현금 + 보유수량 × 그날 종가        (미청산 포지션 포함)
2) 일별 손익 변화율                r[coin, arm, d] = (E[d] − E[d−1]) / 초기자본
3) 검사 기간을 길이 L 의 연속·비중첩 **공통** 시간 블록으로 나눈다
       주 L = 30일,  민감도 14일 · 60일
4) 복제마다 블록을 복원추출 — **전 코인·전 팔에 같은 블록 집합을 적용**한다
5) δ* = 평균_코인( Σ_블록 r[coin,A,d] − Σ_블록 r[coin,B,d] )        ← **짝지은 차이**
6) B = 2000, 시드 20260924.  95% 구간과 중심화 단측 p값
```

4 가 **코인 간 동시 상관**을, 3 이 **시간 의존성**을, 5 가 **A·B 의 짝**을 보존한다.

🔴 **이 재표집은 "관측된 운용 성과의 불확실성" 분석이다.**
재배열된 시장에서 전략을 다시 운용한 시뮬레이션이 **아니다** — 블록을 섞어도 전략은
원래 시간축에서 내린 결정 그대로이며, 우리는 그 결과의 표집 변동만 본다.

(앞선 신호 실험 `SIGNAL_STUDY_PREREG.md` v5 §6 과 같은 구조다.)

⚠️ **평균·중앙값·15/22 개선 수는 서로 독립적인 증거 세 개가 아니다.**
같은 22개 값에서 나온 세 요약이며, **함께 봐야 하나의 판단**이 된다.

## 4. 🔴 판정 — 두 가지를 분리해 착수 전 고정

### (가) 변경안의 가치 — A 가 B 보다 개선됐는가

코인별 `순수익(A) − 순수익(B)` 에 대해:

| 조건 | 판단 |
|---|---|
| 평균 > 0 **AND** 중앙값 > 0 **AND** 개선 코인 ≥ **15/22** **AND** §3 구간 하한 > 0 | **A 로 변경할 근거 있음** |
| 평균 ≤ 0 **또는** 중앙값 ≤ 0 | **근거 없음.** A 변경안을 접는다 |
| 그 사이 | **판단 보류** |

### (나) 수익 후보 자격 — A **자체**가 비용을 넘는가

🔴 **(가)를 통과해도 A 와 B 가 모두 손실일 수 있다.** 그래서 따로 건다.

| 지표 | 주 비용 | 비용 스트레스(왕복 0.5%) |
|---|---|---|
| 코인 동일가중 평균 순수익 | **> 0** | **> 0** |
| 중앙값 순수익 | **> 0** | 보고만 |
| 양수 코인 수 | **≥ 12 / 22** | 보고만 |
| **거래당 순수익률**(아래 정의) | **≥ 0.10%** | **> 0** |

#### 🔴 거래당 순수익률의 분모 — 착수 전 고정

왕복 비용 0.30% 는 **가격 기준**(= 진입 포지션 금액 대비)이다. 비교하려면 분모를 맞춰야 한다.

```
왕복 거래 하나의 순수익률 =  (청산금액 − 진입금액 − 수수료 − 슬리피지) / 진입 포지션 금액 × 100
집계:  ① 코인별로 그 코인의 모든 왕복 거래에 대해 **단순평균**
       ② 그 코인별 평균들을 **동일 가중 평균**
```

🔴 `총수익률 / 거래 수`(= `PerformanceReport.expectancyPct`) 는 **초기자본 기준**이므로
이 기준과 **섞어 쓰지 않는다.** 두 값을 나란히 보고하되 판정은 위 정의로만 한다.

거래당 0.10% 기준의 근거: 주 비용 왕복 0.30% 의 1/3 — 비용을 넘고도 남는 최소 마진.
**자의적인 선택이며 착수 전에 고정했다는 데 의미가 있다.**

### 네 가지 결과

| (가) | (나) | 판단 |
|---|---|---|
| 근거 있음 | 충족 | **A 를 전향 검증(§5) 후보로** — 배포는 §5 이후 판단 |
| 근거 있음 | 미충족 | **A 의 상대적 개선은 관측됐으나 수익 후보 기준은 충족하지 못했다. 배포하지 않는다** |
| 근거 없음 | — | **A 변경안을 접는다.** B 유지 |
| 보류 | — | 판단 보류. 전향 검증에서 다시 본다 |

`B − OFF` 는 **판정에 쓰지 않고 보고만** 한다.

📌 **이 판정 다음에 무엇을 하는가는 [`docs/LIVE_ENTRY_PREREG.md`](LIVE_ENTRY_PREREG.md) 에
사전 등록했다** (2026-10-01 고정, T0 직후·중간 성과를 보지 않은 상태). 네 조합별 후속 결정,
Walk-Forward 게이트의 적용 대상과 통과 요건, 고정 슬리피지로 확인하지 못한 **실제 체결 비용**의
검증 방법, 소액 실전의 자본·손실·노출 한도와 중단·확대 조건이 거기 있다.
🔴 그 문서는 이 문서의 판정 기준을 **완화하지 않는다.** 실전 진입에 **관문을 더하는** 방향이다.

엔진은 `findByStatusOrderByStartedAtAsc` 로 돌므로 **생성 순서가 평가 순서로 고정된다.**
코인마다 OFF→B→A 로 만들면 **A 가 언제나 마지막**이다. 한 틱의 캔들은 `TickCandleCache` 로

(`:667`) — 루프가 캔들 경계를 가로지르면 먼저·나중 평가된 세션의 `lastCandleClosed` 가
갈릴 수 있다. 코인마다 팔 순서를 **한 칸씩 돌려**(OFF·B·A → B·A·OFF → A·OFF·B) 그 영향이
특정 팔에 쏠리지 않게 한다. 22 는 3 으로 나뉘지 않아 첫 팔 분포는 8·7·7 이다.

메커니즘에 대한 판단은 유지된다 — `fixedDelay` 는 현재 실행이 끝나야 다음을 잡으므로,

##### 🔴 blocker 확정 — `idle in transaction` 이 2시간 동안 잠금을 붙잡고 있다 (2026-09-26)

```
pid 323739  idle in transaction  ClientRead  xact_age 1:56:27
            마지막 문장: insert into position (...)
            blocked_by: {}          ← DB 를 기다리는 게 아니다. **앱이 다음 문장을 안 보낸다**

pid 323733  active  Lock/transactionid  blocked_by {323739}
            update market_data_cache set close=$1,…        ← 🔴 우리 동기화
pid 323730  active  Lock/transactionid  blocked_by {323739}
            update dynamic_session set available_krw=$1,…  ← 🔴 동적 매매 엔진
```

`pg_locks` 에도 두 건이 `transactionid ShareLock · granted=false` 로 남아 있다.

**읽는 법**: `update market_data_cache` 가 `transactionid` 를 기다린다는 것은, 323739 의
트랜잭션이 **그 행을 이미 수정했다**는 뜻이다. 즉 323739 는 한 트랜잭션 안에서
`market_data_cache` → `dynamic_session` → `position` 을 차례로 쓴 뒤 **커밋하지 않고 멈췄다.**
그 조합은 `DynamicTradingService.processTick` 의 범위와 일치한다 — `@Transactional` 이고
(`:680`), 캔들을 `marketDataSyncService.fetchWithCache` 로 가져오며(`:1950`) 주문까지 같은
트랜잭션 안에서 처리한다. ⚠️ **일치는 정황이다. 소유 스레드를 덤프에서 확인해야 확정된다.**

🔴 **이것은 전향 검증만의 문제가 아니다.** `dynamic_session` 갱신도 같은 잠금에 막혀 있으므로
**동적 매매 엔진이 2시간째 멈춰 있다.** 검증 표본 문제보다 우선순위가 높다.

📌 곁가지로 드러난 것: `strategy_log` 에 대한
`SELECT DISTINCT ON (coin_pair, date_trunc('hour', created_at)) …` 가 병렬 워커 4개를 물고
**2분 40초** 동안 돌고 있다(`IPC/MessageQueueSend`). blocker 는 아니지만 무거운 질의다.

##### ⚠️ 개입 전에 짚어둘 위험 — 되돌리면 기록이 사라진다

`pg_terminate_backend(323739)` 로 풀 수 있고 그러면 막힌 둘이 즉시 진행된다. 그러나
**그 트랜잭션이 롤백되므로 `position` insert 가 사라진다.**

🔴 **거래소에 실제 주문이 나갔는데 DB 기록만 롤백되면 장부와 실제가 어긋난다.**
그 세션이 실자본인지, 그 insert 에 대응하는 체결이 거래소에 있는지 확인하기 전에는
종료시키지 않는다. 백엔드 컨테이너 재시작도 같은 롤백을 일으키고 증거까지 없앤다.

##### 🔴 소유 스레드가 없을 가능성 — 커넥션에 트랜잭션이 남은 것 (2026-09-26)

덤프를 다시 떴다. 앱 프레임을 가진 스레드 중 **`scheduler-4`·`-6`·`-7` 세 개가 모두 PG 소켓
읽기에 파킹**돼 있다(RUNNABLE, `Net.poll`). 나머지는 `upbit-rate-refill`(정상 수면)이다.

🔴 **그런데 이 셋은 blocker 가 아니다.** 323739 는 `idle in transaction / ClientRead` —
**DB 가 앱의 다음 문장을 기다리는** 상태다. DB 호출 중인 스레드라면 백엔드 상태가 `active` 여야
하므로, **이 세 스레드 중 어느 것도 323739 의 주인이 아니다.**

그러면 주인은 누구인가. 후보가 둘로 갈린다.

| 후보 | 예측 | 확인 |
|---|---|---|
| ⓒ 어떤 스레드가 트랜잭션을 열어둔 채 DB 밖에서 대기 중 | 덤프에 그 스레드가 앱 프레임과 함께 보인다 | 덤프 전체 목록 |
| ⓓ 커넥션이 풀로 반납됐는데 트랜잭션이 안 닫혔다 (소유 스레드 없음) | — | 🔴 **지표 대조로는 가려지지 않는다.** 아래 정정 참조 |

⚠️ ⓓ 를 잡아낼 장치가 없다 — `application.yml` 의 Hikari 설정은 `maximum-pool-size: 20`,
`minimum-idle: 5`, `connection-timeout: 30000` 뿐이고 **`leak-detection-threshold` 가 없다.**
그래서 반납된 커넥션이 트랜잭션을 쥔 채 영구히 남아도 아무 경고가 없다.

##### 🟢 개입 위험이 낮아졌다 — OPEN 포지션이 없다

`position` 을 집계했다.

| `session_kind` | status | 건수 | 마지막 진입 |
|---|---|---|---|
| `DYNAMIC` (REAL 동적) | CLOSED | 30 | 2026-08-16 |
| `DYN_PAPER` (PAPER 동적) | CLOSED | 446 | 2026-09-25 |
| `LIVE` | CLOSED | 277 | 2026-08-07 |

🔴 **OPEN 행이 하나도 없다.** 막힌 insert 는 커밋되지 않아 보이지 않지만, 되돌려도
**"열려 있다고 DB 가 믿는 포지션"이 사라지는 일은 없다** — 애초에 없다.
남은 위험은 하나뿐이다: 그 insert 가 **REAL**(`DYNAMIC`) 이고 거래소에 실제 체결이 나갔다면,
롤백 후 거래소에만 포지션이 남는다. REAL 동적 진입은 **2026-08-16 이 마지막**이고 최근 활동은
전부 `DYN_PAPER` 이지만, **그것만으로 단정하지 않는다** — RUNNING 세션의 `trading_mode` 를 본다.

📌 컬럼 이름을 정정한다: `dynamic_session` 에는 `session_kind` 가 없고 **`trading_mode`**
(REAL/PAPER) 다. `session_kind` 는 `position`·`order` 쪽 컬럼이며 REAL 동적은 `DYNAMIC`,
PAPER 동적은 `DYN_PAPER` 로 갈린다(컬럼 주석).


##### 🔴 정정 — "트랜잭션을 열어둔 채 풀로 반납됐다"는 입증되지 않았다 (2026-09-26)

나는 `Hikari active 3` 과 PG `idle in transaction 1` 을 근거로 ⓓ(주인 없는 누출 커넥션)를
**확정이라고 적었다. 그건 과했다 — 철회한다.**

두 값은 **다른 시각의 두 스냅샷**이고, 그것만으로는 어느 커넥션이 어느 스레드의 대여인지
잇지 못한다. 입증하려면 **같은 순간의 DB 연결 식별자 · 애플리케이션 스레드 · 풀 대여 상태**를
연결해야 한다. 지금 확정된 것은 이 수준이다.

| 확정 | 미확정 |
|---|---|
| 미종료 트랜잭션(323739)이 존재했다 | 그 커넥션을 **쥔 스레드가 있었는지 없었는지** |
| 그것이 보유한 잠금을 두 작업이 기다렸다 | 열린 채 반납된 것인지, 스레드가 붙잡고 있었던 것인지 |
| 잠금 대기에 제한이 없어 2시간 이어졌다 | |

⚠️ 그 상관은 **사후에 잇는 수단이 없어서** 못 한 것이다 — `leak-detection-threshold` 가 없어
"어느 스레드가 대여했는가"를 기록한 것이 없었다. 그래서 ③ 을 재현보다 먼저 넣는다.

##### 📌 ① 유력한 형태 — 문서에 이미 적혀 있던 자기 데드락 (정황)

`DynamicTradingService.emergencyStop` javadoc(2026-08-25 P0)이 **관측된 모양을 그대로**
기술한다.

> 바깥 트랜잭션(커밋 대기 중)이 쥔 행 잠금을 안쪽 트랜잭션이 기다리고, 바깥은 안쪽 호출이
> 끝나야 다음으로 진행해 커밋하는 순환 대기 — 타임아웃 없는 Postgres 에서 영원히 멈춘다
> (동적 세션 16개 전부 **29시간 무응답** 사고의 원인)

관측과 맞아떨어지는 점 둘:

1. 막혀 있던 질의가 `update dynamic_session set available_krw=$1, circuit_breaker_reason=$2,
   circuit_breaker_trigger…` 였다 — **`balanceUpdater`(REQUIRES_NEW)가 서킷 브레이커 필드를
   한 번에 싣는 모양**이다. javadoc 이 "모든 필드 변경을 이 REQUIRES_NEW 갱신 하나로 모아야
   한다"고 지시한 바로 그 경로다.
2. PAPER 매수 경로는 **바깥 트랜잭션에서 세션 행을 직접 쓴다**(`:1588-1596`,
   `dynamicSessionRepo.save(session)`). 그 행에 뒤이어 REQUIRES_NEW 갱신이 오면 같은 순환이 된다.

🔴 **정황이다. 어느 호출 순서가 실제로 그 조합을 만드는지는 재현으로 확정한다.**
`market_data_cache` 쪽 대기(323733)는 같은 바깥 트랜잭션이 `fetchWithCache` 로 쓴 행을
동기화가 건드려 생긴 **부수 피해**로 보이며, 순환의 일부는 아니다 — 이것도 재현으로 가른다.

##### ③ 먼저 — 무엇을 제한하고 무엇을 관측하는가 (대상이 다르다)

| 설정 | 무엇을 끊는가 | 왜 이 값 |
|---|---|---|
| `lock_timeout = 10s` (신설) | **잠금 대기만** | 이 사고에 정확히 대응한다. 초과 시 예외 → 롤백 → 커넥션 반환 → 다음 회차 진행 |
| `leak-detection-threshold = 60s` (신설) | 아무것도 끊지 않는다 — **진단** | 대여 스레드의 **스택**을 남긴다. 위 상관을 다음번엔 이을 수 있게 하는 유일한 수단 |
| `connection-timeout = 30s` (기존) | 커넥션 **획득** 대기 | 이 사고를 막지 못한다 — 이미 획득한 뒤였다 |
| `statement_timeout`·`socketTimeout` | 잠금 대기가 아닌 **정상 질의까지** | 🔴 **넣지 않았다.** 운영에 2분 40초짜리 무거운 질의가 실재한다(strategy_log 시간별 DISTINCT ON). 그 질의를 먼저 손본 뒤 별도로 판단한다 |

⚠️ **테스트 기반의 한계를 명시한다.** 테스트는 H2(PostgreSQL 모드)이고 Testcontainers 가 없다.
`lock_timeout` 은 서버 설정이라 **H2 로는 검증되지 않는다** — 오히려 H2 는 그 구문
(`SET lock_timeout = '10s'`)을 못 받아 테스트 프로파일에서 지워야 했다.

따라서 검증을 둘로 나눈다.

| 검증 | 방법 |
|---|---|
| 값이 실제 커넥션에 적용되는가 | 운영에서 `SHOW lock_timeout` — 앱 커넥션이 10s 로 보이는가 |
| 초과 시 **롤백·커넥션 반환·다음 회차 정상 진행** | 운영에서 **의도적인 잠금 대기**를 만든다 — psql 로 `market_data_cache` 한 행을 UPDATE 한 채 트랜잭션을 열어두고, 동기화가 10초 뒤 예외로 실패하는지 · 그 다음 회차가 정상 수집하는지 본다. psql 을 닫으면 원복된다 |

🔴 이것이 사용자가 요구한 "실패 후 자동으로 회복되는 것까지 확인"에 해당한다.
값 주입만 확인하고 넘어가지 않는다.


✅ **변이 검증 — "H2 는 그 구문을 못 받는다"는 주장을 시험했다.**
테스트 프로파일 오버라이드를 지우면 Spring 컨텍스트 테스트가 **10/10 실패**하고
(`Failed to load ApplicationContext`), 되돌리면 **10/10 통과**한다. 주장하기 전에 시험해야
했던 것을 이번에는 시험하고 적어 둔다. 전역 회귀는 없다 — `web-api` **514건 통과 / 실패 0 / 스킵 1**.

##### ① 재현 설계 — H2 로도 잡힐 수 있다

잠금 경합 자체는 H2 에서도 생긴다 — 다만 H2 는 짧은 기본 잠금 제한이 있어 **예외로 끝나고**,
Postgres 는 제한이 없어 **영원히 멈춘다**. 그 차이를 이용한다.

> 생산 호출 경로를 그대로 통과시키며 **잠금 대기 예외가 나지 않을 것**을 단정하는 테스트를 쓴다.
> 바깥 트랜잭션이 쓴 행을 REQUIRES_NEW 가 다시 갱신하는 순서가 있으면 H2 에서 잠금 제한에 걸려
> **테스트가 실패한다.** 없으면 통과한다.

🔴 이 순서다 — 먼저 결함이 실재함을 보이고(테스트 실패), 그 다음에 ② 경계를 고친다.
고치기 전에 통과하는 테스트는 아무것도 말해주지 않는다.


##### 🔴 철회 — "막힌 질의 모양이 `balanceUpdater` 를 가리킨다"는 근거가 아니다

나는 `update dynamic_session set available_krw=$1, circuit_breaker_reason=$2, …` 라는 컬럼
구성을 보고 "서킷 브레이커 필드를 함께 싣는 `balanceUpdater` 모양"이라고 적었다. **틀렸다.**

스택에 `UpdateCoordinatorStandard.doStaticUpdate` 가 있다 — Hibernate 의 **정적 UPDATE**,
즉 **어느 필드가 변했든 전 컬럼을 쓴다.** 따라서 그 SQL 은 `dynamic_session` 을 쓰는
**모든 경로에서 동일하게** 생성되며 호출자를 식별하지 못한다. 그 추론을 근거 목록에서 뺀다.

##### 🔴 ① 경로 확정 (코드 수준) — 바깥이 세션 행을 쓴 뒤 REQUIRES_NEW 가 같은 행을 갱신한다

`processScanningTick` 은 `@Transactional` 이다(`:771-772`). 그 안에서 순서가 이렇게 된다.

| 순서 | 코드 | 무엇을 하는가 |
|---|---|---|
| 1 | `:774` `resolveWatchlist(session)` | → `:1766` |
| 2 | `:1766-1848` 워치리스트 갱신 | 🔴 **`dynamicSessionRepo.save(toUpdate)`** — 바깥 트랜잭션이 **`dynamic_session` 행을 UPDATE** (`watchlist_json`, `watchlist_refreshed_at`). 공용 유니버스 경로(`resolveSharedWatchlist`)도 json 이 달라지면 같은 행을 쓴다 |
| 3 | `:786` `executeBuy(...)` | |
| 4 | `executeBuy` 안 | `position` INSERT — id 가 필요해 **즉시 flush** 된다 |
| 5 | `:1513` `balanceUpdater.apply(sid, …)` | 🔴 **REQUIRES_NEW — 새 커넥션으로 같은 `dynamic_session` 행을 UPDATE** |

5 는 2 가 쥔 행 잠금을 기다리고, 2(바깥)는 5 가 돌아와야 진행해 커밋한다 —
**`emergencyStop` javadoc(2026-08-25 P0)이 금지한 그 순환**이 워치리스트 쓰기를 통해 다시 들어왔다.
그 javadoc 의 지시는 "바깥 트랜잭션은 이 행을 **절대 직접 쓰지 않는다**"였다.

관측과 맞는 점 셋:

| 관측 | 이 경로의 예측 |
|---|---|
| 막힌 커넥션의 마지막 문장이 `insert into position` | 4 까지 진행한 뒤 5 에서 다른 커넥션으로 넘어갔다 |
| 다른 트랜잭션의 `update dynamic_session` 이 그 잠금을 기다림 | 5 가 그것이다 (단, 위 철회대로 SQL 로는 식별 불가 — 다른 스레드일 수도 있다) |
| 드물게 발생 | 워치리스트 갱신은 `watchlistRefreshMin` = 60분 주기다. **매 틱이 아니다** |

📌 `balanceUpdater` 경로는 **REAL 매수**에 있다(`:1513`). PAPER 매수는 바깥에서 세션을 직접
갱신한다(`:1595`) — 같은 트랜잭션이라 순환이 없다. 그리고 현재 RUNNING 동적 세션 중
**REAL 은 92 하나**다. 이 경로가 92 에서만 발생한다는 뜻이며, 관측된 미종료 트랜잭션도
`position` INSERT 를 포함했다.

🔴 **여전히 정황이다.** 실제로 그 순서가 실행됐는지는 재현으로 확정한다.

##### ① 재현 테스트가 입증해야 하는 것 — 세 가지를 분리한다

내 앞선 설계에는 빈 곳이 있었다. 세 조건을 명시한다.

| 조건 | 왜 | 어떻게 |
|---|---|---|
| **실제 Spring 프록시 경유 REQUIRES_NEW · 서로 다른 커넥션** | 자기 호출(self-invocation)이면 `@Transactional` 이 무시돼 **같은 커넥션**이 되고, 그러면 잠금 경합이 아예 생기지 않는다 — 재현이 아니라 헛통과다 | 프록시 빈을 통해 호출. `balanceUpdater` 는 별도 빈이므로 프록시가 적용되는지 단정 전에 확인한다 |
| **바깥 UPDATE 가 실제로 실행되어 잠금을 획득했는가** | 🔴 **JPA 객체 변경만으로는 SQL 이 아직 나가지 않는다.** flush 전이면 잠금이 없어 경합이 생기지 않는다 | 바깥에서 명시적 `flush()` 후 잠금 보유를 확인하고 나서 안쪽을 호출 |
| **실패 원인이 의도한 동일 행 잠금 대기인가** | 예외가 내부에서 잡히면 **거짓 통과**한다. 예외 종류가 달라도 통과할 수 있다 | 예외 유무만 보지 않고 **잔액·포지션의 최종 상태**를 함께 단정한다 (차감이 반영됐는가, 포지션이 남았는가) |

⚠️ 표현도 고친다. "수정 전에 통과하는 테스트는 아무 의미 없다"가 아니라 —
**그 통과는 이 결함의 재현 증거가 되지 않는다**가 정확하다. 다른 이유로 통과할 수 있다.

| #19·20 | **안쪽#1** | `update dynamic_session` | `available_krw=2000`, `POSITION_MONITORING` → **성공** (= `balanceUpdater`) |
| #21·22 | **바깥** | `update dynamic_session` | `available_krw=10000`, `SCANNING`, `watchlist=["KRW-BTC"]`, `version=0` → **0행** |
| #25·26 | 안쪽#2 | `update dynamic_session` | `available_krw=10000`, `version=1` → **성공** (= 보상) |

🔴 **바깥의 세션 UPDATE 는 커밋 시점까지 지연돼 안쪽보다 나중에 실행됐다.**
따라서 안쪽이 돌 때 바깥은 그 행의 잠금을 쥐고 있지 않았고, **잠금 대기 순서가 만들어지지 않았다.**

📌 **사용자가 경고한 함정이 직접 확인됐다** — `insert into position` 은 실행됐지만(#15)
`update dynamic_session` 은 그 시점에 실행되지 않았다. **두 사실을 묶어 읽으면 틀린다.**

**② 대기·실패가 발생한 정확한 지점과 원인**

- **잠금 대기는 없었다.** `FAIL` 로 기록된 문장도 없다.
- 실패 지점은 **바깥 커밋의 flush** 다. `update … where version=0` 이 **0행**을 갱신했고
  (안쪽이 이미 version 1 로 올려놨다) → `StaleObjectStateException` →
  `ObjectOptimisticLockingFailureException` → 바깥은 rollback-only →
  `UnexpectedRollbackException`.
- **안쪽은 성공했다** (차감 커밋).

작동했다 — 앞서 test A 변이로 본 부분 커밋 위험은 **보상 훅이 없는 경로**의 이야기였고,
생산 경로에는 보상이 붙어 있다. 그 구분이 이제 관측으로 확인됐다.

##### 🔴 그래서 ② 의 근거가 달라진다

| 앞서 세운 것 | B 이후 |
|---|---|
| "생산 경로가 잠금 대기 순서를 만든다" | 🔴 **이 관측으로는 지지되지 않는다** |
| "그래서 경계를 고쳐야 한다" | 근거가 약해졌다 — 관측된 실패는 잠금 대기가 아니라 낙관적 락 충돌이고, **보상이 수습한다** |

잠금 대기가 생기려면 **바깥 UPDATE 가 안쪽 진입 전에 flush 돼야** 한다. 그 조건을 만드는 것은
`dynamic_session` 을 건드리는 질의(auto-flush 유발)인데, 이 경로에서는 그런 질의가 없었다.
즉 **위험한 순서는 잠재적이며, 지금은 만들어지지 않는다.**

그래서 B 의 단정을 **감시 장치**로 남겼다 —
> 바깥 연결의 세션 UPDATE 가 안쪽보다 **먼저** 실행되면 이 테스트가 **실패**한다.
> 그때가 위험한 순서가 생긴 시점이다.

🔴 **그리고 운영 사고의 blocker 가 이 경로였는지는 여전히 미확정이다.** B 는 그 가설을
지지하지 않았고, 증거 대장의 그 칸은 🔴 로 남는다.

##### ⚠️ 내 관측 로직의 오류 2건 — 기록해 둔다

1. `isInsertInto("position")` 을 `contains` 로 구현해 `insert into risk_config (… max_position …)`
   이 걸렸다. 테이블 이름이 **다른 테이블의 컬럼명**에 들어 있는 경우를 못 걸렀다 → 접두사 일치로 고쳤다.
2. "다른 연결의 첫 문장"을 안쪽 진입으로 썼는데, 실제로 그것은 `balanceUpdater` 가 아니라
   **더 앞선 별도 연결 작업**(risk_config 쪽)이었다 → **바깥이 아닌 연결의
   `dynamic_session` UPDATE** 로 정확히 지목하도록 고쳤다.

두 오류 모두 **처음 판정을 반대로 낼 수 있었다.** 관측 장치도 관측 대상만큼 검증이 필요하다.


##### 🟢 재현된 버전 충돌 수정 — 동작으로 고정했다 (2026-09-28)

🔴 **범위를 먼저 못 박는다: 이것은 운영 장기 잠금 사고의 원인을 해결하지 않는다.**
잠금 대기 가설은 test B 에서 지지되지 않았다. 여기서 고친 것은 **test B 가 실제로 관측한**
다음 결함뿐이다.

```
안쪽 REQUIRES_NEW 차감 성공(커밋)
  → 바깥 커밋에서 @Version 충돌 (where version=0 이 0행)
  → 매수 기록(포지션·주문·워치리스트) 전부 롤백
  → 보상이 차감을 되돌림
```

보상이 **잔액 불일치는 막았지만 정상 매수가 완료되지 않았다** — 진입 신호가 있었는데
포지션이 남지 않는다. 그래서 감시만 남기지 않고 고쳤다.

**원인**: 워치리스트 기록이 `getOrThrow(id)` 로 **바깥 트랜잭션의 관리 엔티티**를 꺼내 필드를
바꿨다. `save()` 호출 여부와 무관하게 dirty 가 되고, 커밋 시점 flush 가 안쪽이 올린 버전과
충돌했다.

**수정**: `persistWatchlist(sessionId, json)` 하나로 모으고 `balanceUpdater.apply` 를 거친다 —
변경이 **새 트랜잭션의 자체 컨텍스트에서 재조회한 엔티티**에 적용되므로 바깥은 그 행을 쓰지
않는다. 낙관적 락 재시도도 유지된다.

##### 고정한 동작 (구현이 아니라 동작)

| 기준 | 어떻게 확인했는가 |
|---|---|
| 정상 매수 완료 + 일관성 | 커밋 성공 · 포지션 1건 OPEN · `currentPositionId` 일치 · `scanState=POSITION_MONITORING` · 워치리스트 보존 |
| 잔액 **정확히 한 번** 차감 | 🔴 `0 < 잔액 < 초기값` 범위 단정을 **버렸다** — 두 번 차감도 통과시킨다. `10,000 − 8,000 = 2,000.00` **정확 비교** |
| 정상 경로에 보상 없음 | 🔴 UPDATE 횟수가 아니라 **보상 진입을 직접 계측**한다 (`@SpyBean DynamicSessionBalanceUpdater`). 직접 관측한 사실은 **"이 세션의 updater 진입 총 2회"** 다 — 보상이 UPDATE 전에 실패해도 이 숫자에 잡힐다. ⚠️ 그것을 "워치리스트 1 + 차감 1" 로 읽는 것은 **다른 단정이 그 둘을 각각 확인한다는 전제 아래에서만** 유효하다. UPDATE 횟수는 **보조 진단** |
| 생산 불변식 | 바깥 연결이 `dynamic_session` 을 쓰지 않음 (SqlTrace) |
| 외부 제출 경계 | 🔴 별도 테스트 — **엔진은 실제로 쓰고 `UpbitOrderClient` 만 대역**. 롤백 후 **0회**, 커밋 후 **정확히 1회**. `@Async` 라 즉시 검사하지 않고, **정상분 호출을 기다린 뒤 총 1회**로 확인한다(고정 sleep 대신 진행의 증거를 쓴다) |

✅ **변이 검증 3건**
- `persistWatchlist` 를 수정 전 방식으로 되돌리면 주 회귀가 `ObjectOptimisticLockingFailureException` 으로 실패
- 외부 경계 테스트에서 롤백 시나리오를 커밋으로 바꾸면 `TooManyActualInvocations` 로 실패
- (앞서) `SqlTraceSelfTest` 의 REQUIRES_NEW → REQUIRED 변이로 커넥션 분리 시험 실패

##### 🟢 PostgreSQL 잠금 제한 검증 — 수행하고 통과했다 (2026-09-28)

**통제 경로**: `lockprobe` 로 실거래·동적·22코인과 겹치지 않는 코인(`KRW-ARDR`)에 페이퍼 세션 1개를
만들고, 동기화가 그 코인을 **따라잡은 것을 확인한 뒤**(수집 로그 + 캐시 `to` 최신) 최신 행을
75초간 잠갔다. 잠금은 `pg_sleep` 후 자동 `ROLLBACK` 으로 풀린다.

| 시각 | 관측 |
|---|---|
| 01:21:22 | `캔들 수집 완료: KRW-ARDR H1 6 건` (REST 수집) |
| **01:21:32** | 🟢 **`ERROR: canceling statement due to lock timeout`** — 정확히 **10초 뒤** |
| 같은 시각 | `PessimisticLockingFailureException` → 트랜잭션 롤백 |
| **01:22:33** | 🟢 `캔들 수집 완료: KRW-ARDR H1 6 건` — **다음 회차 정상 수집** |

🟢 확인된 것: **`lock_timeout = 10s` 이 애플리케이션 풀 연결에 적용되고**, 잠금 대기가 제한
시간에 끊기고, 트랜잭션이 롤백되고, **다음 회차가 정상 진행**한다. 이번 사고의 핵심이었던
"한 번이 끝나지 않아 다음 회차가 영구히 없어지는 것"은 이 경로에서 재현되지 않는다.

##### ⚠️ 예상과 달랐던 두 가지 — 기록해 둔다

**(1) 실패가 `시장 데이터 동기화 실패` 로 남지 않았다.** `SchedulerConfig` 의 errorHandler 가
`스케줄러 작업 오류` 로 잡았다 — 즉 예외가 **`syncMarketData` 밖으로 전파됐다.**
`syncPair` 의 per-pair try/catch 에 걸리지 않았다는 뜻이고, 이유는 UPDATE 가 **커밋 시점 flush**
에서 실행되기 때문이다(루프 안이 아니다).

**(2) 따라서 그 회차의 쓰기는 ARDR 만 잃은 것이 아니다.** 하나의 `@Transactional` 이 전 코인의
upsert 를 담으므로, 한 행의 잠금 대기가 **그 틱의 모든 코인 쓰기를 함께 롤백**시킨다.
🔴 앞서 내가 "다른 코인 수집은 영향 없다"로 읽으려던 것은 **틀렸다** — 같은 창에 다른 코인의
`캔들 수집 완료` 가 보이는 것은 **REST 수집 로그**이고, 그 회차의 DB 반영은 함께 사라졌다.
(추론이다. 커밋 시점 실패라는 관측에서 따라오지만, 코인별 `to` 전진 여부로 따로 확인할 수 있다.)

📌 그러나 **다음 회차가 다시 받아 쓴다** — 01:22:33 이 그것이다. 손실은 한 회차 지연이며
영구 정지가 아니다. 코인별 트랜잭션으로 쪼개 실패를 격리하는 것은 **별도 개선 항목**으로 남긴다.

##### 시험 과정에서 세 번 헛돌았다 — 기록해 둔다

## 6. 🔴 결과를 읽을 때

- **절대 순수익이 양수여도 수익 전략 확보가 아니다.** 앞선 Walk-Forward 는 이 계열 전략들을

- 래퍼는 **BUY 뿐 아니라 SELL 도** 막고, 그 결과 포지션·청산 시점 → 호출 생략 → 내부 상태 경로로
  이후 신호까지 바꾼다. 결과는 **"배포된 래퍼와 엔진의 결합"** 의 효과로만 귀속한다
- **비개선·비유의 결과가 효과의 부재를 입증하지 않는다**

## 6.5 🔴 착수 전 회계 검증 — 먼저 한 코인으로

전체 실행 전에 **한 코인**으로 다음을 확인하고, 통과해야 22코인으로 확대한다.

| 검증 | 기준 |
|---|---|
| 일별 손익 합 = 최종 자산 변화 | `Σ_d (E[d] − E[d−1])` 가 `finalEquity − 초기자본` 과 일치 (반올림 오차 내) |
| 확장 전 러너와 동일 | 주 비용에서 `총수익률`·`거래 수`·`MDD` 가 `SupertrendFilterQ2Runner` 와 **같은 값** |
| 자산곡선 정합 | 마지막 시점 포지션이 0(엔진의 강제청산 후)이고 `E[마지막] = finalEquity` |

자산곡선은 **엔진을 고치지 않고** 거래 기록(`TradeRecord`: side·price·quantity·fee·executedAt)과
캔들 종가로 재구성한다 — 운영 코드 변경 없이 검증 가능한 경로다.
