## 1. 결정과 이 시험의 목적

**운영자 결정(2026-10-29 이번 대화에서 전달받은 결정문)**: `VALIDATION_FIT_REVIEW.md` §6-5 (나). 12월에 자본 10만 원 이내의 제한 실거래 시험을 목표로 준비한다. 준비 착수 결정이며, 실거래 활성화 승인이 아니다.

- 🔴 **이 결정은 기존 진입 기준을 완화한다.** 수익성 입증을 실자금 투입의 선행 조건에서 뺐다. 운영자가 결정문에서 직접 밝혔다.
- **프로젝트 목표와 시험 목적은 다르다.**
  - 프로젝트 목표는 허용 위험 안의 비용 차감 절대수익이다(`VALIDATION_FIT_REVIEW.md` §1).
  - 8주 시험의 목적은 다음 네 가지 확인이다.
    - 구현 일치
    - 실제 체결 비용
    - 잔액·수량 정산
    - 중단 기능
- **수익은 기록만 한다.** 8주 흑자를 지속적인 수익성의 입증이나 증액 근거로 쓰지 않는다. 문헌·백테스트도 미래 수익을 보장하지 않는다(운영자가 결정문에서 인용한 SEC 투자자 안내).
- **자본과 보호 기준은 유지한다.**
  - 자본: 총 10만 원, 포지션당 2만 원, 동시 최대 3개.
  - 보호 기준: `LIVE_ENTRY_PREREG.md` §6의 누적·24시간·포지션별 중단 기준 그대로.
  - 시험 중 추가 입금과 증액은 하지 않는다. 8주가 끝나면 자동으로 연장하지 않는다.
- **WF 20왕복(`LIVE_ENTRY_PREREG.md` §2 OOS ≥ 20)은 이 경로의 공통 진입 문턱으로 쓰지 않는다.**
  - 대신 후보에 맞는 시간순 과거 구간 대조와 비용·위험 진단을 미리 정한다(§3).
  - 이 대조와 진단은 **동등한 통계 검증을 대신하지 않는다.**
  - 기존 66세션과 종료 후보의 판정은 보존한다.

**시간 청산 24시간의 효과 (구조, §5-2 시험으로 확인)**:
- 진입은 일봉 마감 직후이고, 24시간 뒤 다음 마감 무렵에 시간 청산이 걸린다.
- 같은 회차에서 시간 청산이 먼저 돌면 그 회차는 끝난다(`return`). 그래서 그날의 BUY 신호로 다시 사지 않는다.
- 결과적으로 SMA 가 계속 "보유"여도 **하루 보유 → 하루 현금**이 반복되고, 왕복 횟수는 순수 규칙보다 크게 늘어난다.
- 이 영향은 §5-3 개발 자료 대조(A 팔)로 잰다. 시간 청산을 끈 경우(B 팔)는 참고로만 잰다. **B 는 운영 보호 해제라 리뷰·운영자 판단 전에는 채택하지 않는다.**

### 5-4. WF 게이트 — 연결 상태와 이번 시험의 처리 범위

- **정정(리뷰)**: v1.1 §5 의 "코드의 WF 게이트는 LIVE 에 연결돼 있지 않다"는 틀렸다. `LiveTradingService.createSession` 이 `walkForwardValidationGate.throwIfBlocked(전략, 코인, 타임프레임)` 을 부른다(운영 `98aaac4` 의 같은 파일 400행, 2026-08-06 `f8d1376` 부터). **연결돼 있고, 강제 여부는 설정 `REQUIRE_WALK_FORWARD_GATE`(`strategy-validation.require-walk-forward-gate`, 기본 false)로 달라진다.** `LIVE_ENTRY_PREREG.md` §2 의 같은 오기도 정정 표시했다.
- 강제일 때 `DAILY_SMA20 × KRW-BTC × H1` 은 WF 실행 이력이 없어 **세션 생성이 막힌다**(코드 게이트 표본 하한 5건 이전에 이력 없음으로 차단).
- **처리 범위 (이번 시험)**:
  1. 운영 값 확인: 운영자가 `GET /api/v1/strategies/walk-forward-gate-status` 의 `gateEnabled` 를 읽는다(조회만).
  2. `false` 면: 바꾸지 않는다. 이 시험 세션도 게이트 강제 없이 만들어진다. 이것은 (나) 결정의 "WF 20왕복을 공통 문턱으로 쓰지 않는다"와 같은 상태이며, 이 시험이 WF 검증을 받았다는 뜻이 아니다.
  3. `true` 면: **전체 게이트를 끄지 않는다.** 이 조합 하나(`DAILY_SMA20 × KRW-BTC × H1`)만 예외로 두는 좁은 허용 목록을 별도로 구현·리뷰한 뒤 배포한다(추정 2h). WF 를 돌려 게이트를 통과시키는 방식은 쓰지 않는다 — (나) 결정에서 WF 를 이 경로의 문턱으로 쓰지 않기로 했기 때문이다.
  4. 다른 전략·다른 세션의 게이트 동작은 바꾸지 않는다.

  - **실제 기능** (코드·시험으로 확인, §5-7)
    - **청산 없이 신규 주문만 막는 기능은 없다.** 정지는 ⓐ 미종결 매수에 취소 요청(응답을 잃은 주문은 식별자로) ⓑ 장부 수량이 있는 OPEN 포지션 시장가 매도 ⓒ 세션 STOPPED 를 **함께** 한다. 진행 중 매도는 취소하지 않는다.

    - **불명 주문이 남은 채 정지해도 그 주문을 다시 내지 않는다.** 매수 불명: 식별자 취소 요청만, 수량 0 포지션은 매도하지 않고 정리 대기로 열어 두며 자금을 복원하지 않는다. 매도 불명: 새 매도도 취소도 하지 않는다.
  - **대응 순서 (주문 상태 불명)**
    1. 자동 차단을 확인한다(조회만): `GET /api/v1/trading/sessions/{id}/orders` 에서 `UNKNOWN` 주문, 그 뒤 새 매수가 없음.
    2. 불명 주문을 업비트에서 **UUID(있으면) 또는 identifier(`clientOrderId`)로 조회**한다(업비트 주문 조회 API `GET /v1/order` 의 `uuid`·`identifier`, 또는 웹·앱 주문 내역). 그 시각의 체결 내역과 BTC 보유량도 확인한다.
    3. 청산이 필요하면 **세션 정지 API 하나로만** 청산한다(`POST /api/v1/trading/sessions/{id}/stop`). 🔴 **업비트에서 직접 매도하지 않는다** — 시스템이 늦은 체결을 반영해 정리 대기 포지션을 팔 수 있어, 겹치면 이중 매도다. 직접 매도는 아래 5번 확인 뒤에만 한다.
    4. 정지 뒤에도 남은 불명 주문·정리 대기는 사람이 근거를 확인하고 종결한다(30분 이상 된 불명 매수는 기존 수동 조정 경로 — 회계만, 주문 상태는 UNKNOWN 유지).
    5. 🔴 **STOPPED 만으로 청산·정산 완료라고 기록하지 않는다.** 완료는 세션 STOPPED · 활성 주문 0(불명 포함) · 정리 대기 0 · 업비트 BTC 보유량과 내부 기록 일치를 모두 확인한 뒤에만 적는다. 업비트 직접 매도는 활성 주문 0·정리 대기 0 을 확인한 뒤 남은 차이에만 한다.
  - **대응 순서 (정산 불일치, 불명 주문 없음)**: 신규 매수는 일봉 마감(09:00 KST, 승인 ≤ 5분) 회차에서만 나간다.
    1. 업비트 미체결 주문·보유량과 내부 기록을 대조한다(조회만).
