캔들의 `time` 을 epoch 기준 `ltfInterval × factor` 에 내림 정렬해 묶는다. 업비트 상위봉도

## 🟢 2026-09-21 Wave 3-I · 3-H 완료 — 규칙 v4 에 함께 묶었다

### I. GRID 레벨 해제 — 해제 조건이 **구조적으로 도달 불가능**했다

매수는 `positionRatio <= 0.3`(레벨 0~3), 해제는 `positionRatio >= 0.7`(레벨 7~10) 에서만
시도됐다. **두 집합이 절대 겹치지 않는다**(gridCount 가 3 보다 크면 언제나). 따라서
`activeLevels.remove(levelIndex)` 는 **평생 아무것도 지우지 못했다.**

결과: GRID 는 레벨 0~3 에 각각 한 번씩, **평생 최대 4번** BUY 를 내고 그 뒤로는
"이미 진입됨" HOLD 만 반복했다. 유일한 탈출구는 범위가 1% 넘게 변해 `activeLevels` 가
통째로 비워지는 우연이었다.

⚪ 코드에 이미 흔적이 있었다 — 누군가 증상을 보고 `levelDedupEnabled` A/B 스위치를 달아
뒀지만(주석: "복합 전략의 투표 성분으로 쓰일 때 … 이후 기여가 침묵하는 상태 오염") 원인은
고치지 않았다. GRID 는 COMPOSITE 프리셋의 **0.2 가중 성분**이므로 그 지분이 조용히 사라진
채로 돌고 있었다. 그런데 **GridStrategy 전용 테스트가 하나도 없었다.**

🟢 수정: `activeLevels.removeIf(level -> level <= levelIndex)`.
가격이 위로 올라가 청산했으면 그 아래 레벨은 전부 다시 살 수 있어야 한다.

⚠️ 정직하게 적어 둔다 — 매수 구역이 언제나 하위 30%, 매도 인덱스가 언제나 상위 30% 이므로
**오늘 기준 `removeIf(l <= levelIndex)` 와 `clear()` 는 관측상 동일하다.** removeIf 를 쓰는
이유는 의도를 코드에 남기고 구역 임계값이 바뀌어도 맞게 동작하게 하려는 것이지, 지금 그
차이를 잴 수 있어서가 아니다. 테스트 이름도 그에 맞게 고쳤다(처음엔 잴 수 없는 성질을
검증한다고 이름 붙여 놨었다).

#### 연쇄 — `WalkForwardHoldOutGateTest` 가 깨졌다

그 테스트는 GRID 를 매개로 홀드아웃 게이트를 검증하는데, 고정 데이터가 **수정 전 GRID

**비교 가능한 칸을 57 → 15 로 스스로 버리는 셈**이었다.

**수정 — v3 실행을 DB 에서 읽어 복제한다.**
기간·코인을 하드코딩하지 않고 `backtest_run` 에서 v3 의

코인을 한 배치에 섞으면 서로 다른 시장 국면을 비교하게 된다.

| Job | 범위 | 성격 |
|---|---|---|
| 1·3 | v3 실행 복제 (기간·코인 그대로) | **v3↔v4 를 1:1 로 비교할 수 있는 묶음** |
| 2 | 9전략 × 메이저 5종 = 45조합 | v3 대응짝 없음 — v4 출발점 |

Job 2 만 코인을 고정한다. 복제할 원본이 없어 비교가 불가능하고, 19코인으로 돌리면
171조합인데 **비교 대상도 없는 숫자에 그만큼 쓸 이유가 없다.** 기간은 Job 1 에서
BTC 가 속한 묶음을 따라간다.

`--verify` 도 (전략·코인·타임프레임·**기간**) 네 가지가 모두 같은 칸끼리만 대조하도록
고쳤고, 판정 변동 요약표를 추가했다.

**결함 3 — 날짜가 하루 밀려 있었다 (`--plan` 이 잡았다).**
`--plan` 출력이 `2022-12-31 ~ 2026-08-29` 를 보여줬다. v3 스크립트는
`2023-01-01 ~ 2026-09-07` 로 제출했는데 **하루씩 당겨져 있다.**

원인은 저장 경로다. 요청 DTO 는 `LocalDate` 인데 백엔드가
`atStartOfDay(ZoneId.of("Asia/Seoul")).toInstant()` 로 변환해 `TIMESTAMPTZ` 에 넣는다
(`BacktestJobService:117`). 그래서 `2023-01-01` 요청은 **`2022-12-31T15:00Z`** 로 저장되고,
psql 세션이 UTC 면 `start_date::date` 가 `2022-12-31` 로 나온다.

🔴 **그 값을 그대로 다시 제출하면 하루가 더 밀린다** — `2022-12-31` 을 KST 자정으로
해석해 `2022-12-30T15:00Z` 로 저장한다. v3 와 다른 Instant 가 되고,
`--verify` 의 기간 JOIN 이 **한 칸도 맞지 않는다.** 복제가 통째로 깨진다.

수정: 조회 시 `(start_date AT TIME ZONE 'Asia/Seoul')::date` 로 KST 달력 날짜를 되돌린다.
이 변환은 psql 세션 타임존과 무관하게 결정적이다. JOIN 자체는 raw `timestamptz` 를
비교하므로 영향 없다.

📌 **`--plan` 을 만들어 둔 것이 이걸 잡았다.** 바로 제출했으면 132조합을 다 돌린 뒤
`--verify` 에서 대조표가 전부 비어 있는 것을 보고서야 알았을 것이다.

⚠️ 이 스크립트는 **v3 결과가 DB 에 있어야 동작한다** — 복제할 원본이므로. 없으면 중단한다.

⚠️ 완료 후 **반드시 `--verify`** — 컨테이너가 옛 이미지면 결과가 v3 로 저장되고,
그러면 **낡은 코드의 숫자를 새 기준선으로 믿게 된다.**

`RANGE_RESET_THRESHOLD = 0.01`. 100봉 고저가가 **1% 만 변해도** `activeLevels` 가
통째로 비워진다(`GridStrategy:73`). 3.7년 메이저 백테스트에서는 500봉 슬라이딩
윈도우의 100봉 레인지가 거의 매 봉 1% 넘게 움직이므로 **리셋이 상시 발동**하고,
"레벨이 영원히 잠긴다"는 버그는 **도달할 일이 없었다.**

버그가 무는 조건은 **레인지가 1% 안에 머무는 구간** — 즉 유동성이 없어 캔들이
납작한 시장이다. B구간 6종(TRUMP·WLD·WLFI·ENA·LA·MIRA)이 정확히 그렇다
(전부 −69~−93% 폭락 후 거래가 말랐다). H(무변동 경계) 수정이 발동하는 조건과
같은 시장이다 — 그래서 두 수정의 효과가 같은 칸에 겹쳐 나타난다.

### 고친 방식 — 문서가 아니라 경로로 막았다

🔴 결함의 발생 경로는 **나눗셈이 호출자마다 흩어져 있던 것**이다.
규약을 주석으로만 적어 두면 다음 전략이 또 갈라진다. 그래서 변환을 한 곳으로 모았다:

- `StrategyParamUtils.getPercentAsRatio(params, key, defaultPercent)` — double 판
- 같은 이름의 `(..., int scale)` 오버로드 — BigDecimal 판 (돈 계산용)
- `StrategyParamSchema` — 이름 → **단위** 선언. 기본값은 두지 않는다
  (기본값은 전략마다 정당하게 다르다 — 1.5% vs 2.0%. 하나로 선언하면 거짓이 된다.
  **이름마다 하나뿐이어야 하는 것은 단위이지 값이 아니다.**)

두 전략 모두 이 경로를 쓰도록 바꿨고, `HeikinAshiStochStrategy` 의 사설 `pct()` 는 제거했다.

⚠️ **기본값 거동은 불변이다** — 0.02 비율 ≡ 2.0 퍼센트로 수치가 같고,
BigDecimal 판은 구 `pct()` 와 스케일·반올림(SCALE=8, HALF_UP)이 동일하다.
따라서 **`BACKTEST_RULESET_VERSION` 을 올리지 않는다.**
바뀌는 것은 호출자가 값을 **명시로** 넘길 때의 해석뿐이다.

## 🟢 2026-09-09 (2차) WF 판정 표본 하한 — "잴 것이 없다"를 "양호"로 읽던 문제

09-09 재검증 결과를 읽다 발견한 결함 2건을 고쳤다. 둘 다 **판정을 관대한 쪽으로 틀리게**
만드는 종류다.

### ① `verdict` 가 표본 크기를 보지 않았다

과적합 점수(`avgDropRate`)는 **인샘플 수익률이 양수인 윈도우**에서만 계산된다. 거래가 거의
없으면 그런 윈도우가 하나도 없고, 그러면 `dropRateSamples == 0` 이라 점수가 0 으로 남아
**가장 좋은 판정인 `ACCEPTABLE`** 이 나왔다 — "하락이 없다" 가 아니라 "잴 것이 없다" 인데도.

운영 실측 (09-09 재검증 80조합):

```
MTF_BTC   / KRW-EUL  / M15  →  ACCEPTABLE,  기대값 −4.160%,  n=2
ICHIMOKU  / KRW-PROM / H1   →  ACCEPTABLE,  기대값  0.000%,  n=0
```

`WalkForwardTestRunner.empty()` 도 같은 모양이었다 — **캔들이 부족해 윈도우를 하나도 만들지
못한 경우에도 `ACCEPTABLE`** 을 돌려줬다.

게이트는 자체 하한(`MIN_TRADES=5`)으로 걸러 실피해는 없었다. 하지만 **화면·텔레그램·리포트는
verdict 만 본다** — 거기서는 "양호"로 읽혔다. 판정을 내는 쪽에서 막는 것이 옳다.

**조치**: `INSUFFICIENT_DATA` 판정 신설(`MIN_OOS_TRADES_FOR_VERDICT = 5`).
"과적합이 아니다"와 "아무 말도 할 수 없다"를 값으로 구분한다. 게이트는 검증 이력이 없는 것과
동일하게 차단하고, 텔레그램은 `➖` 로 별도 집계한다.

### ② 배치 요약이 존재하지 않는 판정값을 세고 있었다

`BacktestJobService.buildWalkForwardSummary` 가 `"ROBUST"` 를 세는데, **어떤 코드도 그 값을
만들지 않는다**(러너가 내는 값은 `ACCEPTABLE`/`CAUTION`/`OVERFITTING`). `robustCount` 는 항상 0
이었고, `overfittingCount` 를 뺄셈으로 구하는 탓에 **양호 판정이 전부 과적합으로 집계**됐다.

**조치**: `ACCEPTABLE` 을 세도록 수정하고 `insufficientCount` 를 추가. 기존 화면 호환을 위해
`robustCount` 키에도 같은 값을 싣는다.

### 검증

전체 스위트 통과. 신규 `WalkForwardVerdictSampleFloorTest`(4) + 게이트 테스트 1건 추가.
뮤테이션 3/3 잡음 — 표본 하한 제거 · `empty()` 를 ACCEPTABLE 로 되돌림 · 게이트가
`INSUFFICIENT_DATA` 를 통과시킴.

### 재실행이 필요한가

**아니다.** 이 수정은 판정 문자열만 바꾸며 백테스트 계산 자체는 건드리지 않으므로
`EXIT_RULES_VERSION` 은 2 그대로다. 다만 09-09 재검증 결과의 `verdict` 컬럼에는 옛 값이
남아 있으므로, 화면에서 EUL/PROM 조합이 여전히 `ACCEPTABLE` 로 보인다 — 다음 WF 실행부터
`INSUFFICIENT_DATA` 로 바뀐다. 게이트 판정은 이미 표본 하한으로 막고 있어 영향 없다.

#### 핵심 — SL/TP 공식이 다르다

`BacktestEngine` 은 `ExitRuleChecker.calculateStopLevels`, 세 매매 엔진은
`ExitRuleCalculator.resolveStopLossPct` 를 쓴다. **이름이 비슷한 다른 함수다.**

| | BACKTEST | LIVE · DYNAMIC · PAPER |
|---|---|---|
| SL 폭 | **항상 5.0% 고정** | `clamp(ATR(14)/가격 × 1.5, 5%, 8%)` → 5~8% |
| ATR 반영 | **안 함** | 함 |
| TP 폭 | **SL × 2 = 항상 10%** | `min(SL × 2, 8%)` → ≤8% |
| 전략 제안 SL | 그대로 채택 | `.min()` — 더 넓은 쪽 |
| 시간 초과 청산 | **없음** | `maxHoldHours` (운영 24h) |

원인: `ExitRuleConfig.atrStopLossEnabled` 기본값이 `false` 인데
`RiskManagementService.toExitRuleConfig()` 가 이 필드를 **설정하지 않는다** — DB 로 켤 수단도 없다.

**나중에 실행된 쪽이 다른 쪽 판정을 덮어쓴다** — `evaluate(String)` javadoc 이
"실행 순서에 따라 결과가 좌우되는 우연" 이라고 적어 둔 것과 정확히 같은 결함이다.

운영 실태가 이 구분을 요구한다: 고정코인 PAPER 40세션 전부 M15, 동적 12세션 H1 6 / M15 6 인데

**조치**:
- `BacktestRunRepository` — `...AndTimeframeAnd...` 조회 추가
- `WalkForwardValidationGate` — `evaluate(전략, 코인, TF)` / `evaluateStrategy(전략, TF)` 로 확장,
  `latestPerCombo` 키를 `coinPair + "@" + timeframe` 으로 변경. `timeframe=null` 이면 종전 동작(하위 호환)
- 호출부 3곳에 타임프레임 전달 — LIVE 생성(코인·TF 앎), DYNAMIC 생성(`throwIfBlockedByTimeframe`,
  코인은 스캔 후지만 TF 는 생성 시점 확정), DYNAMIC 매수 직전(둘 다 앎)
- `WalkForwardGateTimeframeTest` 신설(5건). **뮤테이션 테스트로 검증** — 키를 예전(코인만)으로
  되돌리니 "같은 코인의 H1/M15 가 서로를 덮지 않는다" 가 정확히 실패했다.

- **Walk Forward 게이트 활성화** (`REQUIRE_WALK_FORWARD_GATE`) — `WalkForwardValidationGate` 구현 완료, 기본값 비활성. 대부분 전략이 Walk Forward 이력이 없어 켜는 즉시 신규 세션 생성이 전면 중단된다. 켜기 전에 `GET /api/v1/strategies/walk-forward-gate-status`로 어떤 전략이 막히는지 먼저 확인하고, 운영 중인 전략들(COMPOSITE_MOMENTUM_ICHIMOKU_V2 등)에 Walk Forward부터 돌려 통과시킬지 판단할 것.
- ~~**LIVE time stop 활성화** (`maxHoldHours`)~~ ✅ **2026-08-18 완료** — 기본값 0 → 24 (V68, LIVE·DYNAMIC·PAPER 3종 동시). 운영 RUNNING 10세션에도 소급 적용. 아래 08-18 섹션 참조. ⚠️ 켜자마자 LIVE 경로에서 중복 SELL 1건이 재현됐다(같은 섹션 "새로 드러난 것" 참조) — 미해결.

- ~~**시간 초과 청산(time stop) 텔레그램 알림 부재**~~ ✅ **2026-08-18 완료** — `notifyTimeStop` 신설, LIVE·DYNAMIC 배선. 08-18 오전 XRP 4건 청산에 알림이 안 간 것이 실측 사례였다.
